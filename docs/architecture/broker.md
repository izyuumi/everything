# Durable Tool Broker

Issue [#14](https://github.com/izyuumi/everything/issues/14) implements `tools::broker` as the native privileged-execution boundary. It composes the immutable tool registry, host-issued execution authority, persistent permission decisions, and SQLite operation journal. It does not supply shell, filesystem, or MCP implementations.

The host starts exactly one `ToolBroker` after acquiring its exclusive host-service lock and before starting workers. Startup marks interrupted running operations unknown and scans persisted unknown outcomes for unresolved cleanup risk. Task-scoped brokers are lightweight clones of that one instance. They share admission limits, concurrency slots, a global read/write exclusion gate, and quarantine state. Constructing independent brokers over the same store would defeat these guarantees and is forbidden by the host lifecycle contract.

An invocation first validates arguments and obtains a current permission decision on a blocking worker. Its immutable execution inputs are then reserved durably. Existing terminal records replay without repeating the tool; an existing running operation returns in-flight status. Pending approval returns its exact durable approval request to the host. Denial and cancellation before invocation become terminal journal records. No ask, deny, validation error, or policy error grants execution.

Allowed pending work waits for a shared concurrency slot and the global exclusion gate. Concurrent tools hold read access; exclusive tools hold write access and therefore exclude every other tool across tasks. The broker reauthorizes after these waits and changes pending to running through a compare-and-update in the same blocking closure. Only the winner of that journal claim invokes the tool.

A supervised Tokio task owns the invocation, exclusion guards, and admission slot. Dropping the caller's future requests cancellation but cannot release the guards while execution continues. Cancellation and execution deadlines signal the tool's host-issued token and allow a bounded cleanup grace period. A noncooperative future is dropped after that period; its outcome becomes unknown and the shared broker is quarantined. Native implementations must own and clean up their subprocesses, I/O, and other resources. Dropping a Rust future cannot prove that an operating-system process or remote operation stopped.

Success, completed semantic-error output, and a definitive failure known to have no side effects are persisted before returning. Completed error output uses the generic `ToolOutput.is_error` flag and remains a known failed outcome with full output, including when partial effects are possible; it is distinct from transport or cancellation uncertainty. Generic tool failure or cancellation after invocation has an unknown effect and cleanup outcome, returns a structured reconciliation error, and quarantines execution. A trusted native implementation can explicitly report uncertain effects with confirmed completed cleanup through `ToolError::EffectsUnknown`; that operation still cannot be retried. Oversized results and journal-write uncertainty also cannot be presented as replay-safe failures. An unknown operation remains terminal and is never automatically rerun. Interruption metadata is retained even when cooperative cleanup returns a successful result; the native loop must stop the current task when `ExecutionRecord::requires_stop()` returns true.

Unknown outcomes with unfinished cleanup, malformed legacy records, and interrupted startup work preserve global quarantine across restarts. A separate immutable storage attestation records an explicit owner's cleanup review against the exact persisted result digest. The host-only `acknowledge_cleanup` API holds the global exclusive gate, records that attestation, and rescans all unsafe outcomes before clearing quarantine. It never changes the original unknown result or authorizes retry. Unexpected supervisor termination, a tool panic, or journal-write failure requires a host restart in addition to any cleanup review. Model-controlled tools must never expose this attestation API.

The [broker contract](../contracts/broker.md) describes the public types, persistence invariants, timeout behavior, recovery, and validation limits. Tool implementations remain responsible for operating-system boundaries; broker permissions and workspace metadata do not sandbox arbitrary shell execution.
