# Native settings action foundations

The native modules in `apps/Apple/Shared/Settings` implement device-local preference persistence, saved app appearance, notification capability observation and contextual OS interaction, plus a private credential input field. They consume the scope and outcome semantics from the [hybrid settings contract](../contracts/settings.md). Host settings remain in the existing SettingsRepository. These modules do not implement a second Host configuration store or model runtime.

These modules are registered in both Apple targets and consumed by the actual [This Mac](../contracts/this-mac-settings.md) and [iOS local controls](../contracts/apple-local-device-controls.md). Local preferences and OS observation do not depend on a model, relay or running Host. macOS also composes the [private Host Session](../contracts/apple-native-settings-session.md), [secure entry/linking](../contracts/apple-native-credential-entry.md), [Devices ceremony](../contracts/apple-native-devices.md) and optional [Ask Settings](../contracts/apple-settings-assistant-composition.md). iOS replaced generic cursor-activity notices with the bounded [committed-event path](../contracts/ios-notification-delivery.md); remote Host Settings remains separate.

## Device preference authority

`DevicePreferenceStore` is an actor over a separate device-local SQLite file, `device-preferences-v1.sqlite3`. Schema2 stores notification completion/attention choices and system/light/dark appearance under one genuine local revision and bounded shared mutation history. Notification defaults are false and appearance defaults to system; the initial revision is one. iOS uses the strict initializer with its actual Keychain-backed Replica identity. macOS uses the same-connection local factory, which adopts the existing canonical preference UUID or creates one only with genuinely empty initial preferences. That UUID is local preference identity, not a Host/peer/native-session grant. Malformed or mismatched identity fails rather than being repaired or switched. The [local authority](../contracts/local-device-preferences.md) and [appearance migration](../contracts/device-appearance.md) contracts define original receipt compatibility.

`DevicePreferencePatch` accepts one or two unique typed changes, a non-nil request ID, the exact device and an expected positive signed-64-bit revision. It cannot represent a Host key, OS authorization write, arbitrary path or another preference. Appearance uses its own closed typed patch and the SAME revision/request table; cross-kind original-ID reuse conflicts. Its private sorted-key request encoding is a local deduplication identity, not a registered Host/relay wire DTO. Future wire consumers must validate the actual merged contract and trusted caller before constructing a local request.

An immediate SQLite transaction checks retained identity before revision/capacity, validates the whole batch, commits both booleans and the incremented revision together, and retains the exact result in that same transaction. An exact replay returns its original Applied or Conflict outcome. Reusing an ID for changed content fails; stale edits are not rebased. A conflict is also retained, so replay cannot apply it after a later revision change. Inspection by original request ID returns a redacted result without issuing a new mutation. Cancellation of an awaiting caller does not undo a synchronous transaction already executing in the actor.

The directory is app-private, excluded from platform backup, and uses complete file protection on iOS. SQLite uses FULL synchronization and a bounded database/page/request configuration. Identity and outcome text reads are byte-bounded before strict UTF-8 decoding and reject embedded NULs. At 8,192 retained request identities or the database capacity, new requests fail explicitly; retained replay and reads remain available. Identities are not evicted to silently permit a second application of an old ID. The store is not a network authentication boundary: only trusted app composition/adapters may call it. Remote caller/grant validation belongs to the actual scoped transport, not to a UUID in this local structure.

SQLite is the one local transaction boundary. Neither OS notification permission nor Host configuration is included in that transaction. A failed rollback makes the connection unusable, preventing its potentially uncommitted rows from being reported as authoritative state. Reopen the store and inspect the original request after that uncertainty before considering another mutation. There is no backup, restore, distributed rollback or secret store here.

## Notification observation and foreground interaction

`NotificationAuthorizationService` uses the real `UNUserNotificationCenter.current()` and does not install another notification-center delegate. Observation includes the actual authorization status and separate alert, sound and Notification Center feature settings with a query time. `requestAuthorization`'s Boolean is deliberately not used as a combined enabled preference: Apple may grant only some requested interactions. Authorization is observed again after interaction. Callers must refresh observation on foreground return and before presenting capability or scheduling activity.

For a not-determined status, the contextual action requests the currently used alert/sound options. A denied action uses the supported iOS notification-settings URL constant and public open API, or supplies accurate System Settings instructions on macOS. It never accepts an arbitrary URL or a private settings-pane scheme. Successful navigation is not an authorization grant. Provisional/ephemeral/unavailable observations are kept distinct. No push token, APNS, background wake, critical alert entitlement or human-delivery guarantee is introduced.

`DeviceForegroundSession` is a device-local UI lifetime, not Host native-session authority. It requires the real application to be active, a matching retained session generation, an unclosed foreground lifecycle, and both wall/monotonic expiry before an interaction. App composition invalidates foreground eligibility synchronously when its actual surface/application becomes ineligible and closes the session at its owning lifetime end. The platform active-state check prevents a new dialog while inactive; an already admitted OS callback remains owned through completion.

`DeviceNotificationActions.prepare` is synchronous on the MainActor and must run at the actual native gesture before creating a UI Task. It reserves the exact request/device/session/revision/expiry and captures one original foreground generation and monotonic deadline into an opaque admission ticket. `authorize(ticket)` consumes only that retained admission and never captures a newer generation or renews expiry. Calling the old asynchronous entry point from a queued UI Task could otherwise let a request queued before inactivity adopt a later foreground generation; that unused entry point has been removed.

The ticket belongs to its actual service, session object and preference-store actor. Another service cannot consume it, and reusing the request ID with another store/session or changed identity fails. Exact preparation replay returns the same ticket, including its original rejection or cancellation; authorization replay joins the same owned task and cannot repeat a dialog. Cancellation reaches prepared requests before consumption, and an already-cancelled consuming Task records cancellation before starting work. An expired unused ticket returns expired when consumed; preparation does not start a timer, query SQLite or open OS UI.

Prepared, rejected, cancelled and completed identities share the existing 256-request bound and remain retained for exact replay until that service is released. Unused expiry does not evict an identity or permit renewed admission under the same ID. Capacity fails visibly rather than growing a waiting-task queue. Closing the owning foreground session invalidates unpresented tickets while an already admitted OS callback remains owned. This local in-memory ledger is not another Host action registry, and a new UI session cannot confer authority to replay an old Host reference. Scene/window composition still must update foreground eligibility synchronously; the ticket alone does not establish actual presentation or Host authority.

After awaiting the OS capability query, the action rereads the actual device preference store and rechecks its original expected revision immediately before the final foreground/cancellation checks and OS interaction. A change observed during that query returns Conflict rather than opening a stale prompt or Settings navigation. This is the latest observed admission precondition, not an atomic CAS over a system dialog: a preference change can race the final read or occur during the OS interaction. No SQLite transaction or actor lock is held across OS UI, and its admission does not freeze or roll back preferences.

An admitted OS request remains owned through actual completion, even after an awaiting task is cancelled or the UI closes. There is no supported notification API here to dismiss that system dialog or reverse its resulting permission change. The eventual result reports the actual observed interaction; it does not falsely report cancellation as rollback. A completed local interaction receives an opaque local receipt ID for exact in-session result inspection. It is not a Host receipt, an authority token or a serializable confirmation. This local receipt is not a Host-native admission: the current clients use their actual device-local adapter, and the Settings agent cannot request a notification-authorization handle.

macOS preferences do not schedule completion/attention notices. iOS now claims actual authenticated committed completion/undecided-permission events, silently baselines initial catch-up and advances a durable floor before an OS attempt. It rereads saved choices from the SAME actor and observes OS settings without asking permission in that delivery path. Loss after a claim can lose a notice; this is at-most-once attempt admission, not exactly-once delivery, background/APNS or a presentation guarantee. The existing single privacy delegate is retained.

## Private credential presentation

`SecureCredentialField` is a real SwiftUI SecureField over a separate non-Codable `SecureCredentialDraft`. It disables autocorrection, marks the field privacy-sensitive and clears its private draft when the field disappears. The iOS field disables automatic capitalization. The draft is neither a SettingsStore property nor a conversation value.

This input leaf itself does not submit, persist, validate a destination, mint an action or claim storage. The separately integrated macOS consumer binds its actual original NativeUI action to existing CredentialVault/SecretTransfer through authenticated private FIFO input/output. Credential bytes and native proofs are rejected by the request-file bridge. Configured replacement uses one original submit; initial storage and nonsecret metadata linking are separate gestures/receipts. No model, file, argv/environment transfer or simulated vault is introduced.

SecureField masks presentation; it does not provide storage/transport protection or universal Swift heap erasure. Clearing the draft releases that UI reference on a best-effort basis. The integrated protected route retains exact endpoint binding, one-shot submission and original result inspection; actual OS-store/cancellation behavior remains unverified. An ambiguous write is not rollback or permission to repeat a secret effect.

## Integration and validation gates

Root owns Apple target membership and actual signing-disabled build/analyze checks for both schemes. Host session/pipe operations must consume the real reviewed #109 authority/action/reconciliation implementation; public action IDs and Completed DTOs provide no authority. Pairing invitation/revocation effects continue through the existing device core and #112 wrappers. Native controls and later optional chat share those real services, rather than parsing ordinary chat text as privileged actions.

Historical foundation evidence includes source/structure validation, full Swift grammar and strict Swift6 Foundation-only checking of preference values. Later composed #163 passed actual supported Mac/iOS build/analyze at its corrected exact head; [the checkpoint](settings.md) records source/CI provenance. SQLite/device/UI/Keychain/foreground/OS permission behavior is not established by those builds and remains manual acceptance. No new automated tests or fixtures were created; [#32](https://github.com/izyuumi/everything/issues/32) tracks deferred assertions. These checks do not establish security review or production readiness.
