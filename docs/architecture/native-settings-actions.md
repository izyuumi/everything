# Native settings action foundations

The native modules in `apps/Apple/Shared/Settings` implement device-local preference persistence, notification capability observation and contextual OS interaction, plus a private credential input field. They consume the scope and outcome semantics from the [hybrid settings contract](../contracts/settings.md). Host settings remain in the existing SettingsRepository. These modules do not implement a second Host configuration store or model runtime.

This foundation is registered in both Apple project targets but is not yet connected to the existing Settings screens. Its source has no dependency on a model, the relay or a running Host. App composition and the actual protected Host action route remain integration work. Existing iOS generic activity notification behavior is unchanged; completion/attention event classification and preference migration must be connected by the client integration owners before delivery can be described as category-aware.

## Device preference authority

`DevicePreferenceStore` is an actor over a separate device-local SQLite file, `device-preferences-v1.sqlite3`. It stores only `notifications.completion`, `notifications.attention`, their genuine local revision and bounded nonsecret mutation identities/outcomes. Both preferences default to false and the initial revision is one. The caller supplies that app device's stable non-nil identity. iOS composition must reuse the actual Keychain-backed device identity; this store cannot mint or substitute a paired device identity. macOS composition must select and retain its actual stable local identity before opening this store. A store already bound to another identity fails visibly.

`DevicePreferencePatch` accepts one or two unique typed changes, a non-nil request ID, the exact device and an expected positive signed-64-bit revision. It cannot represent a Host key, OS authorization write, arbitrary path or another preference. Its private sorted-key request encoding is a local deduplication identity, not a registered Host/relay wire DTO. Future wire consumers must validate the actual merged contract and trusted caller before constructing a local request.

An immediate SQLite transaction checks retained identity before revision/capacity, validates the whole batch, commits both booleans and the incremented revision together, and retains the exact result in that same transaction. An exact replay returns its original Applied or Conflict outcome. Reusing an ID for changed content fails; stale edits are not rebased. A conflict is also retained, so replay cannot apply it after a later revision change. Inspection by original request ID returns a redacted result without issuing a new mutation. Cancellation of an awaiting caller does not undo a synchronous transaction already executing in the actor.

The directory is app-private, excluded from platform backup, and uses complete file protection on iOS. SQLite uses FULL synchronization and a bounded database/page/request configuration. Identity and outcome text reads are byte-bounded before strict UTF-8 decoding and reject embedded NULs. At 8,192 retained request identities or the database capacity, new requests fail explicitly; retained replay and reads remain available. Identities are not evicted to silently permit a second application of an old ID. The store is not a network authentication boundary: only trusted app composition/adapters may call it. Remote caller/grant validation belongs to the actual scoped transport, not to a UUID in this local structure.

SQLite is the one local transaction boundary. Neither OS notification permission nor Host configuration is included in that transaction. A failed rollback makes the connection unusable, preventing its potentially uncommitted rows from being reported as authoritative state. Reopen the store and inspect the original request after that uncertainty before considering another mutation. There is no backup, restore, distributed rollback or secret store here.

## Notification observation and foreground interaction

`NotificationAuthorizationService` uses the real `UNUserNotificationCenter.current()` and does not install another notification-center delegate. Observation includes the actual authorization status and separate alert, sound and Notification Center feature settings with a query time. `requestAuthorization`'s Boolean is deliberately not used as a combined enabled preference: Apple may grant only some requested interactions. Authorization is observed again after interaction. Callers must refresh observation on foreground return and before presenting capability or scheduling activity.

For a not-determined status, the contextual action requests the currently used alert/sound options. A denied action uses the supported iOS notification-settings URL constant and public open API, or supplies accurate System Settings instructions on macOS. It never accepts an arbitrary URL or a private settings-pane scheme. Successful navigation is not an authorization grant. Provisional/ephemeral/unavailable observations are kept distinct. No push token, APNS, background wake, critical alert entitlement or human-delivery guarantee is introduced.

`DeviceForegroundSession` is a device-local UI lifetime, not Host native-session authority. It requires the real application to be active, a matching retained session generation, an unclosed foreground lifecycle, and both wall/monotonic expiry before an interaction. App composition must call `setForeground(false)` for genuine backgrounding and `close()` at the actual settings-session end. Transient inactivity caused by an OS permission dialog must not be mapped to genuine backgrounding. The platform active-state check still prevents a new dialog while inactive.

`DeviceNotificationActions` retains each exact original request/device/session/revision/expiry before suspension, checks the real local preference revision, and coalesces retries on the same owned task. Changed ID reuse fails. Cancellation before OS admission and a later session generation invalidate the old request rather than queueing it for future activation. One DeviceNotificationActions instance suppresses concurrent authorization prompts. The local in-memory invocation ledger is bounded to 256 requests and fails visibly at capacity; it is not a duplicate Host action registry. A new UI session cannot confer authority to replay an old Host reference.

After awaiting the OS capability query, the action rereads the actual device preference store and rechecks its original expected revision immediately before the final foreground/cancellation checks and OS interaction. A change observed during that query returns Conflict rather than opening a stale prompt or Settings navigation. This is the latest observed admission precondition, not an atomic CAS over a system dialog: a preference change can race the final read or occur during the OS interaction. No SQLite transaction or actor lock is held across OS UI, and its admission does not freeze or roll back preferences.

An admitted OS request remains owned through actual completion, even after an awaiting task is cancelled or the UI closes. There is no supported notification API here to dismiss that system dialog or reverse its resulting permission change. The eventual result reports the actual observed interaction; it does not falsely report cancellation as rollback. A completed local interaction receives an opaque local receipt ID for exact in-session result inspection. It is not a Host receipt, an authority token or a serializable confirmation. The Host action service must bind and reconcile its own admission when that later route is integrated.

This foundation does not schedule completion/attention notifications or claim exactly-once delivery. The existing notification-center delegate and privacy-limited activity submission remain in the iOS service. Integration must connect actual trusted event categories, preference/OS gates, pre-await event/throttle reservation and replay suppression before those toggles govern delivery.

## Private credential presentation

`SecureCredentialField` is a real SwiftUI SecureField over a separate non-Codable `SecureCredentialDraft`. It disables autocorrection, marks the field privacy-sensitive and clears its private draft when the field disappears. The iOS field disables automatic capitalization. The draft is neither a SettingsStore property nor a conversation value.

This leaf does not submit, persist, validate a destination, mint an action or claim successful credential storage. Its actual local-owner credential workflow must be bound to the reviewed Host session/action core and existing CredentialVault/SecretTransfer route. The current request-file owner bridge cannot receive credential bytes or private native-session proof. A dedicated authenticated sensitive pipe route remains required. No secret-bearing submit callback, file request, argv/environment transfer or simulated vault exists in this foundation.

SecureField masks presentation; it does not provide storage/transport protection or universal Swift heap erasure. Clearing the draft releases that UI reference on a best-effort basis. Actual credential cancellation, ambiguous writes, exact provider/System One endpoint binding and redacted result inspection remain work in the protected route.

## Integration and validation gates

Root owns Apple target membership and actual signing-disabled build/analyze checks for both schemes. Host session/pipe operations must consume the real reviewed #109 authority/action/reconciliation implementation; public action IDs and Completed DTOs provide no authority. Pairing invitation/revocation effects continue through the existing device core and #112 wrappers. Native controls and later optional chat share those real services, rather than parsing ordinary chat text as privileged actions.

Current evidence is source/structure validation, full Swift grammar parsing, and strict Swift 6 Foundation-only type checking of the preference value types. Apple SDK checks, SQLite/UN/SwiftUI type checking against supported SDKs, and actual device/UI/Keychain/foreground/OS permission behavior remain pending. No new automated tests or fixtures were created; [#32](https://github.com/izyuumi/everything/issues/32) tracks deferred assertions. These checks do not establish security review or production readiness.
