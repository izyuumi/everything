# Background service and local host endpoint

Issue [#18](https://github.com/izyuumi/everything/issues/18) provides launchd user-agent management in `src/service` and authenticated Unix socket IPC in `src/transport/local.rs`. The service manager does not depend on any graphical client. A macOS menu bar app or CLI can exit without owning the launchd job's lifetime.

This module does not contain an agent loop, task scheduler, or model runner. The application entry point must connect the bounded IPC inbox to its authoritative command processor and durable store before it can execute agent work. Local transport status reports the endpoint process, not model or scheduler readiness.

## Module boundaries

`service::LaunchdService` validates immutable executable, state, and LaunchAgents paths, renders a native property list, installs it atomically, and invokes the current user's launchctl domain. `ServiceStatus` separates the presence of an installed plist, a loaded job, its current PID, and its last reported exit code. Service errors remain structured and distinguish unsupported platforms, unsafe paths, filesystem failures, launchctl failures, cancellation, and timeout.

The internal state-directory helper walks absolute path components through open directory descriptors with `O_NOFOLLOW`. Ancestors must belong to this user or root; writable ancestors require the sticky bit. Missing directories are created with mode 0700. Input is bounded before filesystem access: socket paths at 100 bytes and general directory paths at 4096 bytes, preventing an oversized bind argument from creating a directory tree before rejection. The final host state directory must belong to this user with exact mode 0700. Executable ancestors are independently walked and verified as root-owned or user-owned trusted directories, with a non-symlink executable opened relative to that descriptor. LaunchAgents directories and plist files are checked again when status, start, or enable operations use them; inspection does not rely solely on an earlier successful installation. Relative paths, parent traversal, and setuid execution are rejected. A symlinked ancestor, such as macOS `/tmp`, `/var` or a symlinked home, is resolved inside the same descriptor walk only when the link is owned by this user or root and sits in an already verified directory; its target components, including `..`, are walked with the same ownership and sticky-bit checks, and at most 40 links are followed. Any other symlinked ancestor is rejected. A state directory that is itself a symlink is followed under the same rule (owned by this user or root, in a verified directory), so the `~/.vorra -> ~/.everything` migration fallback is accepted; its target must still be an owner-only mode-0700 directory. The verified directory reports its resolved physical path, which the socket and state files use.

`service::StateLease` retains the verified directory descriptor and exclusive singleton lock in one shared owner. `StateLease::acquire` performs its filesystem work on a blocking worker. The agent and socket server can retain the same lease rather than acquiring independent locks. `Agent::open` uses this lease and passes its validated private database descriptor into `Store::open_validated`; every Store clone retains that descriptor until its SQLite connection closes. Agent clones retain the lease during blocking operations. The foreground broker retains an actual Agent clone through shared recovery work; application Host startup and shutdown wiring remain separate integration work.

`transport::local::LocalServer` owns the socket, a shared state lease, bounded request inbox, and connection tasks. `bind_with_lease` accepts an already acquired lease; standalone `bind` acquires one. The host consumes `LocalCall` values and replies through their oneshot channel. `LocalClient` authenticates the server and validates matching request IDs, versions, response types, and synchronization cursors. See the [local IPC contract](../contracts/local-ipc.md).

## launchd lifecycle

Construct `LaunchdService::new(executable, state_directory, launch_agents_directory)` with absolute paths. `render_plist()` is pure and uses the established `plist` library for XML escaping. The fixed label is `to.yumi.vorra.host`; the file is `to.yumi.vorra.host.plist` inside the supplied user LaunchAgents directory.

Program arguments are exactly the executable followed by `--state-dir`, the state directory, and `serve`. The application CLI must implement that entry point. The working directory and stdout/stderr paths use the private state directory. The property list contains no credentials or conversation data. `RunAtLoad`, `KeepAlive`, background process type, a 10-second restart throttle, a 20-second graceful-exit allowance, and umask 0077 configure background operation and restricted newly created files.

- `install(cancellation)` writes the plist through an exclusive private temporary file and atomically renames it. Existing targets must be owned, single-link regular files. It does not stop or replace a running host.
- `set_enabled(enabled, cancellation)` invokes `launchctl enable` or `disable` for the current user's service target. Disabling controls future launch eligibility; stop a current job separately when desired. An installed plist in the login LaunchAgents directory is launched at login unless disabled.
- `start(cancellation)` is idempotent for a running job, bootstraps an unloaded installed job, and kickstarts it without force-killing an existing process. An unloaded disabled job returns `ServiceError::Disabled` instead of an opaque bootstrap failure.
- `stop(cancellation)` boots out the fixed user service target and is idempotent for an unloaded job; unsafe on-disk configuration cannot prevent stopping that target. Missing-job exit codes 3 and 113 are treated as already stopped; other failures propagate. The installed plist remains available for subsequent login or explicit start.
- `status(cancellation)` inspects the installed file, reads `launchctl print-disabled` for `enabled`, and runs `launchctl print`. A documented missing-service exit code yields an unloaded status; other launchctl failures remain errors. `last exit code = (never exited)` yields no exit status, and `N: description` yields `N`.

There is no uninstall command: `stop`, then remove the plist file. launchd keeps its own enable/disable override for the label after the file is removed.

Operations target `gui/<current uid>/to.yumi.vorra.host` and require the user's launchd login domain. There is no root installation, system LaunchDaemon, or privileged helper. A CLI can manage the user agent headlessly within that login session. Another graphical application is never required to stay open. `install`, `start` and the `vorra update` restart first look for a leftover `com.everything.host.plist` from the former Everything name in the LaunchAgents directory; if present they run `launchctl bootout gui/<uid>/com.everything.host` (an absent job is fine) and remove that plist. The old host logs live in the state directory and move with it.

The manager invokes `/bin/launchctl` directly without a shell. Each invocation is limited to 10 seconds and 64 KiB per output pipe, observes cancellation, and kills an unfinished child on drop. Error values contain the operation and exit status rather than launchctl output. Installation disk work and the status/start/enable filesystem preflights run on blocking workers; an already running bounded atomic file write can finish after cancellation, so callers should inspect installation status if interrupted.

On other platforms, install/start/stop/status/enable return `ServiceError::UnsupportedPlatform` before mutating service files. Pure plist rendering remains available for review. Unix IPC remains usable independently of launchd.

## Endpoint ownership and cleanup

The state directory contains `host.lock` and `host.sock`. The lock is an owned mode-0600 single-link regular file opened without following symlinks. Its exclusive advisory lock is held for the entire server lifetime; its PID text is informational and never authorizes stale-host cleanup. A second compatible host receives `AlreadyRunning`.

An existing socket is accepted for inspection only when it is an owned mode-0600 socket. While holding the lock, bind attempts to connect before removing an apparent stale endpoint. A live endpoint is preserved. Only explicit connection refusal or disappearance permits stale cleanup; permission failures and timeouts never cause unlinking. Server shutdown removes only the socket inode it originally bound, leaving changed or unsafe paths untouched. The lock file can remain after shutdown; releasing the file descriptor releases the lock. Startup path walking, lock initialization/fsync, standard socket binding, chmod, and metadata capture run on blocking workers. An RAII ownership guard spans prepared and running endpoints, preserving the singleton lock across the asynchronous stale-socket probe and cleaning a newly bound inode if its setup future is abandoned. The listener becomes nonblocking before Tokio registration. The final Drop fallback intentionally uses only a descriptor-relative inode check and optional unlink synchronously, so it remains available after executor shutdown. Filesystem preparation already in progress can finish after its caller is cancelled; the worker result guard then closes the listener, removes its owned socket, and releases the lock. Private directories and an inert lock file may remain.

Both peers verify kernel-provided UID credentials. The socket and state directory restrict filesystem access, and the peer check remains mandatory on every connection. This authenticates the operating-system user, not a distinct UI application. It does not authorize arbitrary tool execution; command validation, durable deduplication, permissions, and task ownership remain host responsibilities.

## Integration and verification

The standalone transport can answer real process status without a command processor. All mutating and synchronization requests require the host's inbox consumer. The transport never reports a command as accepted by enqueueing it. A `CommandAccepted` response is valid only after the consumer's durable transaction succeeds; command IDs make an ambiguous timeout safely retryable with the same contents and identity.

Validation passed with `cargo fmt --all --check`, `cargo check --workspace --all-targets --locked`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, and `cargo build --workspace --release --locked`. A disposable executable exercised real same-user IPC status, mode-0700/0600 creation, duplicate-host rejection, unavailable-processor rejection, oversized-frame isolation, pre-cancelled client requests, cancellation socket cleanup, stale-socket recovery, symlink/public-directory rejection, plist XML escaping, and typed Linux unsupported-platform results. A follow-up disposable walkthrough rejected an oversized bind path before creating any directory. A controlled single-worker exercise abandoned the bind future after queuing its socket-creation stage, then observed no remaining socket, a released singleton lock, successful real rebind, and cleanup on drop. These are manual observations, not automated lifecycle coverage. It created no mock server or committed fixture. Independent source review found and resolved executable/LaunchAgents ancestor validation, preflight path bounds, and blocking startup/client/launchd filesystem work before integration. macOS launchctl execution, login restart behavior, and a long-lived host executing model tasks are not verified in the Linux environment. The macOS CI build must compile the platform-gated manager before merge. Deferred automated lifecycle, peer-credential, socket-race, framing, and restart assertions are tracked in [#32](https://github.com/izyuumi/everything/issues/32). No production-readiness or full runtime-lifecycle claim is made by this module alone.

### macOS launchd observation (2026-10-17)

On macOS (Apple Silicon, uid 501, `gui/501` domain, no root), a debug CLI was run against a disposable state directory and a disposable `--launch-agents-dir`, with no pre-existing `com.everything.host` job or plist. `install` wrote the expected plist. `start` bootstrapped the job; the Host ran as a launchd child after the CLI exited. `status` on that running job failed with `invalid launchctl response: invalid exit code` because launchd prints `last exit code = (never exited)`; after the fix it reported `installed/enabled/loaded` and the PID. A conversation created through the CLI proxy to the launchd Host was listed again after `stop` (bootout, graceful SIGTERM shutdown that removed `host.sock`) and a second `start`, and directly after the final stop. A repeated `start` kept the same PID and `runs = 1`. `disable` was reported by `status`; `start` then returned the typed disabled error instead of `bootstrap ... Some(5)`; `enable` restored it. Launchd-created stdout/stderr logs were mode 0644 inside the 0700 state directory. A follow-up run with the fixed CLI and fresh disposable directories created a conversation through the launchd Host, then sent `launchctl kill SIGKILL gui/501/com.everything.host`; launchd relaunched the job within two seconds with a new PID (`runs = 2`), `status` reported it loaded, and the same conversation was listed through the relaunched Host. `stop` then booted it out (`launchctl print` returned 113) and the disposable plist was removed. Not exercised: login launch from `~/Library/LaunchAgents`, and model task execution. (Recorded before the rename to Vorra, under the former label.)
