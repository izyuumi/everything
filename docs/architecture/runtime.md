# Native runtime

The host runs one native Rust agent kernel with persistent text conversations and optional native tool rounds. `init`, `chat`, and `status` work without a graphical client. `chat --tools` composes the real filesystem and shell builtins, local tool selection, permissions, and one Tool Broker for its foreground host. The reusable kernel also accepts a host-owned registry and scoped broker; it does not create another runtime or gateway.

## Responsibilities and ownership

`src/agent.rs` owns typed text acceptance, coherent conversation reads, durable message conversion, and admission. `src/agent/native.rs` owns context construction, model attempts, tool rounds, limits, and private execution checkpoints. `src/agent/foreground.rs` admits and settles the CLI's durable foreground task rows. `src/main.rs` owns terminal arguments, environment credentials, native provider construction, local tool composition, and process signals. The stable caller interface is described in [the agent contract](../contracts/agent.md).

`Agent::open` validates a private Unix state directory through the service's descriptor-based implementation and retains its exclusive host lock. An existing foreground or background owner prevents another foreground runtime. `Agent::from_store` and `Agent::store` support trusted host composition; their caller must retain one host lock and start one global broker. Admission is shared across Agent clones and permits distinct conversations concurrently, with one active native turn per conversation. Independent Agent instances must not bypass that admission.

Filesystem bootstrap, SQLite operations, history conversion, request/context construction, schema validation, and bounded serialization run on blocking workers. Owned network and tool futures run asynchronously. Blocking durable operations retain host ownership and admission even if their awaiting caller is dropped. Linux and macOS are the initial foreground platforms; unsupported platforms return an explicit error.

`src/agent/steering.rs` owns the typed persistent input queue, exact acceptance replay, child-wait state and strict control-only merge validation. It has no dependency on Host or Scheduler. A short per-conversation write gate protects checkpoint commits while the existing execution gate retains one native loop per conversation. Steering and child input consumption preserve immutable task inputs and original budget accounting; see [the steering contract](../contracts/steering.md). Scheduler delivery repair and event-driven wakeups follow in PR #75; production background-host and owner-command wiring remain separate work in #18/#68.

## Accepted commands and durable history

`TextCommand` contains the complete foreground command identity: conversation, command UUID, and exact text. Acceptance checks its original durable user event and causation before inference. Exact pending replay returns the prior acceptance; exact completed replay returns its saved assistant response. Changed text or conversation under the same command ID is rejected. External device `CommandEnvelope` identity belongs to the host command processor and is not synthesized from this narrower command.

Conversation configuration fixes the native provider, model, instructions, endpoint, and sampling options. Initialization appends a typed `ConversationCreated` event with its private configuration. An interrupted metadata-row initialization can be retried with its original identity and configuration. User acceptance and its pending checkpoint commit atomically. Assistant messages, tool requests, public results, permissions, and their corresponding private checkpoint changes also commit atomically using both event-head and checkpoint-revision comparisons. Private-only execution transitions use the storage checkpoint journal without inventing public events.

Reads capture head, checkpoint, and the first event page in one SQLite transaction, then paginate immutable events only through that captured head. The loader validates sequences, message counters, pending user identity, checkpoint version, and native call mappings. Checkpoint version 1 remains readable and upgrades to version 2 on the next durable transition. A legacy provider continuation cannot enter native tool/context mode; use a new conversation. Existing text continuation behavior remains available through the text path.

## Model and context flow

For a native turn, the kernel saves the immutable task objective, constraints, memory excerpts and provenance, execution authority, initial advertised tools, budget, and run limits. ContextBuilder constructs requests from those fixed inputs plus immutable raw history. Saved extractive compaction records retain source digests. Tool selection can expand through a successful local `search_tools` operation; every returned definition must match the actual trusted registry, saved allowlist, and selected-tool bounds. Restart validates expanded definitions even when the next phase is tool execution.

Context bindings preserve opaque native reasoning, thinking, signatures, provider call identifiers, and other continuation data without inspecting their payload. Tool-catalog expansion does not change the history-affecting binding. Fixed-context or compaction changes follow ContextBuilder's explicit invalidation rules; required continuation cannot be discarded while a native tool round remains unresolved. The kernel does not mutate authoritative raw history to compact it.

Before a native API call, the kernel durably records its attempt UUID, reserves estimated input plus the output-token cap, and saves the built context. A crash, cancellation, or provider error can leave `ProviderInFlight`: the request may already have reached the provider. A normal resume reports that boundary. `ProviderResume::RetryUncertain`, exposed as `--retry-uncertain`, explicitly permits another request and can incur another charge. No exactly-once remote inference is claimed. Reported provider input/output counts are tracked separately from conservative charged token budget; unreported usage does not refund a reserved request. The text-only legacy path retains its original explicit-resume behavior.

Only a provider's validated `Completed` response can produce durable assistant content. Streaming deltas remain provisional. Tool-argument fragments never execute. Completed calls must name an advertised tool and pass actual registry JSON Schema validation. Invalid calls receive a canonical explicit error result without execution. Response stop reasons, duplicate provider call identifiers, count limits, and size limits are checked before dispatch.

## Native tool rounds and recovery

Each accepted model call receives a stable internal UUID, a separate exact `provider_call_id`, and an operation UUID derived from the internal call identity. The assistant message, all mappings, and opaque provider continuation commit before any broker operation. Durable model-history conversion restores provider IDs from that mapping and parses the exact stored JSON tool result. Host-only calls without provider IDs cannot enter provider history.

Eligible round slots are durably marked dispatched before bounded concurrent execution through the single injected broker. The broker enforces authority, exact-operation approvals, concurrency, execution journal replay, and cleanup boundaries. Terminal per-call results commit as they arrive. A complete Tool-role message is appended only after every slot has a known result, in the original assistant-call order. The provider cannot advance past missing, awaiting-approval, or uncertain results.

A required approval is checkpointed with the exact call and published through `PermissionRequested`; a later invocation resolves that saved operation and resumes the same UUID. Semantic tool failure output remains a model result with `is_error=true`. Safe known results, including denied operations, are retained. Broker interruption flags stop the run even when a known result exists. `Unknown`, reconciliation-required errors, and rejected broker operations pause rather than retry privileged work. An in-flight operation can be looked up again using its same UUID; it never becomes a new operation. Owner cleanup reconciliation remains the broker's responsibility, and an immutable unknown result is never re-executed by the agent.

Cancellation signals active operations, drains broker completion/cleanup boundaries, and stops before the next model call. Dropping a stream cancels its child token; the broker still owns supervised cleanup and durable quarantine. A host must retain its global state ownership until that work is drained. The foreground CLI drains its stream on output failure and SIGINT/SIGTERM before settling task state. Durable appends can win a cancellation race; inspect status after an uncertain exit.

## Foreground composition

`chat --tools` admits an actual Queued TaskRow with a typed TaskRecord, using the accepted command UUID as its typed task UUID and the durable accepted user timestamp. Exact task identity is checked on restart. It transitions the task to Running before the kernel, Waiting on a durable pause/error, and Completed only after a saved final native response. Exact completed command replay also reconciles a task left Running or Waiting by a crash after its final response commit, without repeating inference. This works from original acceptance and immutable response history even after a later run replaces the latest private run summary. These helpers do not implement background scheduling or public task lifecycle orchestration.

The CLI uses only real registered `read_file`, `write_file`, `search_files`, `shell`, and local `search_tools`. Read-only is the default mode. Shell requires explicit FullHost authority and exact host approval; it is not a sandbox. Workspace, mode, and budgets are saved on the first native turn. Active resume reconstructs them and rejects overrides. Before a native setup exists, an accepted pending command can still supply those initial options. Environment provider credentials are neither events nor checkpoint data. Injected provider callers must construct the adapter from the exact stored endpoint; a provider ID alone cannot attest that configuration.

## Resource limits

- User and completed assistant text each have a 128 KiB UTF-8 bound. JSON escaping can hit the public event limit sooner.
- Every public event is at most 256 KiB; every private checkpoint is at most 8 MiB.
- Loaded immutable history is limited to 65,536 events and 64 MiB of serialized rows. Native provider contracts additionally bound requests.
- Tool arguments are never truncated. Model-facing tool-result JSON is capped at 32 KiB. Larger results become an explicit truncation object with original JSON size, SHA-256, and a bounded UTF-8 preview; full output remains in the broker journal. Persisted and submitted canonical result content are identical.
- Saved native definitions are bounded to 2 MiB, memory to 1 MiB, and selected tool definitions to 512 KiB.
- Default limits are 16 model attempts, 64 tool calls, 16 calls per response, eight concurrent call futures, 64 selected tools, one million charged tokens, and one hour. Validated callers can tighten them, including a zero-tool-call budget. Limits and wall-clock rollback stop execution before dispatch.
- Credentials come from the environment. Literal loopback HTTP(S) proxy selection is explicit and immutable per conversation. The foreground CLI does not proxy commands to an already running background owner.

Each native stream anchors one monotonic deadline. Before provider requests and buffered broker admission, the kernel checks the saved observed-wall floor and effective wall deadline as well as that monotonic deadline. Samples below the floor or at expiry stop further admission without refunding charges or replacing stronger in-flight/reconciliation status. Legacy records use the original start as their floor, and the constructed timeout remains capped by the configured duration. Historical seeded clock-phase inspections are described in the [agent contract](../contracts/agent.md); actual operating-system clock changes and successful inference across rollback remain unverified.

Automated coverage is deferred to [#32](https://github.com/izyuumi/everything/issues/32). Compilation and disposable local inspection do not verify live provider inference, provider billing, or successful opaque continuation through a live provider. This implementation is not a security audit or a claim of production readiness.

## Validation performed

Formatting, all-target workspace compilation, strict Clippy, and release compilation passed on Linux. Disposable native recovery inspection seeded call-round records through the actual Store API and then ran the real CLI, builtin tools, authorizer, and broker. It verified ordered filesystem success/error results, native writes, offline discovery, exact shell approval, known-result persistence, in-flight slot re-entry with the original UUID, and model-attempt-limit pauses. Restart preserved operation counts and side-effect marker counts. An actual shell timeout and SIGINT during an approved shell produced Unknown and a reconciliation stop; SIGINT returned 130 after cleanup. No unknown effect was retried by --retry-uncertain.

A disposable SQLite abort on a private phase commit prevented all broker reservations and filesystem writes; removing that injected storage failure allowed recovery. A manually seeded final durable response verified task-settlement crash repair on completed replay without credentials. SQLite integrity remained valid. Failure-only local HTTP responses verified one initial request, no request on ordinary uncertain resume, exactly one additional request after explicit retry, and no request beyond the attempt budget; zero-tool budgets sent empty tools with tool_choice none. These checks did not generate a successful provider response or verify live inference. Temporary inspection drivers and disposable data are not repository features or retained test fixtures.
