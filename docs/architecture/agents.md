# Agents and task scheduling

The Scheduler composes a caller-provided shared Agent, ToolRegistry/Authorizer, and global ToolBroker. Primary tasks and subagents use the same native kernel. The scheduler owns durable admission, task lifecycle, parent/child relationships, worker cancellation and restart decisions; its host caller owns authenticated command acceptance, provider credentials, state lease and service lifetime. Production background-host composition remains separate work in #18/#68. There is no second host inference loop.

`scheduler/types.rs` defines captured execution policy, provider construction, submissions, snapshots and bounded scheduler limits. `repository.rs` owns scheduler TaskRow encoding and state transitions over the shared Store. Insert uses an immediate transaction for identity replay, conversation ownership and capacity. All subsequent state mutations run through the sole control actor. Other host modules may read snapshots, accept commands or invoke public scheduler methods; they must not write scheduler-owned TaskRows directly.

`actor.rs` runs a bounded event-driven control queue on one host-owned blocking thread, so SQLite and descriptor operations do not block Tokio workers. It awaits native workers through a JoinSet and dispatches only when a control/completion event changes eligibility. Primary and subagent slots are separate, with at most three total active descendants. It does not hold a broker permit while awaiting a child task. Nested spawning rejects admission when the shared descendant slots are already occupied rather than creating an implicit wait cycle.

`worker.rs` constructs the native provider from the task's exact immutable configuration, reconstructs the inherited authority and optional local discovery binding, and drains the existing Agent kernel. It persists no task state. Each worker reports known final output, explicit waiting boundary, cancellation or failure to the actor. Unknown effects and uncertain provider attempts cannot enter normal model tool results or receive fresh identities to overcome recovery.

`workspace.rs` creates owner-only isolated physical child directories with durable ownership markers. `tools.rs` supplies the four native controls through weak scheduler bindings, avoiding a registry/scheduler ownership cycle. Parent instructions and subsequent messages provide explicit context; isolated workspaces begin without a repository copy or access to parent files through child filesystem tools. ReadOnly native task controls can create application-owned private workspace metadata while preserving the child's read-only tool authority.

Task definitions and current checkpoints live in the existing tasks table. Definitions capture original accepted instruction, immutable parent and conversation IDs, configuration and execution policy. Checkpoints hold status, active command, bounded queued messages, cancellation intent, waiting reason and retry audit. Host acceptance time remains independent of native user-message time. No credentials enter these records.

Cancellation is durable at the parent before descendants are notified. Startup and dispatch inspect ancestor cancellation; process interruption cannot reopen a descendant just because its own cancellation flag was not written. The host starts broker recovery before scheduler activation. Explicit provider retries require an exact owner request and an ephemeral one-attempt permit that is never restored on restart. A coalescing watch channel lets IPC clients requery durable events and task state without another run queue.

See the [scheduler contract](../contracts/scheduler.md) for public APIs, limits, workspace recovery and shutdown ownership, and the [native kernel contract](../contracts/agent.md) for model/tool durability. Memory-service host composition remains tracked separately; this scheduler does not silently infer parent memory or substitute simulated provider behavior.
