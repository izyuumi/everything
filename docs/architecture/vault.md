# Credential vault

Status: **core, agent use and the 1Password and Proton Pass providers implemented; clients not yet.** [#217](https://github.com/izyuumi/everything/issues/217) added the vault core, the local provider and owner IPC. [#219](https://github.com/izyuumi/everything/issues/219) added the Host agent tools, vault leases, broker environment injection and the per-task redactor described below. [#220](https://github.com/izyuumi/everything/issues/220) added the 1Password provider over `op` and [#221](https://github.com/izyuumi/everything/issues/221) the Proton Pass provider over `pass-cli`; real behaviour of both is unverified ([status](../status/implementation.md)). Tracker [#215](https://github.com/izyuumi/everything/issues/215). Decision: [ADR-0016](../decisions/ADR-0016-credential-vault.md). Wire shapes, grammar and limits: [vault contract](../contracts/vault.md).

The vault lets the agent use the owner's secrets by reference. The model sees item metadata and `vault://` references; the Host resolves values inside the Tool Broker and hands them to one approved destination.

## Data flow

**Search.** The model calls `vault_search { query, kinds?, limit }`. The broker authorizes it under `ToolScopeRule::Vault`: TrustedWorkspace and FullHost allow it, ReadOnly asks. The vault service searches the local index first and, while results remain under the limit, asks each connected external provider (1Password `op item list`, then Proton Pass `pass-cli vault list` and `item list` per vault) and keeps only metadata; the local provider never touches the native store. Results are `VaultItemSummary` rows, merged and bounded, returned as the tool result with any disconnected, locked or failing provider listed under `unavailable_providers`. External summaries are also kept in a bounded process-wide cache keyed by reference, because the synchronous authorizer needs an item's kind, label and fields; a `vault://1password/...` or `vault://protonpass/...` reference is therefore usable only after a search in the current Host process returned it.

**Use.** The model calls `vault_use { ref, destination, reason }` in a FullHost task. The authorizer looks the item up in the index (refusing missing items, missing fields, cards and the reserved destinations) and adds the item's provider, kind, label, field, sites and the destination to the approval scope. The arguments hold only the reference, so the permission row and the inspection rendered by the CLI, macOS and iOS clients carry no value. The owner chooses *Allow once* or *Allow for this task* (a vault lease). Nothing resolves for `env`: the succeeded journal row is the binding. When a later `shell` call in the task is about to spawn, the broker re-authorizes it (its approval already listed `$NAME` and the item label), checks each binding's grant is still live, calls `resolve` into a `CredentialSecret` (for 1Password, `op read --no-newline`; for Proton Pass, `pass-cli item view pass://…` with one trailing newline removed; both into a bounded zeroizing buffer), adds the value to the task's values and injects `NAME=<value>` into the child's otherwise empty environment. The shell's own arguments show only `$NAME`. Output passes through the builtin redactor and then the broker's redaction before it reaches the journal, the model, events or memory. When the task's run ends other than for a wait, its values are dropped and zeroized; leases are bound to the task and expire within the hour. For `mcp_env` the tool resolves once after approval and stores the value as that server variable's native MCP credential for its next start.

**Request.** The model calls `vault_request { kind, label, site?, env_name? }` when nothing fits. That always creates an approval request showing what is wanted. The owner adds the item through a masked owner surface (`everything vault add`, the TUI `/vault` modal or `vault_put` on the private owner pipe; the macOS SecureField sheet arrives in #222), so the secret travels only as `SecretTransfer` on that pipe, and then approves. The tool result contains only the reference of the newest ready item with that kind and label, which the model then passes to `vault_use`.

## Threat model

**In scope.**

- A prompt-injected model trying to read, exfiltrate or widen access to secrets: it only ever handles references, every use needs an exact approval scoped to its own task, empty searches are refused, and output is redacted.
- A stolen or compromised paired device or relay: it sees references and metadata, never values. Secret entry is not possible over the relay in v1.
- Accidental leaks into logs, events, journals, permission rows, memory, settings or error text: values only exist in `CredentialSecret`/`SecretTransfer` buffers, whose Debug is redacted and which no durable record serializes.
- A model trying to reach its own provider's bearer token: SIWC and other model credentials are not vault items and cannot be listed or resolved.

**Out of scope, stated honestly.**

- A FullHost `shell` the owner approved can exfiltrate an injected value: echo it somewhere the redactor does not see, send it over the network, or transform it (base64, reversal, splitting) past literal redaction. The approval chip naming the vault item is the defence; redaction is not.
- A FullHost `shell` can call `op` or `pass-cli` directly. A 1Password app-integration session or a persistent Proton Pass session then bypasses Everything entirely. Approvals for shell commands that mention those binaries carry a `warning=` target ([#219](https://github.com/izyuumi/everything/issues/219)); a vault-scoped Proton Pass access token narrows the exposure.
- A Proton Pass personal access token is stored as an ordinary local `api_secret` item, so `vault_search` can return its metadata and a FullHost task could ask to use it; that still needs the owner's approval, which names the item `Proton Pass personal access token`. The Host passes it to `pass-cli login` only as `PROTON_PASS_PERSONAL_ACCESS_TOKEN` in that child's environment; the standard library does not zeroize that copy.
- 1Password and Proton Pass errors are classified, never echoed: stderr is read into a bounded zeroizing buffer, matched for locked and not-found phrases, and otherwise reported only as the exit status. For 1Password the matching beyond "signed in" is not from 1Password documentation; the Proton Pass phrases come from the pass-cli source.
- A swapped binary at the pinned `op` or `pass-cli` path runs with the Host's user rights; the path is shown to the owner at connect and in `vault status`, but its signature is not checked.
- A compromised process running as the same user, as for every native credential ([credentials](../contracts/credentials.md)).
- Copies made inside native keyring or HTTP libraries, the process-spawn environment copy, transient strings made while masking, and values already handed to a running MCP server or shell child.
- An `mcp_env` value written for an MCP server outlives the task and its lease until the owner removes that MCP credential; later tasks' MCP results are masked only by that task's own values.
- A value a shell wrote to a file is masked when read back only by tasks holding that value; another task reading the file sees it.
