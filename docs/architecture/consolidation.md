# Background wiki maintenance

Issue [#26](https://github.com/izyuumi/everything/issues/26) adds `memory::consolidate::Consolidator`. It owns one `Wiki`, a separate private SQLite execution journal, and an optional injected native `ModelProvider`. Markdown remains authoritative for memory facts, citations, and decision supersession. The journal records work identity and interrupted writes; it is not another memory source. This module has no filesystem watcher, periodic scheduler, source downloader, tool executor, or embedding dependency. The background host must construct and run the service and submit bounded evidence when conversations or documents should become memory.

`run(shutdown)` starts one event-driven worker. Enqueue and retry wake it through Tokio notifications; idle maintenance does not poll. A supervised task retains the worker lease until active work has unwound, including when the caller drops `run`. Disk and SQLite operations acquire one asynchronous admission permit before `spawn_blocking`, sharing one mutex and one owned wiki. Accepted enqueue/retry operations notify from inside that durable blocking operation, so dropping their caller futures cannot leave persisted work asleep. Model streaming runs asynchronously outside that mutex. Other requests may enqueue, query job status, or cancel generation while a provider request is active. Duplicate `run` calls fail.

## Ingest

The caller supplies a topic and one to sixteen `MemorySource` values containing a stable caller ID, title, absolute source locator, and evidence text. The module does not fetch locators or attest source truth. Locators permit `https`, `http`, `file`, and `everything`, reject embedded credentials, and are written verbatim as citations. Evidence and native-provider requests can contain private information: selecting a remote provider explicitly sends the bounded task and selected wiki excerpts to that provider. Host permission and provider configuration must authorize that disclosure.

Before generation the worker synchronizes the wiki, searches up to eight topic terms, and selects at most four existing candidate pages and sixteen excerpts. Source evidence, candidate content hashes, and active managed entry IDs enter `ContextBuilder` as task state. The builder retains excerpts within the configured token and byte budget. There is no conversation-wide history or tool catalog in this narrow maintenance request. Source text and memory are explicitly marked untrusted data; maintenance cannot invoke tools or follow instructions embedded in evidence.

A real injected provider returns a typed JSON `ConsolidationPlan`. The host validates the complete plan before changing a file. A plan updates exactly one candidate page when candidates exist; it may create a new page only when no candidate exists. Existing-page selection is bounded lexical retrieval, so an unrelated or unindexed topic can still create a new page. Entries cite only supplied source IDs. Unknown fields, paths outside the wiki, stale expected hashes, repeated entries, invalid headings, excessive output, and unknown supersession IDs are rejected. Model text never selects arbitrary file operations or permissions.

The host preserves all old page bytes except explicit managed status lines and appends new sections. Each section receives a deterministic entry ID and source digests, followed by blockquoted model summary text. An entry may supersede a listed active ID on the same candidate page. The old section and citations remain present, its status records the successor, and the successor records the old ID. Model text cannot emit host metadata because every summary line is quoted. Factual accuracy and whether a decision truly supersedes another remain model and human review responsibilities; validating a cited source ID does not establish entailment.

Without a provider, ingest becomes `waiting_for_model`. `apply_host_plan` accepts an actual host-authored plan under the identical validation, write, and recovery rules, and records `host_provided` origin. This is also useful for deliberate maintenance without inference. It never reports a model-generated result.

## Durable writes and recovery

The private SQLite journal uses WAL, synchronous `FULL`, exclusive connection locking, a version/application identity, bounded retained payloads, and a single owner. Its parent directory must already exist in private host storage. The host store and the derived wiki index are not modified by this schema. One wiki writer must own this journal and canonical wiki root; a different journal path does not create a shared cross-process lock on the wiki.

Before any Markdown mutation, a `prepared` row durably stores the complete validated final Markdown, its before/after SHA-256 hashes, entry IDs, and origin. The worker then uses the existing crash-safe wiki page operation and reindexing. Completion clears the staged page and persists the resulting page hash and IDs. A crash after writing Markdown but before journal completion therefore retains enough information to reconcile the write.

Recovery reads canonical Markdown. A page matching the after hash is synchronized and completed without appending a second copy. A page matching the before hash receives the staged write. A page matching neither is preserved and the prepared job records a diagnostic. Failed prepared work retains its immutable plan and stops automatic retries within that process. Explicit `retry` reattempts reconciliation; startup also permits one new reconciliation attempt. It cannot regenerate or cancel an already prepared write. Generation interrupted before preparation becomes `interrupted`; explicit retry is required because the remote request outcome may be unknown. Multi-page writes are deliberately unsupported, preventing an unjournaled partially applied batch.

Internal writes are serialized and compare the expected content hash before replacement. These checks prevent lost updates among this service's jobs. An uncooperative external editor can still replace a file between the comparison and atomic rename; ordinary filesystem APIs do not provide a file-content compare-and-swap. Hosts should direct coordinated edits through the owner or pause maintenance during external editing. This implementation does not claim protection against concurrent malicious same-UID writes, or power-loss durability for newly created ancestor directory chains. See the underlying [wiki filesystem contract](memory.md#page-api-and-filesystem-boundary).

## Query and lint

Query synchronizes and retrieves up to sixteen lexical hits. It reads actual chunk contents and includes the canonical content hash and one-based inclusive line range with each result. Without a provider, or without evidence, it returns `answer: null` and the available cited excerpts. With a provider, only excerpts retained by `ContextBuilder` may be cited in the bounded JSON answer. Unknown or duplicate citation IDs are rejected. A citation records the read snapshot; a later external edit can make that snapshot stale. No model answer is fabricated when inference is unavailable.

Lint is deterministic and performs no inference or network access. It pages through canonical files, checks chunk identity/provenance, managed entry syntax and source URL/digest shape, duplicate managed IDs within the selected lint page, reciprocal supersession and cycles, invalid or missing wiki targets, and missing heading fragments. Native fragments use Unicode-lowercased alphanumeric heading text, whitespace converted to hyphens, retained hyphens/underscores, and numbered duplicate suffixes. It does not check remote URL availability or prove the content behind a source digest. Findings include a page, source line, stable code, and bounded detail. Cross-page duplicate detection requires those pages to appear in the same lint job; there is no persistent global lint result index.

## Limits and validation

A request is at most 128 KiB; source text is at most 16 KiB each and 64 KiB total. Generation accepts at most 4,096 events and 64 KiB of response text. Plans append at most eight entries with 4 KiB summaries. A consolidated page is at most 2 MiB with at most 1,024 managed entries, and must also satisfy the owned Wiki's configured page/chunk limits and current page capacity before becoming prepared. The final parsed Markdown must retain every generated managed entry outside code blocks. Persistence repeats the same internal Wiki preflight; neither preflight nor the existing hash check reserves filesystem capacity against external editors. The journal retains at most 4,096 jobs, accepts at most 128 unfinished jobs, bounds payloads below its 64 MiB page ceiling, and rejects further work when full; no automatic deletion or backup subsystem exists. Host setup owns file permissions and retention policy. Journal request data is local plaintext.

Lint scans one to sixty-four pages per job with a 16 MiB aggregate read budget and 128 findings. Additional findings set `findings_truncated`; a path cursor continues later pages. Budget exhaustion returns an explicit failure and requires smaller pagination. Wiki scans, synchronous filesystem operations, and SQLite calls have cooperative boundaries rather than hard preemption. A cancelled generation is observed before durable preparation; a prepared write completes or remains recoverable. Native provider cancellation releases its stream according to the provider contract, but a timeout cannot retract a request already received remotely.

Formatting, workspace compilation, strict Clippy, and release compilation passed during implementation. Disposable runtime inspection exercised real host-authored ingest, exact and cross-ID request replay, preserved citations and superseded decisions, stale-hash conflict, traversal rejection, queued cancellation, unavailable-model waiting, actual lexical query excerpts, and malformed-source/broken-link/missing-fragment lint findings. An induced SQLite index-insert failure occurred after the canonical file write: the job retained its prepared bytes, refused cancellation, and completed after reopening without appending a second managed entry. The private journal reported an `ok` integrity check. Queue and cancelled-job retry admission rejected work at 128 unfinished jobs. Live provider-generated maintenance requires configured provider credentials and was unavailable; these file/journal observations do not verify model output quality or native-provider maintenance behavior. Automated crash, concurrency, parser, provider, and adversarial input coverage remains deferred to [#32](https://github.com/izyuumi/everything/issues/32).
