# Reversible semantic memory controls

The source in `host::memory`, `memory::consolidate` and `memory::search` supplies trusted Rust controls for the revision-safe Settings facade. The controls keep the existing canonical Wiki, FTS index, maintenance journal, provider and Consolidator. They do not authorize a settings mutation or persist Host settings. An operation identifier or runtime generation cannot establish caller authority. The Settings writer must validate and journal its immutable Applying intent before suspension, reconcile the real file result, and invoke application only for the proven committed original request.

## Startup preferences

`MemoryService::open` preserves its previous signature and delegates to `open_with_embedding_preferences(agent, settings, providers, cancellation, preferences)`. `EmbeddingPreferences` contains the captured operator `EmbeddingSettings`, an effective enable flag and `EmbeddingDimensionChoice::{Inherit, BackendDefault, Selected}`. Startup requires that the captured configuration equals `settings.embeddings`; it preserves that original snapshot in `settings()` while resolving the effective embedding choice before initialization. Explicit off reaches lexical initialization without opening a model/runtime/vector file or constructing a helper. Syntax validation still applies to retained configuration.

Inherit preserves the configured dimension. BackendDefault uses the actual compiled EmbeddingGemma 2 loader's named 768-dimensional default. `EmbeddingSettings::backend_default_dimensions()` performs no I/O and returns no value for a disabled configuration or an uncompiled backend. Without that backend, enabled preferences are unavailable and use FTS; no replacement profile or dimension is synthesized. Selected values must satisfy the existing backend validation. The facade separately rejects new dimension edits when no real cached profile can establish supported choices. Previously saved desired preferences remain representable during unavailable execution.

## Admission and queued work

One independent short semantic gate belongs to the actual Consolidator. It tracks a checked generation, original operation, admission state and invalidation token. `MemoryService::suspend_semantics(original_operation_id)` closes new semantic admission synchronously. It acquires neither the maintenance semaphore nor MaintenanceState and does not await helper shutdown. Same-current-operation suspension returns the same opaque generation; a different operation advances it. Permanent shutdown or generation exhaustion remains closed. Generations contain the actual originating gate identity and are not serialized.

Retrieval and explicit rebuild capture once before their first real admission wait. A queued maintenance Query captures at enqueue, before its database wait; only a successfully inserted new job retains that capture under its existing job identifier. Exact replay and retry keep the original capture. The private map is bounded by the existing 4096 retained-job ceiling, needs no DDL and retains no Core reference. Recovered or missing captures use lexical retrieval. An off capture stays lexical after re-enable.

The original capture is rechecked after real semaphore/state admission, during semantic preparation, immediately before each actual document/query embed, before vector activation and before returning a hybrid answer. Stale/off retrieval executes the existing Wiki synchronization and genuine FTS search. Rebuild stops instead of adopting a new backend. Semantic invalidation does not cancel the retrieval caller's token and therefore does not relabel a genuine lexical result as caller cancellation. An inference or vector write admitted immediately before suspension may finish; gate closure is neither rollback nor proof of instant native interruption.

Existing MaintenanceState serialization still spans synchronous inference/IPC. The new gate and application metadata locks remain short and do not span SQL, file/model operations, awaits or displaced-backend cleanup. Public low-level backend setters retain their signatures and invalidate prior captures. Internal live installation checks the exact originating generation and leaves queries closed until real compatible readiness.

## Proven no-file-effect restoration

Only after the Settings writer proves the exact original pre-file snapshot, `restore_semantics(&original_generation)` may restore prior admission without applying embeddings. The opaque ticket privately retains the actual pre-suspend query flag. Restore requires its exact live originating gate, operation and epoch, and rejects any bound or started same-generation application. It preserves the actual backend, process, status and cached profile; it performs no helper/model/vector/provider/SQL work and never retries a failed backend. An originally closed gate remains closed. A backend that became unavailable remains unavailable.

Restore advances to another checked fresh epoch and retires the supplied ticket, so neither pre-suspension nor suspension-era captures revive. Repeating the retired ticket fails instead of creating another restoration. Exact command replay must read the durable original no-effect outcome and must not call suspend/restore again. A later generation, application binding, permanent close or exhaustion rejects restoration. This trusted control API does not establish pre-file proof itself; the facade owns that proof and invokes restoration outside reads and client replay.

## Bounded original-operation application

`apply_embeddings(generation, EmbeddingApplyRequest)` validates the positive original settings revision, canonical lowercase SHA-256 request identity and complete private capture, bounded to 32 KiB. Its generation must belong to this service and exact original operation. A changed request on the same generation conflicts. One owned application step may be active; admission returns Started, Observed or Deferred without creating an unbounded waiting-task queue. A dropped response does not drop admitted work.

The worker detaches the old backend through the existing serialized Consolidator, then shuts down/reaps its helper on a blocking worker retaining the Agent. Only afterward may it load the new strict isolated backend. Isolation/model initialization precedes vector database access, with no in-process fallback. A stale constructed result is actually shut down off Tokio. The same Core and Agent remain retained, with Agent after Store-bearing resources in retained bundles. Explicit off settles Disabled after actual cleanup; persistence and immediate suspension can already be complete while cleanup remains Pending.

One step uses the existing `BuildBudget::default()` of 64 chunks/30 seconds. Partial ChunkBudget/TimeBudget reports retain the same helper and vector building generation and report actual counters. Explicit facade-owned advancement may call the same exact request/ticket again for one more bounded step. An exact user command replay or a status read must not invoke advancement. Terminal Failed/Unavailable/Ready/Disabled reentry is observational and never reloads a helper. A different approved operation needs a fresh generation. There is no automatic helper respawn or retry. If actual old-backend stop or stale-construction cleanup fails, the worker synchronously latches quiescence failure, closes service intake and requests supervised shutdown before releasing application admission. A later operation cannot start another helper through that service. Its application snapshot reports Failed with QuiescenceFailed before the ordinary closing-to-Stopped classification; it does not certify completed cleanup. Structured errors preserve both the original operation failure and cleanup failure when both occur; helper shutdown and worker errors retain their actual typed causes. Normal successful off/superseded cleanup keeps its existing behavior.

Ready requires the actual completed BuildReport and compatible active vector generation, followed by exact-generation activation. Compatible existing ready vectors may be reused and are reported as such. Pending, failed, stale or incompatible work keeps new queries lexical. No running task's captured model/provider/context changes.

## Metadata and shutdown

`embedding_metadata()` returns numeric generation, semantic-admission state, whether an owned application step is actually active, actual backend status, an optional profile cached only from successful real construction, and the current bounded application snapshot. Closed phases distinguish Pending stages, Disabled, Ready, Unavailable, Failed, Superseded and Stopped. Progress contains numeric actual build counters. Raw backend errors, artifact paths, Wiki content and captured request bindings stay out of this metadata. Previously known profile metadata may remain available while off; that is separate from backend availability or query admission.

`embedding_changes()` returns one shared Notify hint. Consumers register and enable notification before reading authoritative metadata and wait only when that snapshot still requires it. Hints do not form a durable event queue; the facade owns operation history. No status read starts work.

Permanent shutdown closes the gate, cancels its current generation, refuses new application and waits for the active owned step, actual Consolidator idle, backend detachment and off-Tokio helper shutdown before publishing Stopped. Metadata poisoning closes admission and remains an explicit failure; cleanup recovers poisoned state only to retain/join actual work and release its resources. Backend shutdown still takes and stops the actual helper if serialized backend detachment fails. A combined structured error preserves both failures when detachment and stop fail; any such result sets the quiescence failure latch and cannot publish successful shutdown. Reversible off never calls permanent service shutdown.

## Integration and validation boundary

The [shared service](../contracts/settings-service.md), [startup mapping and owned driver](../contracts/host-settings-startup.md) now connect these hooks to real file-intent ordering and bounded change hints. Their presence alone does not establish usable UI controls or full issue #109 acceptance. Root owns integration and all compiler/artifact windows.
