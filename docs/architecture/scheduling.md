# Native scheduling

Issue #51 extends the existing host with `scheduling::engine::ScheduleEngine`, the pure `scheduling::clock` calculator, and durable isolated execution. Issue #52 adds serial factory-safe attempts, cumulative budgets, explicit uncertainty acknowledgement and optional terminal notifications. It uses the host's existing Agent, Scheduler, ToolRegistry, Store and global Tool Broker. It creates no second task runtime, provider gateway or service. Markdown memory and cloud delegation are independent features.

`ScheduleEngine::start(agent, scheduler, registry)` validates the actual schema-9 execution ledger and starts in a recovery-only inactive state. It performs no schedule dispatch until the host explicitly calls `activate()`. Host composition must finish broker recovery and native scheduler setup before activation. The headless HostService owns one engine on those shared services, activates it after the initial metadata publication and native scheduler, and closes schedule controls before draining the engine and scheduler. Its owner IPC and [CLI](../development/scheduling-cli.md) expose the same bounded controls and exact uncertainty acknowledgements. Disabled jobs are absent from due scans. An explicitly claimed manual run can still execute for a disabled job. Construct one engine for the host; SQLite claims and reserved identities remain the durable deduplication boundary.

The engine owns admission and observation, while the native scheduler owns task execution and cleanup. `wake()` follows committed schedule changes or manual claims. `status()` and `subscribe()` expose process-local operational state, bounded diagnostics, total blocked-job count and up to 64 blocked previews. These are hints, not durable event cursors. A restart rescans storage. The host binds owner management and all eight native scheduling tools to the shared [controls service](../contracts/scheduling-controls.md). Retries and result publication follow the [execution contract](../contracts/scheduled-execution.md).

## Calendar and timer

See [ADR-0005](../decisions/ADR-0005-scheduling-calendar-and-admission.md) for calendar, clock and admission decisions. Once and anchored intervals retain UTC millisecond instants. Croner 4 generates integral-second wall-calendar candidates under the validated native grammar; chrono-tz maps them to instants. Nonexistent wall times are skipped. Repeated wall times use their earliest UTC mapping exactly once, including wildcard patterns. The reverse latest helper accounts for a later fold's wall-future but UTC-past candidates.

Calculations reject overflow, use checked library calendar arithmetic, observe cancellation, and bound candidate work. The cron library's supported year range is narrower than storage's once/interval range. Search limits are explicit blocked errors, not silent exhaustion. A synchronous library call cannot be forcibly interrupted by the outer cooperative budget; it runs under retained blocking-worker admission.

The timer combines Tokio's monotonic sleep with a fixed one-second realtime audit and explicit edit/native-scheduler wakes. It rereads actual wall time before due admission. Tokio sleep alone does not track wall-clock jumps. Recording timestamps may clamp to the record's prior update time; eligibility never uses that clamp. The engine stops unadmitted work when its current sample precedes the original claim and preserves the original native absolute deadline. This comparison alone cannot detect every backward movement that remains after the claim; native execution clock guards are a separate boundary.

The engine selects the latest due occurrence at or before the sampled wall time. Five seconds is normal lateness. Default missed Skip dispatches that recent occurrence, including after restart, and does not backfill an old backlog. Captured Latest can additionally admit its latest occurrence within its configured window. Older due prefixes are collapsed into one terminal missed-range history entry. No omitted occurrence count is invented. SQLite atomically persists that skip and next-pointer advancement, avoiding a crash gap which could dispatch skipped work.

Due pages are bounded. Temporarily blocked IDs are excluded from the next page so one failed oldest job does not prevent independent due jobs from progressing. After a successful durable advance, a bounded 20 ms continuation rereads due state so a dense interval's latest occurrence is admitted promptly. Failures use a five-second backoff and visible diagnostics; retained quotas remain fail-closed. Database/source failures do not become successful empty work. Native watch revisions and explicit wakes shorten latency; the one-second audit recovers missed wake hints.

## Durable native admission

The occurrence claim already reserves one immutable native TaskId. The first-attempt ledger reserves the corresponding isolated ConversationId, conversation-creation CommandId, input CommandId, accepted timestamp, exact captured execution policy and absolute deadline before calling either Agent API. The first task identity must equal the occurrence's reservation. All admission fields are immutable, bounded and read with metadata limits before string copies. Aggregate policy storage is capped at 64 MiB; history is retained.

The engine idempotently creates that isolated conversation from the captured provider/model/endpoint configuration, accepts the exact instruction and enqueues the exact TaskSubmission. Restart uses the same IDs and policy. Existing task snapshots must match the original conversation, command, instruction, parent and acceptance time. A missing previously admitted task becomes Unknown, requiring owner reconciliation; it is never replaced. Ambiguous enqueue or finish returns are reconciled against durable state.

Credentials stay in the host's provider factory and are resolved for the saved destination. Native runtime-control tools are filtered from the initial scheduled allowlist because their independent child budgets are not an aggregate occurrence budget. Other tools remain subject to the inherited explicit ceiling and current broker permission checks. No approval or uncertain paid retry is automatic.

The occurrence deadline is original claim time plus captured timeout, including queue, approval, offline and retry waiting. The native absolute-deadline boundary prevents queued work from extending authority at worker start. A completed native result is recorded only through the scheduler's durable terminal identity. Before success, failure or cancellation mapping, the engine reads the original task and durable terminal evidence together, validates its immutable occurrence binding, and inspects original typed waiting/native evidence plus immutable Running/Unknown tool journal rows. It never attributes a later command's native summary to the original attempt. Unavailable legacy accounting consumes full conservative allowances with known=false without changing a known effect outcome. Any uncertain boundary records Unknown, keeping the existing overlap slot occupied until an exact owner acknowledgement releases scheduling overlap only; native uncertainty and cleanup remain independent.

New policies retain the captured request ceiling and enforce the exact remaining output-reservation ceiling before each native request. Historical schema-8 policies retain their original conservative request allocation. Serial attempts share the original timeout, request, tool and reserved-output ceilings. Only the native actor's proven unused ProviderUnavailable retirement can authorize automatic retry; generic failure or uncertainty cannot. Optional result publication appends a terminal notification to an idle destination without creating a message or turn. Busy delivery remains durable. See [ADR-0007](../decisions/ADR-0007-scheduled-execution-policy.md).

## Operations and client boundaries

| Observed state or action | Meaning and next step |
| --- | --- |
| Disable or delete a job | Stop future automatic admission; already claimed runs retain their captured definition and require a separate explicit native task cancellation |
| Missing provider credentials | A proven unused factory boundary can consume a bounded attempt and back off; the host does not invent credentials or retry paid uncertainty |
| Unknown outcome | Inspect the occurrence, native task and Broker state; exact owner acknowledgement releases only its scheduling overlap hold |
| Blocked job | Inspect the bounded engine diagnostic and captured job; invalid calendars, exhausted retention or other errors remain visible |
| Pending result delivery | Wait for an idle authorized destination or inspect its delivery error; the host never injects a notification into an active turn or selects another conversation |

An edit creates a new definition generation when the definition changes; existing occurrences keep the original generation, provider destination, permissions, budgets and deadline. Overlap counts active and unacknowledged Unknown occurrences across every generation, including manual runs. The default is one slot; explicit Allow permits at most sixteen. The owner controls and model tools do not erase native uncertainty or bypass current Broker permission enforcement.

The optional macOS [schedule status view](../development/schedule-status.md) uses same-user owner IPC for bounded engine/job/history reads. The iOS client displays [terminal result metadata](../contracts/scheduled-results.md) from encrypted synchronization of explicitly known authorized conversations. It does not enumerate the host's jobs or discover arbitrary execution conversations. Neither client owns a timer, execution loop or host lifetime. The current native clients passed actual macOS/iOS SDK build and static analysis in [#111](https://github.com/izyuumi/everything/pull/111). Device interoperability, UI and notification presentation remain unverified.

## Lifecycle and validation

`shutdown()` stops schedule intake and drains any current admission operation. It does not shut down the shared native scheduler. A ten-second wait can return ShutdownPending while the worker still owns host services; the host must retain its state lease, engine and global services and retry. Dropping the final engine handle requests the same stop. The engine never aborts a native worker or treats disconnect as proof an external effect stopped. The actual host first closes schedule mutations and drains their admitted operations, then drains engine admission before the shared Scheduler. It keeps owner inspection and cleanup controls available while obtaining the Broker all-admission quiescence proof and resolving explicit cleanup requirements. The state lease is retained until those ownership barriers and the final metadata publication pass complete.

The calendar, original-task terminal evidence, serial execution and owner controls are integrated through [#97](https://github.com/izyuumi/everything/pull/97), [#101](https://github.com/izyuumi/everything/pull/101), [#103](https://github.com/izyuumi/everything/pull/103) and [#105](https://github.com/izyuumi/everything/pull/105). Their exact-source Linux/macOS formatting, default/all-feature all-target checks, strict Clippy, release builds and Rust 1.88 checks passed before normal merges. The actual Host activation and control wiring is implemented; new current-source terminal-reentry, legacy accounting, delivery-capacity and lifecycle observations remain pending.

Earlier schema-eight calendar and real Store/Agent/Scheduler observations are qualified in the [engine contract](../contracts/scheduling-engine.md); the [execution contract](../contracts/scheduled-execution.md#focused-current-main-validation) separately records historical schema-nine observations. Neither is relabeled as a new run of current main. Successful native inference, operating-system clock adjustment, forced process-crash recovery, Apple runtime behavior and production readiness remain unverified. Automated coverage is deferred to [#32](https://github.com/izyuumi/everything/issues/32).
