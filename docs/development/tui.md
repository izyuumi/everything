# Terminal UI

`vorra` with no subcommand, or its alias `vorra tui`, opens an interactive full-screen chat against a Host. It talks to the Host only through the existing owner IPC (`HostClient`): conversation/task/approval/agent queries, `Initialize` and `Text` owner commands, `ResolvePermission` and `CancelTask` domain commands, and `ChatGptModels`. It adds no runtime, store, protocol field or credential path; the Host keeps owning execution and durable state.

```sh
vorra                          # same as `vorra tui`
vorra tui                      # new conversation with the latest conversation's provider/model
vorra tui --continue           # reopen the most recent conversation
vorra tui --conversation UUID
vorra tui --provider openai --model MODEL_ID
vorra tui --agent NAME         # new conversations use agent NAME
```

Flags (`--continue`, `--conversation`, `--provider`, `--model`, `--agent`) need the `tui` form. `--agent` with `--conversation` or `--continue` exits with an error unless that conversation is already bound to the agent. Without an interactive terminal on stdin and stdout, it exits non-zero with "the terminal UI needs an interactive terminal; run `vorra --help` for commands" before touching the terminal or the state directory. A conversation is created on the first message, titled from it. Provider, model and instructions stay immutable per conversation, so `/model` and `/instructions` apply to the next new conversation.

## Starting the Host

When no Host answers for the state directory, the TUI offers, inside the terminal UI:

- **Start the host in the background until this window closes.** It spawns `vorra --state-dir DIR serve` in its own process group with null stdio, waits up to 30 seconds for the owner socket, and sends it SIGTERM when the TUI exits (normal quit, Ctrl+C, SIGTERM, terminal hangup or an error). Work still running in that Host is interrupted like any other Host shutdown.
- **Install and start the login service** (macOS only). It runs the existing `vorra service install` and `start` code (enabling a disabled service first). The LaunchAgent label is global, so this replaces any existing Vorra LaunchAgent and points it at this state directory.
- **Quit**, which restores the terminal and exits with the usual "cannot reach the Vorra host" error.

## First-run onboarding

After connecting, the TUI decides whether a usable model credential is configured: any API-key binding in settings counts as usable (the TUI cannot inspect stored secrets); a ChatGPT binding counts only if its status is signed in with plan usage enabled; with no binding at all, onboarding runs only when the Host has no conversations, so existing environment-variable users are not prompted. Source is `src/tui/onboarding.rs`; its steps are an ordered list (`Welcome`, `Provider`, `Verify`, `Save`, `Service`, `Pair`, `Vault`). `Pair` offers to pair an iPhone when the Host has a relay: it shows the same QR code as `vorra pair` (refreshed before expiry), then an Approve/Reject choice (Reject selected) naming the device with its code and short fingerprint and reminding the owner to compare the code with the phone; without a relay it explains how to add one. Esc withdraws the code. This step is compiled and shares `src/host/pair.rs` with `vorra pair`, but it has not been exercised in a terminal. Skipping the model steps jumps to `Vault`, the optional "Connect a password manager" step: Skip continues; 1Password points to `vorra vault connect onepassword` and connects nothing; Proton Pass points to `vorra vault connect protonpass` and connects nothing; "Add an API secret to the local vault" asks for a label and then the secret in the masked input, saves it with `vault_put` and shows only the new reference.

1. **Welcome.** A one-line security note (credentials stay on this machine in the system keychain; the model provider sees conversation content) and Quick start / Custom / Skip. Quick start means OpenAI, native keychain storage and the default model (`gpt-5` for an API key, the plan's first listed model for ChatGPT). Custom asks for provider (OpenAI or Anthropic), endpoint (official or a loopback URL), model and storage (keychain or Host memory).
2. **Provider.** A read-only scan shows whether `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` are set in the TUI's environment and whether settings hold a ChatGPT binding that needs signing in again; values are never shown. Choices are Sign in with ChatGPT (the same owner `chatgpt` sign-in/wait/cancel operations as `vorra chatgpt sign-in`, opening the browser and showing the URL; an existing ChatGPT binding is reused), using a found environment key, or typing an API key into a masked input. The input buffer is a preallocated `Zeroizing<String>` capped at 8 KiB so it never reallocates; pasted text is also zeroized.
3. **Verify.** For an API key, the TUI builds the provider with the Host's own construction (`host::providers::api_key_provider`) and streams a tiny prompt (`max_output_tokens` 256, 60-second limit); success means the provider completed the response. For ChatGPT, verification is the signed-in status with plan usage plus an authenticated plan model listing (`chatgpt_models`); it is not a completion, because ChatGPT tokens live in the Host's vault. On failure the TUI offers Retry, Pick another provider, or Skip.
4. **Save.** Only a verified route is saved: an API key goes through the owner `credential` `store` operation (keychain or session storage per the choice), then `ReplaceSettings` adds the binding to `model_credentials`, replacing any binding for the same provider and endpoint. Settings are re-read to confirm; if the settings write fails, the just-stored credential is removed. The default conversation in settings is not changed, because a model-selection change is a protected setting that needs native confirmation; the chosen provider, endpoint and model are used for the TUI's next new conversation instead. Skip at any point leaves settings untouched.
5. **Service.** On macOS, when no LaunchAgent is installed, an offer (default *Not now*) to run `vorra service install`. It does not start the service while a Host is running.

Esc goes back (on the first screen it skips), Ctrl+C or SIGTERM exits cleanly and restores the terminal. Later launches with a saved route but no conversations start with no model selected; pick one with `/model`.

## Layout

The transcript starts with a banner (agent, model, conversation, tools, Host state directory, cwd). User turns are prefixed `❯`; replies render Markdown under `◈ Vorra` with a model/duration footer, extended with `used N memories` when the Host retrieved Wiki memory excerpts for that reply. Single newlines in replies are shown as line breaks. While a task runs, provisional text from the `task` query's [`live_text`](../contracts/owner-ipc.md#live-assistant-text) streams under a spinner; the committed final message replaces it. The input sits above a status bar showing model, provider, agent, title, message count, tool mode, state, elapsed time and queued messages. Source lives in `src/tui/` (`host` IPC adapter, `app` state, `render`, `markdown`, `input`, `theme`).

## Commands and keys

`/help`, `/new [title]`, `/sessions` (also Ctrl+X), `/agents`, `/agent NAME`, `/agents edit NAME`, `/skills`, `/skills update`, `/resume <n|id-prefix>`, `/model [id]` (lists the ChatGPT plan's models when a ChatGPT binding is selected), `/provider`, `/instructions`, `/tools on [dir] [read-only|trusted-workspace|full-host]` / `/tools off`, `/approvals`, `/vault [list]` / `/vault add LABEL` / `/vault remove ID|REF`, `/history`, `/retry`, `/copy`, `/stop`, `/status`, `/clear`, `/mouse`, `/queue`, `/quit`.

`/agents` opens a picker of agents (name, `(default)`, description, model, tool ceiling); Enter, like `/agent NAME`, starts a new conversation with that agent, which is created on the first message through `Initialize` with the agent's id. An agent with a model always uses it: it sets the provider and model, `/model` and `/provider PROVIDER` are refused while it is selected, and `tui --agent NAME --provider/--model` exits with an error. The current default agent's model applies the same way: without `--agent`, a default agent with a model is selected at launch (its route shown and `/model` locked), and `tui --provider/--model` then exits with `default agent NAME sets its own model`. `/new` applies the selected agent's route again, or the launch route when no agent is selected, so resuming a conversation of another agent does not leak its route into the next new conversation. Right before every `Initialize` (the first message of a new conversation, or `/new TITLE`), the TUI reads the agents from the Host again and adopts the fresh definition of the selected agent, else the current default. If that changes the agent, provider, model or endpoint on screen (another shell ran `vorra agents default` or `vorra agents edit`), nothing is sent: the text goes back into the input with a warning naming the new route, and Enter sends it on that route. A selected agent that no longer exists, or an agents file the Host cannot read, also stops the send with an error. `Initialize.agent` carries the agent id that was just checked. If the agents query fails at launch, the TUI still opens, shows `cannot read agents: …` and the agent as `unavailable`, and keeps transcripts, `/vault`, `/approvals` and `/status` usable. Choosing a model-less agent restores the launch route (the `--provider`/`--model`, onboarding route or latest conversation's model, as changed by later `/model` and `/provider`) instead of keeping the previous agent's model. The banner and status bar show the agent of the open conversation, or the chosen agent (else the current default) before the first message. `/agents edit NAME` only prints the matching `vorra agents edit` command; editing agents is a CLI task.

`/skills` opens a picker of the skills the Host discovers for the TUI's tools workspace (else the Host workspace setting): name, root, source or status, and `shadowed`, `not offered` or the issue count; `◈` marks skills assigned to the current agent (the open conversation's agent, else the selected agent, else the current default). Enter prints the skill's frontmatter fields, `allowed-tools (never applied)`, issues and the first body lines. `a` toggles the highlighted skill for that agent through `agent_put` at the agent's current revision and reopens the picker: assigning to a `none` agent makes it `only` that skill, removing from an `all` agent makes it `only` the other offered skills, and removing the last skill makes it `none`. Skills that are not offered cannot be toggled. The change applies from the next turn with tools on. `/skills update` runs `vorra skills update --check` as a child process (at most 10 minutes; the TUI waits) and prints its report. Installing and removing stay in the CLI.

Enter sends; Alt+Enter, Ctrl+J or a trailing `\` inserts a newline; Tab completes commands; Up/Down walk input history or lines; PageUp/PageDown or the wheel scroll; End jumps to the latest output. Ctrl+L starts a new conversation and Ctrl+D exits on empty input. `/mouse` releases mouse capture for terminal text selection.

## Vault

`/vault add LABEL` validates the label and opens a masked modal for a local `api_secret` item. Typed and pasted characters render as `•` (at most 8192 bytes); Enter sends the value straight into `SecretTransfer` and the `vault_put` owner operation, Esc or Ctrl+C discards it. The value lives only in a pre-sized zeroizing buffer: it never enters the input line, input history, transcript, chat events or logs. The transcript note shows the label and the new reference. `/vault` lists provider statuses and items as label, fields and reference; `/vault remove` takes an item UUID or `vault://local/` reference. Other kinds and metadata use `vorra vault add`.

## Tool approvals

`/tools on` sends `tools`, `workspace` and `execution_mode` as `RequestedRunOptions` with each message. When a task reaches `awaiting_permission`, the exact pending request is shown with tool, mode, workspace, capabilities, targets, expiry and arguments. `y` and `n` submit `ResolvePermission` for that operation and keep following the task; Esc leaves it pending for `/approvals` or another client. Full-host mode still requires each operation's approval.

## Interrupting

Typing while a reply runs queues the message; queued messages send in order after the task completes. Ctrl+C first warns, and a second Ctrl+C within three seconds (or `/stop`) submits `CancelTask`. Cancelling while a provider request is in flight makes the task a nonretryable `Failed` with an uncertain outcome, and the conversation cannot continue ([scheduler contract](../contracts/scheduler.md#cancellation-shutdown-and-recovery)). The TUI therefore asks twice. Before sending, it compares `pending_command_id` with the conversation's tasks: a terminal pending task moves to a new conversation, a running one is followed with the message queued, and one awaiting permission reopens its approval. Quitting the TUI never cancels Host work.
