# Continuous backlog synchronization

GitHub Issues, including current bodies and comments, are the authoritative implementation backlog. Issue #30 supplies the evolving roadmap. Local plans and previous assignments are snapshots.

Run `python3 scripts/sync_issues.py` from any checkout at startup, at least every five minutes during active work, immediately after every PR merge, issue completion or milestone, and before a repository completion claim. Python 3 and an authenticated GitHub CLI are required. The script uses read-only GitHub API requests, fetches all open and closed issues and comments with pagination, excludes pull requests, and compares requirement hashes, state and comments. A failed refresh does not advance the last successful synchronization time; report that blocker and retry while continuing independent work.

A common POSIX advisory lock serializes the complete read/fetch/write cycle across concurrent agents and worktrees, preventing an older refresh from overwriting newer pending changes. The script atomically persists `<git-common-dir>/vorra-orchestration/checkpoint.json`, shared across worktrees. Find the common directory with `git rev-parse --path-format=absolute --git-common-dir`. The checkpoint contains the last successful sync time, next due time, full issue snapshots, detected and unacknowledged changes, and coordinator-maintained assignments, dependency graph and blockers. Unacknowledged changes survive subsequent refreshes and restarts. It contains no credentials or application user data and is local orchestration state, not a product backup subsystem. Read it after compaction or restart before resuming work.

Supply `--coordination /absolute/path/to/coordination.json` to replace the checkpoint's coordination object. Record active issue owners, branches/worktrees, frozen interfaces, prerequisites and unresolved integration or validation blockers. Importing an existing assignment preserves its previous assigned requirement/comment digests unless explicitly replaced; a refresh never silently treats edited requirements as assigned. New assignments receive the current snapshot digests and full assigned requirements/comments. Imports retain those assigned snapshots when their digests differ from the latest issue, allowing comparison after a restart. Matching reviewed digests can capture the corresponding current snapshot. After notifying an owner of changed requirements, copy the reviewed digests from the issue snapshot into that assignment. Without the option a refresh retains the existing coordination object. Only the primary coordinator updates this object. Keep the shared implementation status document synchronized at integration milestones.

After reviewing a pending change and updating affected owners and dependencies, pass `--acknowledge 17 20` with the appropriate issue numbers. This acknowledges only previously observed changes; newly fetched changes remain pending even when their issue number was passed. Inspect both new and pending changes on every refresh. Do not acknowledge merely because the command succeeded.

After each refresh, the coordinator must read every changed requirement and relevant comment. Compare active issues with the exact requirements assigned to their owners. Send changes immediately, redirect incompatible work safely, preserve useful completed work and update priorities. Newly opened and reopened issues enter the graph automatically; closed issues require reconciliation with their actual integrated implementation. Dispatch newly unblocked independent work without waiting for another user instruction.

Before merging, refresh and confirm that the final PR satisfies the latest issue body and comments. Before declaring completion, refresh again, inspect every outstanding implementation issue and reconcile issues created or edited during final validation. Deferred automated verification stays explicitly tracked in #32 and must never be counted as verified.
