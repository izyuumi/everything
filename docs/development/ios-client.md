# Native iOS client

The optional iOS 17+ Swift 6 application is in `apps/Apple/iOS`, with E2EE records and identity handling in `apps/Apple/Shared/Crypto` and relay replication in `apps/Apple/Shared/Relay`. `EverythingIOS` is the iOS scheme in the shared Apple project. The Rust host owns execution independently of this app. This document records the source implementation and the validation that remains unavailable; it does not establish an Apple build or a successful phone-to-host conversation.

## Focused draft and prerequisites

This focused addition extends the macOS-only project from draft PR [#82](https://github.com/izyuumi/everything/pull/82). Existing macOS sources, owner CLI bridge, scheme and target settings remain unchanged. The sixteen iOS/shared sources match the reviewed aggregate source at `13e72be`; this extraction does not add Rust services or change native contracts.

Encrypted transport, device identity and native steering use the existing #13/#22/#25 contracts. Actual task and permission-decision publications require PR [#85](https://github.com/izyuumi/everything/pull/85); scheduled-result event publication requires PR [#86](https://github.com/izyuumi/everything/pull/86). Exact replicated permission inspection targets the fixed schema at native commit `58e4284`, whose focused prerequisite is being prepared separately. Legacy requests without complete inspection remain host-review-only for Allow. This client consumes bounded scheduled-result metadata for part of #54; it provides no schedule CRUD or claim of complete #53/#54 integration.

The PR remains a draft until the Apple build and runtime criteria below can be verified. Source extraction and Linux parsing do not satisfy issue #28's iPhone message/reconnect/dedup acceptance or issue #54's device scheduling delivery acceptance.

## Boundaries

`EverythingIOSApp` owns one observable, main-actor `AppModel`. SwiftUI views display immutable service snapshots and dispatch actions. `ReplicaService`, `ReplicaStore`, `RelayConnection`, `DeviceIdentity` and `NotificationService` isolate mutable service state in actors. No model provider, agent loop, tool executor, scheduler or external model gateway runs on the phone.

The service starts a connection only after the user chooses Connect. It reconnects while the scene remains active and joins its owned socket workers when stopping. A shared stopping task prevents a new connection from racing shutdown. Scene suspension or termination interrupts synchronization. There is no APNS registration, background push entitlement or claimed background execution. The generic local notification reflects activity this running client has actually received.

The phone submits the actual schema-1 domain commands `send_message`, `steer_task`, `cancel_task` and `resolve_permission`. Steering names a task; the native host selects and validates its current active command and preserves the original execution authority and budgets. Sending a command does not select a paid provider, delegate to cloud workers, widen a device grant or bypass host admission.

## Pairing and trust

1. The host creates a short-lived signed invitation using its existing pairing commands. Scan the JSON using AVFoundation, or paste it into the secure manual field. The invitation includes a one-use secret and must stay out of relay traffic, messages and logs.
2. Compare every group of the displayed host fingerprint with the fingerprint on the intended host and explicitly confirm the match.
3. The phone creates an authenticated pairing request. Transfer this request to the host owner, who confirms the phone fingerprint, grants its actual capabilities/conversations and returns the signed acceptance.
4. Paste the acceptance. The app verifies the original invitation ID, complete inviter and responder key sets, expiry and host signature before atomically pinning the host. The local pin cannot silently change to another host.
5. Separately enroll the displayed public phone keys with the chosen relay operator. Pairing acceptance contains no relay enrollment or device grants. Add only conversation UUIDs the host owner has authorized; adding an ID creates no host conversation and grants no access.

Invitations and incomplete ceremonies stay in memory. Requests and acceptances contain public authenticated records rather than private identity keys. Used pairing IDs are recorded locally. The host still performs its authoritative single-use pairing checks. Cancellation discards the current in-memory ceremony.

Device secrets use one versioned binary Keychain item, with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and synchronization disabled. Ed25519 and X25519 use independent CryptoKit private keys. Secrets are never serialized into JSON, SQLite, preferences, relay frames or logs. An existing database whose identity Keychain item is missing fails closed rather than generating a replacement identity. These Curve25519 keys are not Secure Enclave keys. Temporary buffer clearing is best effort; Swift copies do not provide a general secret-memory-erasure guarantee.

## Wire contract

The implementation follows the existing Rust `crypto.rs`, `relay_protocol.rs`, `devices.rs`, `protocol.rs` and `transport/remote.rs` contracts. CryptoKit supplies Ed25519, X25519, HMAC-SHA256, HKDF-SHA256 and ChaCha20-Poly1305. There are no custom cryptographic primitives.

UUIDs contribute their 16 RFC bytes. Integer fields use unsigned big-endian widths. Domain strings include their terminating zero byte. Device canonical bytes are the UUID, 32-byte signing public key and 32-byte encryption public key, in that order. The fingerprint is SHA-256 of these 80 bytes, grouped in four-byte lowercase hexadecimal groups.

The envelope header authenticates its version, message ID, sender, recipient, creation and expiry times, 12-byte nonce and 32-byte key salt. X25519 shared-secret HKDF uses the header salt and `everything.envelope.key.v1` domain followed by complete sender keys and complete recipient keys. ChaChaPoly uses the full canonical header as AAD. The serialized ciphertext is ciphertext plus its 16-byte authentication tag; the nonce remains in the header. Ed25519 signs the canonical header, a four-byte ciphertext length and that ciphertext/tag. The invitation, request HMAC, acceptance and relay challenge follow their existing native domain-separated layouts. Relay authentication signs the native inner relay challenge inside `everything.authentication.v1`.

`WireValue` delegates JSON syntax, string escaping and numeric parsing to Foundation. Integral protocol fields preserve unsigned 64-bit values and reject floating, exponent, Boolean and negative representations. Base64 must decode and re-encode to the exact padded standard representation. Crypto, pairing, relay and device packet records reject unknown fields. Additive domain event fields remain in the stored event. A bounded object-key uniqueness preflight rejects repeated keys, including escaped equivalent spellings, before conversion. It also rejects canonically equivalent duplicate Swift string keys rather than silently collapsing them. Object nesting is limited to 64 and object keys to 32,768. Unknown event kinds fail visibly rather than disappearing from history.

The initial endpoint subset accepts canonical ASCII lowercase DNS/IPv4 `wss` origins, or literal `ws://127.0.0.1` for development, without paths, credentials, queries, fragments or explicit default ports. IPv6 and non-ASCII hostnames are rejected rather than signing a guessed native origin. The relay path is `/ws`. The ephemeral URLSession disables cookies and caching, uses normal TLS validation, and rejects HTTP redirects. No broad App Transport Security exception is included. Apple loopback ATS behavior requires an actual SDK/device check.

CryptoKit acceptance of weak/noncanonical Ed25519 and X25519 inputs must still be checked against Rust's `verify_strict` and key validation on Apple hardware. Successful syntax parsing is not that interoperability evidence.

## Durable replication

The app stores its replica under Application Support/Everything in a versioned SQLite database. It requests complete iOS file protection and owner-only permissions for the directory, database, WAL and SHM. The directory is excluded from OS backups. There is no backup or restore subsystem. The database wrapper is the sole narrow unchecked-Sendable owner of the SQLite handle; its actor serializes access and SQLite uses FULLMUTEX. Prepared statements bind all data values and finalize on every path. Transactions use `BEGIN IMMEDIATE`, full synchronous WAL and explicit rollback on failure.

Outgoing user commands persist their original ID, timestamp, complete command and original encrypted envelope in one transaction before becoming sendable. Reconnect sends those exact bytes. Relay acceptance means only that the relay retained ciphertext; the UI says it is awaiting a host result. Completed/rejected command results are a separate durable application outcome. Expired delivery is displayed as an unknown host outcome and does not silently create a replacement command.

Incoming messages must match the pinned host and local recipient, pass expiry/signature/AEAD validation, and enter a durable replay/inbox transaction before the client sends the relay acknowledgment. The transaction rechecks the pin, local identity and sticky revocation state. Repeated identical encrypted message IDs return the recorded receipt without applying plaintext again; changed ciphertext under the same ID is rejected. Replay digests remain through envelope expiry after processed plaintext is removed.

Sync batches validate conversation binding, contiguous sequences, unique event IDs, event shape and size before application. The store commits immutable events, derived projections, the conversation cursor, encrypted application acknowledgment, any continuation request and inbox completion atomically. A gap retains the current durable cursor and queues a new encrypted request from that cursor. Overlapping event history must match its existing ID and canonical contents. Repeated permission requests for an existing operation compare their immutable bindings before idempotent projection. Schema 2 adds bounded inspection metadata without replacing prior history or decisions. An earlier missing inspection may be hydrated by a complete authenticated request for the same operation; differing non-null inspection metadata conflicts, and absence cannot erase an existing inspection or reopen a decided request. Full command results may fill a previously archived null result; a later null archive cannot erase a full result.

Schema 3 retains each permission decision independently of request arrival, keyed by its operation and bound to its conversation and original Allow/Deny choice. The native Authorizer can commit a resolution before the native kernel publishes its request, so a synchronized decision can legitimately precede that request. A late or repeated request remains decided, including when inspection metadata arrives later. Reusing an operation in another conversation or changing its saved decision fails closed. Existing databases backfill decisions from their immutable event history in the schema-version transaction, validating each event against its stored conversation, sequence and event ID. The exclusive row cursor advances through decision records while skipping unrelated events. Each page holds at most eight events/2 MiB; the migration permits at most 262,144 records and 64 MiB of event bytes. Failure rolls back the backfill and schema version without replacing inbox, ciphertext, cursor or event records. No historical Allow grants current execution authority.

There is one outstanding synchronization marker per known conversation. Foreground automatic polling schedules at most one conversation every five seconds, alternating the selected conversation with round-robin other explicitly known conversations. This gives the selected conversation at most a ten-second scheduling interval while others progress within the same request/replay budget. Network delays and an existing outstanding request can extend receipt time; pull to synchronize remains available. A changed selection gets priority on the next automatic interval. Reconnect does not generate replacement user commands. Queue pressure preserves existing work; a full inbox is not relay-acknowledged, and the socket reconnects for redelivery after local pressure drains. A full outbox drains before retrying inbox application that needs to enqueue sync acknowledgments.

Bounds are explicit: 64 known conversations, 128/16 MiB queued outbound envelopes, 128/16 MiB pending inbox payloads, 150,000 retained replay receipts, 5,000 original commands and a 64 MiB database page limit. At most 16 envelopes are in flight; socket frames are limited to 2 MiB. Sync batches contain at most 256 events/512 KiB, and an event at most 256 KiB. Recent history and each snapshot payload projection are limited to 100 rows and 2 MiB before payload allocation. Storage exhaustion fails visibly and preserves existing data; there is no automatic history deletion. The chat currently displays this bounded recent history window rather than an unbounded transcript.

WebSocket writes have five-second bounds, authenticated reads ninety seconds and challenge reads twenty seconds. Timers and cancellation cancel the underlying socket before structured children are joined. A fatal protocol/identity/storage error stops automatic retries and requests inspection; network interruption uses bounded exponential reconnect delays. A shared stop completion prevents start or endpoint changes until owned connection work has finished.

## Permissions, controls and privacy

The host remains authoritative for operation state, exact arguments, expiry, captured authorization scope and device grants. The source consumes the actual replicated PermissionInspection schema frozen at native commit `58e4284`: approval ID, workspace root, execution mode, capabilities, targets, exact argument JSON/digest and requested/expiry timestamps. It validates bounds and strict fields, then verifies SHA-256 over the unchanged `arguments_json` UTF-8 bytes using CryptoKit before projecting or displaying the inspection. It does not recreate Rust JSON number serialization. The UI displays every saved argument, scope field, operation/conversation/task/call identity, digest and time. Expired, missing or stale selected inspections disable Allow. Legacy or oversized requests remain host-review-only, with exact-operation Deny available. Arguments from a tool-request event alone cannot enable Allow.

The final queue transaction reloads the unresolved stored operation and compares the selected conversation, task, call, tool, complete inspection and displayed arguments. It validates the exact decision command's operation/conversation and rechecks expiry and raw argument digest before persisting it with its original encrypted envelope. The host subsequently revalidates its own stored approval and device grant. A queued choice is not displayed as completed execution. Apple execution of this path remains unverified.

`scheduled_run_finished` consumes the existing bounded native notification schema. It validates job/occurrence IDs, generation, paired task/execution-conversation provenance, outcome, timestamps, summary and digest, then displays the result as conversation metadata. It does not convert results into model history or add schedule CRUD controls. Broader scheduling delivery integration remains tracked in #54 and depends on #53.

Task controls derive from replicated native lifecycle events. Native lifecycle publication and host reconciliation are tracked in #73; this client source does not establish their integrated delivery. It consumes the existing event synchronization rather than adding a remote management query.

A host-signed revocation packet permanently disables local submission, clears pending outbound traffic and closes the connection. Local Disable has the same sticky local effect and preserves received history; host and relay operators must still revoke their own grants/enrollment. The app cannot promise receipt of a revocation while offline. Actual host authorization is checked again for each remote command.

Conversation content is marked privacy-sensitive and an opaque inactive-scene overlay hides it from normal app switcher snapshots. This is not a screenshot-prevention guarantee. Local notifications have a generic Everything title/body, random identifiers, no conversation/device/message/tool/pairing metadata and a thirty-second throttle. Notification permission is explicit. No payloads, private keys or raw errors are logged.

## Validation and remaining blockers

The focused extraction passed a fresh explicit Swift 6 syntax parse of all sixteen files. Linux Foundation parsed both the macOS-only base and expanded OpenStep project; metadata inspection verified all sixteen iOS source memberships, Debug/Release settings, framework references, plist and scheme, and preservation of 33 unchanged base objects, with only the three project/group containers extended for iOS. Existing macOS sources, owner IPC and scheme are byte-identical. The retained Foundation wire and extracted SQLite helper observations below match the copied source hashes; unchanged helpers were not rerun. These are source and project-metadata checks, not Xcode validation.

All sixteen Swift files were parsed with the official Swift 6.0.3 Linux `swift-frontend`. The Foundation/CoreFoundation-only `WireValue.swift` and `WireRecords.swift` passed `-typecheck -swift-version 6`. A disposable manually invoked executable compiled these actual files and observed exact `UInt64.max` parse/encode; rejection of floating/exponent/Boolean/negative integer fields, nil UUIDs, noncanonical base64, strict unknown fields, duplicate/escaped duplicate keys, sync gaps and empty continuation batches; retention of additive domain fields; RFC UUID bytes; and ordinary nested/escaped JSON, a 32,768-key object and rejection above that key limit. Duplicate-key tracking owns one local mutable set per object, avoiding repeated copy-on-write of growing key sets. The same actual Foundation decoder accepted the genuine public `PermissionRequested` event emitted by native `58e4284` from a real Broker Ask operation. It preserved the exact 70-byte Unicode argument string, which independently matched its native SHA-256 using Python's standard implementation. That native walkthrough explicitly seeded the dispatch phase and made zero provider requests or shell executions; it proves this wire boundary, not inference. Manual changes to that disposable record confirmed rejection of relative workspace, unknown mode/capability/field, invalid expiry/digest shape/JSON, target controls/count and oversized arguments. Scheduled-result shape inspection accepted paired-empty provenance and rejected an unmatched task/conversation. CryptoKit digest execution and full SQLite actor/UI behavior remain unverified. This driver is outside the repository and is not automated acceptance coverage.

A separate disposable Swift executable compiled the actual Foundation-only database helper source and schema-migration transaction against the cached established SQLite header and system SQLite library. It observed decision-before-request, request-before-decision, inspection hydration without reopening, exact decision replay, rejected conversation reuse and rejected contradictory choices. A schema-2 history containing interleaved unrelated events migrated across three decision pages; contradictory historical choices rolled back the entire migration and retained schema version 2, and an event whose stored conversation disagreed with its envelope failed closed. The manually invoked request-order driver used the same SQL externally; it did not execute the full replica actor, encrypted synchronization, CryptoKit or Apple framework behavior.

The official toolchain archive's detached signature was verified using the published Swift 6.x release key `52BB7E3DE28A71BE22EC05FFEF80A866B47A981F`. Only a disposable compiler/runtime subset was extracted; no system toolchain, PATH or trust store was changed. These Linux checks do not typecheck SwiftUI, UIKit, AVFoundation, CryptoKit, Security, UserNotifications or Apple SQLite imports.

The current environment has no Xcode, Apple SDK, simulator or physical iPhone. Required GitHub Actions are also blocked by repository billing before job steps run. The following remain unverified: Apple Swift 6 concurrency/API checking and build/analyze, camera/privacy/accessibility behavior, Keychain and file-protection behavior, native CryptoKit/Rust positive and negative interoperability, relay authentication and phone-to-host round trip, disconnected replay/event convergence, live steering and exact approval decisions, revocation on device, notification behavior, suspension/cancellation cleanup and ATS handling.
