# Native iOS client

The optional iOS 17+ Swift 6 application is in `apps/Apple/iOS`, with E2EE records and identity handling in `apps/Apple/Shared/Crypto` and relay replication in `apps/Apple/Shared/Relay`. `VorraIOS` is the iOS scheme in the shared Apple project. The Rust host owns execution independently of this app. This document records the source implementation, the [Simulator protocol walkthrough](#simulator-protocol-walkthrough) and the validation that remains unavailable.

## Current-main integration and prerequisites

This focused addition extends the macOS client merged through [#104](https://github.com/izyuumi/everything/pull/104) on actual main `34f13f8f987af7a1173219c467030ba601f73949`. It extracts the twenty-one paths from reviewed iOS PR [#87](https://github.com/izyuumi/everything/pull/87), then applies the separately reviewed foreground scene and relay-acceptance corrections. Existing macOS sources, CLI cleanup, scheme and target settings remain unchanged. The shared project gains only the iOS target, its sixteen sources and scheme. No Rust service, dependency, storage schema or native contract changes.

Encrypted transport, device identity and native steering use the merged #13/#22/#25 contracts. Authoritative current task snapshots and exact permission decisions use the publication integrated in [#100](https://github.com/izyuumi/everything/pull/100). The optional replicated inspection uses the actual bounded schema integrated in [#102](https://github.com/izyuumi/everything/pull/102). Scheduled notifications use the existing event contract and execution integrated in [#103](https://github.com/izyuumi/everything/pull/103); this core only decodes and displays their metadata. It adds no future schedule controls, macOS schedule UI, remote-worker report decoding or claim of complete #53/#54 integration. Legacy requests without complete inspection remain host-review-only for Allow.

The Apple workflow now selects both actual existing schemes for unsigned SDK build and static analysis. Fresh exact-head results remain pending for this extraction. Source preservation, static checks and the earlier published client's SDK build do not satisfy issue #28's iPhone message/reconnect/dedup acceptance or issue #54's device scheduling delivery acceptance.

## Boundaries

`VorraIOSApp` owns one observable, main-actor `AppModel`. SwiftUI views display immutable service snapshots and dispatch actions. `ReplicaService`, `ReplicaStore`, `RelayConnection` and `DeviceIdentity` isolate mutable service state in actors. The same app-owned `NotificationService` is now a MainActor class for its synchronous final foreground admission check. No model provider, agent loop, tool executor, scheduler or external model gateway runs on the phone.

The service starts a connection only after the user chooses Connect. It reconnects while the scene remains active and joins its owned socket workers when stopping. A shared stopping task prevents a new connection from racing shutdown. Scene suspension or termination interrupts synchronization. There is no APNS registration, background push entitlement or claimed background execution. This iPhone preferences remain local and independent of the Host connection. The [committed-event notification path](../contracts/ios-notification-delivery.md) uses actual authenticated completions and pending permission requests, fresh saved choices and OS observations while synchronization is enabled in the active app. First catch-up is silent; claims precede OS submission, so lost or skipped attempts are not replayed. The former cursor-based generic activity producer remains removed.

A foreground start waits for the existing owned stop task instead of failing while shutdown is in progress. Stop completion is identified before clearing connection resources, so a delayed second waiter cannot clear a newer runner. Each stop request invalidates pending starts before joining; a later Disconnect, scene suspension or local Disable prevents an earlier waiting start from reconnecting. Cancellation of a waiting start leaves the shared shutdown task owned until its workers join. This correction has source inspection and available syntax validation only; its scene transitions have not been executed on an Apple runtime. The successful SDK build and analysis of the earlier published client do not verify this correction.

The phone submits the actual schema-1 domain commands `create_conversation`, `send_message`, `steer_task`, `cancel_task` and `resolve_permission`. Steering names a task; the native host selects and validates its current active command and preserves the original execution authority and budgets. Sending a command does not select a paid provider, delegate to cloud workers, widen a device grant or bypass host admission.

## Pairing and trust

1. On the Mac, run `vorra pair`. Scan its QR code with the Camera app, or tap Pair with Mac in Vorra and use Scan QR code or Paste. Opening a `vorra://pair#…` or `https://vorra.yumi.to/pair#…` link anywhere (Camera, Safari, Messages, `xcrun simctl openurl`) goes straight to the pairing sheet.
2. The app checks the invitation signature and expiry, creates the signed pairing request, signs this iPhone's name, connects to the relay named in the link and shows "Approve on your Mac" with the 8-digit code. That is the only thing the phone user sees.
3. When the owner approves on the host, the relay delivers the host's signed acceptance. The app verifies the original invitation ID, both key sets, expiry and host signature, saves the relay origin and atomically pins the host, then shows "Paired with <host>" and connects. The local pin cannot silently change to another host.
4. Tap New conversation (the compose button in Chat, or the empty-state button). The app generates a fresh conversation UUID, records it locally, queues the existing `create_conversation` command with the title "New conversation" and opens it at once; there is no manual ID entry. The host creates the conversation with the owner's default model when it receives the command, which needs a device grant covering that ID (`vorra pair` grants all conversations) and a configured default conversation; otherwise the host rejects the command and nothing is created. Existing conversations are chosen from the Conversation picker as before.

Failures are plain messages: invalid link, expired or already used, rejected on the Mac, another device already pairing with this code, Mac unreachable through its relay, relay without pairing support or not allowing this host, already paired with this host, paired with a different host. The pending request and the invitation stay in memory; cancelling or leaving the sheet discards them. Used pairing IDs are recorded locally, and the host performs its authoritative single-use checks. The manual fingerprint comparison and request/acceptance copy-paste screens were removed. A phone installed before the Vorra rename has a new bundle ID, container and Keychain item, so it pairs as a new device; revoke the old one on the host with the owner `revoke_device` operation. The protocol is in the [pairing contract](../contracts/device-pairing.md).

- `https://vorra.yumi.to/pair`: the fallback page when the universal link does not open the app. Its script tries `vorra://pair` plus the fragment in the browser, and otherwise the page links to the App Store (`https://apps.apple.com/app/id6829295744`) with a TestFlight note. The fragment never leaves the phone.
- The tunnel routes `/.well-known/apple-app-site-association`, `/pair` and `/pair/open.js` on `vorra.yumi.to` to `vorra-help-mcp`, alongside `/mcp` and `/healthz`.
- VorraIOS carries `com.apple.developer.associated-domains` = `applinks:vorra.yumi.to` (`apps/Apple/iOS/VorraIOS.entitlements`). The App ID `to.yumi.vorra.ios` needs the Associated Domains capability. Automatic signing with `-allowProvisioningUpdates` normally enables it; if an archive fails with a provisioning profile that lacks `com.apple.developer.associated-domains`, enable Associated Domains for that identifier at developer.apple.com → Certificates, Identifiers & Profiles → Identifiers, then archive again.

Device secrets use one versioned binary Keychain item, with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and synchronization disabled. Ed25519 and X25519 use independent CryptoKit private keys. Secrets are never serialized into JSON, SQLite, preferences, relay frames or logs. An existing database whose identity Keychain item is missing fails closed rather than generating a replacement identity. These Curve25519 keys are not Secure Enclave keys. Temporary buffer clearing is best effort; Swift copies do not provide a general secret-memory-erasure guarantee.

## Wire contract

The implementation follows the existing Rust `crypto.rs`, `relay_protocol.rs`, `devices.rs`, `protocol.rs` and `transport/remote.rs` contracts. CryptoKit supplies Ed25519, X25519, HMAC-SHA256, HKDF-SHA256 and ChaCha20-Poly1305. There are no custom cryptographic primitives.

UUIDs contribute their 16 RFC bytes. Integer fields use unsigned big-endian widths. Domain strings include their terminating zero byte. Device canonical bytes are the UUID, 32-byte signing public key and 32-byte encryption public key, in that order. The fingerprint is SHA-256 of these 80 bytes, grouped in four-byte lowercase hexadecimal groups.

The envelope header authenticates its version, message ID, sender, recipient, creation and expiry times, 12-byte nonce and 32-byte key salt. X25519 shared-secret HKDF uses the header salt and `everything.envelope.key.v1` domain followed by complete sender keys and complete recipient keys. ChaChaPoly uses the full canonical header as AAD. The serialized ciphertext is ciphertext plus its 16-byte authentication tag; the nonce remains in the header. Ed25519 signs the canonical header, a four-byte ciphertext length and that ciphertext/tag. The invitation, request HMAC, acceptance and relay challenge follow their existing native domain-separated layouts. Relay authentication signs the native inner relay challenge inside `everything.authentication.v1`.

`WireValue` delegates JSON syntax, string escaping and numeric parsing to Foundation. Integral protocol fields preserve unsigned 64-bit values and reject floating, exponent, Boolean and negative representations. Base64 must decode and re-encode to the exact padded standard representation. Crypto, pairing, relay and device packet records reject unknown fields. Additive domain event fields remain in the stored event. A bounded object-key uniqueness preflight rejects repeated keys, including escaped equivalent spellings, before conversion. It also rejects canonically equivalent duplicate Swift string keys rather than silently collapsing them. Object nesting is limited to 64 and object keys to 32,768. Unknown event kinds fail visibly rather than disappearing from history.

The initial endpoint subset accepts canonical ASCII lowercase DNS/IPv4 `wss` origins, or literal `ws://127.0.0.1` for development, without paths, credentials, queries, fragments or explicit default ports. IPv6 and non-ASCII hostnames are rejected rather than signing a guessed native origin. The relay path is `/ws`. The ephemeral URLSession disables cookies and caching, uses normal TLS validation, and rejects HTTP redirects. No broad App Transport Security exception is included. Apple loopback ATS behavior requires an actual SDK/device check.

CryptoKit acceptance of weak/noncanonical Ed25519 and X25519 inputs must still be checked against Rust's `verify_strict` and key validation on Apple hardware. Successful syntax parsing is not that interoperability evidence.

## Durable replication

The app stores its replica under Application Support/Vorra in a versioned SQLite database. It requests complete iOS file protection and owner-only permissions for the directory, database, WAL and SHM. The directory is excluded from OS backups. There is no backup or restore subsystem. The database wrapper is the sole narrow unchecked-Sendable owner of the SQLite handle; its actor serializes access and SQLite uses FULLMUTEX. Prepared statements bind all data values and finalize on every path. Transactions use `BEGIN IMMEDIATE`, full synchronous WAL and explicit rollback on failure.

Outgoing user commands persist their original ID, timestamp, complete command and original encrypted envelope in one transaction before becoming sendable. Reconnect sends those exact bytes. Relay acceptance means only that the relay retained ciphertext; the UI says it is awaiting a host result. Completed/rejected command results are a separate durable application outcome. Expired delivery is displayed as an unknown host outcome and does not silently create a replacement command.

Relay acceptance keeps its exact message ID in the service's in-flight set until the store has committed the acceptance and removed the original outbox entry. Concurrent pumping therefore excludes that ciphertext while the actor awaits the store. A failed acceptance still propagates its error and cannot make the message eligible for another send in the same connection. This actor-ordering correction has source and syntax checks only; no new Apple relay or reconnect runtime observation is claimed.

Incoming messages must match the pinned host and local recipient, pass expiry/signature/AEAD validation, and enter a durable replay/inbox transaction before the client sends the relay acknowledgment. The transaction rechecks the pin, local identity and sticky revocation state. Repeated identical encrypted message IDs return the recorded receipt without applying plaintext again; changed ciphertext under the same ID is rejected. Replay digests remain through envelope expiry after processed plaintext is removed.

Sync batches validate conversation binding, contiguous sequences, unique event IDs, event shape and size before application. The store commits immutable events, derived projections, the conversation cursor, encrypted application acknowledgment, any continuation request and inbox completion atomically. A gap retains the current durable cursor and queues a new encrypted request from that cursor. Overlapping event history must match its existing ID and canonical contents. Repeated permission requests for an existing operation compare their immutable bindings before idempotent projection. Schema 2 adds bounded inspection metadata without replacing prior history or decisions. An earlier missing inspection may be hydrated by a complete authenticated request for the same operation; differing non-null inspection metadata conflicts, and absence cannot erase an existing inspection or reopen a decided request. Full command results may fill a previously archived null result; a later null archive cannot erase a full result.

Schema 3 retains each permission decision independently of request arrival, keyed by its operation and bound to its conversation and original Allow/Deny choice. The native Authorizer can commit a resolution before the native kernel publishes its request, so a synchronized decision can legitimately precede that request. A late or repeated request remains decided, including when inspection metadata arrives later. Reusing an operation in another conversation or changing its saved decision fails closed. Existing databases backfill decisions from their immutable event history in the schema-version transaction, validating each event against its stored conversation, sequence and event ID. The exclusive row cursor advances through decision records while skipping unrelated events. Each page holds at most eight events/2 MiB; the migration permits at most 262,144 records and 64 MiB of event bytes. Failure rolls back the backfill and schema version without replacing inbox, ciphertext, cursor or event records. No historical Allow grants current execution authority.

There is one outstanding synchronization marker per known conversation. Foreground automatic polling schedules at most one conversation every five seconds, alternating the selected conversation with round-robin other explicitly known conversations. This gives the selected conversation at most a ten-second scheduling interval while others progress within the same request/replay budget. Network delays and an existing outstanding request can extend receipt time; pull to synchronize remains available. A changed selection gets priority on the next automatic interval. Reconnect does not generate replacement user commands. Queue pressure preserves existing work; a full inbox is not relay-acknowledged, and the socket reconnects for redelivery after local pressure drains. A full outbox drains before retrying inbox application that needs to enqueue sync acknowledgments.

Bounds are explicit: 64 known conversations, 128/16 MiB queued outbound envelopes, 128/16 MiB pending inbox payloads, 150,000 retained replay receipts, 5,000 original commands and a 64 MiB database page limit. At most 16 envelopes are in flight; socket frames are limited to 2 MiB. Sync batches contain at most 256 events/512 KiB, and an event at most 256 KiB. Recent history and each snapshot payload projection are limited to 100 rows and 2 MiB before payload allocation. Storage exhaustion fails visibly and preserves existing data; there is no automatic history deletion. The chat currently displays this bounded recent history window rather than an unbounded transcript.

WebSocket writes have five-second bounds, authenticated reads ninety seconds and challenge reads twenty seconds. Timers and cancellation cancel the underlying socket before structured children are joined. A fatal protocol/identity/storage error stops automatic retries and requests inspection; network interruption uses bounded exponential reconnect delays. A shared stop completion prevents start or endpoint changes until owned connection work has finished.

## Permissions, controls and privacy

The host remains authoritative for operation state, exact arguments, expiry, captured authorization scope and device grants. The source consumes the actual replicated PermissionInspection schema integrated in #102: approval ID, workspace root, execution mode, capabilities, targets, exact argument JSON/digest and requested/expiry timestamps. It validates bounds and strict fields, then verifies SHA-256 over the unchanged `arguments_json` UTF-8 bytes using CryptoKit before projecting or displaying the inspection. It does not recreate Rust JSON number serialization. The UI displays every saved argument, scope field, operation/conversation/task/call identity, digest and time. Expired, missing or stale selected inspections disable Allow. Legacy or oversized requests remain host-review-only, with exact-operation Deny available. Arguments from a tool-request event alone cannot enable Allow.

The final queue transaction reloads the unresolved stored operation and compares the selected conversation, task, call, tool, complete inspection and displayed arguments. It validates the exact decision command's operation/conversation and rechecks expiry and raw argument digest before persisting it with its original encrypted envelope. The host subsequently revalidates its own stored approval and device grant. A queued choice is not displayed as completed execution.

### Vault-use approvals

A `vault_use` request (tool `vault_use` with the `vault_use` target) adds a Vault use block parsed from the inspection targets (`vault_label`, `vault_provider`, `vault_kind`, `vault_site`, `vault_field`, `vault_destination`) and the `reason` argument. Only that metadata reaches the phone; the value never does, and iOS has no secret entry. Buttons are Allow once, Deny and, when the request is leasable (no `vault_kind=card`, the Host's rule), Allow for this task. Both allows go through a confirmation dialog. The queue transaction accepts `allow_for_task` only for a leasable selection and rechecks expiry and digest as for `allow`. The Host already accepted `allow_for_task` in a device `resolve_permission`; its published `permission_decided` event still says `allow`. See the [vault contract](../contracts/vault.md#vault-lease-grant).

On 2026-10-31 (#223) a fresh iPhone 17 Pro iOS 27.0 Simulator ran the real iOS app sources with only `EverythingIOSApp.swift` replaced by a scratch driver outside the repository. The driver called the `AppModel` pairing, relay, conversation and connect methods, then selected the tab, scrolled and activated buttons through accessibility. A disposable `everything serve`, a loopback `everything relay serve` and a scripted loopback model created a real pending `vault_use` approval for a fake local login item. The phone showed the Vault use block, Allow once, Deny and Allow for this task, then the confirmation dialog. Confirming sent `allow_for_task`: the command completed, the approval cleared and `vault_use` bound. In a second task, a second identical `vault_use` bound with no new approval, so the lease was granted. A grep for the fake value over the state directory, the Simulator device data, relay state and logs found nothing. Not observed: real taps, Deny and Allow once from the phone, a card request (Allow for this task hidden), a physical iPhone or TestFlight build, and a non-loopback relay. Earlier Apple execution of the generic approval path was unverified.

`scheduled_run_finished` consumes the existing bounded native notification schema. It validates job/occurrence IDs, generation, paired task/execution-conversation provenance, outcome, timestamps, summary and digest, then displays the result as conversation metadata. It does not convert results into model history or add schedule CRUD controls. A committed `scheduled_run_finished` event whose validated outcome is `succeeded` is also eligible for the generic [completion notice](../contracts/ios-notification-delivery.md); other outcomes produce none. Device-level delivery acceptance remains tracked in #54.

Task controls derive from replicated native lifecycle events. The projection accepts the host's authoritative current task snapshot without requiring every intermediate transition. Exact permission decisions remain independently retained when they precede their request. Native publication and host reconciliation are integrated for #73; this client source does not establish their delivery to an actual Apple device. It consumes the existing event synchronization rather than adding a remote management query.

A host-signed revocation packet permanently disables local submission, clears pending outbound traffic and closes the connection. Local Disable has the same sticky local effect and preserves received history; host and relay operators must still revoke their own grants/enrollment. The app cannot promise receipt of a revocation while offline. Actual host authorization is checked again for each remote command.

Conversation content is marked privacy-sensitive and an opaque inactive-scene overlay hides it from normal app switcher snapshots. This is not a screenshot-prevention guarantee. The existing single privacy notification delegate is retained. Permission is requested only through a fresh foreground local-settings gesture with original revision and lifetime checks; saving a notification preference does not authorize or prove delivery. The committed-event producer adds one bounded claim/delivery worker, fixed generic content and the existing single delegate. It owns each actual OS submission callback through completion and rechecks the original device, Host and foreground generation; later retirement requests pending removal without guaranteeing that presentation stopped. No payloads, private keys or raw errors are logged.

### Simulator protocol walkthrough

On an iOS 27.0 Simulator, a plain Debug build installed, launched and opened its Keychain identity, showing the empty chat screen. A build with `CODE_SIGNING_ALLOWED=NO` showed the `-34018` failure above. Taps were not automated, so the SwiftUI screens, QR camera, approval UI and notifications were not exercised.

Instead, a disposable command-line driver outside the repository compiled the actual `Shared/Crypto`, `Shared/Relay` and `Shared/Settings` sources for the Simulator. It ran inside the booted Simulator with `simctl spawn`, using a Simulator `application-identifier` entitlement, the real Keychain identity, `ReplicaService`, `ReplicaStore` and CryptoKit. It talked to a debug `vorra-relay` (the separate relay binary that predates `vorra relay serve`) and `vorra serve` over `ws://127.0.0.1` with disposable state. The Host conversation's loopback model endpoint was unreachable, so no provider was contacted. Observations:

- **Pairing.** The phone inspected the Host invitation and showed the Host's exact fingerprint. It created a request the Host approved for one selected conversation, then verified the Rust acceptance and pinned the Host. Both public identities were enrolled with the relay separately.
- **Message roundtrip.** A message sent while the Host's relay session was down reached `relayed`. After the Host reconnected and the phone reconnected, sync applied `conversation_created`, `message_appended` (caused by the phone command), `task_created` and `task_status_changed`. The command became `completed`.
- **Relay blindness.** The plaintext marker was absent from the relay SQLite database and WAL and present in the Host WAL.
- **Reconnect and dedup.** Two more reconnect-and-sync runs kept the same sequences and event IDs, with no duplicates.
- **Steering.** A steering command produced Host `steering_received` events. A second paired identity on a fresh Simulator caught up the full seven-event history.
- **Revocation.** After relay revocation, the phone stopped with the identity error. Host owner `revoke_device` sends no revocation notice to the replica, so the client's signed revocation path was not exercised.
- **Duplicate sessions.** A concurrent session for the same device makes the relay return `session_already_active` right after authentication. The client now retries with backoff and reconnects. The previous build treated this as a protocol violation and stopped permanently.

Still unverified on an Apple runtime: UI interaction, camera, accessibility, approval resolution (no model produced a permission request), notifications, scene suspension, physical devices and ATS beyond loopback. Do not claim these from SDK compilation. Deferred automated verification is tracked in issue #32.

## Connected Host settings

The Settings tab keeps This iPhone (appearance, notification choices, OS authorization through the existing `NotificationService`) separate from the connected Host. Local preferences need no Host, model or connection. Host configuration is never copied into local authority: the phone shows only what the Host returns for keys the owner granted to this device, over the scoped E2EE [query client](../contracts/apple-settings-access-client.md).

- **Refresh** (automatic once per connection when the Host page appears, or explicit) checks access, replays an open change, reads granted values and pages the Host change feed. Values read on an earlier connection stay visible as stale read-only data while offline.
- **Save** is enabled only for keys in the grant's writable set (at most `memory.embeddings.enabled` and `memory.embeddings.dimensions`), with values from the current connection and a usable generation. It sends one Update with a fresh `request_id` and the displayed revision. Only the Host's typed Update reply is shown as saved; a relay acknowledgment never is. An uncertain outcome keeps the exact identity and is replayed by the next refresh; "Stop tracking" forgets it locally without telling the Host anything.
- A revoked, reduced or changed grant (`grant_unavailable`/`grant_changed`) clears the generation at once, disabling Host controls until a refresh shows current access; reduced keys disappear from the editable set. Protected keys (model and tool selection) and read-only keys are labelled, not editable.
- **Requires the Host** lists credential entry, pairing, revocation, grant, policy, consent and lifecycle actions. Tapping one asks the Host, which answers `host_action_required`; nothing executes and no secret is sent.
- **Ask Settings** is a pane that opens the Host's restricted Settings chat for this device only when the grant carries `configured_provider` consent. It shows the Host-disclosed provider, model and recipient before any message is sent, echoes the binding digest on every turn, polls while a turn runs and pages committed text. Turn identities are kept until accepted and resent unchanged. Chat text stays in RAM and is rendered as plain text. Action cards come only from the Host's authenticated change feed recorded after the message. There is no phone-side agent, no access to conversations or wiki, and no fallback provider: an unavailable Host model or credential is reported as such.

Leaving the Settings surface, a cover, scene or app inactivity, disconnect or Disable cancels the in-flight request and clears queued steps; the Host and any running turn continue. Nothing is replayed as a dialog later. There is no APNS or background wake.

The new views are `iOS/Settings/HostSettingsView.swift` (iOS target only); state and the serial driver live in `AppModel`. Compiled and statically analyzed only; the SwiftUI screens were not exercised. The shared Swift client was exercised in the Simulator against a real Host ([record](settings-validation.md#ios-remote-settings-client-walkthrough)).
