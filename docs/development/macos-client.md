# Build and run the macOS client

The application requires macOS 14 or newer and Xcode 16 or newer for Swift 6. The Rust headless host and its CLI must be built and installed separately. The app contains no bundled runtime and does not automatically install or start one.

```sh
cargo build --release --bin vorra --locked
xcodebuild -project apps/Apple/Vorra.xcodeproj -scheme VorraMac -configuration Debug -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO build analyze
xcodebuild -project apps/Apple/Vorra.xcodeproj -scheme VorraMac -configuration Release -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO build
```

The project uses no Swift package manifest or test target. Its one package dependency is Sparkle 2 (`upToNextMajor` from 2.9.0, pinned in `Vorra.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`), linked into `VorraMac` only, so the first build resolves it from GitHub. Development signing is disabled by those commands. Distribution signing, notarization, the DMG and the Sparkle appcast are CI-only through `scripts/release_mac.sh` ([Mac releases](releases.md#mac-beta-and-stable-releases)).

Updates: a build without `VORRA_SPARKLE_PUBLIC_KEY` (the project default) has no updater; Settings › About › Updates says so and the menu bar panel's Check for Updates… is disabled. Release builds carry the key, check `SUFeedURL` hourly, download and install automatically and show Sparkle's alerts; Settings › About › Updates switches automatic checks and installs, Stable or Beta Versions, and offers Check Now with the last check. To exercise it locally, build with a throwaway key and a loopback feed, never the release key: `VORRA_SPARKLE_PUBLIC_KEY=<test public key> VORRA_SPARKLE_FEED_URL=http://127.0.0.1:<port>/appcast.xml PRODUCT_BUNDLE_IDENTIFIER=to.yumi.vorra.mac.sparkletest`, so the test app's defaults stay apart from a real install.

Settings is a native tabbed window in the style of Yorozu: General (This Mac appearance and notifications), Models, Memory, Tools, Devices, Vault, Host (owner connection, defaults for new tasks, ChatGPT plan, background service and the read-only native Host settings) and About (version and updates). Open Vorra, choose Settings › Host, select the physical trusted Rust CLI executable and the existing private state directory, then Connect. The CLI's default state directory is `~/.vorra`; the owner socket's complete physical path must fit 100 UTF-8 bytes. The app stores only these connection preferences in UserDefaults. Revisioned This Mac preferences use their own SQLite store in `~/Library/Application Support/Vorra/DevicePreferences`. It does not store credentials or open the Host database.

The menu shows host connection/draining state, conversations with a readable transcript, recent tasks and pending approvals across all conversations. New Conversation in the conversations list submits the existing owner `create_conversation` command with a fresh conversation UUID and the title "New conversation", then opens its transcript; the host uses the owner's default model and rejects the command when none is configured. Inspect full scope and arguments before allowing an operation. Settings edit future-task defaults with revision comparison. Existing tasks retain their captured authority. Models/Memory/Tool Selection, secure key entry and Devices now have explicit native controls. Provider retry, cleanup attestation and advanced owner operations retain their separate CLI authority; the optional assistant cannot grant them.

The General tab works independently of the Host connection and includes saved app appearance. Edit completion/attention preferences or system/light/dark appearance and Save; a revision conflict keeps the draft until explicit Reload. Inspect an unresolved original save instead of resubmitting it. Saved preference values and observed macOS authorization are separate. Request permission contextually in the foreground; denial shows supported System Settings instructions. Closing Settings blocks unpresented actions while accepted writes/callbacks retain their original identity. These Mac controls do not schedule notification delivery. Saved appearance styles only this app, including inherited native presentations; it does not change the machine theme. See the [consumer contract](../contracts/this-mac-settings.md).

Use the Ask Settings toolbar button to show its optional native inspector beside the controls. Open Host settings through the conventional forms, then explicitly Open Ask Settings to inspect the configured provider, model, recipient and tools. Opening and expansion send no question. Review each question and data boundary before Send; never paste credentials into chat. Use Models or Tool Selection for secure key entry. Authenticated cards reuse native controls and known destinations; literal model text has no action authority. Collapse requests closure of that original child and clears private display without stopping the Host. See [composition and lifetime semantics](../contracts/apple-settings-assistant-composition.md).

Install/start/stop/login controls use the actual per-user launchd service in `~/Library/LaunchAgents`; the app has no disposable LaunchAgents option. Installation is explicit. After each control the app reads `service status` and shows installation, login enablement, launchd PID and last exit status in Settings and the menu. Quitting the menu bar app drains its own local work and CLI children; the host keeps running. Stopping the service is a separate confirmed action and does not stop a foreground `serve` process.

If an action fails after possible delivery, inspect its authoritative original before choosing a new action. The ordinary owner reminder's explicit Repeat preserves its original command/request identity and payload. Native credential submission never repeats the secret; use its original Inspect and keep storage/linking uncertainty separate. The in-memory reminder is lost if the app is forcibly terminated; reopening performs reads and does not automatically resend mutations.

## Repair configuration without Ask Settings

No model or assistant is needed for a valid-but-unusable provider configuration. Connect in Host, open Host settings from Models, and read the actual saved revision before editing. Choose the provider/model and official or explicit loopback endpoint, Save, then separately confirm the original protected batch. A missing credential does not authorize fallback. Use the native credential control for that exact saved recipient; initial storage Completed needs its separate Link button, while configured replacement performs no metadata CAS. Inspect original storage/link results after uncertainty instead of entering another key. A syntax-invalid settings file that prevents Host startup is a different recovery problem; these controls do not claim to repair arbitrary invalid files.

Memory exposes the real opt-in and reported dimension choices, including model default. Save once and distinguish Saved from pending rebuild/application, unavailable helper and restart-required. Off preserves the operator's model paths; unknown metadata cannot produce guessed choices. System One is opt-in: use the TypeSafe preset or a valid compatible custom endpoint/model, then confirm the exact recipient change. This configuration consent is separate from later exact payload disclosure through ordinary tool selection. See [embedding limits](../architecture/embeddinggemma2.md) and [System One consent](../contracts/host-selection.md).

A stale revision or changed registry retains your draft: explicitly Reload, review and make a new request only after resolving originals. Inspect is observational; Reconcile examines the original unresolved file intent without rewriting or applying a new backend. Applying/Unknown, a successful transport response or another ready backend is not an Applied receipt. Do not turn a newer query into an old request's changed replay.

The existing CLI can inspect/reconcile without an LLM. These are setup instructions, not executed walkthrough evidence. Use the existing trusted CLI and private state while its ONE Host serves; no second Agent is opened. For a nonsecret settings query:

```sh
umask 077
EV_SETTINGS_REQUESTS="$(mktemp -d)"
printf '%s\n' '{"kind":"query","query":{"kind":"settings"}}' > "$EV_SETTINGS_REQUESTS/settings.json"
vorra --state-dir /absolute/private/state owner --request-file "$EV_SETTINGS_REQUESTS/settings.json"
```

For original outcome inspection, put this typed query in another private request file and replace the placeholder with the actual retained UUID:

```json
{"kind":"query","query":{"kind":"settings_operation","request_id":"ORIGINAL_OPERATION_UUID"}}
```

Explicit original file reconciliation uses a distinct transport request ID; it does not replace the original write ID:

```json
{"kind":"operation","request_id":"TRANSPORT_REQUEST_UUID","operation":{"kind":"reconcile_settings","operation_id":"ORIGINAL_OPERATION_UUID"}}
```

Submit either file with the same `owner --request-file` command. The [#118 walkthrough](settings-validation.md#hybrid-integration-walkthrough-118) ran these routes and the native pipe on disposable state. When scripting `owner --sensitive-stdin`, a malformed native frame is reported only as `native settings and credential input require the private stdin route`; check the JSON shape (for example `scope` is `{"kind":"host","host_id":…}` and an invocation `reference` is `{"kind":"confirmation"|"action","reference":{…}}`) before suspecting the pipe. Preserve original IDs/candidates across response loss. A permitted full replacement uses `kind: operation`, an explicit `request_id`, and `operation.kind: replace_settings` with the observed `expected_revision` and COMPLETE edited settings object. Preserve every unrelated field/reference; the service performs actual CAS. Raw owner replacement returns HostActionRequired for protected provider/recipient changes: use the native Models/Tool Selection confirmation rather than inventing a consent reference or editing the Host file around the service. [Owner command setup](host.md#owner-inspection-and-configuration) and [receipt recovery](../contracts/settings-owner-routes.md) define the exact route. Credential bytes/native proofs never belong in these files; only the existing private pipe or explicit operator environment-credential route can transfer them.

Notification choices are not OS permission. The foreground permission button observes capability before/after genuine OS interaction; denial yields supported instructions, not repeated prompts or a fabricated grant. Mac choices do not schedule notices. iOS has its separate bounded foreground committed-event attempt path, not APNS/background delivery. Devices requires its own private invitation, full identity comparison, explicit access and separate approval; an invitation or Host pin is not completion on the phone. Close/cancel/Inspect retain their original identity and never imply rollback, remote stop or secure erasure. See [native actions](../architecture/native-settings-actions.md).

## Optional ChatGPT plan card

Settings → Host has an optional "Use your ChatGPT plan for OpenAI" card. **Continue with ChatGPT** creates a native-storage `chatgpt` binding, or reuses the selected one, and sends the owner `chatgpt` `sign_in` operation. It opens the returned `https://auth.openai.com` URL with NSWorkspace and polls `wait`. After a completed sign-in it adds the binding to settings through the existing revision-checked `replace_settings`, unless the official OpenAI endpoint already has another binding. When signed in, the card shows the account email, **Using ChatGPT plan** (or that plan usage was not granted), a **Manage usage** link to `https://chatgpt.com/settings/usage`, **Sign out**, and **Use API keys instead** (deselect). API keys remain the default. The app never shows the card as required, and other provider paths are unchanged. The card was compiled and analyzed for the supported SDKs only. Browser hand-off, Keychain storage and the real login have not been exercised in the app.

## Vault

Settings → Vault ([#222](https://github.com/izyuumi/everything/issues/222)) lists local vault items as metadata (label, kind, environment name, service, username, sites, field names and reference) and incomplete rows, with Remove behind a confirmation. Add item opens a sheet for an API secret or a login; label, environment name, service, sites and username are metadata the agent can see, and the masked value goes to the Host only over the private `owner --sensitive-stdin` pipe. The 1Password card takes the pinned `op` path; Find accounts lists the accounts `op` reports, then Connect with the chosen account UUID triggers 1Password's own approval. The Proton Pass card takes the pinned `pass-cli` path and either a personal access token (masked, sent over the same pipe) or, after `vorra vault connect protonpass --web` in a terminal, Check web login. Each card shows the Host's status (ready, locked, disconnected or unavailable) and has Disconnect. See the [vault contract](../contracts/vault.md#owner-ipc), [1Password setup](onepassword.md) and [Proton Pass setup](protonpass.md).

Approvals for `vault_use` show the item label, provider, kind, field, destination, sites and reason, never a value, and offer Deny, Allow once and Allow for this task (a one-hour lease for that task, item and destination; not offered for cards).

The app launched against that Host with `-hostExecutable`/`-hostStateDirectory` and a disposable home, but the Vault tab, add sheet, provider cards and vault approval details were not seen, because Settings and approval windows open only from the menu bar extra.

## Owned CLI cancellation

The app retains each launched CLI Process, its pipes and private request input until the actual child exits and is joined. A request timeout starts cancellation; the supervisor attempts SIGINT immediately, SIGTERM after two seconds and SIGKILL after four seconds, each once and only for its tracked positive CLI PID while that Process is running. It does not look up the Host PID or signal a process group; signal attempts use only the captured CLI PID. Failed nonblocking descriptor setup enters the same cleanup path, and only successfully configured nonblocking descriptors are read. Signal and pipe/input cleanup failures are reported alongside the original cancellation, timeout or command failure.

The timeout bounds the start of cancellation and signal escalation rather than kernel process death. An uninterruptible OS process can leave the actual join and app Quit pending; the supervisor retains its ownership rather than reporting a live child as joined. Foundation Process plus a raw PID does not provide atomic PID pinning. Historical correction evidence includes source inspection and Swift syntax/Foundation checks. Its code is also present in the later integrated #163 source that passed supported SDK build/analyze. Actual macOS cancellation, signal, descriptor-error, real cleanup and quit/Host-PID observations remain pending; compilation does not prove them.
