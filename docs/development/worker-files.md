# Worker files

The worker file boundary is a synchronous Unix library. Its caller must run filesystem work outside Tokio workers and retain the actual leased Agent until the call finishes. An Agent created from an unleased Store is rejected. Non-Unix calls return Unsupported. These functions do not send data, grant execution authority, create a model request, install a sandbox, or apply generated files to a user's workspace.

## Public API

- `capture_inputs(&Agent, &Path, &[String]) -> Result<Vec<WorkerFile>, WorkerError>` captures exactly the explicitly named files under the declared physical workspace. It returns their exact bytes as canonical base64 and established SHA-256 digests for subsequent manifest approval.
- `prepare_workspace(&Agent, &WorkerManifest) -> Result<PathBuf, WorkerError>` stages the validated manifest inputs at `<state>/worker-jobs/<delegation>/<attempt>/workspace`.
- `collect_artifacts(&Agent, &WorkerManifest) -> Result<Vec<WorkerFile>, WorkerError>` reads only existing permitted output names. Missing names are optional. Any invalid or oversized produced candidate fails the whole collection. The caller must settle native execution and broker cleanup before collection; the file-area lock does not pause native tools.
- `quarantine_result(&Agent, &WorkerManifest, &WorkerResult) -> Result<QuarantinedArtifacts, WorkerError>` validates the complete result and publishes it at `<state>/worker-results/<delegation>/<attempt>/<result digest>`. The returned directory contains `receipt.json` and `files/`; returned file names are relative to `files/`. Nothing overwrites the live workspace.

Inputs and exported artifacts each have at most 64 files and 256 KiB aggregate decoded contents. Paths are normalized UTF-8 relative names, at most 1024 bytes and 16 components, without controls, backslashes, traversal or reserved scheduler names. Files overlapping directory prefixes are rejected before staging. Administrative manifests and receipts live outside the tool-visible workspace, so an artifact named `receipt.json` remains ordinary data under `files/`.

## Descriptor and state protection

Directory components are opened through pinned descriptors with NOFOLLOW. Files are opened nonblocking, must be regular and have exactly one hard link, and are checked again after reading. Reads are bounded before allocation and reject observed size changes. Supplied symlinks, special files, hard links, reserved names and filesystem-equivalent aliases of adjacent scheduler control entries are rejected.

Capture requires an absolute nonroot workspace and rejects lexical/canonical paths inside the actual Agent state directory. A metadata-only inventory records protected state file and directory device/inode identities, including an explicit private database descriptor check. Every selected open descriptor and traversed directory is compared with that inventory. This also rejects observed bind-mount aliases whose source inode is in the inventory. The inventory follows no symlink, reads no file contents, and fails closed on traversal errors, more than 16384 entries, depth over 64, or a sampled five-second scan limit.

These checks describe inspected inodes and bytes, not a filesystem snapshot or arbitrary-code isolation. Another process with the same UID or mount privileges can rename entries, change same-size contents, alter hard-link counts or create a new alias after inventory. Native workspace tools and their broker remain the supported execution profile; unrestricted shell, MCP, network tools and hard OS resource guarantees require separate implemented enforcement. A blocked operating-system filesystem call cannot be forcibly interrupted by these synchronous functions.

## Publication, replay and recovery

Worker administrative directories require the current UID and mode0700; administrative and staged files require mode0600 and a single link. One advisory lock per file area serializes cooperating file operations without another host lease. Contention returns a typed conflict. Directory entries and records are bounded and validated; unknown administrative entries are rejected.

A complete immutable manifest is published without replacement before input staging. Its deterministic pending record binds the manifest digest. A valid partial pending record or input file must exactly match a prefix of the requested bytes before completion; unexpected entries and different contents fail without truncation or deletion. Input staging accepts only the exact expected directory/file tree, syncs files and directories, then renames the complete staging directory without replacement. Once the final workspace exists, preparation verifies its full manifest and private root and returns it without rewriting files changed by the task.

Quarantine first binds the attempt to its complete immutable result. It writes a private pending receipt and artifact tree, verifies all contents and names, syncs them, and publishes the final directory without replacement. Exact replay rereads the full stored result, receipt and artifact bytes; changed results or tampering fail. Peer-provided paths cannot name administrative metadata. A result remains quarantined for explicit review and cannot become a host permission, tool result or automatic file application through this module.

Each file area retains at most512 administrative directories, with at most2049 scanned entries and a sampled five-second scan limit. Staging trees contain at most1088 entries. Private records are at most512 KiB. Retained workspaces can contain files subsequently created by the separately bounded native tool loop; this module does not implement an aggregate OS disk quota. Exhaustion fails closed. Failed publication may retain owned partial records or staging directories for exact retry. No unrelated data is removed, and no automatic garbage collector or backup/restore subsystem is provided; owner-reviewed retention must preserve live execution and immutable result identity.

## Validation

No automated tests, fixtures or frameworks are added. Deferred coverage belongs to [#32](https://github.com/izyuumi/everything/issues/32). Compilation/static analysis and focused disposable filesystem observations are recorded separately. Successful native inference, hostile same-UID mutation, Apple runtime filesystem behavior and arbitrary-code isolation are not established by this module's checks.

Rust1.88 formatting, default/all-feature workspace all-target checking, strict all-feature Clippy and the disposable release inspection executable passed with temporary module registration and an isolated package identity. The final worker composition must register this module and repeat its integration gates. The inspection used real leased Agents and files: exact UTF-8/binary capture, unchanged outside markers, traversal/symlink/hard-link/special/state-database denials, private staging, no-reset replay, a seeded pre-publication partial file, unexpected/tampered staging, optional outputs, individual/aggregate bounds, immutable quarantine replay, unsafe/tampered artifacts, retention/inventory exhaustion and lease reacquisition after reopen. Its terminal artifact result was manually constructed for file-boundary inspection; no agent inference or remote execution was represented as successful.

A separate disposable process ran in an actual private user/mount namespace and bind-mounted only its generated Agent database and state subdirectory onto its generated source workspace. Capture rejected both aliases by observed inode identity, and the outside marker remained unchanged. Namespace setup was used to inspect aliases, not as a production worker sandbox or proof of malicious-code containment. No model, relay, credential-store or external network operation was performed by these inspections. The raw observations and driver remain outside the repository at `/tmp/vorra-worker-boundary-inspection`.
