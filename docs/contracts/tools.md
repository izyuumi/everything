# Tools contracts

## Implementations and descriptors

`Tool: Send + Sync` exposes `descriptor(&self) -> &ToolDescriptor` and asynchronous `execute(&self, context: &ToolExecutionContext, arguments: serde_json::Value) -> Result<ToolOutput, ToolError>`. Implementations use `async_trait`. `ToolOutput.content` is a JSON value owned by the result. `is_error` is a generic completed semantic-failure flag, defaulting to false when decoding older output. A true flag preserves completed error output without asserting that no effects happened; the broker journals it as a known failed operation. Production success constructors set false explicitly. Transport errors and uncertain cancellation remain `ToolError` failures with unknown outcome semantics.

`ToolDescriptor` contains `name`, `description`, `input_schema`, `capabilities`, `read_only`, and `concurrency`. Names contain 1–128 ASCII letters, digits, underscores, dots, or hyphens; descriptions contain 1–8192 bytes and cannot be whitespace-only. Capability values are `filesystem_read`, `filesystem_write`, `shell`, `network`, and `mcp`. Concurrency is `concurrent` or `exclusive`. These values declare execution requirements for the [broker](broker.md); they are not permission grants or enforcement.

## Registry

`ToolRegistry::new()` creates an empty registry. `register(Arc<dyn Tool>)` synchronously compiles and validates the descriptor's JSON Schema before adding the tool. Call registration during startup or on a blocking worker. Registration snapshots the descriptor and cannot replace an existing tool. Schemas may use locally embedded references; external resource retrieval is disabled. Supported JSON Schema drafts follow the `jsonschema` library's supported drafts and schema auto-detection. Format assertions are enabled. Schemas with regular expressions that exceed configured resource limits fail registration or argument validation.

`discover()` returns cloned descriptors in ascending name order. `descriptor(name)` returns a borrowed descriptor or `UnknownTool`. `validate(name, &arguments)` performs synchronous validation; callers must move potentially expensive calls off async executor threads. `execute(name, &context, arguments)` performs validation on a Tokio blocking worker and requires a Tokio runtime. Registry execution does not acquire permission, persist operations, or serialize exclusive tools. Production privileged execution uses the [Tool Broker](broker.md), which provides those boundaries before exposing execution to models.

Serialized schemas are limited to `MAX_TOOL_SCHEMA_BYTES` (262144 bytes) and arguments to `MAX_TOOL_ARGUMENT_BYTES` (1048576 bytes). Invalid argument results contain up to 32 `ArgumentViolation` values with JSON Pointer instance and schema paths and a diagnostic message truncated to 2048 characters. Schema-registration diagnostics have the same character limit. Diagnostics can contain submitted values and must receive the same privacy treatment as tool arguments; the general invalid-argument error display includes only the tool name. Schema validation does not mutate arguments or insert defaults.

## Trusted context and cancellation

`ToolExecutionContext::new(request_id, task_id, workspace_root, cancellation)` accepts host-supplied identifiers and a `tokio_util::sync::CancellationToken`. Identifiers contain 1–256 bytes, cannot be whitespace-only, and cannot contain control characters. The workspace root must be absolute. Private context fields are exposed through read-only accessors. The context has no Serde deserializer and must never be constructed by decoding model arguments.

Native Agent dispatch attaches a private retained owner to each invocation context. Cloning the complete context preserves that owner without exposing the Agent or granting authority. The registry's blocking validation and builtin filesystem worker retain the complete context until their actual work and resource cleanup finish, even if an awaiting future is dropped. Tool implementations that move work into separate owned workers must preserve the complete context for the same lifetime. A path or cancellation-token clone alone does not retain the owner. Context debugging does not inspect the retained owner's contents.

`check_cancelled()` returns the typed `Cancelled` error. The registry checks cancellation before validation and before invoking the implementation. Once execution starts, implementations must observe `cancellation()`, stop their work, and release resources. The registry does not drop an executing future automatically, because doing so would not guarantee cleanup. An absolute workspace path is metadata, not a security boundary; arbitrary shell confinement requires operating-system enforcement or explicit trusted execution policy.

## Errors and deferred verification

`ToolError` distinguishes `UnknownTool`, `DuplicateTool`, `InvalidDescriptor`, `InvalidSchema`, `InvalidArguments`, `ResourceLimit`, `InvalidContext`, `Cancelled`, `Execution`, `FailedWithoutSideEffects`, `EffectsUnknown`, and `ValidationWorker`. Validation and lookup errors occur before tool invocation. `FailedWithoutSideEffects { name, message }` is valid only when the implementation knows no external, filesystem, subprocess, or other effect happened. `EffectsUnknown { name, message, cleanup_completed }` reports uncertain effects; only a trusted implementation that has confirmed all owned work stopped may assert completed cleanup. A remote request requires confirmed remote completion, not merely a returned client future. Generic `Execution` and `Cancelled` after invocation imply uncertain effects and cleanup. The broker persists unknown outcomes, quarantines unconfirmed cleanup, and forbids automatic retry; see its [result and recovery contract](broker.md#results-interruption-and-uncertainty).

The registry foundation does not include privileged implementations or scheduling. [Permission policy](../architecture/permissions.md) and [durable broker tracking](broker.md) are separate implemented modules. Automated registration, discovery, invalid-argument, and unknown-tool tests are deferred to [#32](https://github.com/izyuumi/everything/issues/32) under the current no-new-tests instruction.
