# Host worker coordinator data contract

Issue [#29](https://github.com/izyuumi/everything/issues/29) defines the optional coordinator's public request, disclosure, status and inspection records in `host::worker`. These validated data records carry no approval or result authority. The implemented [service](host-worker-service.md), [Host admission](host-worker-admission.md), owner IPC and [CLI](../development/worker-coordinator-cli.md) compose the actual endpoint, capture, native Gate and result bridge. The actual combined Host credential-rejection/recovery walkthrough passed with the limits recorded below; DTO validation alone proves no operation succeeded.

## Settings and preparation

`WorkerCoordinatorSettings` contains only the explicit `relay_origin: RelayOrigin`. `HostSettings.worker` represents disabled operation with `None`. Decoding settings performs no identity creation, trust change, connection or worker scan. The existing RelayOrigin type validates and canonicalizes its own encoding.

`WorkerPreparationRequest` contains an executor identity, owner-selected workspace, objective, explicit constraints/context/input paths/outputs, mode, WorkerModelBinding, ContextBudget, LoopLimits, absolute deadline and explicit tool set. `validate()` checks bounded metadata shape, established model/loop/context component validators, unique requested input paths, the exact requested absolute deadline and a 256 KiB serialized cap. Workspace validation is lexical absolute UTF-8 shape only; it does not establish a physical directory, path isolation or authority. Relative-path, file identity/content and supported execution semantics remain the existing capture and WorkerManifest validators' responsibility. No files are read merely by decoding or validating this request.

All new DTO structs and kind/snake_case enums reject unknown own fields. Preparation request/local-plan/full-disclosure Debug implementations expose only a small identity subset; they omit selected data, files, objective, workspace and execution policy. The new preparation input alone uses a private five-field ContextBudget decoder to reject unknown budget fields without changing the established global type. Other reused nested output contracts, including ContextBudget and historical CommandReceipt, retain their existing additive-field behavior. Typed domain IDs and the existing worker/profile types preserve their own encoding and validation rules. Call the public validation method after deserializing or mutating these public data fields; serde shape checks alone do not perform all cross-field validation. Transport callers must bound raw bytes before deserialization.

`WorkerLocalPlan` discloses the dedicated local conversation, create/input commands, root task, title and exact captured ExecutionPolicy. The four local UUID values are distinct; the policy serializes within 32 KiB, leaving space in the existing 64 KiB journal boundary for the coordinator's compact private snapshot. Its validator does not capture or recapture a registry or physical workspace. The actual host must do that before creating the disclosure.

`WorkerPreparation` returns the complete manifest, its existing canonical fingerprint, exact executor public keys/fingerprint, local plan, ticket and authoritative preparation/expiry times. Its `validate()`:

- Runs the actual WorkerManifest fingerprint/validation, including its supported model, tools, files, deadlines, cumulative limits and lack of hard-OS guarantees.
- Binds executor keys and full fingerprint to the manifest's executor.
- Requires an increasing ticket interval of at most sixty seconds within the manifest deadline, with preparation no earlier than manifest creation.
- Requires local mode, explicit tool set, budget and limits equal the manifest policy; tools are enabled exactly when the set is nonempty, and an empty set has zero tool calls.
- Keeps the four local IDs separate from every worker-side native ID.
- Bounds the complete disclosure to 768 KiB without truncating selected data or base64 file bodies.

`validate_for(&WorkerPreparationRequest)` additionally compares every requested field to that full disclosure, including ordered input paths, selected context, model/reference, physical-workspace field, budgets and deadline. This is request/result equality, not proof that the workspace was validated or that the bytes still match a live filesystem. The owning ticket service must retain the actual opaque PreparedDelegation, current pin and captured authority. A decoded public WorkerPreparation cannot mint or recreate any approval.

The disclosed `local.create_command_id` is the Delegate request ID. Delegate response validation checks its CommandReceipt against the supplied actual enclosing request ID. The service also binds that ID to the retained ticket's original disclosed local plan before effects. Ticket expiry is not ApprovedDelegation expiry; actual approval time and monotonic lifetime are minted by the explicit Delegate operation. Serialized times do not grant renewed consent.

## Inspection

`WorkerNativeInspection` exposes only local task/conversation/input-command identity, actual TaskStatus/RemoteTaskPhase, immutable RemoteBudgetCharge, admission/dispatch times and optional accepted RemoteResultInspection. It omits instructions, captured policy and raw unaccepted result payloads. `validate()` checks bounded reservation charges, chronology and the real remote phase/status relationship. Accepted reports use the existing crate-private RemoteResultInspection validator for deterministic public receipt identity, plus local task/command identity and model/tool count ceilings. Reported token usage is informational and can exceed the original estimate; it never rewrites, refunds or increases the immutable captured charge. It does not convert inspection JSON into RemoteResultReceipt or VerifiedRemoteOutcome.

`WorkerJobInspection` exposes the existing WorkerJobBinding, peer, ledger state, cancellation intent/acknowledgement, rejection/result digest, quarantine flag, optional receipt command and optional native inspection. Its validator binds accepted report source and IDs to the job, keeps rejection/result/receipt state consistent, requires a result digest for its data-quarantine flag, and compares any returned native receipt to the recorded job receipt. `native: None` is data describing an actually known missing reservation; consumers must propagate query/storage failures rather than convert them to None. Historical ledger metadata remains inspectable when the native reservation is missing. Ledger Offered does not establish that an Offer was queued or transmitted: locally staged manifests also have that state.

`WorkerJobSummary` retains binding, peer, state, cancellation flags and paired optional local task/phase. It omits full native reports, file bodies and result summaries. `WorkerCoordinatorStatus` carries actual enabled/accepting/draining/relay state, admission blocking, four-ticket/four-operation counts, at most 256 retained jobs and an optional fixed error code of at most 128 lowercase ASCII letters/underscores. Its optional unresolved count describes native reservations for those inspected jobs and cannot exceed that job count; the Scheduler's separate global limit is 4096 retained remote tasks. Accepting requires enabled, not draining and inspected counts; enabled status identifies its relay origin. No default or producer fabricates readiness. A disconnected relay never proves remote execution stopped.

## Queries and operations

`WorkerCoordinatorQuery` variants are Status, Identity, Peers, Jobs, Delegation and Task. `validate()` rejects nil UUID cursors/lookup IDs and requires job page limits from one through 32. `WorkerCoordinatorQueryResult::validate_for(&query)` checks the matching response kind, actual public identity fingerprint, at most sixteen unique validated purpose peers and their chronology, strict ascending exclusive delegation UUID order, exact continuation identity and selected task/job identity. An empty page cannot promise continuation. Responses serialize within 256 KiB; oversized records fail explicitly instead of disappearing or being truncated.

`WorkerCoordinatorOperation` variants are PinPeer, Prepare, Discard, Delegate, Cancel, RevokePeer and Release. Release carries the task ID, exact WorkerJobBinding, expected phase, operator and reason. Its `Released` result must return a native inspection whose `release` record repeats the request ID and those fields. `WorkerNativeInspection` carries the optional `release` record; a released inspection must be Failed, in phase `released`, and hold an Unknown report exactly when the expected phase was `outcome_unknown`. Request validation bounds encoded data to 256 KiB, validates full pin fingerprints and existing bindings, and rejects nil tickets, malformed digests or malformed full executor fingerprints. `OwnerOperation::WorkerCoordinator` routes them through the actual bounded owned Host operations. They are unavailable through model or paired-device command ingress.

`WorkerCoordinatorOperationResult::validate_for(&operation, request_id)` validates matching kinds and immutable identities for PeerPinned, Prepared, Discarded, Admission, Cancellation and PeerRevoked. Rust callers box the Admission job and Cancellation task fields; their JSON object fields are unchanged. Prepared uses full request/disclosure comparison. Admission retains the existing CommandReceipt plus exact ticket/digest/fingerprint and job inspection; it does not assert remote execution or transmission. An available native inspection must agree with the receipt's conversation, task and acceptance chronology. Cancellation validates the original task/binding and actual non-Reserved remote phase without treating cancellation intent as successful effect cleanup. Peer revocation remains purpose-specific and sticky. Ordinary results serialize within 256 KiB; full preparation results use the 768 KiB disclosure cap. The outer owner transport's separate two-MiB frame bound still applies.

CommandReceipt preserves Accepted/Applied/Completed/Rejected, original acceptance time, exact applied metadata and archived result semantics. Acceptance is durable owner admission, not remote success. Its historical nested result Value is retained; it grants no authority. A missing native projection never authorizes replacement IDs, reconstructed consent, local execution or a remote retry. The service must prove same-Store durable receipts and retain real owned authority using the existing [native remote admission](remote-tasks.md), [result admission](remote-result-admission.md) and [worker protocol](worker.md) contracts.

## Validation boundary

The actual combined consumer at `d273c52`, including immutable-binding, indexed-lookup/schema12 and unknown-count corrections, passed the six normal-package Rust 1.88 gates. The actual Host native-admission/credential-rejection/recovery walkthrough passed. See [worker validation](../development/worker.md#combined-host-validation-checkpoint) for exact commands, artifact provenance, runtime limits and separately qualified executor/bridge observations. DTO validation alone establishes no network, credential-store, inference or security-audit result. Automated verification remains deferred to consolidated [#32](https://github.com/izyuumi/everything/issues/32).

An absent coordinator service does not inspect retained worker state merely to answer status or create a worker identity. `jobs` and `unresolved_remote_tasks` are paired optional counts: `None` means that history is uninspected, while a retained coordinator returns `Some` actual counts after its bounded scan, including after live settings disable. An absent service reports known zero preparation/operation counts independently of its unknown retained history. `accepting` requires available counts. Disabling or restarting cannot manufacture a zero retained history from the absence of a service.
