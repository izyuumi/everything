# Native Ask Settings consumer

The macOS consumer consists of `SettingsAssistantController`, `SettingsAssistantView` and `SettingsAssistantOperationView`. They consume the existing [owning-layer bridges](apple-settings-assistant-ui-bridges.md) and [restricted assistant Session](apple-native-settings-assistant-session.md) through the SAME app-owned `NativeSettingsStore`. The [app composition](apple-settings-assistant-composition.md) now registers the files, mounts the inspector and supplies closed acknowledged navigation and the hooks below. Corrected #163 passed supported SDK compilation; actual Apple UI/provider execution remains unverified.

## Ownership and publication

The MainActor observable controller receives only the existing Store, immutable connection UUID and optional closed `Navigation`. It receives no client, Session, proof, provider or generic Owner capability. Explicit Open synchronously captures the original sealed Store action before its owned task. Expanding the inspector performs no Open or inference. One current-or-closing child is allowed per exact native Owner, with at most eight retained contexts; an uncertain original cannot be replaced on that same Owner. Public IDs are display/lookup metadata, never authority.

Each context retains its original Open/Send handles, exact connection and bounded authenticated operation cohort. Every private callback checks the same context, publication incarnation, current sealed Store Owner, actual parent window/application and original child lifetime before publishing. New-Owner reuse of the same connection does not make an old callback current. Old callbacks still settle their original owned tasks and cleanup metadata. Only genuine Closed for the known child, Closed(nil) before a child was known, or original Unavailable permits release; NotAccepted, Unknown, Closing, missing state and a clean generic parent report do not establish per-child closure.

Root app composition must synchronously call `parentWillRetire` BEFORE every Store close/replacement, window-owner change or connection replacement. It must bind actual inspector expansion, Settings visibility, application activity and weak real parent window through `setExpanded`, `setSurfaceVisible`, `setApplicationActive` and `attachWindow`. `applyConnectionKey` retires old contexts before changing the future connection epoch. `ownershipChanged` checks exact Store ownership, reconciles original metadata and can resume only an already opened eligible child. These flags supplement actual window/NSApplication checks; they are not service authorization.

Covering presentation calls `setCovered`: it clears private text/review, invalidates publication and pauses reads, without CloseOpen. The authenticated Device handoff marks its ownership BEFORE the synchronous existing Store bridge can attach its real native sheet. That original child remains live during its own invitation/approval ceremony. Actual collapse, application/window hide or parent retirement instead closes the original child and dismisses its owned native ceremony. On uncover, publication resumes only after that actual original ceremony is marked retired and the real window has no sheet. The original Store/lifecycle remains responsible for genuine UI retirement, hidden acknowledgement and native callback cleanup.

`SettingsAssistantView` is inspector content with a 300–420-point preferred column range, not an independently presented window. Root owns actual native inspector layout, expansion binding and covering/window observer. The content's NSView bridge holds only the actual weak parent and retires a rebind/dismantle; onAppear does not grant activity or Open a session. Root must keep the conventional controls independently available.

## Disclosure and bounded private text

Open reveals the actual decoded provider, model, full recipient and closed tool list without inference. Every original Send requires a separate review and final native Button gesture. That gesture synchronously calls actual disclosure consent and `prepareAssistantSend` before starting its task. Edits, cover, inactivity, collapse and Owner changes invalidate review. No saved consent, automatic retry, provider fallback, replacement Open or implicit paid Send is introduced. An Unavailable Open or Send shows that the Host reported no usable model/credential or no Settings chat capacity, that no other provider is selected, and points to Models; conventional controls stay usable. The backend's 32768-byte escaped frame limit can still reject an otherwise valid question; it is neither truncated nor resubmitted.

Composer and review/submitted-question cells are each bounded to 8192 UTF-8 bytes. Four completed recent turns each retain at most 8192 question plus 16384 answer bytes; current committed and provisional cells are each bounded to 16384. This totals at most 147456 private text-cell bytes, excluding temporary Swift/UI/Session copies, public metadata and allocation overhead. Review and submitted question share one cell. Completed display history alone can be evicted; original handles, claims and prepaid capacity are not refunded. Retirement clears the controller's text references without claiming secure erasure or detection of arbitrary pasted secrets.

Text is rendered literally. Markdown, text, URLs and model-created UUIDs cannot become executable controls. There is no transcript Codable/hash/equality cache, ordinary conversation/wiki/embedding intake, persistence, clipboard/export or diagnostic raw-text path. Private display and recipient disclosure are marked privacy-sensitive, which is not a universal recording or memory-erasure guarantee.

## Reads, cards and authoritative outcomes

One owned Poll loop awaits each actual Store callback before the next read and waits about one second between completed reads. One pending refresh Boolean coalesces demand; no timer, chunk tasks or continuation queue accumulates reads. Cancellation retires publication first and joins the original callback. An earlier-turn response cannot clear a newer Send's pending identity or republish its prior answer. Decoded provisional/interrupted text, provider/usage completion and actual charged/reserved counters remain distinct from committed text and service effects. Context revision/time is a point-in-time observation, not a latest-read guarantee or wall-clock freshness ordering.

Cards are created only from sealed authenticated operation handles belonging to that original child/turn and the returned bounded cohort. Scoped Inspect reads the original receipt; a live exact Awaiting reference can request sealed Details. The controller inspects each new card once automatically, one at a time through the same single card task, and again once when its original turn completes if the earlier observation was not Finished. These are reads only; Confirm, device ceremonies and navigation still need their own native gestures, and the manual Inspect button remains. Never-materialized terminal receipts have no fabricated target. A once-materialized target remains display metadata after its live Details expires/disappears so original file Unknown can still expose actual native Inspect/Reconcile. New execution still requires current actual Store admission, not that cached display target.

Patch cards show the genuine original snapshot/registry, exact diff and revision. Confirm synchronously uses the existing Store method; stale revisions, conflict, pending application/reindex, restart-required and file Unknown remain authoritative receipt states. Existing original file reconciliation remains available; no autorebase, resubmit or requested-value Saved assignment is introduced. When the original receipt is Conflict, or an awaiting patch's revision differs from the fresh shared Store snapshot, the card states the newer revision and that nothing was saved by it. Its re-propose button only fills the composer with a fixed native request to reread and propose again; that question still needs the normal review and Send gesture. The restricted turn context separately tells the model to call `settings.get` after a conflict, explain the change, never resubmit the old patch and describe a change as saved only from its receipt; this guidance is not an enforcement boundary. The existing Store refreshes actual controls after its mutation/recovery workers; dirty drafts remain preserved/conflicted by that Store.

Device cards use only the existing sealed Device handoff and real private ceremony. Pair's additional final-approval slot is reserved by the existing Store bridge, and full identity/access selection plus separate native approval remains unchanged. Host approval is not Replica completion. Native OpenSection is the only allowed native Details action: the synchronous bridge captures the original admission before its task, invokes real Admit → presentation → Finalize, and passes only the closed `SettingsSection` to Root navigation. Immediately before invoking Root, the callback rechecks the original current context/Owner and lifetime; a late old callback cannot register a route after retirement.

Root's `Navigation.open` must settle only on genuine matching destination acknowledgement or actual dismissal, returning `.opened(exactSection)` or `.dismissed`. Its synchronous `retire` must settle that exact pending route during retirement. A missing callback disables that presentation; no default navigation success is simulated. There are no Agent credential, OS-notification or final-pair-approval cards in the current whitelist. Native Models/Tool Selection/Notifications controls retain their separate fresh native gestures after actual known-section navigation.

## Cleanup, bounds and validation

Each context owns at most one Open, Send, card/navigation and Close task; there is one Poll and one coalesced final drain. Contexts are capped at eight. Sealed Send/operation membership remains bounded by the SAME Store's 64 combined identities, worst-eight prepaid mutation slots per Send, four effects, eight native Owners, one Device ceremony and eight Pair contexts. The SAME client/process supervisor enforces its four-call bound. No second supervisor or unbounded retired-context queue is introduced.

Cancel, Clear and real retirement clear private cells synchronously, stop fresh intake and own actual original CloseOpen after the captured original Open/Send/read/Poll joins. An explicit cleanup attempt reuses only the same sealed original. Unknown cannot become Closed from a refusal, timeout, parent-retired marker or generic report. Metadata-only cleanup lookup can outlive the old Store registry entry. Missing per-child state remains uncertain and retained within the eight-context limit.

Root must call permanent `invalidate`, await the coalesced `drain`, join the existing Store/lifecycle/native presenters and original section-navigation retirement, and only then shut down the SAME shared client. Controller drain joins its captured callback tasks; it does not substitute for genuine native UI/OS/provider drain. It never stops the independent Host. No hard process/provider/OS exit bound or rollback of admitted changes is asserted.
