# Broker contract

`src/tools/broker.rs` is the centralized native tool execution service. It uses `ToolRegistry`, `permissions::Authorizer`, `ExecutionAuthority`, and `storage::Store`. No model-controlled argument can construct or widen its authority.

## Lifecycle and shared limits

Call asynchronous `ToolBroker::start(store, registry, authorizer, limits)` exactly once per exclusively locked host store, before workers start. The authorizer must use that same store and registry. Startup recovers running rows to unknown and inspects persisted unknown cleanup risk. It can return a quarantined broker so the owner can inspect and reconcile it. It does not execute recovered operations. `recovered_operations()` reports how many running rows startup recovered; `is_quarantined()` reports the current execution gate.

Clone this broker or call `scoped(ExecutionAuthority)` to create `TaskToolBroker`. Never call `start` independently for each task, workspace, or request. Independent broker instances do not share gates, and startup recovery while another instance is executing would misclassify live work. Host process locking and lifetime management remain the background service's responsibility.

`BrokerLimits` contains `max_concurrent` (1–64), `max_in_flight` (at least concurrency and at most 1024), `queue_timeout`, `execution_timeout`, and `cancellation_grace` (each 1 millisecond–24 hours). In-flight admission uses a nonwaiting bounded semaphore; exhaustion returns `Busy` before reservation or execution. Concurrent execution uses another shared semaphore. All tools additionally use one shared read/write gate: `ToolConcurrency::Concurrent` permits shared readers, while `Exclusive` excludes all other operations across task-scoped brokers. Trusted descriptor metadata must accurately describe the implementation.

All SQLite, permission evaluation, filesystem-scope inspection, and schema preparation run on blocking workers. Queue deadlines are checked after preparation and while waiting for execution/exclusion. Cancellation during a synchronous operating-system or SQLite call is observed when that call returns; Rust cannot forcibly cancel a blocked system call. SQLite's own busy timeout and bounded JSON sizes remain applicable.

## Invocation, approval, and replay

`ToolInvocation` has immutable `operation_id`, `tool_name`, and JSON `arguments`. Operation IDs contain 1–256 bytes, cannot be whitespace-only, and cannot contain controls. Use an internal host operation ID, preserving the model provider's separate opaque call identifier for conversation reconstruction. The host must durably assign and retain the same operation ID across permission waits, caller reconnection, retries of an uncertain response, and restart. Generating a new ID to evade an unknown outcome defeats idempotency and is forbidden.

`ToolBroker::execute(&authority, invocation, CancellationToken)` and `TaskToolBroker::execute(invocation, token)` return `BrokerOutcome` or `BrokerError`. The task-scoped broker exposes its trusted authority through `authority()` for host integration. Quarantine rejects execution before cached replay as well; use the owner recovery report or authorized journal inspection for status while quarantined.

Preparation validates the tool/schema arguments, evaluates authorization, and reserves a pending journal row in that order. Journal identity binds conversation, task, tool name, arguments, canonical workspace, execution mode, descriptor SHA-256, execution timeout, and cancellation grace. Changing those values under an operation ID returns a storage conflict. Each request/result record has a 1 MiB serialized bound including its envelope, so arguments/results near the registry's standalone limit may exceed the journal limit and fail explicitly. Descriptor hashing uses the established SHA-256 implementation and is content identity, not authentication.

`ApprovalRequired { operation_id, approval }` means no tool executed. The host displays the complete approval, obtains an explicit decision through `Authorizer::resolve`, and resubmits the same invocation and authority. Merely polling or resubmitting does not approve it. Permission denial becomes a durable terminal `Denied` result. Approval waits do not hold execution slots or the exclusion gate. Policy errors fail closed and do not become successful tool output.

After queue/exclusion waits, the broker reauthorizes and attempts pending → running in one blocking closure, checking cancellation, deadline, and quarantine immediately before the claim. Revocation racing an already-running operation cannot undo its effects. Only a successful compare-and-update invokes the tool. Competing calls observe the existing state. `InFlight { operation_id }` is a status, not tool output or permission to assign a new ID; the host waits for or reads the durable original operation.

`Completed { operation_id, record, replayed }` supplies an `ExecutionRecord`. An exact retry of succeeded, failed, cancelled, or denied work returns its stored record with `replayed = true`. No tool is rerun. Existing running rows return `InFlight`; existing unknown rows return `OutcomeUnknown`. Returning an earlier terminal result is an inspection of the same task operation, not a new execution grant.

## Results, interruption, and uncertainty

`ExecutionRecord` has `version = 1`, an `OperationResult`, and optional `Interruption`. Results are `Succeeded { output }`, `Failed { code, message, output }`, `Cancelled { reason }`, `Denied { reason }`, or `Unknown { reason, cleanup_completed, diagnostic }`. Their states map directly to storage journal states. Missing, incompatible, or state-inconsistent records return `CorruptJournal` and require reconciliation.

`ToolError::FailedWithoutSideEffects { name, message }` is the only error variant that asserts a definitive failure without side effects after invocation. An implementation may return it only when it knows no external, filesystem, subprocess, or other effect happened. It must not use the variant for a partially completed write, uncertain request, nonzero shell exit after execution, or interrupted work that might have changed anything. That error becomes durable `Failed` with no output. A returned `ToolOutput { is_error: true, content }` instead represents a completed semantic error, such as a completed MCP tool result or a known shell exit failure. It becomes durable `Failed` with code `completed_tool_error` and the complete output retained in `output: Some(...)`; it does not assert an absence of partial effects. A false flag becomes `Succeeded`. The native loop maps failed status to the provider-neutral tool-result error flag and forwards retained output content without parsing MCP-specific JSON. The optional failure output defaults to `None` when decoding old records, and old ToolOutput values default `is_error` to false. `ToolError::EffectsUnknown { name, message, cleanup_completed }` explicitly reports uncertain effects. Only a trusted native implementation that has confirmed all owned operations stopped and cleanup finished may set `cleanup_completed = true`; ending its Rust future alone is insufficient. Remote MCP/HTTP work cannot claim completed cleanup without confirmed remote completion. This result remains unknown and nonretryable even with completed cleanup. Generic `Execution`, `Cancelled`, and other tool errors after invocation conservatively become `Unknown` with `cleanup_completed = false` and persistent quarantine. Initial schema/permission failures happen before invocation and retain their typed errors.

Interruption values are `CancellationRequested`, `QueueDeadline`, and `ExecutionDeadline`. Cancellation before invocation becomes durable `Cancelled`. After invocation, cancellation or execution expiry signals the tool token and awaits cleanup for the configured grace. A returned success during grace remains a known success and includes interruption metadata. A definitive no-effect error remains failed. A generic error remains unknown with unconfirmed cleanup; an explicit `EffectsUnknown` error retains its trusted cleanup attestation. Failure to finish cleanup produces `Unknown(CleanupDeadline, cleanup_completed = false)`; a panic produces an unknown panic outcome. A result too large to persist becomes an explicit unknown result instead of truncated output.

The supervised worker owns all gates until cleanup and result persistence. Caller cancellation/drop requests cancellation through a child token; it cannot drop the execution future or release exclusion directly. After the cleanup deadline the worker drops the noncooperative future, records uncertainty, and quarantines the broker because independently spawned work or subprocesses may remain active. Tool implementations must use structured ownership and operating-system cleanup rather than detached work.

`ExecutionRecord::requires_stop()` is true for interruption, cancellation, or unknown result. The native runtime must stop the current loop in those cases. `BrokerError::requires_reconciliation()` is true for unknown outcome, corrupt journal, or quarantine; those errors must stop further automatic native execution and surface owner review. A generic tool error must never be converted to a normal retryable model error. Journal persistence failure after invocation returns `OutcomeUnknown` with journal diagnostics and requires a host restart; a second best-effort unknown write cannot establish that the original write failed atomically.

## Persistent cleanup quarantine and owner review

Startup streams unknown journal rows starting with pages of eight, avoiding an unbounded result buffer. A page exceeding storage's aggregate byte budget is retried with half as many rows, down to one, without advancing its cursor. A valid version-one unknown record with `cleanup_completed = true` still cannot be retried but does not alone imply an active cleanup hazard. Incomplete-cleanup records, malformed results, missing results, and unsupported legacy versions require a matching immutable cleanup attestation. The original unknown operation state and result remain unchanged.

`recovery_report().await` reports startup recovery count, actual `running_count`, total unresolved cleanup count, up to 128 `CleanupRequirement` records, current quarantine, and whether restart is required. Each requirement contains operation ID, the storage-provided exact persisted result digest, and risk kind. Repeated owner review returns the next unresolved requirements as earlier ones are acknowledged. The scan is linear in unknown-operation history with bounded per-page memory. Storage corruption or inspection errors fail closed. An ordinary report is a point-in-time observation and does not prove that all supervisors have stopped.

`acknowledge_cleanup(operation_id, expected_result_digest, operator, note).await` is an owner-only host API. The owner must inspect the original operation and establish that no remaining local process, detached worker, or remote activity can continue before asserting cleanup. Acknowledging possible effects is distinct from proving their absence. The owner supplies the exact digest reviewed, a bounded operator identifier, and a nonempty note of at most 4096 bytes without control characters. The broker obtains the global exclusive gate before persisting the review and rescanning hazards. It cannot clear quarantine while an active supervised operation still holds exclusion. A stale digest or changed immutable review conflicts. An identical review reuses its original timestamp and is idempotent.

The store's separate `ToolCleanupAttestation` binds operation ID, exact original-result digest, operator, note, and timestamp. SQL NULL and serialized JSON have distinct digest markers. The storage transaction requires an existing unknown operation and an unchanged digest; exact replay is permitted and changed attestations are rejected. It never updates original tool-call content, makes unknown retryable, grants permissions, or resolves semantic uncertainty about external effects.

Quarantine clears only when every unsafe or malformed unknown record has matching cleanup review and the live broker does not require restart. Unexpected supervisor termination, a tool panic, or journal-write uncertainty still requires restart before new execution. Shutdown recovery can durably classify remaining running rows before that restart, allowing owner review while the original host retains its lease. The host UI/CLI must obtain explicit owner approval for this security-sensitive attestation. Never register it as a model tool or let remote task content manufacture owner identity or notes.

## Shutdown quiescence

`recover_after_drain().await` is a trusted host API after execution admission is closed and scheduler workers have drained. It acquires all `max_in_flight` admission permits, then the existing exclusive gate, under one `queue_timeout` deadline. Active supervisors or reconciliation holding the gate cause `RecoveryBusy`; this does not reclassify their journal entries. A caller must retain host services and the state lease while quiescence fails or remains unconfirmed.

The owned guards move into the blocking recovery worker and remain held through journal classification, cleanup inspection, and live gate updates. Dropping the caller cannot release them while SQLite work continues. With no supervised admission remaining, one atomic Store update converts stranded Running entries to immutable Unknown records with `AbandonedAfterDrain` and `cleanup_completed=false`. They require exact-digest owner cleanup review just like startup recovery. This operation never acknowledges cleanup, supplies ordinary model results, or retries work. Any recovered entry retains restart-required quarantine in the current process; subsequent owner acknowledgments do not authorize new execution there. `recovered_operations` keeps its startup-only meaning.

A successful call reports `running_count=0` while both gates are held. It proves a point-in-time supervisor/journal boundary, not that detached operating-system or remote activity has ended. Only explicit reviewed cleanup attestations can discharge those hazards. The host must continue rejecting new execution after the method returns, retain owner query/attestation access during drain, and repeat recovery after review. It may release the lease only after scheduler workers are zero, a successful drain reports zero Running and unresolved entries, and its requirements list is empty. Restart-required may remain true at that safe exit boundary; it continues to forbid new work in the current broker. Pending entries have no invoked effects and may remain pending. No separate broker or permanent global closed-state mechanism is introduced.

## Validation

Automated broker crash, duplicate side-effect, permission, exclusion, cancellation, and recovery assertions requested by #14 are deferred to [#32](https://github.com/izyuumi/everything/issues/32). No mocks or test fixtures are committed. Formatting, compilation, strict Clippy, release compilation, and disposable real-tool runtime inspections validated this stage. Actual capability-confined file append operations verified success, exact replay without additional writes, no append on deny/pending approval, approval resumption, definitive no-effect failure, completed semantic failure with retained error output and no repeated writes on replay, unknown after a real write, and unchanged side effects on unknown replay. Two task-scoped concurrent operations overlapped with maximum activity two and no exclusive overlap. Caller-drop supervision completed cleanup with a durable unknown result. Explicit uncertain-effect errors with confirmed cleanup allowed independent work while remaining nonretryable; a generic error instead quarantined the host until owner review. A noncooperative future produced quarantine that survived restart; an explicit owner review cleared cleanup risk without changing the original journal row. Eight near-limit legacy request/result pairs exceeded a fixed eight-row page yet startup inspected all eight through page shrinking, and owner review cleared their cleanup quarantine. An actual child host exited after a durable append while its operation was running; restart recovered one unknown operation and quarantined it, and replay after cleanup review left its one appended line unchanged. None establishes operating-system sandboxing, remote idempotency, or production readiness.

Shutdown checks used a real confined append tool held after its file sync. Drain returned `RecoveryBusy` and left that live operation Running until its supervisor completed. A separately seeded abandoned Running row then became `Unknown(AbandonedAfterDrain)` with incomplete cleanup. Holding a separate SQLite writer transaction and dropping the recovery caller verified that its worker retained admission and exclusion until persistence finished. Exact-digest owner review preserved the original Unknown record, left zero Running and unresolved cleanup entries, and retained the current-process restart gate. After restart, exact replay remained Unknown without another append. The abandoned row was seeded deliberately; this check does not claim an additional real crash or provider inference.
