# Native macOS Settings session

The macOS-only `NativeSettingsWire`, `NativeSettingsSession` and `NativeSettingsLifecycle` consume the current [native Host routes](native-settings-routes.md), [shared metadata](apple-settings-wire.md) and [private owner pipe](native-owner-pipe.md). The macOS target registers them with `NativeSettingsStore`; the actual Settings scene uses it for conventional Host controls and a read-only Host pane alongside General and This Mac notifications. This increment composes existing native APIs without a provider, model, alternate runtime or second CLI client. Supported integrated Apple SDK and runtime validation remain separate gates.

## App-owned composition

`HostModel` constructs one actual OwnerIPCClient and injects that same instance, its applied immutable OwnerConnection and its connection-incarnation UUID into the app-owned observable `NativeSettingsStore`. Connection edits remain drafts in General. Connect synchronously retires the old native owner before assigning the new connection and UUID. The app-owned This Mac SQLite store and stable Settings-window callback identity are not replaced by a Host change.

The pane's Open button calls `store.open()` synchronously. That method constructs one lifecycle for the applied connection, supplies the latest real window/activity state, captures `prepareOpen()` before scheduling one retained task, and calls the actual Open, Describe and host-scoped Get RPCs. Duplicate Open handlers coalesce into the original owner; a failed or lost Open is never automatically repeated. A new explicit Open requires closing the old owner first. Refresh calls Describe and Get on the same original proof and never renews it. No ordinary scene appearance, foreground return, connection change or timer opens a session or replays an effect.

The store publishes only typed Information, registry and snapshot metadata plus sanitized errors. The pane distinguishes saved and effective values, actual setting state, original expiry, unsupported embedding metadata/boundary and unavailable provider state; it does not infer successful inference from configuration. Descriptions are the actual shared Host registry. The [conventional Host controls](apple-native-settings-controls.md) add revision-bound draft/update/confirmation consumers using this same owner. Secure entry, pairing presentation and model requests remain separate. Existing General controls remain separate. Proofs, invitation material and secret values never enter observable state, generic owner requests, files or display formatting.

Each owner has one retained Open/read task and one retained retirement task. Conventional controls additionally retain bounded original effects and one change-hint observer, which retirement joins before lifecycle drain. At most eight current/retired owners exist. Closing Settings or choosing Close invalidates the current lifecycle synchronously, then its owned retirement joins the original store work and lifecycle drain. The current pointer clears before a later explicit Open can choose a new owner. Read callbacks publish only for their exact current owner/connection. A read-only presentation generation marks observations stale across visibility/activity changes, including false/true cycles; it grants no authority. There is no wall-clock freshness comparison, automatic Open or effect replay. Conventional controls may perform bounded read-only refreshes through the existing original session on change hints or foreground return; equal saved revisions may still carry genuinely changed effective-state metadata.

An issue-free drain releases its owner. Any reported failure or unresolved original ID conservatively retains the owner, original actor/proof and report without eviction. DrainReport includes original operation failures as well as cleanup failures, so the UI says that drain reported issues rather than inferring rollback or an unacknowledged Close from an empty operation list. The bounded limit refuses another Open instead of discarding such owners. Reports and the actual idempotent drain are preserved; no cleanup retry or successful close is fabricated. The shared client's four-process admission remains authoritative and can refuse excess work; a refusal is an error, not an acknowledged drain.

Real SettingsWindowObserver callbacks route visibility and application activity to both the local This Mac store and current native owner. The native lifecycle additionally checks the real NSApplication activity. Hiding/inactivity invalidates original gesture generations; window close retires the native owner. Reopening the window preserves local preferences but requires another explicit native Open. Normal app Quit invalidates current/retired native owners before awaiting, joins all original store/lifecycle/presentation/cleanup work and existing local drains, reports sanitized drain issues, and only then shuts down the same CLI client. No close, connection replacement or app drain stops the independent Rust Host.

## Composition and original gestures

Create `NativeSettingsLifecycle(client:connection:connectionKey:)` with the actual existing `OwnerIPCClient`, immutable `OwnerConnection` and actual `HostModel.connectionKey` UUID. The lifecycle exposes its one actor as `session`. It does not construct a client, process supervisor, Host identity or service controller. A different connection incarnation needs a new lifecycle after invalidating the old owner; equal paths or Host IDs do not transfer old work.

The MainActor owner receives synchronous `setSurfaceVisible` and `setApplicationActive` calls from actual window/application observation. The latter also checks `NSApplication.shared.isActive`. Closing or replacing the Settings owner calls `invalidate` synchronously. Visibility and activity transitions change the captured generation, so a false/true cycle cannot admit an older queued gesture. Foreground return does not open or renew a session.

Call `prepareOpen()` synchronously before queuing the explicit Settings-opening task, then call `session.open(admission)`. For a mutation, call `prepare(intent, expiresAt:)` synchronously at the original native gesture, then pass that exact opaque admission into the actor. The closed intent contains only a typed patch, native/device preparation or exact invocation. Its expiry is integer Unix milliseconds. Credential values never enter an intent or ticket.

Admission captures the actual lifecycle object, immutable connection UUID, original generation, wall expiry and one ContinuousClock deadline capped at 300 seconds. Original rejection and cancellation remain attached to the ticket. Re-preparing an identical stage returns that original ticket; changing its intent or expiry conflicts. The lifecycle retains at most 64 original operation identities with one preparation and one execution ticket each, including unused, rejected and terminal identities. An explicit ticket cancellation prevents unstarted work; cancellation of a later duplicate waiter does not cancel already owned work.

## Open and transport ownership

The actor owns one coalesced Open task. A dropped waiter cannot discard a late proof. An uncertain Open is never retried automatically: even an identical outer Open request can create another Host session. An inaccessible response leaves cleanup unavailable and the existing Host session limits apply; this client does not claim successful closure without the proof and an actual Closed response.

After a valid Open, the proof remains private actor state. Public Information contains only Host ID, original expiry and the connection UUID. The monotonic deadline is the earlier of 300 seconds from the original Open start and the remaining original server wall expiry measured at response receipt. Reads, duplicate waiters, foreground return and cleanup never renew either limit.

The private wire implements the read, preparation, original confirmation and cleanup subset of the native routes. The later Rust final-pairing approval/acceptance route from #138 is not yet exposed by this Swift consumer. It encodes the bounded `native_settings` input wrapper directly to Data and consumes the bare result Data from `requestSensitive`. Input is at most 32 KiB; output is at most 2 MiB, with the smaller shared DTO bounds preserved. Every decoded object is closed. The response matcher checks the actual request variant, scope, original operation and revision, reference/attempt where represented, native parent session and closed device/pairing shapes. A LocalOwner binding cannot become a NativeUi operation. Foundation duplicate-key/numeric limitations and Rust-authoritative endpoint policy remain those of the shared metadata contract.

Details must return the exact requested reference, including its confirmation/action variant, identity and expiry, in the corresponding awaiting phase before the actor can adopt the target. Invocation-bearing responses also match the original native attempt whenever the public inspection represents it as InFlight. Applying and Finished inspections do not expose the native request ID; their existing operation/session/binding checks and authoritative Host claim validation remain necessary. The private Rust file-write intent is not a client-visible attempt field, and valid terminal cleanup is not rejected for its absence. These client checks validate response coherence and do not replace Host authorization.

At most four private calls are outstanding, using the same injected client's actual four-process gate. Capacity refuses work rather than creating a waiting queue. Each issued call is owned through actual CLI completion, decoding and cleanup. No private payload goes through OwnerRequest, JSONValue, a request file, environment, argv, model/chat data or a generic response cache. Errors contain only closed sanitized states, never raw buffers, stderr or copied decoder diagnostics.

## Original operations and effects

The actor retains at most 64 original operation records, including terminal records; it never evicts an unresolved identity. Each record holds the exact nonsecret target, original stage/RPC IDs, task outcome, binding/inspection and native observation where applicable. Changed payloads, invocations, references or original bindings conflict. Typed original outcomes are retained for exact replay, and explicit Inspect reads actual Host truth. Repeating a caller method never performs a second credential write, device effect or OS presentation.

`perform(admission)` handles Update, RequestAction, PairDevice, RevokeDevice, ConfirmPatch and ConfirmDevice. `details(operationID:reference:)` can adopt only an actual matching same-native-parent Host target into the bounded original record set. Original targets and shared metadata are display/validation data, not authority. Host caller and current-scope checks remain authoritative.

`submitCredential(admission, secret:)` uses the actual one-shot SubmitCredential route directly, without generic Admit or legacy credential storage. The secret exists only in the owned call, not replay records or comparisons/hashes. A duplicate submission joins the original task and discards the newly supplied value. Credential presence, secure-entry controls, first-enrollment policy and the separate metadata-linking CAS are not implemented by this actor. The coordinator must integrate the actual backend policy and UI before claiming those flows.

`present(admission, presenter:)` accepts only a matching native notification/navigation target. Only a fresh matching Admitted result with the exact native attempt can call the MainActor presenter. Immediately before invocation it checks the original admission and actual application activity again. An Inspected replay never presents. If the original admission became invalid before the callback starts, the actor finalizes Dismissed without invoking an OS effect.

The presenter must retain the actual OS work until its real callback or dismissal completes. The actor then finalizes the original unchanged observation even if the app became inactive meanwhile. A throwing presenter produces uncertainty, without fabricating Dismissed. `retryFinalization(operationID:)` repeats only the already retained observation and native attempt; it does not call the presenter again. Existing local notification adapters still require their genuine same-device preference/revision ticket. This foundation supplies no Host-mediated device-revision bridge or notification success claim.

Inspect, Reconcile, Cancel and pairing cleanup retain the same original proof and operation. They never migrate work to a new session, infer NotFound from a CLI error or treat disconnect/cancellation as rollback. File Applied, PendingApplication, terminal backend application and Finished Unknown retain their distinct shared meanings. The Host's existing worker advances committed backend application.

## Ephemeral pairing

The current private device results retain Existing, Revoked and Pairing distinctions. PairingStatus exposes operation/lifecycle and invitation availability without QR material. Invitation strings stay in at most eight actor-private slots, bounded by their original wall expiry, first-captured monotonic deadline and session deadline. Their original public identity/deadline metadata remains attached to the operation after private bytes are released, so reread or clock movement cannot renew an expired invitation. Non-retained/nondeliverable invitations are retired rather than redisplayed.

`showInvitation(admission, presenter:)` uses the same original ConfirmDevice admission and one owned MainActor callback. Its macOS-only PairingPresentation is ephemeral private display data with redacted descriptions; it is not shared metadata or a saved state value. The presenter receives the exact operation, pairing ID, expiry, fingerprint and invitation. On completion or failure the actor calls CancelPairing and reports its actual lifecycle. A cancellation error remains uncertain; there is no secure-erasure or remote-stop claim.

Invitation secrets are released on retirement, expiry inspection or drain; this is not a guarantee of immediate background memory erasure. Expiry is checked before display. Creating or displaying an invitation is not final approval, grant selection or trust. This source includes only currently merged device variants; later final-approval routes require their actual frozen backend contract and separate native ceremony integration.

## Drain and Root responsibilities

`invalidate()` immediately closes new gesture intake and retains one owned drain task. `await lifecycle.drain()` joins late Open, original operation calls and actual presentation callbacks, then uses the original session to inspect/cancel outstanding work, reconcile unresolved file truth, repeat a retained finalization and cancel pairing. Only an actual matching Closed response acknowledges Host session closure. A failure retains the original proof for truthful cleanup state rather than claiming success.

DrainReport retains sanitized failures and unresolved original operation IDs, including uncertain external presentations. Root must retain the old lifecycle and any real dialog/controller owners until this drain completes, and only then call the shared client's shutdown. A real OS callback or process join can remain pending; no hard cleanup time bound is claimed. No path stops the independent Rust Host. Explicit app/window/connection wiring and presentation dismissal are mandatory; actor deinitialization is not asynchronous shutdown.
