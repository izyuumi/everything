# Device settings primitives

`DeviceEndpoint` provides trusted, synchronous host primitives for the settings device integration. They reuse its existing Store, identity and pending-pairing mutex. They do not create settings callers, native confirmations, grants or a second device store. Callers run them off Tokio workers and retain their actual leased Agent and owned admission through completion, including caller drop. The actual shared settings authority/action service and native routes remain separate work under [#109](https://github.com/izyuumi/everything/issues/109), [#110](https://github.com/izyuumi/everything/issues/110) and [#112](https://github.com/izyuumi/everything/issues/112).

## Redacted device pages

`settings_devices(after, limit, observed_at)` requires an active Host endpoint. It reads at most `limit + 1` rows by ascending canonical DeviceId through the existing devices primary-key index, with a limit of 1–100. The cursor is the exact last returned ID only when another row remains; an unreturned row is not skipped. Pages observe current state independently rather than claiming a transaction across successive requests. `observed_at` comes from the trusted caller's clock; it is not a device revision, CAS precondition or authorization proof.

The projection contains only the actual Host ID, observation time, bounded labels, validated public keys, revocation flags and a `this_device` flag derived from the endpoint's own identity. It includes revoked peers without reauthorizing them. It validates the private registration version, exact canonical row/key identity, existing access shape, 256-byte label bound and timestamp ordering; malformed metadata and genuine storage errors propagate. Private keys, conversation/access grants, pending invitations and worker-purpose trust are absent. Registration text is checked before allocation/deserialization against an 8-KiB bound, which accommodates the existing canonical registration and 64-conversation access ceiling.

The JSON-encoded core page is at most 28 KiB, leaving 4 KiB within the settings contract's 32-KiB page ceiling for its version field and enclosing representation. A page may return fewer rows to respect this bound; stored labels and identities are not truncated. The later service must validate the final [SettingsDevicePage](settings.md) after mapping and enforce the real principal's read scope. This low-level projection is not itself an authenticated model or remote route.

## Exact invitation cancellation

`cancel_pairing(pairing_id, now)` requires an active Host endpoint and removes only that pending invitation under the same mutex used by `approve_pairing`. `Cancelled` means this call removed a still-live pending invitation; subsequent approval cannot consume that entry. `Expired` means this call removed an already-expired pending invitation. `NotPending` means no entry existed: it may have been consumed by approval, cancelled, pruned, lost on restart or never present. It cannot certify that pairing or another effect did not occur.

Cancellation never changes pinned devices, replica completion entries, access grants or the existing fingerprint/approval ceremony. It does not erase displayed QR material, screenshots or data already delivered, and it proves no remote stop. Creating or cancelling an invitation is not final device approval. The existing pairing implementation keeps its ten-minute library ceiling; the settings wrapper must additionally cap a new invitation to the original authenticated action's five-minute maximum expiry and must not renew it on replay. Native action close/expiry must attach or cancel the exact actual pending ID through the shared action lifecycle rather than merely hiding a QR view.
