# Device settings primitives

`DeviceEndpoint` provides trusted, synchronous host primitives for the settings device integration. They reuse its existing Store, identity and pending-pairing mutex. They do not create settings callers, native confirmations, grants or a second device store. Callers run them off Tokio workers and retain their actual leased Agent and owned admission through completion, including caller drop. The shared service and private native routes now wrap these primitives as described below; native presentation and broader acceptance remain work under [#110](https://github.com/izyuumi/everything/issues/110) and [#112](https://github.com/izyuumi/everything/issues/112).

## Redacted device pages

`settings_devices(after, limit, observed_at)` requires an active Host endpoint. It reads at most `limit + 1` rows by ascending canonical DeviceId through the existing devices primary-key index, with a limit of 1–100. The cursor is the exact last returned ID only when another row remains; an unreturned row is not skipped. Pages observe current state independently rather than claiming a transaction across successive requests. `observed_at` comes from the trusted caller's clock; it is not a device revision, CAS precondition or authorization proof.

The projection contains only the actual Host ID, observation time, bounded labels, validated public keys, revocation flags and a `this_device` flag derived from the endpoint's own identity. It includes revoked peers without reauthorizing them. It validates the private registration version, exact canonical row/key identity, existing access shape, 256-byte label bound and timestamp ordering; malformed metadata and genuine storage errors propagate. Private keys, conversation/access grants, pending invitations and worker-purpose trust are absent. Registration text is checked before allocation/deserialization against an 8-KiB bound, which accommodates the existing canonical registration and 64-conversation access ceiling.

The JSON-encoded core page is at most 28 KiB, leaving 4 KiB within the settings contract's 32-KiB page ceiling for its version field and enclosing representation. A page may return fewer rows to respect this bound; stored labels and identities are not truncated. The later service must validate the final [SettingsDevicePage](settings.md) after mapping and enforce the real principal's read scope. This low-level projection is not itself an authenticated model or remote route.

## Exact invitation cancellation

`cancel_pairing(pairing_id, now)` requires an active Host endpoint and removes only that pending invitation under the same mutex used by `approve_pairing`. `Cancelled` means this call removed a still-live pending invitation; subsequent approval cannot consume that entry. `Expired` means this call removed an already-expired pending invitation. `NotPending` means no entry existed: it may have been consumed by approval, cancelled, pruned, lost on restart or never present. It cannot certify that pairing or another effect did not occur.

Cancellation never changes pinned devices, replica completion entries, access grants or the existing fingerprint/approval ceremony. It does not erase displayed QR material, screenshots or data already delivered, and it proves no remote stop. Creating or cancelling an invitation is not final device approval. The existing pairing implementation keeps its ten-minute library ceiling; the settings wrapper must additionally cap a new invitation to the original authenticated action's five-minute maximum expiry and must not renew it on replay. Native action close/expiry must attach or cancel the exact actual pending ID through the shared action lifecycle rather than merely hiding a QR view.

`DeviceEndpoint::revoke_device_exact` is a separate settings-facing Host helper. It validates the complete existing private registration and exact expected public keys, including an already-revoked row, before invoking the existing revocation transaction. Existing pinning makes that registration immutable; this helper duplicates none of the established outbox/inbox/remote-command/sync cleanup. It then reads the exact row again and returns its retained revocation timestamp. Revoked describes the observed transition from the initial read; it does not prove which concurrent request won or that a remote process stopped. AlreadyRevoked preserves the actual original timestamp. SQL, malformed identity, missing row and endpoint failures propagate; self-revocation's final exact row inspection does not falsely require the newly revoked endpoint to remain active. The actual settings caller/effect lease remains a separate service obligation. This helper has formatting/source inspection only at this candidate, without a new compilation/runtime claim.

## Shared settings facade

The settings service retains the exact Host DeviceEndpoint clone supplied during its leased construction. Its device facade cannot accept another endpoint or select another Store. `devices` requires the actual DevicesList caller ceiling and an exact Host scope, validates limit1–100 and the original cursor, then calls the bounded endpoint projection in the whole-core blocking worker. It rechecks live caller authority after the read and validates the final versioned SettingsDevicePage against its32-KiB contract bound. `this_device` denotes the retained Host endpoint's identity in this local projection. Endpoint revocation/storage failures stay visible rather than becoming an empty successful page.

`pair_device` and `revoke_device` accept only their exact typed action variant and reuse the same original prepare_device_action path. A restricted Settings caller must have its matching DevicesPair or DevicesRevoke ceiling. The model sees the existing action handle, expiry and redacted operation state; it never receives an invitation or performs an effect. No caller is created from supplied IDs, and no remote constructor or ordinary conversation grant is added. Future remote wrappers must return host_action_required for these owner-only actions.

`confirm_device_action` is a separate native-only operation using the authenticated original native session and exact retained invocation. An existing native claim returns its actual historical/current inspection without a new effect or renewed grant, including retained cleanup inspection after close/expiry. Changed native request IDs, references or session bindings conflict. Fresh admission requires live caller/original source authority and the unchanged original action deadlines, then consumes actual NativeActionAdmission and NativeHostEffectAdmission. Pairing invokes the [single owned creation/attachment worker](settings-service.md#original-operations-and-native-actions). Revocation executes the exact-key endpoint helper in one blocking worker retaining the complete service core, actual Host mutation guard and Agent. After potentially blocking configuration/endpoint preparation, it checks original source, session cancellation, both expiry bounds and exact target again immediately before the existing endpoint effect. Admission already completed is not rolled back by a later cancellation or expiry.

A successful actual revocation generates a service-owned Completed receipt without a fabricated settings/device revision. Already-revoked targets preserve the existing real revocation state; self-revocation uses the same endpoint cleanup and does not require the endpoint to remain active before recording that known result. Exact replay is checked before endpoint effects, so a disconnected/revoked endpoint cannot turn a retained success into another revocation. Any effect/journal error whose outcome is not established records conservative Unknown where possible and returns the original operation identity with structured repair diagnostics; no retry, changed target or generic UI success is authorized.

The closed NativeDeviceActionResult is output metadata only: Existing inspection, Pairing creation or Revoked inspection. Pairing response DTOs support strict typed wire decoding and share only the existing private zeroizing SecretTransfer allocation when cloned. They are never accepted as effect-completion input or opaque admissions. Invitation-bearing results/get/cancel remain in the authenticated native-only sensitive pipe family; transport and client buffers do not provide universal zero-copy or secure erasure. The actual [native routes](native-settings-routes.md) now register this facade. Private UI presentation and grant selection remain separate integration work; the native-only approval backend below has its own verification boundary.

The exact `dadceaa7` integrated source passed the Rust checks/builds and actual list, invitation creation/cancellation and confirmation replay observations recorded in [Settings validation](../development/settings-validation.md), with independent retained-evidence review. That fresh list was empty and invitation creation left it unchanged; it does not prove positive paired-peer pagination or final pairing. Exact-peer revocation, expiry/races, full native ceremony/UI and current combined required CI retain separate gates. No device approval or trust widening is inferred from the model-safe handle or native invitation receipt.

Apple's existing public-key type is now a separate [DevicePublicKeys.swift](../../apps/Apple/Shared/Crypto/DevicePublicKeys.swift) leaf. Its validated initializer, wire conversion, canonical bytes, fingerprint and signature verification are byte-identical to the prior definition. The private identity and envelope implementations remain in DeviceIdentity.swift. The leaf uses CryptoKit and the existing Foundation/CoreFoundation WireValue helpers; it creates no private key, network identity or device preference identity. The project registers the leaf in both native targets and the existing WireValue helpers plus the system CryptoKit framework in macOS. It adds no private identity, Keychain or relay source to macOS. Supported macOS/iOS build/analyze remains a separate integration gate. Grammar parsing and exact extraction checks do not establish native Settings composition, pairing behavior or cryptographic interoperability.

## Native final approval backend

The private NativeSettings family adds ApprovePairing and PairingApproval status. This is a local native-owner ceremony, not another Settings tool or model action. ApprovePairing accepts the actual Host-minted proof, original invitation-creation operation, a distinct approval operation/native request identity, the existing signed PairingRequest and the exact label, public responder fingerprint and DeviceAccess. A strict private grant DTO uses the existing scope/ids wire shape and converts to actual DeviceAccess validation; unknown nested grant fields are rejected. Its public metadata cannot create a caller, grant or receipt. Existing seven model tool names and Pair/Revoke request variants are unchanged.

The service requires the real retained original invitation lease and native session, original wall and monotonic bounds and exact creation metadata. It retains one actual Host mutation guard continuously across the absent-marker check, journal admission, real DeviceEndpoint.approve_pairing and first receipt. It factors the established native claim/effect checks rather than admitting a second action store. The complete service core, original session, invitation lease and owned guard remain in the blocking worker through caller drop; Agent/StateLease outlive those resources. Close/cancel latches cancellation and calls the actual endpoint outside the small state locks. An already-started pin is not rolled back by a late close.

An armed private approval guard also covers unwinding and abnormal return after ceremony reservation. It owns the original lease and actual Host mutation guard, closes invitation/acceptance delivery and retires that exact pending invitation under the endpoint mutex before releasing mutation. The retirement helper is Host-only and performs no Store, clock, active-endpoint or cryptographic work; absence does not prove no pin. A poisoned endpoint pending mutex stays an explicit failure and also blocks legacy approval. Standard unwind capture remains inside the same owned blocking worker, preserves the fixed Worker/original-operation diagnosis, and surfaces bounded cleanup/repair errors instead of discarding Drop failures. It never copies the panic payload into a response. Fatal process abort is not an in-process unwind guarantee.

The existing pairing protocol still verifies the invitation secret proof, responder signature and exact invitation identity/expiry. Approval is not a fingerprint-only bypass. The raw request/proof/signature and actual acceptance use redacted shared wrappers and private pipe/RAM buffers. They never enter operation targets, journal updates, hints, chat, relay queues or generic owner requests. A canonical digest of the signed request is non-authorizing replay identity; it contains no invitation secret, native session proof or credential value/hash. Transport/parser buffers and existing protocol temporaries do not provide universal zero-copy or secure erasure.

A distinct nonsecret PairingApproval target records original creation/pairing IDs, full responder keys, request digest, exact fingerprint/label/access and original invitation expiry. The creation Completed receipt remains immutable and refers only to invitation creation. The approval uses one existing native request claim and its original deadlines; changed request contents, grants, labels, IDs or session conflict. Existing peer keys/access are immutable and revocation stays sticky. An already-matching peer keeps its actual older label and pin time; the result reports that retained label rather than claiming relabeling.

DeviceEndpoint.pairing_approval_state reads the exact pairing_uses marker joined to the full bounded registration in one coherent Store read. It validates canonical identities, version, complete keys/access, label and actual timestamps before matching the expected original target. No peer row alone, public device page or NotPending cancellation result proves this operation completed. Missing marker returns absence; malformed/dangling metadata, mismatched pins and real errors remain explicit. Historical revoked pins can be inspected without reauthorizing the endpoint, and the independent pairing timestamp has no invented ordering against a preexisting pin. The read never pins a peer or inserts a marker.

Terminal Unknown and failed workflows immediately close the original private delivery cell rather than leaving a retained invitation view. Actual pending retirement runs outside the small state mutex; failed cleanup remains inspectable and retains ownership until confirmed. A Completed response requires coherent Committed pin metadata, and startup validates the original operation against this actual Host scope before settlement.

Known exact Host-pin evidence settles the approval's first Completed receipt, including ambiguous endpoint completion. A known absent marker after a returned failure can retain an original failed receipt; inconclusive evidence remains Unknown with original-ID diagnostics. Startup and exact approval replay inspect original evidence before the generic InFlight-to-Unknown fallback. A previously Finished Unknown is never rewritten. No settings/device revision is fabricated. Status reads do not reapply approval; explicit original approval replay can finish only that existing admission from durable evidence, never create another grant or receipt.

The actual returned acceptance is cached only in the original ceremony slot. Before storing or cloning it, the worker checks the exact original cell/operation/session, cancellation and both original clocks; late success can establish historical Host completion while discarding acceptance. Peer or local-endpoint revocation, close and expiry suppress delivery. At most one approval/cache belongs to each of the existing eight invitation slots; original expiry is never renewed and capacity is explicit. After consumption, creation inspection reports NoLongerPending without another invitation. Cancel may remove private response material; it never rewrites the creation/approval receipt or revokes an established peer.

Same-session exact replay can return the identical cached acceptance without signing or pinning again. After restart, the original session, invitation and acceptance are unavailable; the authenticated owner can inspect the durable historical Host receipt, but a new session cannot impersonate the old one or obtain a regenerated acceptance. The result describes Host pinning and private acceptance availability separately from the replica's actual finish. A fresh explicit ceremony is required when acceptance was lost; no automatic trust/regrant or new cryptography is introduced.

This backend candidate has source/format/bounds review only until its own required checks and disposable native-pipe observations are recorded. Apple private serializers, final approval UI and actual selected-grant ceremony remain follow-on integration; the generic macOS file-transfer allowlist must reject approve_pairing before that UI is composed. Existing earlier runtime observations do not validate this addition. No tests or source comments were added; automated acceptance remains #32.
