# Local preference-store identity

`DevicePreferenceStore.local(directory:)` opens the existing device preference database without requiring an external device identity. It reads or creates the preference-only installation UUID in the same `preferences.device` singleton that owns its revision and values. No Host, network, cryptographic identity, UserDefaults value, second database or separate identity table is involved. This is an internal store factory; native macOS app composition and settings controls do not call it yet.

The factory uses one SQLite connection and a `BEGIN IMMEDIATE` transaction. It rereads the schema version after acquiring that transaction, so concurrent creators observe the winning committed identity rather than using an earlier version observation or competing UUID. A genuinely uninitialized version0 database with no preference row or request history receives one Foundation UUID, default-off completion/attention values and revision1 together. A compatible partial schema bootstrap can finish only while those tables remain empty.

A version1 store must contain one valid preference row with a canonical lowercase nonzero UUID, positive integer revision and valid Boolean values. The factory adopts that identity and preserves the revision and exact request receipts. A missing row, malformed/noncanonical/zero identity, inconsistent snapshot, orphaned uninitialized request history or unsupported schema fails explicitly. It never regenerates identity, deletes data, resets revision or relabels historical requests to recover from an error.

The existing `init(directory:deviceID:)` remains the strict externally bound path: it requires a nonzero supplied identity and rejects a stored different identity. The iOS composition must continue using its actual replica identity through that path. The local factory does not weaken that check or infer an identity from a caller Boolean. Both paths share the existing private database setup, transaction behavior, CAS and exact request replay. Rollback failure poisons the connection; request/page limits, private file modes and iOS protection remain in effect.

The installation UUID identifies only this authoritative local preference store. It is not a physical Mac identifier, Host ID, paired device identity, native UI session proof, peer grant or authorization for a remote action. A future macOS composition can keep one app-owned store in its private Application Support directory, independently of the selected Rust executable or Host state path, then use its actual snapshot deviceID for local foreground preference/notification actions. It must initialize off the UI executor, share the resulting actor across scenes and report storage failures without deleting or reseeding state. Restarting or changing Host connection does not require a new preference identity. Deleting the authoritative app data can create a new preference installation.

This factory supplies no Host device-revision adapter and does not make Host-mediated notification actions available. OS authorization remains observed separately from completion/attention preferences. Actual settings scenes, notification preference migration and private native-session integration remain separate work under [#110](https://github.com/izyuumi/everything/issues/110), [#114](https://github.com/izyuumi/everything/issues/114) and [#117](https://github.com/izyuumi/everything/issues/117).

Source parsing and review do not establish supported Apple SDK or SQLite/runtime behavior. Fresh macOS/iOS build/analyze and disposable first-open/reopen/concurrent-initialization/corruption/replay observations remain required. No automated tests, fixtures or source comments were added; deferred coverage remains [#32](https://github.com/izyuumi/everything/issues/32). See [native action foundations](../architecture/native-settings-actions.md) and [typed settings scopes](settings.md).
