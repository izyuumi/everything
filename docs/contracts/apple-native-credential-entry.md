# Native credential entry and reference linking

The macOS Models and Tool Selection sections use a native SecureField sheet backed by the same app-owned `NativeSettingsStore`, native Session and owner client as [Host controls](apple-native-settings-controls.md). The source uses existing [private native credential submission](native-credential-actions.md) and the [owner metadata helper](apple-owner-settings-metadata.md). It creates no second client, model dependency, proof store or credential backend. Target registration and supported-platform validation are integration gates; source parsing does not establish a successful key entry or OS-vault operation.

## Exact original binding

The closed `NativeCredentialChoice` accepts the actual saved model's initial storage choice, an exact configured Model binding or the actual configured System One purpose. `beginCredentialEntry` requires fresh native/owner metadata at the same real revision, an unchanged configuration draft, foreground Settings and capacity. It captures the current Owner, immutable connection/epoch, Host snapshot/registry, full private owner document, exact purpose and one original wall/monotonic lifetime synchronously before starting work.

Initial Model entry uses the saved provider/Official-or-Loopback endpoint only when that tuple has no configured reference. Storage is chosen before the original Add gesture; replacement locks its existing Session/Native choice. System One uses its configured endpoint and reference even when disabled, and always uses native storage. Entry never selects or enables a provider, changes a model, normalizes a legacy endpoint in Swift or substitutes the TypeSafe preset. A configuration error requires its separate protected settings operation.

A fresh initial UUID is generated once. It is not authority or a presence probe. Actual Rust `credential_binding` rechecks namespace collisions across Model/System One/MCP references, selected/configured binding, real file/revision, native source and original claim immediately before storage. The metadata helper separately rejects a collision before linking. Failure does not fall back to another reference, storage type or recipient.

The original RequestAction admission is captured synchronously before its owned task. Only genuine same-Session Details with the exact original target, reference variant/UUID/expiry, binding and authenticated NativeUI parent/origin can create the opaque `CredentialPresentation`. This source does not adopt settings-agent cards or render privileged controls from chat text. The future assistant bridge is separate work.

## Field and one-shot transfer

`NativeCredentialField` is a MainActor UI-only String owner. The sheet holds it strongly; the Store keeps only a weak typed reference for synchronous clearing when the window hides/closes, app foreground is lost, or its owner is retired/replaced. The field is absent from all operation, metadata, receipt, intent, replay and candidate records. An attach to an old presentation clears the field instead of adopting it. A UI timeline checks original expiry while the sheet is visible; Submit independently enforces actual current foreground and original bounds.

The Store's opaque presentation is object-bound to the retained original Owner and native action. Its original surface generation and deadline cannot adopt a false-to-true foreground cycle. A late Details response is cancelled or remains visibly unconfirmed, not displayed on a later activation. The actual existing lifecycle admission and private Host proof remain the authorization boundary; UI eligibility is not another grant.

The Store credential Button handler is synchronous. It takes and clears the visible field, validates the literal printable/non-whitespace value against the existing 8192-byte UTF-8 limit, creates exactly one invocation/native attempt and `.submitCredential` admission, then retains one worker. The worker calls the existing `NativeSettingsSession.submitCredential(admission, secret:)` directly. It does not call generic Admit first. The secret appears only in the ephemeral UI/call/task and existing typed private wire/OS buffers. It is never put in an Equatable intent, hash, generic JSONValue/OwnerRequest, file, argv/environment, pendingAction, model/chat payload, replay cache or error message.

SecureField masks display and binds a normal String updated on each edit. Clearing visible state cannot guarantee erasure of Swift copy-on-write, serialization or OS buffers. No reveal/copy/pasteboard persistence helper or custom cryptography is introduced. Current [official Apple behavior](https://developer.apple.com/documentation/swiftui/securefield) was read during implementation; supported Apple runtime behavior remains a separate acceptance gate.

Dismissal before submission clears/retire the presentation and cancels only its original Host operation. It reports actual cancellation truth, not an invented receipt. After submission, closing the sheet/window does not discard or repeat the admitted task; the original worker and Session cleanup are joined. An error or Unknown is not a claim that a key was not written or was rolled back. No secret-based Retry, deletion, unlink or presence-query control is exposed.

## Storage and metadata are separate outcomes

Only a genuine matching Finished Completed inspection establishes the original storage result. Configured replacement ends there and performs no metadata CAS. Initial storage is historical Completed storage without an observed link. It does not establish present-day secret availability; Host Session memory may be lost on restart, and native storage behavior requires actual OS observation.

A separate Link button captures the same original Owner, current genuine foreground surface generation, original expiry/monotonic deadline, full original document at R and a distinct owner CAS ID before Task. `OwnerSettingsDocument.credentialMetadataPlan` consumes retained genuine Details and Completed inspection. Its native session ID comes from that actual authenticated binding, not a caller-supplied UUID. The immutable candidate preserves every unrelated field and changes only the exact Model entry or System One reference. Its candidate revision remains R; the backend writes R+1.

The owned worker reinspects the original native Completed result, preserving its exact binding/receipt, and performs a live native snapshot preflight at original Host/R. Immediately before invoking the same owner's `client.request` it checks the exact owner, original capture, actual NSApplication activity and surface again. It then submits the already prepared nonsecret owner request through the existing reviewed file route. No secret enters that request.

This is a separate LocalOwner CAS authenticated by the actual LocalCall. The native read is a preflight observation, not an atomic native-session grant around the later file write. Rust's real expected-revision/file/source guards remain authoritative. A response loss never changes candidate, owner ID, revision or recipient and never stores another key. There is no automatic rebase, resubmission, second-key repair or rollback.

Only the actual helper-validated SettingsReceipt can establish a known file link. Applied file, pending/restart/failed/unavailable application and current configuration remain distinct. A receipt without a current snapshot can still establish the original known file effect; a newer document cannot masquerade as that original readback. Historical storage/linking does not prove current reference configuration, credential presence or successful inference.

Inspect and explicit Reconcile use the original `OwnerSettingsPreparedLink` requests, original immutable connection/client and LocalOwner identity. They do not use native Inspect to adopt an owner CAS. Unknown/Applying and transport-uncertain metadata block fresh mutations in that owner. Terminal phases remain immutable except exactly the original unresolved file Unknown becoming a validated Finished result with the same write identity and actual resolution. No wall timestamp is treated as causal order. Inspection/reconciliation never rewrites settings, restarts the vault effect or invents application success.

## Bounded ownership and retention

Native originals plus metadata CAS capacity share the existing 64-per-owner limit, including unused, terminal and never-submitted candidates. Initial entry reserves one future link slot before even the RequestAction; Link consumes that same reservation instead of competing for capacity after a key was stored. A cancelled initial ceremony retains its bounded reservation until owner retirement. Configured replacement needs one native identity and no link slot. All native/details/submission/metadata and late metadata recovery workers use that Owner's same four-worker registry and actual client/Session RPC bounds; there is no waiting queue. One credential presentation is eligible at a time.

Window/connection retirement invalidates the old native lifecycle synchronously, clears its weak field and stops new effects before replacing any owner. It captures and joins read, observer and every effect task, then joins the same original Session drain. Metadata Unknown IDs and sanitized cleanup errors are merged separately into the client cleanup report, because Session drain alone knows only native operations. A late LocalOwner recovery is chained into that original retirement. Permanent Store drain closes intake synchronously, then also joins all retained late workers before Root shuts down the same shared client. No path stops the independent Host or publishes an old callback into another owner.

`Cleanup.unlinkedCredentialOperationIDs` is separate historical metadata, not a fabricated Unknown/failure. A known initial storage Completed without an observed successful original metadata link retains its exact receipt, purpose/reference and Host ID after window close under the same eight-owner bound. Retired owners cannot submit another key or link candidate; an already attempted original owner CAS remains inspectable/reconcilable through its original handle/connection. No automatic eviction, key deletion or rollback hides an unlinked result. Reaching eight retained owners visibly refuses a new Open. These in-memory histories do not promise durable UI history or current key presence.

The native credential history displays these original Host/reference/operation identities, including when no new Host draft is available. The coordinator must integrate the additive read-only cleanup label for the new typed field alongside source registration; it must not label historical unlinked storage as current presence or native Unknown.

## Validation boundary

The increment is source-only until reviewed and integrated with the actual supported targets. Whole Swift grammar, scoped diff/doc links and genuine dependency checks are useful static evidence; they do not establish SwiftUI/Keychain runtime, no-secret disk observation, actual grant/denial, wrong-session rejection, native cancellation or cross-store conflict/restart recovery. Those require supported-platform observations with disposable data. No new automated tests, fixtures or source comments are added. Deferred automation remains [#32](https://github.com/izyuumi/everything/issues/32); implementation and manual acceptance remain [#110](https://github.com/izyuumi/everything/issues/110) and [#114](https://github.com/izyuumi/everything/issues/114).
