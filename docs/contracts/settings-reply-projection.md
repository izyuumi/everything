# Held paired Settings reply projection

Issue [#116](https://github.com/izyuumi/everything/issues/116) now has a current-gated projection source boundary in the same Settings ServiceCore. It uses the actual shared [reply-build permit](settings-command-receive.md), [paired Authority](paired-settings-authority.md), [operation history](paired-settings-operations.md) and reviewed closed Original/Bind DATA. It is held and uncompiled. No accepted transport, registered build worker, seal, atomic transfer, private send, client adoption or successful delivery is enabled by this source slice.

## One private Core boundary

The cohesive `service/paired/replies.rs` child owns both projections and the separate Bind current-read qualification. Existing Original qualification, command precommit, effect, native factories and history readers are unchanged. There is no callback projector, raw facts getter, new Source/Caller/map/runtime or permission from a row/UUID. `SettingsReplyProjectionError` retains the actual typed authority, permit, Source, DATA or provenance-encoding cause behind fixed redacted Display/Debug; it is never serialized as a diagnostic.

Both projection entries first validate the actual noncloneable ReplyBuildPermit against the genuine Fresh, Historical or Bind owner. That check proves actual receive-joined memory association and the one claimed build slot. It does not prove current Settings authority. The projection then fully rechecks the actual same-Core read qualification on the caller's supplied Main transaction and real borrowed Host mutex guard before constructing DATA. Main provenance and a real registered blocking worker remain the caller's integration obligations; no connection, transaction, await or durable SQL write is created here.

Only the reviewed DATA constructors and checked encoders produce the returned Zeroizing byte vector. Host ID, original authenticated encrypted envelope MessageId, inner request/binding ID and generation come from the genuine Source/parent. No UI-provided correlation or operation UUID creates them. The byte vector is private output, not a successful send or service receipt by itself.
