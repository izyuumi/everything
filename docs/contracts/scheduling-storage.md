# Scheduling storage

Issue [#50](https://github.com/izyuumi/everything/issues/50) supplies `scheduling::ScheduleRepository`, typed definitions, and `0006_scheduled_jobs.sql`. It depends on the actual conversation configuration from #10, device transport schema 4, and the private checkpoint journal in schema 5. The repository uses the existing `Store` connection and mutex. It creates no database, service, timer, task worker, or model connection. All calls are synchronous and belong on a bounded blocking worker when called from async code. Only trusted crate modules can obtain the internal connection; no public connection or transaction API is introduced.

## Definitions and authority

`ScheduleDefinition` has explicit schema version 1, `ScheduleSpec`, `ScheduledTarget`, and `RunPolicies`. Unsupported versions fail validation on writes and reads. IDs are typed non-nil UUIDs: `ScheduledJobId` identifies a job and `OccurrenceId` identifies one durable occurrence. They serialize as UUID strings. All times are typed Unix milliseconds and scheduling rejects values after year 9999. Once and interval times represent UTC instants; cron carries its explicit IANA timezone.

The schedule variants are:

- `Once { at }`, with a next run equal to that instant or no next run after exhaustion.
- `Interval { anchor, every_ms }`, anchored to a UTC timeline. The interval is 1000–31622400000 milliseconds, or one second through 366 days. A supplied next run must be at or after the anchor and an exact interval multiple from it.
- `Cron { expression, time_zone }`. Expressions are 1–512 printable ASCII bytes parsed by pinned Croner 4.0.1. The native grammar accepts five fields or six with leading seconds; omitted seconds mean zero. Year fields are disabled. Numeric weekdays follow POSIX Sunday 0 or 7 through Saturday 6. Day-of-month and day-of-week use the library's OR semantics. The library's supported aliases and extensions remain library-defined; the application does not translate a different grammar. Timezones are parsed by `chrono-tz` from its IANA database, with a 128-byte input bound.

`parse_cron` and `parse_time_zone` return established library types for the future engine. This repository validates syntax and supplied interval/once instants; it does not calculate future occurrences, enumerate missed runs, or apply DST gap/fold policy. Cron next-run membership is deliberately not inferred from a UTC field comparison. Issue #51 owns calendar calculation and an explicit DST decision, because a library can produce a valid gap-adjusted instant that does not directly match the nominal wall-clock expression.

`ScheduledTarget` captures the exact validated `agent::ConversationConfig`, task instruction, physical workspace path, permission ceiling, budgets, and result delivery choice. The captured native provider kind, model, endpoint, system instructions, output limit, and sampling configuration do not follow later host profile or endpoint changes. Credentials are excluded from that configuration and must be resolved by the host for the captured destination at execution time. Task instructions require 1–32768 bytes without NUL. A workspace is absolute UTF-8, at most 4096 bytes, without parent traversal. Model configuration has its existing independent validation.

`create` and `edit` require a trusted `ExecutionAuthority`; `claim_manual` checks it again. The target workspace must equal the creator's canonical workspace, its mode cannot increase the creator's mode, and `restrict_tools` verifies that the explicit allowlist does not widen inherited authority. Optional conversation delivery must match the creator authority's conversation, preventing a restricted agent from selecting another conversation as an injection destination. An empty allowlist permits no tools. Allowlist entries follow native tool-name syntax, with at most 128 entries of 128 bytes each. Defaults are read-only authority and no tools. These checks capture an authority ceiling. They do not grant operation approvals, sandbox shell execution, prove authorization to disclose to a provider, or replace live broker permission checks. CLI/tool owners must authorize access to jobs before invoking repository methods; repository read/delete/enable methods are trusted host operations.

Run budgets are bounded: 1–64 model requests, 0–1024 tool calls, 1–262144 total output tokens, and 1000–86400000 milliseconds of execution time. Each configured model response limit must fit the total output budget. Defaults are 12 requests, zero tool calls, 16384 output tokens, and ten minutes. These values are stored ceilings; enforcement belongs to #52 and the native runtime. `ResultDelivery::Isolated` is the default. Optional conversation delivery stores a typed conversation ID which must already exist when the job is created or edited; it does not reuse that conversation as the agent's execution history.

`RunPolicies` captures defaults and bounds for later execution: overlap skips by default, or allows 1–16 simultaneous active runs; missed runs skip by default, or select the latest occurrence within 1000–604800000 milliseconds; retries permit 1–8 total attempts, initial backoff of 1000–3600000 milliseconds, and maximum backoff from that initial value through 86400000 milliseconds. The repository enforces overlap admission atomically. It does not perform catch-up, retry/backoff, timeout, or budget execution.

## Job lifecycle and reads

`create(NewScheduledJob, authority, now)` creates generation 1 and revision 1. IDs cannot be reused, including after deletion. Names require 1–256 bytes without control characters. Enabled creation and edits require an explicit next run. Every mutation compares the expected current revision, increments it without signed-integer overflow, and rejects timestamps before the previous update. `edit(ScheduledJobEdit, authority, now)` changes the full desired job definition and scheduling state. A changed definition advances its independent generation; renaming, enabling, disabling, or advancing a due time leaves the generation unchanged. A run retains its original generation and complete definition snapshot.

`set_enabled(id, revision, enabled, next_run_at, now)` updates scheduling state without changing the target. Enabling requires a next run; disabling may retain or clear one. `delete(id, revision, now)` is a soft deletion which disables the job and clears its next run. Deleted jobs cannot be edited or newly claimed, and their IDs/history remain reserved. Disable, edit, and delete do not silently cancel runs already claimed. Native execution cancellation requires the later execution layer's explicit operation.

`job(id)` includes deleted records. `jobs(JobFilter, limit)` uses ascending ID pagination, optional enabled filtering, and excludes deleted jobs by default. `due(now, limit)` returns enabled, undeleted records with a non-null next instant at or before now, ordered by instant then ID. `earliest_due()` returns the minimum such instant, regardless of whether it is already overdue. Due lookups are advisory; dispatch requires the claim transaction below. The partial due index excludes disabled, deleted, and exhausted jobs.

Every page requires 1–256 rows and has a 4 MiB aggregate serialized budget. Budget exhaustion returns no partial page; request fewer rows. Job definitions and immutable run snapshots are each at most 128 KiB of JSON. Every stored target and result remains private local plaintext and can contain sensitive instructions or outputs. Nothing in this repository publishes events or sends content to a relay.

## Claims, uniqueness, and restart

`claim_due(DueClaim, now)` verifies the current job revision, enabled/undeleted state, exact expected due instant, and due time at or before now in one immediate transaction. It validates the supplied next run, which must move strictly forward or exhaust the schedule. A one-time claim must exhaust it. The caller owns occurrence calculation; the repository never silently guesses a new due time.

The transaction creates the occurrence with a complete immutable definition snapshot, generation, scheduled instant, trigger, claim time, and unique reserved `initial_task_id`, then advances the job's next/last-run timestamps and revision. `last_run_at` is the time of occurrence admission or overlap skipping; actual task start is recorded separately on the run. Occurrence UUIDs are globally unique. Scheduled occurrences additionally have a unique `(job_id, generation, scheduled_for)` key. Editing a definition deliberately creates a new generation; retries must remain within the original occurrence, rather than obtaining a new occurrence UUID or changing its generation to bypass uniqueness.

`claim_manual(ManualClaim, authority, now)` permits an explicit run of an undeleted job, including a disabled job, after checking the target against the caller's trusted authority. It records the manual trigger and globally unique manual command ID, updates the job's last-run time/revision, and leaves the automatic next run intact. Manual occurrence times are their original claim time. Reusing a manual command ID under a different occurrence is a conflict.

An exact retry with the same occurrence ID and typed claim returns its existing run with `ClaimOutcome.replayed = true` before checking a now-stale job revision. The identity digest is SHA-256 over `everything.schedule.due-claim.v1` or `everything.schedule.manual-claim.v1`, one NUL byte, and the serialized typed claim. Current wall time is excluded so a later retry can recover the original outcome. Changing any claim field under the same ID is a conflict. Replays never advance the schedule or replace the snapshot/task ID.

Overlap admission counts all claimed/running runs of that job across every generation and manual trigger. When the configured limit is reached, the occurrence is durably `skipped` with reason `overlap`, and an automatic claim still advances the due time. No native task is created for a skipped occurrence. Capacity, validation, revision, or uniqueness failure rolls back the complete transaction, including next/last times. Callers must surface capacity exhaustion as blocked scheduling and await owner intervention; repeatedly scanning it does not make progress.

`unfinished_runs(after_id, limit)` exposes all claimed/running records for restart reconciliation with stable ID pagination. A process can crash after committing a claim and before native dispatch. The later dispatcher must recover and use the same reserved initial task ID with native durable idempotent acceptance. A claimed record is not evidence that a native task was accepted. Running or unknown outcomes never authorize creating a replacement occurrence or replaying an external effect. This schema reserves the first task identity; #52 must represent additional retry attempts durably under that occurrence before implementing them.

## Run lifecycle and limits

`run(id)` reads an occurrence; `history(job_id, before_cursor, limit)` pages by claim time and occurrence ID in descending order. `start_run(id, expected_revision, now)` requires `claimed` state and an existing native task with the reserved identity, then records `running`, start time, and a new revision. Native task creation/acceptance is outside this transaction and must be idempotent by the reserved identity. An existing task row alone is not proof that external execution completed.

`finish_run(id, expected_revision, outcome, now)` records one typed terminal outcome and completion time. Outcomes are `succeeded`, `failed` with a bounded code/message, `cancelled`, `skipped` with reason, or `unknown`. Success requires running state; overlap/missed skipping is only valid before starting. Failure, cancellation, and unknown can finish a claimed or running record. Terminal records cannot be reopened or rewritten. Unknown requires owner reconciliation and is not an automatic retry signal. Summaries/reasons/messages are at most 16384 bytes; encoded outcomes are at most 32768 bytes. The schema protects occurrence identity, claim digest, original timing, task ID, and definition snapshot from updates.

SQLite trigger-maintained usage counters bound retained jobs to 4096 and 64 MiB of definitions, and retained runs to 100000 and 256 MiB of snapshots/outcomes. Claims reserve 32768 bytes for each active run's eventual outcome, so completion remains possible after other claims fill the history budget. Soft-deleted jobs and terminal runs still count. There is no pruning or ID reuse API at this stage. A future retention design must preserve occurrence and manual-command deduplication invariants. These caps intentionally fail closed rather than silently discarding history.

## Validation status

The parser dependency was compiled and run in a disposable Rust 1.85.1 program. Actual observations included five/six-field parsing, POSIX Sunday aliases and day-of-month/day-of-week OR behavior, invalid minute/year rejection, and IANA New York conversion. Croner 4.0.1 returned a forward UTC instant during a fold where 3.0.1 returned a past candidate. Its fixed-time spring-gap behavior still snaps to the end of the gap, which confirms that #51 must own its explicit DST policy.

Formatting, workspace all-target checking, and strict Clippy passed with temporary root module/dependency wiring and the frozen internal connection visibility. Release compilation and real migration/CRUD/claim/restart inspection remain pending integration with the actual schema-5 prerequisite. No timer, scheduled task execution, client status delivery, or automatic recovery has been verified by this storage component. Automated migration, concurrency, occurrence, DST, and crash-recovery coverage is deferred to [#32](https://github.com/izyuumi/everything/issues/32). No tests or fixtures are introduced.
