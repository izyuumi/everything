# External task atomic storage

This is a crate-private transaction primitive for the guarded external-result integration. It authenticates no worker, peer, source packet, result, artifact or approval. The Agent/Scheduler caller must supply the real opaque result capability, same-Store identity, native admission, write gate and retained state lease before using it. No public API or arbitrary SQL callback is added.

`ExternalTaskStateUpdate` is Serialize-only and contains the complete `expected: TaskRow`, `next_state: TaskState`, new `checkpoint: Value` and `updated_at: i64`. `Store::append_with_external_task(&AppendRequest, &ConversationStateUpdate, &ExternalTaskStateUpdate) -> StorageResult<AppendOutcome>` reuses the actual append implementation. `Store::shares_connection(&Store)` compares the two underlying `Arc<Mutex<Connection>>` handles with `Arc::ptr_eq`; different connections to the same path are not equivalent.

## Admission and atomicity

The expected task must be a root task in Waiting, belong to the append conversation and have valid bounded identifiers and monotonic nonnegative timestamps. Its input and old checkpoint, and the new task checkpoint, each retain the existing 1 MiB JSON limit. The conversation checkpoint retains its existing 8 MiB limit; append count, event/request bounds and command namespace checks remain unchanged. The external task update timestamp cannot precede its expected timestamp, and every appended event must use that exact new timestamp. The guarded Agent caller supplies one attributed external report; storage does not infer or approve that event's meaning.

A fresh call uses the existing connection and one immediate transaction. It checks the ordinary conversation head and private state revision. After tentative event/checkpoint writes, it bounds and loads the actual task, compares every typed field with the expected row, and performs a strict SQL CAS. Only task state, checkpoint and update time can change. ID, conversation, parent, input and creation time remain immutable. The allowed external next states are Waiting, Completed, Failed and Cancelled. Ordinary `TaskState::can_transition_to` is unchanged, so the general Waiting-to-Completed edge remains forbidden.

Any local `tool_calls` row for the task ID or dedicated conversation rejects fresh admission, including terminal, unassociated and unknown rows. The task and tool exclusion are checked again after inserting the command receipt. A constraint, failed CAS, trigger failure or failed final invariant check rolls back events, conversation head/checkpoint, task/checkpoint and command receipt together. Other connections cannot interleave writes inside the immediate transaction. Existing task JSON encodings originate from the Store's canonical serializer; the SQL CAS also compares those exact expected encodings.

The new task checkpoint is the caller's bounded durable result receipt. Storage neither constructs a native assistant message nor starts or resumes a model, tool or scheduler loop. A Waiting result does not imply a known outcome or permission to retry. Result verification, cancellation/Unknown policy, once-charged budgets, report attribution and slot release remain responsibilities of the guarded caller.

## Identity and replay

Ordinary append-with-state identity is unchanged: SHA-256 over `everything.conversation.state-update.v1`, NUL, and the typed conversation update's JSON. Ordinary append still stores no state digest. No external descriptor follows either existing path.

An external append uses SHA-256 over `everything.conversation.external-task-update.v1`, NUL, and the JSON tuple `(conversation_update, external_task_update)`. The complete original expected task, next state, new task checkpoint and timestamp are included. The command row also retains the unchanged original serialized append request. Different append kinds or any changed event, source/receipt hash, task field or conversation update conflict under the same command ID.

Exact committed replay is recognized before checking the current conversation sequence/revision, task row or tool absence. It returns the original event rows without changing newer conversation or task state. A later legitimate tool row therefore cannot invalidate the historical receipt or cause the old checkpoint to be restored. Eventless private-checkpoint command IDs retain their existing mutually exclusive namespace.

## Validation and integration limits

The historical isolated prerequisite passed formatting and compilation while its two crate-private methods still awaited the actual Agent caller; no production warning suppression or standalone strict Clippy success was claimed. The actual Agent/Scheduler and Worker/Host callers are now composed. Their six normal-package Rust gates and qualified production Host credential-rejection walkthrough are recorded in [worker validation](../development/worker.md#combined-host-validation-checkpoint). This storage primitive supplies no worker authentication itself.

Disposable transaction and failure observations are recorded with the implementation handoff. No automated tests, migration, production shim or new dependency is introduced. Automated assertions remain deferred in [#32](https://github.com/izyuumi/everything/issues/32). Successful worker authentication, native admission and remote execution cannot be established by this storage leaf.

A disposable Rust 1.88 optimized inspector compiled byte-identical copies of the actual modified storage/transport sources and unchanged migrations with `-D warnings`, using the existing combined host library only for protocol types. It exercised actual SQLite commits for all four allowed external next states; preserved ordinary Waiting-to-Completed rejection; rejected changed task fields, oversized payloads and inconsistent times; rejected task, conversation, unassociated, terminal and mismatched-conversation journal rows; and confirmed whole-transaction rollback from task/receipt constraint triggers. Additional receipt triggers injecting a local tool row or changing immutable task input were rejected by the final invariant check, with no partial receipt or checkpoint.

Historical exact replay retained newer task and conversation checkpoints and later tool rows unchanged. Changed source/receipt data, expected task input and conversation state conflicted. Independently calculated ordinary state hashes, serialized original request bytes and absent plain-append digests matched the existing domains. Arc identity distinguished clones, separate memory stores and separate connections to the same disposable file. Evidence is retained at `/tmp/everything-external-task-storage-inspection/{build-status.json,observations-status.json,observations.log,run/verification.json}`. Prepared tool rows were journal metadata only; no model/tool/worker ran, and the inspector established no Agent admission, worker authentication or external-result authorization. No second production dependency graph was built.
