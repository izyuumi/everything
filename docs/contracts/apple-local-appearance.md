# macOS local appearance controls

The existing `ThisMacSettingsStore` now owns an appearance draft and original save alongside its local notification preferences. `ThisMacSettingsView` provides a native system/light/dark Picker, explicit Save/Reload, and original-save inspection. This source uses the same private [DevicePreferenceStore](device-appearance.md) actor, device identity, SQLite singleton, revision and request ledger. It creates no Host session, network request, OS permission action, separate database or defaults mirror.

## Saved values and application composition

`appearanceSnapshot` is the last successfully validated `DeviceAppearanceSnapshot`. `savedAppearance` exposes only that snapshot's closed enum and is nil before a valid read. Neither reads the unsaved draft or a historical Applied receipt. Stale getters treat a missing snapshot or a revision below the shared latest known revision as stale, alongside read failure and their original activity gates. Thus a previously started read cannot label an old projection fresh after a newer actual receipt or the other projection establishes a higher revision. A retained previous snapshot remains explicitly historical when reading fails; corruption and unavailable storage never synthesize or persist a system value.

The existing synchronous `open()` coalesces actual local opening and reads both preference projections. It can be called while Settings is hidden without requesting notification authorization or observing OS capability. `refresh()` coalesces local rereads and observes notification status only while the existing actual Settings-window/application foreground gate is eligible. A genuine `setApplicationActive(true)` transition rereads saved preferences even when Settings is hidden. The existing visible two-second SQLite observer reads both projections; no extra polling loop is added.

The app-owned HostModel, launch read, scene `preferredColorScheme` modifiers and private NSPanel presentation roots are separate coordinator integration. These two source leaves do not apply an application theme themselves. Root must map saved system to the inherited color preference and saved light/dark to their actual SwiftUI presentation values. Apple's [preferredColorScheme](https://developer.apple.com/documentation/swiftui/view/preferredcolorscheme(_:)) affects the nearest presentation; a Settings-only modifier does not establish the menu or a separately hosted private panel's appearance. Host connection replacement must retain this app-local owner and its private preference actor.

## Draft, original receipt and shared revision

`AppearanceDraft` retains the complete original saved snapshot and the selected enum. `setAppearance(_:)` changes only that draft through the existing foreground gate. `saveAppearance()` synchronously validates and retains one exact `DeviceAppearancePatch`, request UUID, device UUID, baseline revision and selected value before creating its owned Task. It reserves one record and marks the shared preference write slot busy before any suspension. The actual `applyAppearance` call runs once. No request is automatically resubmitted, rebased, retargeted or assigned a replacement identity.

The reply must match the retained exact original request/device and patch. Applied requires the genuine original revision plus one; Conflict preserves the dirty draft. The latest revision known from either actual snapshot or an original Applied/Conflict receipt blocks a dirty baseline that no longer matches. In particular, a Conflict cannot disappear because a concurrent coalesced read had already observed an older snapshot. Reload must obtain a compatible actual baseline before Save becomes available again.

Errors and missing original receipts retain `pendingAppearancePatch` and block fresh notification and appearance writes or OS actions. `inspectAppearanceSave()` calls only `appearanceResult(for: originalID)` through the same actor. It does not call apply or treat an absent result as NotApplied. Client request correlation remains app-owned memory, matching the existing notification consumer; durable client correlation across a hard crash is not added.

After Applied, the owner reads real saved state. An observation at the exact applied revision must match the original chosen value before publication; a later actual revision is a separate newer observation. The original historical receipt and current saved appearance remain distinct. Pending readback blocks further preference effects until an actual valid reread resolves it. Expected values or Date never become authoritative saved state.

Notification and appearance APIs return separate projections, not an atomic combined snapshot. Their single shared revision means a save in either category can conflict an old draft in the other. Dirty drafts keep their original baseline. `reloadAppearance()` discards only the appearance draft, with a native view confirmation; the existing notification Reload discards only its own draft. Both reread both saved projections. Clean drafts follow actual observations, and explicit reload never rewrites a receipt or performs an implicit save. Existing notification authorization still checks its actual original revision and generation through the shared native action implementation.

## Bounded work and cleanup

The existing combined 64-record app-session limit now counts notification save records, appearance save records and OS action records together, including terminal and unresolved identities. Capacity refuses new effects without evicting originals. The underlying SQLite ledger retains its separate combined 8,192-request limit; no new ledger or identity encoder is implemented here.

Both preference kinds use the same existing write Task slot and inspection Task slot, with admission excluding another write or inspection across either category. Opening, explicit refresh, actual snapshot reading, OS observation and OS action each have one owned/coalesced slot. Every caller of snapshot reading joins the same retained read Task, which sequentially reads the two actual projections. An explicit reload applies only its chosen draft-discard intent after that read joins. A post-write read that joined an earlier observation can leave readback pending; it does not claim a confirmed new saved value, and the original outcome plus a subsequent real refresh remain available. The visible observer has one owned Task and no new queue.

Appearance work uses the existing `drainSurface()` and permanent `drain()` lifetime. Both include the actual coalesced snapshot-read Task, and original opening/write/inspection/action workers await their read completion. Hiding a surface does not cancel an admitted SQLite write or assume rollback. Permanent invalidation closes new intake, stops the observer and preserves existing actual OS callbacks through their owned joins. No new callback, notification delegate, native Session or process supervisor is introduced. The optional menu app still does not stop the Rust Host.

## Validation and remaining integration

This increment changes only the existing Mac Store/View and this contract. Shared DTOs, SQLite source, project membership, HostModel, app roots, private ceremony, workflows and shared status remain coordinator-owned and unchanged. The two Swift leaves already belong to the macOS target; no source registration is needed.

Source grammar, whitespace, exact-path preservation and documentation destinations can be checked locally. Actual supported macOS/iOS SDK build/analyze and current required Rust CI remain independent final-integration gates. No local database, UI, OS authorization, Host, provider or model was executed for this source work. Real first-open/migration/replay, cross-kind conflict, original receipt recovery, app restart/foreground and appearance in each presentation remain unverified. Existing [This Mac notification](this-mac-settings.md) and shared [storage](device-appearance.md) limitations still apply. No full #114/#117 or security acceptance is claimed; automated coverage remains deferred to [#32](https://github.com/izyuumi/everything/issues/32).
