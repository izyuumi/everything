# Scheduled result notifications

`protocol::ScheduledRunNotification` is a terminal notification, carried by `ConversationEvent::ScheduledRunFinished { notification }` with wire kind `scheduled_run_finished`. It references non-nil job/occurrence UUIDs, a positive generation bounded by SQLite's signed range, scheduled and finished Unix millisecond timestamps, a paired optional native task/execution-conversation reference, the terminal outcome kind, a UTF-8 preview of at most 4096 bytes without NUL, and a canonical 64-character lowercase hexadecimal outcome digest. Outcomes are succeeded, failed, cancelled, skipped and unknown. Deserialization validates those bounds. The protocol DTO does not depend on the scheduling repository.

`Agent::publish_scheduled_result(ScheduledResultCommand).await` is a trusted host API. The command reserves destination conversation, command UUID, event UUID, authoritative acceptance timestamp and the full notification before append. The receipt contains the original typed event sequence. Exact command replay compares the complete original envelope and command request before current destination state, including event identity, body and timestamp. A command UUID previously used by any other Agent operation conflicts. A changed replay never substitutes another body with the same digest.

Fresh delivery acquires the short conversation write gate and requires no pending command. It atomically appends one event and the existing unchanged private checkpoint through the Store's sequence/revision CAS and command journal. It creates no message, pending turn, task or provider request, and changes no configuration or native state. Notifications never enter the active-task input merge path or model message history. A destination with a pending command returns PendingTurn; callers retain their durable outbox record. A missing destination is an explicit delivery error with no alternate destination.

The blocking publication worker retains the complete Agent before its write-guard local, so actual SQL execution and Store-bearing resources finish before the state-directory lease drops, including caller-future drop, errors and unwinding. An Agent constructed with `from_store` has no owned lease; its caller remains responsible for external ownership. This ownership correction is integrated through #103 after exact-source Rust CI; specific caller-drop/lifecycle runtime observations remain pending, separately from the historical validation below.

The host must reserve immutable delivery intent before invoking the API and acknowledge its outbox only after the durable returned sequence. A crash between append and acknowledgement replays the same full command. This API does not grant authority to choose a destination: the scheduling capture and authenticated host command boundary must authorize it. No model tool or remote execution command exposes this trusted primitive directly.

## Encrypted delivery and optional clients

The existing device synchronization path encrypts these ordinary authoritative event envelopes. A replica persists accepted events, its cursor and the application acknowledgement atomically before relay acknowledgement; the host advances its acknowledged cursor only for the matching persisted batch. Conversation access remains the explicit paired-device scope. The relay does not receive the notification, instruction or conversation event body as plaintext. This event adds no separate notification service, transport key or plaintext routing field.

The macOS [schedule status view](../development/schedule-status.md) instead reads bounded local engine, job and history queries over same-user owner IPC. The [iOS client](../development/ios-client.md) validates and displays the terminal notification as conversation metadata for explicitly known authorized conversations. It adds no global job listing, execution-conversation discovery, schedule mutation or model-history message. Client process lifetime never controls the host. Actual macOS/iOS SDK build and static analysis passed for #111. CryptoKit interoperability, device reconnect, UI and OS notification presentation remain unverified.

A separately qualified [issue #54 Linux walkthrough](https://github.com/izyuumi/everything/issues/54#issuecomment-6203741487) used combined production source `2a0a49b`, copied CLI SHA-256 `28afa6c3b3ab38292d5da33227145eaadf945132e66e7972817471917b1270cd` and the genuine Rust DeviceEndpoint/relay. Two owner-created manual occurrences failed for unavailable credentials with zero model requests. The recipient session was cancelled and joined, a real encrypted batch queued while it was offline, and the same replica received that notification before issuing another sync request. Exact event envelopes and durable application acknowledgements converged; duplicate sync and graceful host restart preserved identities and the destination's unchanged private checkpoint/zero message count. No direct SQL/state seeding or successful inference was used. The unselected-conversation refusal was the local replica's `request_sync` scope check, not an adversarial encrypted request reaching the host. This combined schema-10 observation is separate from the focused schema-9 delivery evidence below and does not establish Apple behavior or a cryptographic audit.
