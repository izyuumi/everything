# Native remote binding lookup

`Scheduler::remote_by_binding` preserves its existing public API and actual `RemoteTaskBinding` equality check. Its repository lookup selects at most two task IDs by `tasks.input` path `$.remote.binding.delegation_id`, restricted to native scheduler version 1 and an object-valued remote definition. Each candidate's byte length must be exactly 36 before its Rust string allocation and typed UUID parse. Zero candidates returns the exact `RemoteBindingNotFound(delegation_id)`; multiple candidates fail with Conflict. No first, last, newest or arbitrary candidate becomes authority.

The locked UUID library accepts hyphenated, simple, braced and URN UUID strings, with case-insensitive hexadecimal digits. The lookup binds exactly those four representations from the established `Uuid` formatters and uses the index's SQLite `NOCASE` collation. At most four bounded index seeks expose at most two candidate IDs across all representations. It introduces no custom UUID parser or SQL normalizer and preserves typed duplicate detection for retained alternate spellings. Full typed decoding rejects any conservatively located invalid representation, including an uppercase URN prefix that the UUID parser does not accept.

The sole candidate still passes through existing `repository::load`, including stored input/checkpoint byte bounds, complete deserialization, identity, execution, configuration and remote-task validation, then `remote::snapshot`. The Actor compares its entire binding against the request before returning. The index is a locator, never approval, execution authority or a cached snapshot.

Migration 12 adds the nonunique partial expression index `tasks_remote_delegation` with exactly the lookup's native-version and remote-object predicates. It permits an already ambiguous retained ledger to migrate; actual lookup rejects that ambiguity. Schema 11 databases receive the index through the normal ordered upgrade. Fresh databases use the same migration. SQLite maintains it for every task write, including actual shared Store writers outside this Actor, so post-start additions remain visible without a second mutable identity map.

The previous lookup enumerated up to 4096 retained remote tasks and loaded, deserialized, validated and cloned every task for every binding request. A coordinator scan of 256 jobs could therefore request 1,048,576 full task decodes; even 256 retained composed coordinator jobs produced 65,536. These are source-derived operation counts, not measured latency or throughput. The Actor runs on its retained blocking worker through `Handle::block_on`; this work monopolized the single Scheduler control stream rather than running directly on a Tokio worker. The indexed lookup decodes at most one complete task per unique request, with at most two bounded candidate IDs. Startup recovery and admission retain their separate full-state validation and capacity checks. A targeted lookup does not audit unrelated stored task rows.

Implementation ownership is the narrow repository helper, existing Actor control arm, new migration and this contract. Root composition owns registering schema version 12 in Store and the actual combined build/runtime validation. The isolated change adds no dependencies, identity cache, runtime, tests or source comments. Manual SQL migration/query-plan observations are explicitly distinct from native Scheduler/Host runtime evidence; automated acceptance coverage remains deferred to issue #32.

Focused offline SQLite 3.53.1 inspection used the actual migration files, exact query extracted from this repository, and three serialized task rows from the already-drained genuine worker bridge observation. Fresh schema 12, schema 11 to 12, and reopen all reported `SEARCH tasks USING INDEX tasks_remote_delegation (<expr>=?)`; each original binding selected its unique task, and a missing binding selected none. Explicitly injected contradictory SQL diagnostic rows demonstrated that migration permits duplicate delegations, the query exposes two candidates, later writes remain visible, and oversized ID byte length is available before the Rust allocation boundary. Eight canonical/uppercase/simple/braced/URN hexadecimal-case variants each selected their unique diagnostic row; different IDs carrying alternate spellings of one semantic UUID exposed two candidates across the same indexed query. All three disposable databases reported integrity `ok`, no foreign-key violations and mode 0600. These observations execute SQLite DDL/locator SQL, not the Rust helper, Actor, Host registration, native admission or inference. The registered combined source `d273c52` subsequently passed the six normal-package Rust 1.88 gates; the actual production Host credential-rejection/recovery walkthrough also passed. Exact build provenance and runtime scope are in [worker validation](../development/worker.md#combined-host-validation-checkpoint).
