# Apple Settings metadata

The shared `SettingsWire.swift` and `SettingsOperationWire.swift` files define nonsecret Swift data for the merged Rust Settings contracts. They contain no transport, observable store, session, caller admission, provider execution or UI. The native session and controls remain separate integration work under [#110](https://github.com/izyuumi/everything/issues/110), [#112](https://github.com/izyuumi/everything/issues/112) and [#114](https://github.com/izyuumi/everything/issues/114). The authoritative rules remain [Settings](settings.md), [the service](settings-service.md), [native routes](native-settings-routes.md) and the Rust types they describe.

## Data boundary

`SettingsWireData` combines Codable, Equatable, Sendable and a pure `validate()` method. `SettingsWire.decode` bounds input before Foundation decoding, validates the result and returns a closed error without retaining decoder diagnostics. `SettingsWire.encode` validates before returning bounded bytes. Callers decoding a larger private result envelope must bound that envelope, sanitize its decoder errors and explicitly match its request and connection; a metadata value alone does none of this.

Every object decoder rejects unknown fields. Enum tags and setting keys are closed. The types retain Rust snake-case field names, nullable fields and the two omitted-if-absent inspection fields, `write` and `application`. The known object shape is finite and the shared object decoder limits its coding path to 32 components. Foundation JSONDecoder remains responsible for JSON parsing; these helpers do not detect duplicate object keys or establish exact lexical equivalence with serde's numeric parser. They must consume authenticated Host responses and do not replace Host validation of requests. No custom JSON parser is introduced.

UUIDs used as identities are nonnil. Revisions are positive and at most Int64.max; timestamps may be zero and cannot exceed Int64.max. Text bounds count UTF-8 bytes and reject control characters. Encoded patches/results are limited to 16 KiB, snapshots/inspections/pages to 32 KiB and individual change hints to 1 KiB. The whole private transport retains its separate envelope bounds. Swift UUID encoding and JSON ordering are not canonical request identities; the client does not hash requests or manufacture confirmation authority.

Provider and System One endpoint strings retain their existing metadata and byte/control limits. The Rust provider/selector validators enforce canonical URL spelling, permitted schemes/hosts, credential/query policy and endpoint binding. Swift does not normalize a URL, discover a provider, probe a recipient or duplicate that business policy. Successfully decoding an endpoint does not establish that the Host will accept it.

## Registry, values and revisions

`SettingKey` is the exact eight-key Rust inventory. Its declaration order matches Rust's enum order for sorted changed-key metadata; string sorting is not interchangeable. Registry decoding requires all eight descriptors in that order, including their exact scope, default, sensitivity, agent mutability, apply behavior and constraint type. Optional embedding choices come only from the supplied registry; their validation does not construct a model or establish availability. The seven `SettingsToolName` values preserve the existing logical/provider names without offering or authorizing tools.

`SettingsScope` distinguishes Host, device preference and observed OS identities. Patches reject duplicate, cross-scope and read-only keys. Snapshots preserve desired and effective values, stale metadata, unavailable reasons and pending/restart states. An absent desired value differs from an explicit `SettingValue.dimensions(value: nil)`; no client default converts either into a particular profile dimension. Effective state requires an effective value and, when present, equal desired metadata.

## Original operations and native actions

`SettingsOperationInspection` mirrors the Rust public metadata validator. It checks the original principal/session/request linkage, bounded original lifetime and lowercase digest shape, exact reference expiry, update-time lower bound, finished-result identity/scope, one-revision write increment, Rust-order Host keys and file/application coherence. LocalOwner, NativeUi and SettingsAgent origins remain distinct; an agent binding names its native parent separately from its restricted session. A historical result can complete after expiry. Validation uses no current clock and grants no live authority, original digest proof, journal anchoring or native claim.

`SettingsWriteInspection.resolution == applied` describes the observed file. A `pending_application` result remains the original receipt and can have a separate terminal `SettingsApplicationState` of applied, restart required, unavailable or failed. Backend failure does not rewrite the known file receipt. Applying and Unknown do not certify rollback. Completed native effects carry their actual receipt UUID without inventing a settings revision.

`SettingsActionTarget` uses `{kind, request}`; `NativeActionReference` separately uses `{kind, reference}`. Action and confirmation references are distinct types. The target inventory contains only typed patches, closed native actions, exact device requests and redacted owner replacement identities. Native actions contain endpoint-bound credential references, this-device notification authorization or a known section enum. They cannot carry a credential, arbitrary URL navigation, native admission or model-supplied success. `NativeActionInvocation` and `NativeActionObservation` are nonsecret input metadata; their decoding does not authorize an effect. A native consumer must match the actual original operation, request, session, scope and reference before presentation or cleanup.

## Redacted change and device pages

Change pages preserve strictly increasing durable sequence cursors, sorted unique same-scope keys and nullable operation IDs. `validate(afterSequence:limit:)` applies the original query cursor and its 1–128 limit. Filtered historical rows may advance a cursor without a visible change. Hints contain no setting values and are not a saved-state authority; consumers reread actual snapshots.

Device pages contain at most 100 ordered public identities, bounded labels, revocation flags and the actual cursor. Revocation requests bind the exact device ID and existing public keys. The sole Codable conformance for the existing `DevicePublicKeys` closes its three fields, requires canonical standard-base64 32-byte public keys and calls its established CryptoKit-backed initializer. It introduces no cryptography, second key validator or device store. Pairing invitations, session proofs, SecretTransfer and private Open/SubmitCredential payloads have no representation in these general types.

## Validation scope

The Foundation-only core is checked with the available Swift compiler using Swift 6, complete strict concurrency and warnings as errors. The same compiler options pass for an external byte-exact whole-declaration projection of the operation file that omits the CryptoKit-dependent device/key/target declarations, without substitute types. Both full new files pass grammar parsing. Full dependency type checking requires actual CryptoKit and supported Apple SDK builds; Linux's missing CryptoKit is an explicit limitation, not a substituted key implementation. Project membership and native consumers remain coordinator-owned integration gates. No Apple UI, Keychain, device ceremony, runtime authority or security review is established by this data foundation. No automated tests or fixtures are added; deferred coverage remains [#32](https://github.com/izyuumi/everything/issues/32).
