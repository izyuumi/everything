# Private native pairing client

The macOS `NativeSettingsWire` and `NativeSettingsSession` add typed access to the existing [native final-approval backend](device-settings.md#native-final-approval-backend). This is client source integration, not a new trust protocol or working ceremony UI. Invitation creation, explicit Host approval, private acceptance delivery and the Replica's actual completion are distinct outcomes. Existing creation/cancel/control methods and the seven model tools are unchanged.

`NativePairingCandidate` parses one bounded signed request in native RAM and exposes only its public pairing/Host/responder identity and original expiry for review. The actual native UI must show that same candidate's public identity together with the original invitation's Host fingerprint, and collect exact access selection before the final user gesture. `NativePairingApprovalAdmission.capture` consumes that candidate once on the main actor, checks actual app activity and captures the same session's existing activity gate. It mints the original approval/native-attempt/frame IDs once. It accepts a candidate rather than replacement raw bytes after confirmation. Review metadata, fingerprints and backend request digests confer no authority.

The private admission is neither Codable, Equatable nor hashable. Its request cannot be replaced, reconstructed from public IDs or compared by hashing proof material. Cancellation clears its unsubmitted payload; an already admitted pipe call owns its immutable typed input until the actual call joins. The candidate and admission have redacted descriptions. Swift/JSON/transport temporaries are not a secure erasure or universal zero-copy guarantee.

Before approval, the actor checks the original creation record, actual Host/connection/session proof, pairing ID, invitation expiry and Host fingerprint, responder keys/fingerprint and exact chosen access. The same original activity generation, session clocks and already-retained invitation wall/monotonic deadlines govern send and delivery. Recreating a candidate cannot renew an original approval. Repeated calls with the retained admission share the original task/result; a different object cannot reuse that approval. Ambiguous writes remain inspectable under that original identity without automatic resubmission.

The wire uses only the existing private sensitive pipe. Closed DTOs bound signed requests and acceptances to4096bytes, check actual keys/UUIDs/timestamps/base64 fields and retain the Rust access policy: at most64 selected unique conversation IDs and permission resolution requires command submission. All grants are explicit. The private result matcher requires exact original operation/native/creation/pairing/Host/responder/access/expiry metadata. Completed requires original Committed pin metadata; neither a device page nor a retained invitation proves approval. Existing peers may keep their actual older label and pin timestamp. No order is invented between independent pairing and prior pin times.

`approvePairing` returns nonsecret `PairingApprovalStatus`. It discards the private acceptance from that RPC result rather than putting it in generic `Outcome` or an operation-result cache. `pairingApproval` reads the original receipt. `showPairingAcceptance` uses the original read route, verifies the actual response with the existing `PairingInvitation.finish` implementation, and invokes one owned main-actor callback with a redacted private transfer wrapper. It does not sign, pin, widen grants or claim that the Replica consumed that response. No automatic or cached callback replay occurs. Close, cancellation, revocation, expiry or a stale activity generation suppresses delivery; a known historical Host receipt can remain after delivery becomes unavailable. Restart cannot recreate the original native proof or acceptance.

Signed requests/proofs, invitations and acceptances stay within these private native objects, ephemeral callback and anonymous-pipe buffers. They do not enter generic OwnerRequest/JSONValue, files, model/session chat, durable operation payloads, defaults, logs or error descriptions. Nonsecret status may be retained for inspection. The existing `showInvitation` cancels when its presenter returns, so its UI owner must keep the original ceremony alive through the returning request, explicit final approval and acceptance transfer; dismissing it first retires pending invitation use.

The actor retains at most eight approval ceremonies and counts them with generic records under the existing64-operation ceiling. Original records are not evicted to admit new work; the existing four-RPC bound remains. Drain invalidates activity first, cancels private delivery, joins actual approval/presentation and RPC work, inspects original receipts and closes the same native parent. Caller drop does not detach admitted work. A presenter that does not return can keep drain pending; no forced UI termination or false completion is promised.

This change has source inspection and Swift6.0.3 frontend grammar parsing only until supported SDK builds and disposable native UI observations are recorded. It does not establish Apple pairing/QR presentation, actual long expiry, background/drop/race behavior, remote or SettingsAgent acceptance, security review or full [#112](https://github.com/izyuumi/everything/issues/112) completion. Deferred automated coverage remains [#32](https://github.com/izyuumi/everything/issues/32).

The existing shared `PairingInvitation` request method remains available only under `os(iOS)`, where its private `DeviceIdentity` dependency already belongs. Its request body and shared invitation verification/acceptance-finish code are unchanged. Root must register the existing file in the macOS Sources phase before SDK validation; this source change does not edit project membership or import the iOS private-identity graph. Grammar parsing cannot establish that target integration or semantic compilation.
