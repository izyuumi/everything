# macOS native Devices controls

This source adds a conventional Devices pane and a private native pairing/revocation sheet. Integration must register the three new Mac sources and mount `NativeDevicesControls(store:connectionEdited:)` in the existing Settings scene. The pane uses the same app-owned [Settings Store](apple-native-settings-session.md), Session, immutable Owner connection and private pipe. It neither starts another client/runtime nor controls the independent Host lifetime. Supported Apple SDK builds and disposable UI/phone observations remain required before claiming this new UI works.

## Public list and original operations

`refreshDevices(first:)` explicitly reads one page of at most25 redacted devices through the original Session. Next replaces that page; no unbounded list history, background polling, automatic Open or mutation replay exists. Its read has one owned slot in the existing four-worker registry and coalesces while pending. The captured Owner, observation generation and actual foreground must still match before publication. Host identity, observed device UUID/full public keys, label, revoked and Host-self status come from the real page. Existing grants are unavailable in this projection. Each page is an independent observation; its wall timestamp is display metadata, not an ordering/authority check. Offline/hidden/changed-owner pages are labelled stale and cannot supply a new revocation target.

`beginDevicePairing(parent:)` and `requestDeviceRevocation(_:parent:)` are synchronous gesture APIs. They retain the original Host scope, exact request, snapshot/registry and original activity generation, wall expiry and monotonic deadline before the owned Task. Revocation copies the exact row's full public keys. Device requests have no invented settings revision. The actual same-parent AwaitingAction Details must match the complete original target/reference/binding and authenticated NativeUI origin before the sheet offers confirmation. `confirmDeviceAction(_:ceremony:)` captures one original confirmDevice invocation/admission synchronously; neither duplicate clicks nor Inspect create another effect.

The Store exposes only redacted pages, public operation/approval receipts and opaque pointer-bound `DeviceHandle` values. Inspection resolves that exact handle to its original Owner; it cannot retarget a historical operation to the current connection. Creation and final approval retain separate original IDs. Inspect reads the original receipt and never resubmits approval, changes grants or reopens a private presentation automatically. Lost responses and Unknown remain visibly uncertain and block fresh effects. Original inspections are available while that original Owner is current; after retirement, the real Session drain inspects its original receipts and returns a typed cleanup report.

## Private ceremony and explicit access

`NativeDeviceCeremony` owns one app-local NSPanel on the actual Settings NSWindow. It refuses an absent/inactive/hidden/minimized parent or an already attached/queued sheet before presentation; native `beginSheet` may otherwise queue. Its dedicated SwiftUI view holds private invitation, signed-request input/candidate, verified acceptance and QR display data. Those values never enter observable generic Store rows, JSONValue, model/chat records, operation targets, files, defaults, logs, clipboard exporter, argv or environment. Display necessarily uses ordinary Swift/AppKit/Core Image memory; clearing fields is not secure erasure.

An explicit creation confirmation uses the existing Session.perform followed by the same original `showInvitation` admission. That callback stays alive while the user transfers the genuine invitation, supplies the requesting device's at-most4096-byte signed request, compares the complete public fingerprint and chooses exact access. Request parsing is not approval. Replacing an unconsumed candidate clears comparison and all grant choices, and never renews the original clocks. Once consumed for approval, it cannot be replaced or reused.

Default access is selected(empty), no command submission and no permission resolution. All is an explicit broad choice, including future conversations. Selected access accepts at most64 distinct nonnil conversation UUIDs; permission resolution requires command submission. The actual immutable label/access and SAME candidate enter `NativePairingApprovalAdmission.capture` synchronously on the Approve gesture. The Host verifies the existing signature/proof/source/policy; no public UUID, fingerprint, parsed candidate or comparison Boolean confers authority.

The same Session.approvePairing returns public Host pin metadata; `showPairingAcceptance` uses the SAME admission and existing `PairingInvitation.finish` verification before its private callback displays genuine signed acceptance. Both invitation and acceptance callbacks remain held until actual sheet retirement. The Host's committed pin, private acceptance displayed, and completion on the requesting Replica are separate facts. The Mac never claims Replica completion, updates an older pin's immutable label/grant, performs custom cryptography, approves automatically, or adopts an Agent-origin card. The existing iOS acceptance field takes this text; no currently unsupported acceptance-QR scanning is promised.

Invitation QR generation uses Apple's local `CIFilter.qrCodeGenerator` and CIContext with integer scaling, contrast and a quiet margin. Failure shows the real private text fallback and a fixed message. No QR service, additional camera, file/share action or automatic clipboard copy is used. Native controls, text and explicit actions support keyboard/VoiceOver; private text is not announced as a QR accessibility label.

## Bounds and cleanup ownership

The aggregate identity budget is existing native operation records + credential metadata reservations + one reserved final-approval slot per pairing creation, at most64 per original Owner. Pair reserves both creation and potential approval slots before the first effect. Its unused/terminal reservation stays counted until true Owner retirement. There are at most8 pairing contexts per Owner, matching the Session's eight approval records. Revocations use their original native record. List reads, preparation/details, held invitation, final approval/acceptance and original inspections all use the same four effect slots per original Owner. The shared client still limits actual CLI processes to four across Owners. Work is refused rather than queued. Native Session RPC and shared CLI process bounds remain unchanged.

Only one private ceremony can remain unretired across the existing eight retained Owners. Fresh conventional changes, keys and device actions cannot bypass an existing private sheet or native/metadata/approval ambiguity. Final approval may use a second slot while its own original invitation callback occupies the first; it cannot run alongside unrelated effects. At most the two one-time private callbacks plus the single Owner retirement await that sheet. Original records are not evicted to admit new work.

Dismissal, Devices-pane disappearance, parent close/minimize/occlusion, app background/hide, Host unavailability, connection replacement and Store invalidation synchronously latch retirement and clear private fields/candidate. They cancel unstarted admissions and request endSheet on the original panel. `beginSheet`'s actual completion plus orderOut's observed hidden state and detached sheet parent acknowledge retirement. Only then do owned callback continuations resume. If that acknowledgment is unavailable, cleanup remains pending with the original objects retained; elapsed time or a hidden intent is not a false joined fact.

The Owner joins actual sheet retirement and every admitted effect before returning its Session cleanup. Returning the original invitation presenter lets Session perform original cancelPairing cleanup; calling cancelPairing while waiting for its own presenter would deadlock and is avoided. Already admitted approval/revocation can finish after dismissal; no rollback or key/pin erasure is asserted. If creation returns after dismissal, or showInvitation rejects its cancelled admission before installing a presenter task, the SAME original confirmation worker first retires/joins the actual sheet and then calls original Session.cancelPairing. This happens only after showInvitation has returned or thrown, so no cleanup waits on its own still-running presenter. The original failure and distinct cancellation failure remain retained; returned cancelled/expired/no-longer-pending lifecycle is recorded separately from UI dismissal. Retained, cancellation-pending or unavailable lifecycle remains uncertain, blocks fresh effects and contributes the original identity/errors to cleanup. It is not displayed as successful Host cancellation. Existing credential unlinked-state retention, exact retirement incarnation, effects-empty removal guards and bounded late-recovery generation are preserved. App quit drains these original UI/Session owners before the same shared client's shutdown. The Host stays independent.

## Validation and remaining acceptance

Source grammar, bounded structure, links and exact-path preservation can be checked locally. Actual supported Mac/iOS SDK build/analyze remains a separate integration gate. This source has not observed AppKit sheet/occlusion behavior, Core Image output, long expiry, phone transfer, revocation, Host switches, response loss or final app shutdown on Apple hardware. The prior Rust pairing observations apply to their exact recorded backend artifact, not this UI. Remote Settings grants and authenticated SettingsAgent action adoption are separate work; this increment exposes neither. No security certification, full [#112](https://github.com/izyuumi/everything/issues/112)/[#114](https://github.com/izyuumi/everything/issues/114) completion, or new automated validation is claimed. Deferred automated coverage remains [#32](https://github.com/izyuumi/everything/issues/32).
