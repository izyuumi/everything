# iOS local preference controls

`ThisDeviceSettingsStore` and `ThisDeviceSettingsView` provide the local This iPhone consumer source for saved appearance and completion/attention preferences, plus the existing real OS notification adapter. They consume the [shared appearance and notification store](device-appearance.md), not remote Host Settings, a model or a second agent runtime. The iOS app source now composes these controls with its existing Replica identity, lifecycle, navigation and root appearance. Notification category delivery remains unavailable, and Root must register the two new iOS source leaves before supported SDK compilation.

## Actual identity and app ownership

`AppModel` constructs `ThisDeviceSettingsStore(directory:deviceID:)` at most once from the first actual checked `ReplicaViewState.identity.deviceID` and Application Support/Everything/DevicePreferences. `ReplicaService.open()` already loads the existing Keychain identity against the Replica store identity and binds it before `viewState()` exposes it. Construction follows the existing refresh epoch/cancellation check, retains the owner before opening, and never depends on a paired Host or relay connection. The synchronous throwing constructor rejects a non-file URL or nil UUID, retains immutable `deviceID` and opens no database. The UUID is local preference binding metadata, not a caller/Host/NativeUi grant. A plausible UUID does not prove that source. If the protected identity or local directory is unavailable the app reports that limitation. An unexpected later different identity permanently invalidates and retains the old local owner through actual drain; it does not create another owner, switch its binding or repair storage.

`open()` coalesces one owned off-main strict `DevicePreferenceStore(directory:deviceID:)` initialization and reads both actual projections. It never calls the Mac local-UUID factory, creates a fallback identity or adopts a different stored UUID. Existing mismatch/corruption/schema/file-protection errors remain explicit and do not repair preferences. Both received snapshots must match the immutable device UUID. Opening local preferences needs no paired Host, relay connection, credentials, provider or network. Reconnect/Host changes must retain this same app-local owner, actor and original requests.

The underlying actor remains the sole SQLite authority, revision and combined request ledger. The consumer adds no database, UserDefaults mirror, schema, request encoder, receipt serializer, crypto or remote grant. A corrupt or unavailable store does not produce a saved system appearance or false saved Boolean defaults. Before a real draft is available the Form shows unavailable/read-in-progress text instead of invented toggle values.

## Native drafts and original outcomes

The two draft types retain their complete original saved snapshots. Native setters change only the selected draft. `save()` and `saveAppearance()` synchronously capture and validate one original typed patch, request UUID, immutable device UUID, expected revision and exact chosen changes before reserving their record and creating an owned Task. There is one shared preference write slot and one shared inspection slot across both categories; admission excludes overlapping preference writes or inspections. Neither entry point submits through AppModel's network/chat busy queue.

Only matched original IDs and the actual Applied revision R+1 or valid Conflict update the original result. Unknown errors/missing receipts retain the pending patch and block fresh preference effects and OS actions. `inspectPendingSave()` and `inspectAppearanceSave()` call only the corresponding actual original-ID receipt getter. They never apply again, allocate a replacement mutation ID, infer NotApplied from absence or claim rollback. Retained client correlation is app-owned memory; hard-crash restoration of those original client records is not added.

Dirty drafts keep their baseline across observed changes. The latest actual revision known from either saved projection, an Applied/Conflict receipt or a retained actual notification-action Conflict prevents an old dirty baseline from being silently reused, even if a coalesced read had already observed older state. The bounded original notification records preserve their genuine conflict revision across later display results; Completed or a receipt UUID supplies no invented revision. A Conflict needs a compatible actual reload before Save can become eligible again. Reload is explicit, with a native discard confirmation; each category discards only its own draft while rereading both saved projections. There is no automatic rebase or combined Save implying an unavailable atomic two-category API.

Applied and current saved state remain different facts. The owner reads back real state; at the exact applied revision it verifies the chosen value, and a later actual revision is a separate newer observation. `appearanceSnapshot` and `savedAppearance` derive only from a validated actual read, never the draft or receipt. They are nil before a valid saved read and can retain a labelled stale observation after later failure/inactivity. Both stale getters also reject missing snapshots and projections below the shared latest known revision, so a previously started read cannot label an old value fresh after a newer actual receipt or other projection arrives. Pending readback blocks fresh effects rather than synthesizing the requested saved value. A post-write caller can join a previously started read, leaving readback pending until the next genuine refresh. Dates do not order preference authority.

`EverythingIOSApp` observes only the saved enum and maps it to the actual WindowGroup root `preferredColorScheme`, including ordinary chat, approvals and the existing privacy overlay. One initial observation retains the latest genuine nonnil enum as an ephemeral UI preference: system chooses nil, light/dark choose the matching native scheme. An unavailable value leaves the previous genuine preference unchanged; before any saved read the window inherits the system without claiming that value was saved. No draft, historical receipt, persisted mirror, storage write or appearance-specific Task determines the applied preference. The local Form does not apply a theme itself. Appearance and notification getters are separate non-atomic actor calls; a concurrent save can legitimately leave different observed revisions and require Reload in the other draft. None of these local observations grant remote Settings access or attest notification delivery.

## Synchronous foreground and real OS actions

The root synchronously supplies `setSceneActive(_:)` and `setSurfaceVisible(_:)` through AppModel from its tagged selected tab, single local navigation destination, scene and four closed covering states. Custom tab/path/sheet setters invalidate before changing presentation. The local Form must report both private Reload confirmations through its required callback before presenting them; their combined state cannot clear a separate sheet, global error or device-disable cover. Root sheets keep their cover through actual `onDismiss`. Global errors block before publication. Navigation appearance participates in this aggregate and cannot establish eligibility by itself. Store eligibility also checks real `UIApplication.shared.applicationState == .active`, and the shared foreground session repeats that actual check before OS admission. A public Boolean or device UUID is not authorization by itself.

Actual `UIApplication.willResignActiveNotification` forces a separate platform-eligibility latch false synchronously, without sampling a possibly still-active application state. A later initial/onChange scene-active callback cannot clear that latch. Only the real did-become-active notification, or the single initial platform observation before any resign, can establish platform eligibility. Both scene and platform must allow, and the shared services still repeat the actual application-state check. There is no scheduler hop, new UIApplication/notification delegate or permission wrapper in those callbacks. The original asynchronous Replica scene method and foreground-connect intent remain unchanged; a stale active task cannot reactivate local controls. Independent SwiftUI callbacks do not establish a first-frame or exact callback-order guarantee.

Hidden/inactive transitions synchronously invalidate the original shared foreground generation and cancel unstarted actions. Returning foreground never renews an old ticket. An actual true scene transition rereads saved preferences even while the local surface is hidden, without observing OS status or requesting permission there. The visible foreground observer is SQLite-only and sleeps two seconds; there is no hidden polling loop.

The notification Button calls `requestNotificationAuthorization()` directly on MainActor. Before Task creation it invokes the existing `DeviceNotificationActions.prepare` with the same actual actor, original saved revision, device/session and one 60-second wall expiry. Its owned Task consumes that exact opaque Admission. The existing service retains the original foreground generation and monotonic deadline, checks actual saved revision before the effect, queries authorization/features before and after interaction and enforces exact replay/dialog suppression. No new OS authorization protocol or arbitrary settings URL is implemented.

The same `NotificationAuthorizationService` supplies contextual authorization or the supported iOS notification settings destination/guidance after denial. Opening preferences, switching appearance, returning foreground or rereading status never calls `requestAuthorization`; only a fresh eligible native Button action can do so. Observed authorization, alert/sound/Notification Center capabilities and query timestamp are displayed separately from saved choices. A failed or cancelled eligibility check is not a denied/granted result or proof that an already admitted system dialog was dismissed.

One actual OS observation identity controls publication, retires older pending-query publication and coalesces a follow-up after the owned callback joins. Wall timestamps are display-only. Real action observations are retained; an old query cannot overwrite the post-action observation. The consumer creates no UNUserNotificationCenter delegate and does not call the legacy NotificationService authorization shortcut; the existing app's privacy delegate remains unchanged. The legacy direct authorization button, AppModel session-only notificationsEnabled/authorizeNotifications/lastCursors and the cursor-advance activity branch are removed. The now-unused authorization, generic activity submission and throttle methods are removed from NotificationService. The same app-owned service still retains the original single privacy delegate. This intentionally stops old generic cursor-activity notification production rather than silently interpreting the new completion/attention choices or OS permission as its opt-in.

## Work bounds and suspension

At most 64 original notification-save, appearance-save and OS-action records are retained together, including terminal/unresolved identities. Capacity refuses new effects without eviction. The shared action service retains its existing separate 256-invocation bound, and the authoritative store retains its existing combined 8,192-request limit. There is one owned/coalesced opening slot, explicit refresh slot, actual two-projection read slot, preference write/inspection slot, OS action slot and OS query slot, plus one visible SQLite observer. Calls joining an existing read add no new queued read worker; both projections remain sequential actual actor reads.

`setSurfaceVisible(false)` closes foreground eligibility before Root calls reusable `drainSurface()`. That finite drain joins the captured opening/read/write/inspection/action/query tasks and cancelled old observer, without hiding a subsequently reopened surface or joining its new observer. Permanent `invalidate()` closes all new intake, stops the observer and invalidates the foreground session; `drain()` performs that invalidation and joins actual work. Original workers await their shared read task, so a late post-write read remains transitively owned. AppModel retains the same owner throughout the app lifetime. One coalesced local drain Task uses pending/permanent Booleans; repeated requests do not append tasks or counters. Each pass joins captured work and repeats only when another drain was requested. Completion does not change surface eligibility or stop a reopened observer. An identity mismatch invalidates intake before the same retained owner performs permanent drain; no replacement is constructed. The original Replica scene method never awaits local draining before or between its stop/refresh awaits; independent drain work adds no shutdown barrier.

View/caller disappearance never discards an admitted SQLite write or actual OS callback, fabricates cancellation/rollback or starts another dialog later. An OS callback may remain pending. iOS termination can kill the app and supplies no guaranteed quit drain; this source does not claim otherwise. It never stops the Host, controls the Replica runner or changes the user's foreground-connect intent.

## Explicit pending integration and validation

AppModel and the actual app/root/Settings sources now compose identity, local lifetime, synchronous scene/platform/tab/path/cover hooks, root theme and a standalone navigation destination. `ThisDeviceSettingsView(store:onPresentationChange:)` owns a Form and navigation title; it is not nested inside the existing Settings Form. Its mandatory presentation callback adds no permission worker or authority. The strict Store remains byte-exact reviewed02214f5. Root owns iOS-only membership and shared documentation; both new Swift leaves still require target registration and fresh final-head SDK compilation. The existing privacy overlay and original asynchronous Replica scene body are retained.

Saved completion/attention choices are real local settings, but category delivery is not connected in this increment. Historical cursor advancement indicated generic activity, and Replica snapshots omit terminal tasks; neither is a completion proof. The old generic producer is now intentionally removed. Root must coordinate a separately reviewed actual committed-event metadata producer/dedup path before category delivery, preserving the existing delegate and privacy-safe text. No inferred producer, new relay protocol, APNS, background wake or guaranteed notification delivery is advertised. Scoped remote Host controls/chat, grants and authenticated agent cards remain #116/#115 work and are not prerequisites for these offline choices.

Apple's [preferred color scheme](https://developer.apple.com/documentation/swiftui/view/preferredcolorscheme(_:)) applies to the nearest enclosing presentation and its children; actual sheet/camera/keyboard/system-UI inheritance still needs observation. Actual supported final-head SDK build/analyze, required Rust CI and separately authorized device/storage/foreground/denial/suspension observations remain pending. No database, GUI, permission, Host, provider/model, network, compiler linking or runtime was executed for this source stage; only permitted actual-source grammar validation applies.
