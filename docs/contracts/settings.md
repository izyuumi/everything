# Hybrid settings contract

Issue [#108](https://github.com/izyuumi/everything/issues/108) defines version-one metadata and data contracts in `host::settings::contract`. The existing [SettingsRepository](../architecture/host-settings.md) remains the only host configuration authority. The contract supplies typed descriptors and shape/bounds validation. The [shared SettingsService](settings-service.md) now implements the journal, confirmation/action lifecycle and file/application boundary, with actual [owner routes](settings-owner-routes.md), [native pipe routes](native-settings-routes.md) and [startup policy](host-settings-startup.md) in the existing Host. The dedicated restricted runtime, conventional macOS controls/secure entry/Devices/optional assistant and the scoped paired Settings transport/remote session (#116) and its iOS consumer (#117) are integrated. [Settings architecture](../architecture/settings.md) identifies the actual current capabilities. These source interfaces do not establish integrated runtime acceptance.

## Scopes and authority

Every snapshot, patch, result and action targets exactly one `SettingsScope`: a particular Host identity, a particular device's preferences, or that device's observed OS state. Host revisions come from the existing repository. Device preference revisions belong to that device's own store. OS observations are read-only, with a local observation revision/time. Cross-scope edits are separate operations and receipts; no file/Keychain/job/device transaction is implied.

Requests contain no caller-provided owner flag, principal or grant. The shared service derives an opaque caller from the verified LocalCall or Host-minted native session proof and attenuates restricted callers to one logical tool. The implemented immutable Settings runtime reuses the actual Agent/Broker with the seven-tool ceiling described [here](../architecture/settings-agent.md). Same-user authentication alone does not elevate a model call to an owner operation. The #116 paired route derives identity from the verified envelope pin and intersects an explicit live per-key/session [grant](settings-grants.md) with the restricted profile ([paired authority](paired-settings-authority.md)). Existing paired devices receive no new grant through migration. Every call and pending apply rechecks the current actor, session, device grant, key ceiling and target identity.

| Surface | Restricted settings agent | Local native owner | Paired settings client |
| --- | --- | --- | --- |
| Allowlisted ordinary preferences | Only within origin grants and exact scope | Same validated facade | Explicit per-key grant and current connection |
| Generation selection or System One recipient/configuration | Request exact native confirmation | Trusted confirmation of exact diff/recipient | `host_action_required` for new recipient consent |
| Notification preference | Requesting device only | This foreground device | Requesting foreground device only |
| OS notification authorization | Read status; request native action | OS/user interaction | Local requesting-device action only |
| Credential values and writes | No values; request secure entry | Ephemeral secure owner route only | `host_action_required` |
| Pairing invitation/final approval/grants/revocation | Opaque request/status only | Existing explicit ceremony/confirmation | `host_action_required` |
| Workspace/security/execution policy, shell/MCP startup, lifecycle/recovery | No editable key or pass-through; known owner section navigation only | Existing separate authorized controls | No generic settings route |

The table defines authority ceilings, not availability. The current model adapters are Host-scoped and request only Native OpenSection; device preferences/OS actions use separate local client adapters. The paired route serves only Host-scoped readable/writable grant keys and answers `host_action_required` for the local-owner-only rows ([transport](settings-access-transport.md)); paired notification preference/OS rows have no remote adapter. Descriptor mutability is never a permission or proof of availability. A validated payload or public result DTO cannot create authority. Observed OS state never becomes a device/host grant.

## Registry and values

`SettingKey` is closed; unknown keys and unknown fields fail deserialization. `SettingRegistry::from_active_embedder` returns eight descriptors with a value shape, bounds/choices, default, scope, sensitivity, agent mutability and apply behavior:

| Key | Scope | Default | Agent ceiling | Apply contract |
| --- | --- | --- | --- | --- |
| `models.selection` | Host | No selected model | Native confirmation | Subsequent run; active provider pinned |
| `tools.selection` | Host | Local | Native confirmation | Subsequent selection; disabling stops new external classification |
| `memory.embeddings.enabled` | Host | False | Allowlisted preference with real feature checks | Stop new work on disable; pending apply remains visible |
| `memory.embeddings.dimensions` | Host | Unset | Allowlisted preference with actual model choices | Explicit rebuild/application state |
| `memory.embeddings.model` | Host | Unavailable until reported | Read-only | Observed active model identity |
| `notifications.completion` | This device | False | Allowlisted preference | Local preference only |
| `notifications.attention` | This device | False | Allowlisted preference | Local preference only |
| `notifications.authorization` | Observed OS | Unavailable until queried | Read-only | Actual OS query |

Model selection contains only the existing provider kind, validated official/canonical loopback endpoint and opaque model ID, bounded to 256 bytes. The contract-only `SettingsModelEndpoint` keeps the existing official/loopback serialization tags while rejecting unknown nested endpoint fields; it converts explicitly to the existing native endpoint. It changes no legacy Agent serialization, instructions, execution limits, credential binding or workspace. Validation reuses the existing conversation configuration checks without constructing a provider or sending a request. An absent model is valid: native settings must remain usable.

Tool selection is a closed local/System One preference. An enabled selection contains the exact generic compatible endpoint and bounded opaque model ID and uses the existing System One configuration validator; TypeSafe remains an existing preset, never an exclusive provider. Credential references are managed separately by the native action/credential service. Configuration or confirmation of a configuration change does not approve a later task/payload disclosure: the existing exact [System One consent](host-selection.md) still applies.

The registry derives dimension choices from the actual EmbeddingProfile supported dimensions. Its active-Embedder constructor reads that profile; the service uses actual cached Memory profile metadata. No constructor loads artifacts, initializes a backend or reads vectors. With no known profile the choices are `None`, meaning metadata unavailable, rather than guessed choices or an empty supported list. A cached profile does not establish a loaded or healthy helper. Desired opt-in and an optional desired dimension remain representable without loading anything. The shared service validates new dimension choices against that metadata, reports pending/unavailable state and retains real FTS under [#72](https://github.com/izyuumi/everything/issues/72). Unset dimensions preserve the backend's default selection; the registry invents no default dimension. EmbeddingGemma 2 remains the only shipped model; the Rust interface stays model-independent. Native consumers must use these descriptors rather than maintain a separate model table; the macOS Memory screen now consumes those actual descriptors without inferring helper health.

The apply metadata is implemented through the shared writer and existing Memory/selector generation controls. Durable Applying precedes suspension of affected new semantic/classifier admissions and file effects. Known-applied file work is advanced by one existing Host JoinSet worker; status reads and client replay do not apply it. Pending or failed application remains distinct from a known file save. Non-embedding Memory, MCP, worker and relay changes retain their restart requirements. The historical [live-control walkthrough](../development/settings-validation.md) records its own exact artifact and application observations; it is not Apple UI or current-source runtime verification.

## Patches, snapshots and outcomes

`SettingsPatch` carries version 1, an immutable `CommandId`, exact target scope, expected positive signed-64-bit revision, 1–8 typed changes and an optional confirmation reference. The encoded patch is at most 16 KiB. `validate()` rejects duplicate keys, cross-scope batches, read-only writes, key/value shape mismatches and bounded/canonical model/selection errors. It validates shape, not grants, consent or current backend availability. The service must bound bytes before decoding and invoke validation before processing. Unsupported combinations fail visibly rather than being normalized into permission.

#109 validates the entire same-scope batch and original revision before committing, preserves every unrelated field, and uses the existing private file/CAS path. Request identity binds the authenticated actor, exact target/patch and original expected revision; native confirmation uses a separate invocation bound to that retained operation. Fresh patches carrying confirmation metadata are rejected. Exact replay returns the original durable outcome; changed reuse conflicts. A stale revision is not silently rebased. A disconnect neither proves rollback nor authorizes a new request ID.

`SettingsSnapshot` is a redacted 32-KiB maximum view with target scope, authoritative revision, observation time, stale flag and at most eight unique entries. Each entry distinguishes desired and effective values and Effective, PendingApplication, RestartRequired or Unavailable state; unavailable entries carry a closed reason code. Read-only state has no desired value. Effective state requires an effective value and no differing desired value. No snapshot contains instructions, main-chat history, workspace/security roots, credential references/values, private checkpoints, pairing material or device grants. Endpoint/model metadata is non-secret recipient data and still subject to per-key read authorization and hosted-provider disclosure.

`SettingsOperationResult` retains version, original request ID and target scope. States distinguish Applied with revision, Completed with an opaque receipt ID, PendingApplication, RequiresConfirmation, RequiresUserAction, HostActionRequired, RestartRequired, Conflict with observed revision, Unavailable, Failed, Unknown and Cancelled. Failure/unavailable reasons are closed sanitized enums. These serializable objects are inspection data, not authenticated receipts. Only an authoritative service result from the original authenticated request supports Saved/Applied presentation. #109 owns durable command outcomes and redacted change hints; missed hints/reconnect require a scoped reread. Relay delivery ACK is not mutation acceptance.

Completed is reserved for device/native actions that finish without changing an authoritative settings revision. Its non-nil `receipt_id` is retained lookup metadata bound by the service to the exact original request, scope, actor and outcome; it is not admission or confirmation authority. Applied, PendingApplication, RestartRequired and revision Conflict retain their mandatory genuine positive revision. Device/native work must not invent one or substitute the unrelated HostSettings revision. Pending or uncertain native work stays inspectable through its actual action lifecycle until an authoritative outcome exists; UI interaction alone cannot manufacture Completed. Completion describes only the original typed action: invitation creation is not pairing approval, notification interaction is not an OS grant, and revocation is not proof of remote erasure or stopped effects.

## Exactly seven logical tools

`SettingsToolName::ALL` fixes this complete namespace. `logical_name` is the public contract; `provider_name` is its one-to-one function-name-safe encoding, not another tool or an extensible alias list.

| Logical tool | Provider function name |
| --- | --- |
| `settings.list` | `settings_list` |
| `settings.get` | `settings_get` |
| `settings.update` | `settings_update` |
| `settings.request_action` | `settings_request_action` |
| `devices.list` | `devices_list` |
| `devices.pair` | `devices_pair` |
| `devices.revoke` | `devices_revoke` |

The implemented #113 profile enforces this immutable offered and executable ceiling in trusted runtime/Broker code, including direct-ID calls. There is no shell, MCP, search_tools, System One selector, schedules, subagents, wiki, main history or owner-IPC pass-through. A different prompt on a general-purpose agent is insufficient. Settings context contains only safe descriptors, authorized redacted values and bounded session chat. Session state and its pinned active generation provider remain separate from ordinary conversations, consolidation and embeddings. No provider or credential fallback is silently selected. UI closure cancels its owned inference and expires unapplied ephemeral actions where safe; admitted mutations remain reconciled. The Host lifetime is independent.

## Confirmation and native/device actions

Confirmation and action references are non-secret UUID/expiry lookup metadata. They are not bearer authorization, public constructors of trusted consent or deserializable execution proofs. `SettingsRequestBinding` records the service-derived principal/session identity, exact target, request, optional observed revision, exact request SHA-256 and original issue/expiry times, capped at five minutes. Actual settings patches and their confirmations require Some of the genuine Host/device-preference revision, exactly matching the original patch. Device pairing/revocation uses None: the existing device store has no device-set revision, and the unrelated HostSettings revision must never be substituted for pin/grant checks. Shape validation checks a present revision's range only. #109/#110/#112 must retain the actual trusted request/diff/action and actor binding, enforce that conditional revision rule, generate the reference, and recheck exact contents, native confirmation, monotonic/original expiry and live grants immediately before apply. Never trust a caller-supplied binding or renew expiry on replay. Authenticated native cards come from this service state; model text/Markdown cannot create one. Closing/suspending or switching the owning connection/session cannot retarget a pending action.

`NativeSettingsAction` has exactly three cases: CredentialEntry with a purpose-specific binding, this-device NotificationAuthorization, and OpenSection with a known section enum. There are no arbitrary URLs, paths, commands, scripts, approval operations or generic service/account fields. Model credentials use a strict wire-equivalent binding that preserves provider, endpoint, reference and storage and converts to the existing `ModelCredentialReference`; System One uses its distinct exact endpoint/reference namespace. Neither case contains a credential value. Credential entry stays host-local-owner-only. The Rust `owner --sensitive-stdin` route requires private pipe/FIFO input and output, with bounded zeroizing buffers; native Settings frames and secret-bearing credential operations are rejected by the request-file path. The [credential adapter](native-credential-actions.md) accepts configured replacement and narrow initial storage at the actual selected/configured endpoint with an unused reference. The macOS [secure-entry consumer](apple-native-credential-entry.md) uses that private route and a separate original-revision metadata-link gesture. Supported-platform UI/OS observation remains open. Ordinary chat and pending-action state must never carry secrets. Return only sanitized status/presence. An ambiguous write is inspectable, not presumed rolled back or automatically repeated.

Notification preferences belong to their named device. Observed authorization includes not-determined, denied, authorized, provisional, ephemeral and unavailable; only an actual OS query supplies it. A preference does not grant permission. Request authorization contextually on the requesting foreground device; denial needs supported native settings navigation or accurate instructions. Unsupported/background/disconnected UI actions expire rather than appearing later as surprise dialogs.

Device administration uses separate `SettingsDeviceRequest` and closed Pair/Revoke actions, without an invented expected device revision. Revoke binds the exact typed device ID and validated public keys; apply must recheck those actual pins and live actor/grant/revocation state. A sorted redacted `SettingsDevicePage` carries its observation time and at most 100 bounded labels/public identities/revocation flags and an exact last-row continuation; no access metadata or invitation secret is included. Labels retain the existing pairing bound of 256 bytes, and the 32-KiB page cap may require a smaller page without rewriting stored labels. The existing [device projection and facade](device-settings.md) derive it from current authorized state; authenticated native routes expose that source, and the integrated macOS [Devices consumer](apple-native-devices.md) supplies the private ceremony. The restricted profile obtains only its bounded opaque proposal path. Pair returns only a non-secret action handle and expiry to the model; invitation/QR material stays on the authenticated ephemeral native-owner path. Existing explicit fingerprint comparison, final approval and grant selection are unchanged. Revocation requires exact native confirmation and live authorization. Creating an invitation never approves trust. Remote requests for credentials, pairing/revocation/grants, new recipient consent or lifecycle/security changes return HostActionRequired; no general OwnerOperation value crosses E2EE.

## Implementation gate and validation

The original metadata-only contract started from #107 main `3893843744ab8cbb2ac630c31227df92051881eb` and normally merged `89c09710860e321f3a97949ee891ccfe8809f759`. That stage added no service, database or UI. The later #109 source registers the shared service, existing-Store journal and local/native routes; #113 supplies the restricted profile and #114/#115 supply conventional controls and the optional inspector. #116 adds paired admission, private transport and the remote restricted session over local-owner grants; #117 adds the iOS consumer; physical-device acceptance remains open. [#118](https://github.com/izyuumi/everything/issues/118) reconciles actual macOS and remote/iOS milestones incrementally and reuses [ADR-0010](../decisions/ADR-0010-hybrid-settings-contract.md).

Original contract checks and earlier core runtime identities retain their historical scope. The [current checkpoint](../architecture/settings.md) links actual merged source and exact-head CI. Historical Rust walkthroughs retain their own artifact boundaries; supported SDK compilation is not native UI/credential, successful provider or end-to-end manual verification. No full runtime/security acceptance or issue completion is claimed. Deferred scope/security/replay/UI automation is consolidated in [#32](https://github.com/izyuumi/everything/issues/32); no new tests or fixtures are introduced.
