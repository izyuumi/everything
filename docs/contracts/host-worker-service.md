# Host worker coordinator service

`src/host/worker/service.rs` composes the existing worker-purpose endpoint with the Host's leased Agent, native Scheduler, captured registry and owned mutation lock. It creates no second native loop, provider, Broker, executor runtime, identity or storage schema. The constructor performs no I/O. Actual Host startup supplies an explicitly configured coordinator endpoint and retains this service in its once-initialized optional field; no configured coordinator means no service or worker identity.

## Preparation and approval boundary

`prepare` validates the actual `WorkerPreparationRequest`, captures its explicit files through `capture_inputs`, and captures `ExecutionPolicy` against the Host's registry off the Tokio workers. A request must already name the canonical workspace and exact effective policy. Capture changes fail rather than changing the disclosed scope. The actual endpoint constructs `PreparedDelegation`; its manifest and fingerprint appear in the complete `WorkerPreparation`, alongside separate fresh local conversation/task/create/input identities and the executor's pinned public keys.

Preparation sends no task to a worker. It creates no conversation, task, Host command or stored approval. The service retains at most four preparations, including active captures and preparations already taken by the trusted Host admission workflow. Its aggregate held serialized payload accounting is bounded to 2 MiB. Each capture reserves 1536 KiB before work starts and then charges the actual serialized disclosure plus the opaque preparation's manifest. These bounds describe service-held payloads, not total process RSS or the bounded response held by an owner transport. Capacity exhaustion is an explicit error.

Tickets expire after at most sixty seconds and never extend the manifest deadline. Both wall time, including backwards movement, and monotonic time are checked. `take_prepared(ticket, digest, executor_fingerprint, request_id)` removes the original ticket once and validates the exact disclosed local create command ID. A mismatched attempt consumes that ticket. The returned opaque, non-cloneable `OwnedPreparedTicket` yields the full disclosure, actual one-shot `PreparedDelegation`, and a `PreparedBudgetLease`; the Host must retain that lease through actual approval, staging and native commit. It must capture the owner acceptance time before approval. The lease retains the Agent and preparation quota even if an IPC waiter disappears. Discard, expiry and close remove original in-memory preparations without reconstructing approval.

The Host owns the genuine owner command, durable compact admission mapping, explicit `approve`, `stage_approved`, `acquire_staged`, fresh dedicated conversation initialization and Scheduler admission. Stored JSON and this disclosure grant no fresh authority. An unadmitted record after restart cannot recreate the original monotonic approval.

## Outbound authority

The actual `WorkerOutboundGate` obtains owned Host mutation authority while its caller already owns endpoint authority. It checks exact current worker settings, intake/drain state, manifest endpoint/origin, complete native remote binding and immutable model/tool/mode/budget/loop limits. It recaptures the native execution policy against the current registry and workspace off the Tokio workers, then obtains the actual `Scheduler::remote_dispatch_permit`. Its permit retains the native permit, owned Host lock and leased Host through actual queue/send cleanup. A gate call is an owned bounded operation; dropping its waiter does not release a blocking capture or Actor request early. The Gate never calls back into the endpoint while holding Host mutation authority.

Lock order remains endpoint authority, Host mutation, Scheduler remote-admission mutex, native conversation authority, short write authority and Store. Owner handlers must not enter endpoint methods while already holding Host mutation authority. Disabling or changing the configured origin denies fresh Gates and result admissions and cancels this service's local relay/reconciler. It does not revoke accepted remote authority or prove a worker stopped. Restart is required to open a newly configured endpoint.

The constructor receives the actual startup settings snapshot. After a successful settings replacement, the Host calls `settings_changed(actual_saved_worker.as_ref())` while retaining its existing Host mutation lock. The service records exact desired-settings equality atomically; synchronous admission/status checks never contend with the settings repository's disk-writing mutex. Gate, result and native-admission checks occur after acquiring that same Host mutation authority, so they cannot cross a successful settings change using stale enablement. Direct external file edits are not adopted by the running Host. Changing back to the old origin after closing still requires restart.

## Reconciliation and inspection

`run` owns and joins the genuine `WorkerEndpoint::run_relay` and one reconciler. Worker and Scheduler changes wake reconciliation; a one-second bounded recovery wake handles missed/coalesced notifications. Passes start at most once per second, including failed Gate attempts whose Scheduler response itself emits a change. Reads of full worker jobs are serialized with owner inspection, and the existing worker ledger bounds a scan to 256 jobs. Successful reserved-Offer repair occurs at most once per delegation per service run, avoiding a self-triggered Scheduler-permit loop. Recovery uses the original binding, the real Gate and the original retained Offer. Relay send independently reacquires the Gate. No new attempt, approval or deadline is synthesized.

The genuine owner cancellation workflow records the original endpoint cancellation request before native cancellation. Reconciliation repairs a crash between those steps by mapping an actual ledger cancellation or sticky peer revocation to the exact native binding. Under owned Host mutation it refreshes that binding and requests native cancellation only if not already requested or terminal. This writes no replacement worker message or command ID and preserves Unknown and all original charges. It never derives cancellation from an ACK or a locally fabricated outcome.

Native cancellation that did not come through the coordinator, such as an ordinary owner or client `cancel_task` on the remote task, is also forwarded. When the native reservation has `cancel_requested`, the ledger job has no cancellation, result or rejection, the job is not terminal and the peer is not revoked, reconciliation acquires a cleanup operation permit and queues one worker Cancel with a fresh request ID under endpoint authority. That durable ledger cancellation stops further Offers and is not repeated. The owner Cancel operation skips a second worker Cancel when the ledger already records one, so the earlier request ID stays authoritative.

For an actual terminal worker source, reconciliation obtains `verify_native_outcome`, then owned Host mutation authority, and attaches it to the opaque verified outcome. `Scheduler::admit_remote_result` performs the existing atomic Agent acceptance. Only its actual receipt can enter fresh `acknowledge_native_result`. If cleanup begins after native acceptance, ACK may be omitted and later repaired from the genuine stored receipt. Current trust is rechecked by the endpoint; revocation can deny ACK without undoing accepted history. Rejected emits no invented result ACK. Unknown preserves native reservation, full charge and unresolved status; ACK, cancellation and revocation never imply stop proof or slot refund.

Queries expose the existing bounded public coordinator DTOs. Native mappings come from the full immutable manifest and pinned executor keys. Before lookup, the persisted row's binding and peer must equal the actual manifest binding/executor, and its coordinator/origin must match this endpoint and effective configuration. A mismatched row cannot lend cancellation intent to another manifest's native task. Only the typed exact `SchedulerError::RemoteBindingNotFound` produces an absent native mapping; unavailable manifest, changed binding and other Scheduler errors propagate. Status unresolved counts cover the coordinator's actual retained worker jobs. They do not assert that an independent library user has created no other remote tasks; the native Scheduler shutdown report remains authoritative for every reservation. Diagnostic codes contain fixed nonsecret categories and retain the latest observed reconciliation failure; they are not a claim that a retry or delivery succeeded.

## Ownership and drain

`begin_operation` bounds fresh owned mutations to four and checks current enablement before and after acquisition. `begin_cleanup_operation` uses the same bounded permits for Cancel, Revoke and Discard while fresh intake is closed. `close` stops intake, clears tickets and requests local relay/reconciler cancellation. `settings_changed` closes the old service when the actual saved settings differ. Neither API is a remote cancellation or stop attestation.

`run` places its completion ownership inside an independent spawned supervisor, so dropping its waiter does not lose the actual join. `shutdown` closes intake, waits for that supervisor and then calls `wait_operations`. The final barrier closes cleanup and query admission and waits for owned mutations, active preparation leases and bounded read tasks. Earlier drain queries remain available while their actual components are running. Host must await this barrier before stopping the shared Scheduler. No endpoint network task is aborted to manufacture quiescence, and already admitted Actor/blocking operations retain their guards and leased Agent until they settle.

Its actual production Host credential-rejection/recovery walkthrough also passed. Build provenance and earlier executor/bridge failure-path observations remain separately qualified in [worker validation](../development/worker.md#combined-host-validation-checkpoint); they do not independently establish this later production Host consumer's behavior, whose qualified runtime evidence is recorded at that same link. Successful remote inference, cloud isolation/security review, Apple execution and automated acceptance coverage are not verified here. New automated coverage remains deferred to issue #32.

The status history counts are paired optional values. This service returns actual `Some` counts from its bounded retained-ledger scan; absent composition returns `None` without opening or scanning a worker endpoint. Unknown counts are not zero, particularly after disabling previously active coordination.
