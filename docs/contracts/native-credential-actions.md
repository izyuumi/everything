# Private native credential actions

The Host-private NativeSettings SubmitCredential route carries one original NativeActionInvocation and the existing SecretTransfer through authenticated pipe-only owner ingress. It is excluded from ordinary owner request files, model tools, conversation/domain journals and relay commands. It never accepts a supplied success result or changes HostSettings. The private result is the actual original operation inspection, containing a sanitized receipt/state rather than credential bytes.

Only the original opaque NativeUi capability can request a fresh effect. The service checks the exact original target, session, principal, native attempt and tagged reference. A matching already admitted invocation returns its actual inspection before fresh-authority checks, drops the newly supplied secret and never repeats a write. Changed attempt/reference conflicts. Secret bytes and their hashes are not retained for replay comparison; operation identity binds the target and the first admission. A deliberate later replacement requires a fresh action identity and native ceremony. Inspect remains the recovery route during Host drain.

Fresh effects require resolved settings-file intents and an unchanged original revision. The service validates the actual private settings file and its equality with the authoritative repository cache before using a binding. Existing configured-reference replacement keeps the exact provider, endpoint, reference and Session/Native storage checks. SystemOne uses its existing canonical endpoint plus reference under its distinct ai.everything.system-one purpose; model credentials and ambient environment values cannot become classifier credentials. The route does not migrate keys, create configuration, select a model, contact a provider or perform a credential lookup.

Initial enrollment additionally accepts an unconfigured binding only when the original operation was created by NativeUi and its original native session matches its request binding. An action originally requested by SettingsAgent cannot use this case, even when a native client later submits its secret. The candidate reference must be non-nil and absent from every configured model, MCP environment and SystemOne credential reference. For a model, the exact provider and canonical endpoint must be the currently selected default conversation, with no credential binding already configured for that tuple. Its typed storage remains Session or Native. For SystemOne, the actual selection must already be configured at the requested canonical endpoint with no credential reference. Storing a key neither enables SystemOne nor changes its recipient. The same predicates run at preflight and immediately before the vault call under the existing owned Host effect guard; a public reference identifier supplies no authority.

Successful enrollment stores only the credential and returns the genuine original Completed receipt. HostSettings stays unchanged. A native consumer must separately submit a metadata-only full-settings owner CAS based on the original observed revision to link that exact reference. No combined vault/file transaction, automatic link, rebase, second secret write or rollback is implemented here. A conflicting or uncertain later metadata write leaves a potentially stored but unlinked key. Session storage is volatile to the Host lifetime; a restart between these separate operations can lose the session key. A durable receipt or configured reference alone does not prove current credential presence. The secure-entry consumer and this two-stage client workflow remain separate implementation work.

One service-owned task retains the original workflow when its caller stops awaiting. Admission acquires the existing Host mutation effect guard. Failure between durable admission and acquiring that guard uses the same original claim settlement and cleanup as a storage failure. One owned blocking worker holds the guard, secret, actual vault and whole service Core/Agent until storage and finalization settle. The existing vault session map handles session credentials. A narrow synchronous native entry point acquires the same native-store semaphore and calls the same established keyring implementation directly inside that worker; no inner asynchronous storage worker can outlive its admission guard. Source/revision/expiry/cancellation checks run immediately before the admitted vault call. No short application state mutex spans the OS operation. Close or cancellation after dispatch can leave an actual OS write completed; neither constitutes rollback.

Only a genuine successful vault return produces Completed with an opaque service-generated receipt. A storage/journal ambiguity invokes the existing Unknown repair path. Exact claim/session cleanup is attempted after both success and failure, with original and cleanup errors retained. Known receipts are immutable. An inspectable Unknown or InFlight record never authorizes a replacement write, and native Finalize observations cannot complete a credential action. Host configuration stays unchanged on credential failure; no atomic cross-store or previous-secret rollback guarantee is made.

The actual Host registers this adapter with the shared revisioned service and private native ingress. The [integrated walkthrough](../development/settings-validation.md) exercised the configured Session map through that route, including its original receipt/replay and exact-marker disk scan. It did not exercise initial enrollment or OS native storage. The initial-enrollment admission change requires its own source/build review and disposable runtime observations before acceptance. This source adds no Swift Session, foreground secure-entry ceremony, credential-presence query, metadata-linking consumer or remote settings authority. Supported Apple Keychain/UI observations remain unavailable in this Linux workspace. No automated tests were added; deferred verification remains [#32](https://github.com/izyuumi/everything/issues/32).
