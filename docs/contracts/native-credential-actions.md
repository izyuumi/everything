# Private native credential actions

The Host-private NativeSettings SubmitCredential route carries one original NativeActionInvocation and the existing SecretTransfer through authenticated pipe-only owner ingress. It is excluded from ordinary owner request files, model tools, conversation/domain journals and relay commands. It never accepts a supplied success result or changes HostSettings. The private result is the actual original operation inspection, containing a sanitized receipt/state rather than credential bytes.

Only the original opaque NativeUi capability can request a fresh effect. The service checks the exact original target, session, principal, native attempt and tagged reference. A matching already admitted invocation returns its actual inspection before fresh-authority checks, drops the newly supplied secret and never repeats a write. Changed attempt/reference conflicts. Secret bytes and their hashes are not retained for replay comparison; operation identity binds the target and the first admission. A deliberate later replacement requires a fresh action identity and native ceremony. Inspect remains the recovery route during Host drain.

Fresh effects require resolved settings-file intents, unchanged original revision and an exact currently configured binding. The service validates the actual private settings file and its equality with the authoritative repository cache before using that binding. Model credentials retain the configured provider, endpoint, reference and Session/Native storage. SystemOne uses its existing canonical endpoint plus reference under its distinct ai.everything.system-one purpose; model credentials and ambient environment values cannot become classifier credentials. The route does not migrate keys, create configuration, select a model, contact a provider or perform a credential lookup.

One service-owned task retains the original workflow when its caller stops awaiting. Admission acquires the existing Host mutation effect guard. Failure between durable admission and acquiring that guard uses the same original claim settlement and cleanup as a storage failure. One owned blocking worker holds the guard, secret, actual vault and whole service Core/Agent until storage and finalization settle. The existing vault session map handles session credentials. A narrow synchronous native entry point acquires the same native-store semaphore and calls the same established keyring implementation directly inside that worker; no inner asynchronous storage worker can outlive its admission guard. Source/revision/expiry/cancellation checks run immediately before the admitted vault call. No short application state mutex spans the OS operation. Close or cancellation after dispatch can leave an actual OS write completed; neither constitutes rollback.

Only a genuine successful vault return produces Completed with an opaque service-generated receipt. A storage/journal ambiguity invokes the existing Unknown repair path. Exact claim/session cleanup is attempted after both success and failure, with original and cleanup errors retained. Known receipts are immutable. An inspectable Unknown or InFlight record never authorizes a replacement write, and native Finalize observations cannot complete a credential action. Host configuration stays unchanged on credential failure; no atomic cross-store or previous-secret rollback guarantee is made.

The actual Host registers this adapter with the shared revisioned service and private native ingress. The [integrated walkthrough](../development/settings-validation.md) exercised the configured Session map through that route, including its original receipt/replay and exact-marker disk scan. It did not exercise OS native storage. This source adds no Swift Session, foreground secure-entry ceremony, credential-presence query, first-time enrollment or remote settings authority. Supported Apple Keychain/UI observations remain unavailable in this Linux workspace. No automated tests were added; deferred verification remains [#32](https://github.com/izyuumi/everything/issues/32).
