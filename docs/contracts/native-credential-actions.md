# Private native credential actions

The Host-private NativeSettings SubmitCredential route carries one original NativeActionInvocation and the existing SecretTransfer through authenticated pipe-only owner ingress. It is excluded from ordinary owner request files, model tools, conversation/domain journals and relay commands. It never accepts a supplied success result or changes HostSettings. The private result is the actual original operation inspection, containing a sanitized receipt/state rather than credential bytes.

Only the original opaque NativeUi capability can request a fresh effect. The service checks the exact original target, session, principal, native attempt and tagged reference. A matching already admitted invocation returns its actual inspection before fresh-authority checks, drops the newly supplied secret and never repeats a write. Changed attempt/reference conflicts. Secret bytes and their hashes are not retained for replay comparison; operation identity binds the target and the first admission. A deliberate later replacement requires a fresh action identity and native ceremony. Inspect remains the recovery route during Host drain.

Fresh effects require resolved settings-file intents and an unchanged original revision. The service validates the actual private settings file and its equality with the authoritative repository cache before using a binding. Existing configured-reference replacement keeps the exact provider, endpoint, reference and Session/Native storage checks. SystemOne uses its existing canonical endpoint plus reference under its distinct to.yumi.vorra.system-one purpose; model credentials and ambient environment values cannot become classifier credentials. The route does not migrate keys, create configuration, select a model, contact a provider or perform a credential lookup.

Initial enrollment additionally accepts an unconfigured binding only when the original operation was created by NativeUi and its original native session matches its request binding. An action originally requested by SettingsAgent cannot use this case, even when a native client later submits its secret. The candidate reference must be non-nil and absent from every configured model, MCP environment and SystemOne credential reference. For a model, the exact provider and canonical endpoint must be the currently selected default conversation, with no credential binding already configured for that tuple. Its typed storage remains Session or Native. For SystemOne, the actual selection must already be configured at the requested canonical endpoint with no credential reference. Storing a key neither enables SystemOne nor changes its recipient. These predicates run at preflight and again under the existing owned Host effect guard immediately before the vault call; a public reference identifier supplies no authority.

Successful enrollment stores only the credential and returns the genuine original Completed receipt. HostSettings stays unchanged. A native consumer must separately submit a metadata-only full-settings owner CAS based on the original observed revision to link that exact reference. No combined vault/file transaction, automatic link, rebase, second secret write or rollback is implemented here. A conflicting or uncertain later metadata write leaves a potentially stored but unlinked key. Session storage is volatile to the Host lifetime; a restart between these separate operations can lose the session key. A durable receipt or configured reference alone does not prove current credential presence. The separately integrated [macOS secure-entry consumer](apple-native-credential-entry.md) now implements that two-stage workflow with distinct original storage and metadata-link receipts.

One service-owned task retains the original workflow when its caller stops awaiting. Admission acquires the existing Host mutation effect guard. Failure between durable admission and acquiring that guard uses the same original claim settlement and cleanup as a storage failure; because the vault was never called, its outcome is classified as described below. One owned blocking worker holds the guard, secret, actual vault and whole service Core/Agent until storage and finalization settle. The existing vault session map handles session credentials. A narrow synchronous native entry point acquires the same native-store semaphore and calls the same established keyring implementation directly inside that worker; no inner asynchronous storage worker can outlive its admission guard. Source/revision/expiry/cancellation checks run immediately before the admitted vault call. No short application state mutex spans the OS operation. Close or cancellation after dispatch can leave an actual OS write completed; neither constitutes rollback.

Only a genuine successful vault return produces Completed with an opaque service-generated receipt. A failure known to precede the vault write records a definite terminal outcome on the original operation instead of Unknown: cancellation of the original claim, including its session close, records Cancelled; original expiry or an expired native origin records Unavailable/expired; a changed Host revision records Conflict with the actual observed revision; the vault's pre-write capacity/key/value rejections record Failed/storage; and a platform without native storage records Unavailable/native-action-unavailable. Any other failure, including every keyring/OS write error, session-map tracking error, revision-unchanged conflict, stopped intake or worker failure, remains a storage/journal ambiguity and invokes the existing Unknown repair path. A definite outcome lets the native consumer release its blocking state; it still neither proves that an earlier configured secret is present nor replaces the original receipt. A deliberate retry is a fresh action and native ceremony. Exact claim/session cleanup is attempted after both success and failure, with original and cleanup errors retained. Known receipts are immutable. An inspectable Unknown or InFlight record never authorizes a replacement write, and native Finalize observations cannot complete a credential action. Host configuration stays unchanged on credential failure; no atomic cross-store or previous-secret rollback guarantee is made.

The actual Host registers this adapter with the shared revisioned service and private native ingress. A separate [initial-enrollment walkthrough](../development/settings-validation.md#initial-credential-admission-increment) used the exact `c62739b` release: unconfigured Model Session storage returned genuine Completed without changing settings, replay retained its original inspection, and a separate metadata-only owner CAS linked the reference at revision 3. Configured replacement also completed. Already-bound new-reference, unselected-endpoint, nil-reference and wrong-native-session cases were rejected; original cleanup inspection survived session close. Independent immutable-history review is scoped CLEAR with the recorded limitations.
