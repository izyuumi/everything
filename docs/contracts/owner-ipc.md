# Same-user owner IPC

`ipc` adds typed owner commands, queries, operations, and bounded conversation waits to the authenticated [Unix IPC transport](local-ipc.md). Authentication means the same operating-system user. These requests must not be accepted through paired-device domain command ingress.

`OwnerCommand::Text` retains the CLI's conversation ID, command ID, exact text, and explicit `RequestedRunOptions`. `OwnerCommand::Initialize` retains the original conversation ID, command ID, title, and exact conversation configuration. Durable admission retains their raw JSON before typed decoding can discard fields. The host inbox explicitly distinguishes this legacy narrow identity from full domain-envelope identity.

`OwnerQuery` covers bounded conversation and task lists, individual conversation/task metadata, permission approvals, non-secret settings, public device identity, paired devices, relay connection state, host drain state, actual broker recovery requirements, and a command receipt. Individual task results distinguish scheduler-owned execution metadata from unchanged legacy foreground rows. List limits are 1–100. Query results expose public domain/task information and receipts rather than private provider continuations, raw scheduler checkpoints, or credential values. Conversation history uses the existing bounded synchronization contract.

`OwnerOperation` covers settings replacement with expected revision, ephemeral session/native credential store/remove, pairing invitation creation, explicit fingerprint-and-access pairing approval, device revocation, task wake, an explicit expected-attempt provider retry, exact known-interruption resume, post-drain reconciliation, and exact cleanup acknowledgement. Credential values occur only in the credential operation. Pairing invitation material occurs only in its explicitly requested ephemeral response. Both have redacted debug output. Settings replacement and credential storage are separate operations so a failed platform credential write cannot silently rewrite settings or select another credential source.

Provider retry supplies a target task and exact expected attempt. The transport's unique request ID must reach the native scheduler's one-use transition. A reconnect must reuse that same request ID; it must never persist a reusable retry boolean or automatically retry a changed attempt after a crash. Task wake does not itself authorize an uncertain paid provider attempt. Known `Paused(Cancellation|InterruptedTool)` resumption separately binds the expected active command, checkpoint revision, phase, and unique owner request ID. None of these operations stores a reusable retry default.

`ConversationWait` names one conversation, the last observed sequence, and a timeout from 1 to 30,000 milliseconds. A handler registers the scheduler change subscription before querying durable state, then returns a higher durable event sequence, a scheduler change hint, or a timed-out unchanged cursor. A change hint can concern task state without a new conversation event; clients requery the task and conversation rather than assuming the cursor advanced. Process-local change revisions are hints; clients requery after restart. Waiting is neither an execution queue nor permission to cancel a task when the client disconnects.

`wait_command` names one command ID and a 1–30,000 millisecond timeout. The host subscribes before reading its durable receipt. A non-timeout response requires an exact matching terminal receipt; a timeout may return the current nonterminal receipt or absence. Client disconnection after durable admission never removes or cancels that command.

While draining, normal new commands and work-enabling operations fail closed. Owner inspection and explicit broker recovery remain available after the scheduler actor stops. `reconcile_drained` requires the retained proof that owned scheduler workers drained and records abandoned Running entries as Unknown under real broker exclusion. `acknowledge_cleanup` requires the exact unchanged operation result digest, operator identifier and actual inspection note. The host retains its state lease until no Running operation or unresolved cleanup requirement remains.

The transport captures `original_command` only for durable submit/owner command variants. It never attaches an entire credential-bearing request to a `LocalCall` journal field. All responses must match their request IDs and kinds and fit the two-MiB frame bound. An oversized query result returns a bounded `busy` rejection asking for fewer records. The actual host handler and CLI proxy serve these operations. Settings whose relay origin changes return `restart_required`; the running relay uses its captured origin until restart. Recurring host loop defaults reject absolute deadlines.

Rust 1.88 all-target/all-feature format, compilation, strict Clippy and release build passed. Disposable Linux host/CLI observations verified singleton ownership, exact durable initialization replay and changed-identity rejection, missing-credential task admission and metadata, host lifetime independent of CLI exit, actual event synchronization, settings deadline rejection, clean socket removal and restart preservation. A real literal-loopback native request additionally observed connection refusal, exact one-use retry, replay without another attempt, restart without automatic retry, and absence of transferred session credential bytes from persistent state. A manually inserted disposable abandoned Running journal exercised owner inspection during retained-lease drain, reconciliation, wrong-digest rejection, exact attestation and clean exit; it did not verify live process cleanup. These observations did not verify successful model inference, a live relay, native credential-store access, macOS launchd behavior, or different-UID rejection. Deferred automated coverage is tracked in [#32](https://github.com/izyuumi/everything/issues/32).
