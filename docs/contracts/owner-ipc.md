# Same-user owner IPC

`ipc` adds typed owner commands, queries, operations, and bounded conversation waits to the authenticated [Unix IPC transport](local-ipc.md). Authentication means the same operating-system user. These requests must not be accepted through paired-device domain command ingress.

`OwnerCommand::Text` retains the CLI's conversation ID, command ID, exact text, and explicit `RequestedRunOptions`. `OwnerCommand::Initialize` retains the original conversation ID, command ID, title, and exact conversation configuration. Durable admission retains their raw JSON before typed decoding can discard fields. The host inbox explicitly distinguishes this legacy narrow identity from full domain-envelope identity.

Requests that fail to decode are rejected with the field path described in [local IPC responses](local-ipc.md#responses); `ipc::decode_json` finds that path by removing one key at a time and keeping the key whose removal changes the decoder error, because serde's internally tagged enums do not report positions.

`OwnerQuery` covers bounded conversation and task lists, individual conversation/task metadata, permission approvals, non-secret settings, public device identity, paired devices, relay connection state, host drain state, publication progress, actual broker recovery requirements, and a command receipt. Individual task results distinguish scheduler-owned execution metadata from unchanged legacy foreground rows. List limits are 1–100. Query results expose public domain/task information and receipts rather than private provider continuations, raw scheduler checkpoints, or credential values. Conversation history uses the existing bounded synchronization contract.

Pending approval inspection uses `approvals { conversation_id, limit, cursor }`. The default limit is 20 and explicit limits are 1–100. Responses contain `ApprovalSummary` metadata and an optional exclusive `(requested_at, approval_id)` cursor, capped at 256 KiB. Summaries include the approval, operation, task and tool identities, request/expiry times, argument byte count and pending status. SQLite projects only bounded metadata; arguments and full scopes do not enter the listing result. Pagination is a current pending view, not a fixed snapshot: expiry and resolution can remove entries, and clients restart without a cursor to discover newly inserted earlier keys. A cursor advances only through returned summaries.

Fetch one complete request with `approval { conversation_id, lookup: { by: "approval" | "operation", id } }`. This exact lookup decodes and validates the entire original scope and arguments and returns its current status, including resolved outcomes. It verifies conversation binding and avoids unrelated retained-history scans. Summaries are navigation metadata; exact lookup remains authoritative before requesting a decision. The CLI's approval/denial resume path fetches the supplied approval ID directly and verifies its task and pending status.

`OwnerOperation` covers settings replacement with expected revision, explicit original-ID settings reconciliation, ephemeral session/native credential store/remove, pairing invitation creation, explicit fingerprint-and-access pairing approval, device revocation, task wake, an explicit expected-attempt provider retry, exact known-interruption resume, post-drain reconciliation, and exact cleanup acknowledgement. Credential values occur only in the credential operation. Pairing invitation material occurs only in its explicitly requested ephemeral response. Both have redacted debug output. Settings replacement and credential storage are separate operations so a failed platform credential write cannot silently rewrite settings or select another credential source.

Provider retry supplies a target task and exact expected attempt. The transport's unique request ID must reach the native scheduler's one-use transition. A reconnect must reuse that same request ID; it must never persist a reusable retry boolean or automatically retry a changed attempt after a crash. Task wake does not itself authorize an uncertain paid provider attempt. Known `Paused(Cancellation|InterruptedTool)` resumption separately binds the expected active command, checkpoint revision, phase, and unique owner request ID. None of these operations stores a reusable retry default.

`ConversationWait` names one conversation, the last observed sequence, and a timeout from 1 to 30,000 milliseconds. A handler registers scheduler and metadata change subscriptions before querying durable state, then returns a higher durable event sequence, a process-local change hint, or a timed-out unchanged cursor. A change hint can concern task state without a new conversation event; clients requery the task and conversation rather than assuming the cursor advanced. Process-local change revisions are hints; clients requery after restart. Waiting is neither an execution queue nor permission to cancel a task when the client disconnects.

## Live assistant text

The `task` query's scheduler-owned `execution` metadata carries an optional additive `live_text { attempt_id, text }`. It is the provisional text the running native task has received from the provider so far in its current model attempt, in the order the adapter emitted deltas. `attempt_id` is the native model attempt ID; a new attempt, including a tool-round continuation or an explicit retry, starts a new empty text. Within one attempt the text only grows, so a client that printed an earlier snapshot prints the suffix of the next one. The field is absent when no native task attempt is streaming, after the worker stops, for legacy foreground rows, on the dedicated executor and from a host that predates it. Serialization omits an absent value; deserialization defaults it, so older clients ignore it and newer clients treat an older host as never streaming.

Live text is a best-effort, non-durable, process-local view. The scheduler worker appends each provider delta to one bounded in-memory entry per running task, capped at the 128 KiB chat text limit, and removes that entry when the worker returns. Recording a delta is a short synchronous update and the existing change hint; clients poll it through ordinary owner queries and `wait`. There is no per-client buffer or subscription, so a slow, stalled or disconnected client cannot delay, block or fail the provider turn, and a client can miss intermediate snapshots. No conversation event is appended, no checkpoint changes and nothing is replayed after a restart. The committed assistant message remains the only source of truth: clients replace live text with that saved message rather than concatenating them. Live text contains only provider-visible assistant output that the saved message would also contain, never credentials or private continuation state. It is not part of encrypted synchronization batches, so the relay and paired devices do not receive it.

## Memory use

The `conversation` query's `information` carries an optional additive `memory_use { command_id, excerpts }` for the active or most recent native turn: `excerpts` is the number of retrieved Wiki memory excerpts saved into that turn's definition and supplied to context building. It is derived from the native checkpoint, so it is durable and survives restart; a turn whose context budget omits some excerpts still reports the saved count. Serialization omits an absent value and deserialization defaults it, so an older host reports no memory use and older clients ignore it. Clients compare `command_id` with their own command before showing it.

`wait_command` names one command ID and a 1–30,000 millisecond timeout. The host subscribes before reading its durable receipt. A non-timeout response requires an exact matching terminal receipt; a timeout may return the current nonterminal receipt or absence. Client disconnection after durable admission never removes or cancels that command.

While draining, normal new commands and work-enabling operations fail closed. Owner inspection and explicit broker recovery remain available after the scheduler actor stops. `reconcile_drained` requires the retained proof that owned scheduler workers drained and records abandoned Running entries as Unknown under real broker exclusion. `acknowledge_cleanup` requires the exact unchanged operation result digest, operator identifier and actual inspection note. The host retains its state lease until no Running operation or unresolved cleanup requirement remains.

The transport captures `original_command` only for durable submit/owner command variants. It never attaches an entire credential-bearing request to a `LocalCall` journal field. All responses must match their request IDs and kinds and fit the two-MiB frame bound. An oversized query result returns a bounded `busy` rejection asking for fewer records. The actual host handler and CLI proxy serve these operations. Settings whose relay origin changes return `restart_required`; the running relay uses its captured origin until restart. Recurring host loop defaults reject absolute deadlines.

At the earlier owner-IPC milestone, Rust 1.88 all-target/all-feature format, compilation, strict Clippy and release build passed. Those prerequisite observations do not verify the newer SettingsService routes below. Disposable Linux host/CLI observations verified singleton ownership, exact durable initialization replay and changed-identity rejection, missing-credential task admission and metadata, host lifetime independent of CLI exit, actual event synchronization, settings deadline rejection, clean socket removal and restart preservation. A real literal-loopback native request additionally observed connection refusal, exact one-use retry, replay without another attempt, restart without automatic retry, and absence of transferred session credential bytes from persistent state. A manually inserted disposable abandoned Running journal exercised owner inspection during retained-lease drain, reconciliation, wrong-digest rejection, exact attestation and clean exit; it did not verify live process cleanup. These observations did not verify successful model inference, a live relay, native credential-store access, macOS launchd behavior, or different-UID rejection. Deferred automated coverage is tracked in [#32](https://github.com/izyuumi/everything/issues/32).

A disposable real native `write_file` authorization walkthrough produced three pending requests whose full listing was 3,061,981 bytes. Metadata pages of one and two summaries totaled 1,362 bytes, while exact approval-ID and operation-ID lookup each returned the identical complete 1,020,732-byte response. Cross-conversation lookup was rejected and a resolved denial remained inspectable. No tool was executed for this permission walkthrough.

`discard_unapplied` is an explicit same-user owner operation for a known queued command ID and its exact `expected_accepted_at`, with a nonempty operator of at most 128 bytes and reason of at most 1024 bytes. Its immutable audit stores the IPC request ID. The response is a matching Rejected command receipt. Idempotence is scoped to the original command and discard request ID, with payload availability following retention. For that original command, a changed reason, operator, acceptance time or request ID conflicts; another target is a separate action. It is unavailable during drain and cannot discard controls, Applied records, Agent-journaled work, admitted tasks or an initialization whose conversation exists. See [discard invariants](host-inbox.md#explicit-discard-of-unapplied-queued-work).

OwnerQuery::Publication returns initial/final pass completion, cumulative pass/event/failure counters, last completion time and a bounded last diagnostic. Task metadata converges to observed current state; this status does not certify a complete transient lifecycle history.

## Shared Settings routes

Actual verified LocalCall ingress intercepts `replace_settings` and routes it through the shared [SettingsService](settings-service.md), which owns mutation locking, full validation, exact request identity, file intent/CAS and protected-change rejection. The internal generic owner dispatcher rejects replacement/reconciliation rather than creating a caller from an ID. A raw full replacement cannot approve protected provider or System One recipient changes; it returns the original HostActionRequired outcome.

Production `settings_receipt` returns the original validated operation inspection, the original restart flag and an optional exact-current known-applied settings snapshot. It binds the frame request ID, LocalOwner origin, expected revision and any returned full snapshot to the original submitted settings plus one revision increment. A newer file cannot masquerade as that old result. Applying/Unknown retain the original identity; a known file save remains distinct from pending, failed or unavailable backend application. The legacy macOS general form accepts this and the retained older `settings` reply, adopts only returned saved data and never labels rejection Saved. The final valid signed-64-bit revision is readable, with further edits refused. See [owner receipts](settings-owner-routes.md).

`settings_operation { request_id }` is a bounded original inspection using the central metadata validator. `reconcile_settings { operation_id }` explicitly observes that original pre/post file and returns `settings_reconciled`; it creates no new write identity, rewrites no file and directly launches no helper. Both derive their cleanup caller from the verified owner frame and remain available during drain. Fresh replacement still requires live intake. Reconciliation and status are distinct from the Host worker's later original-operation application.

The separate `owner --sensitive-stdin` path requires private pipe/FIFO stdin and stdout; it accepts bounded native Settings frames and credential operations with zeroizing transport buffers. Regular request files cannot carry those frames or secret-bearing credential requests. The closed [native routes](native-settings-routes.md) include Open, Describe/Get/Changes, Update, exact ConfirmPatch/Reconcile and existing action/device/cleanup operations. A proof is Host-minted and remains ephemeral; public session/operation/reference IDs never create authority. No general OwnerOperation is forwarded through paired-device ingress. Native Settings credential actions require an already configured exact binding; this source does not complete initial enrollment or native screen composition.

[Startup policy and the application driver](host-settings-startup.md) use the same actual settings snapshot, Composition and Agent. An unresolved file intent or exact-current unobserved application keeps optional embeddings/remote selection off before optional access. The driver subscribes before authoritative pending reads and awaits admitted work. Drain closes intake under mutation, releases it, settles settings claims, then starts actual Memory/selector shutdown before the final driver join. Missed redacted change hints require authoritative rereads; reads/client replay never apply work.

These routes are implemented source. Earlier core/runtime receipts and partial Rust checks do not establish final combined #109 validation, Apple SDK/UI behavior, native credential writes, the #113 restricted runtime or remote settings grants. Those gates remain explicit.

## Scheduling owner routes

`schedule { query }` accepts the typed Controls list/show/history/run inspection requests. `schedule_engine` returns the real owned engine status. List uses exclusive `after_id` and optional enabled/deleted filters; history uses exclusive descending `(claimed_at, occurrence_id)`. Both limits are 1–100 and may return a smaller byte-bounded page with its actual continuation cursor. Responses validate their target IDs, limits, strict order, filters and continuation against the originating request.

`schedule { mutation }` accepts create/update/disable/delete and manual `Run` with the full immutable `ManualClaim`. Normal edits use exact observed revisions with no retry/refetch. Result validation checks requested job identity and definition, the expected next revision, or the original manual occurrence/command identity. The owner gate derives requested execution authority from the explicit future or immutable replay target, never from changing host defaults. Queries and mutation results use the real Controls DTOs; [scheduling controls](scheduling-controls.md) defines those semantics.

`acknowledge_scheduled_unknown { request }` requires the full `UnknownAcknowledgementRequest`, including its original acceptance timestamp. A retry retains every field; the response must echo that exact request. The server records the real effective UID and does not accept client UID authority. This same-user route remains usable while draining and is absent from model/paired command ingress. It clears no Broker/native uncertainty and schedules no retry. The [CLI](../development/scheduling-cli.md) prints stable replay metadata before dispatch. The fresh focused Linux walkthrough exercised these owner routes across 115 CLI calls without seeded records, including exact immutable manual replay after edits, paging/CAS, actual provider refusal, digest acknowledgement and graceful reopening. The retained schema-9 database passed independent integrity and foreign-key checks. This does not establish simultaneous mutation races, forced crashes, successful inference or Apple behavior.

## Host composition routes

Defaulted service settings and `composition` status expose desired versus active memory/MCP/selector configuration and restart requirements. The authenticated owner can inspect maintenance jobs and bounded retrieved excerpts, enqueue/cancel/retry maintenance, apply an explicit cited host plan, and explicitly rebuild enabled embeddings within bounded chunk/time limits. These operations use the same Wiki owner and report real FTS/hybrid/fallback/cancellation states.

`prepare_selection` binds the complete original local command, captured execution and registry. Only `approve_selection` for that exact ticket can disclose its actual endpoint/model/payload/authority; the identical later domain command consumes that one-shot result. Missing or expired consent retains local selection. Purpose-bound MCP credential operations use the same vault; session values must be supplied through the explicit startup route before server discovery. No raw secret is accepted in durable settings or a domain command. The [composition](host-composition.md), [selection](host-selection.md) and [MCP credential](mcp-credentials.md) contracts define these typed routes and their limits. Fresh schema 9 owner-route observations passed memory/selector/MCP/bootstrap and actual local embedding operations at all four supported dimensions; the composition contract records exact qualifications.


## Worker owner routes

`worker_coordinator { query }` and `worker_coordinator { operation }` carry the actual [Host coordinator DTOs](host-worker.md). Queries expose Status, Identity, Peers, Jobs and exact Delegation/Task inspection. Operations pin explicit fingerprints, prepare the complete disclosure, discard a ticket, delegate its exact one-shot approval, cancel the original binding or permanently revoke a purpose peer. Delegate's outer owner request ID must equal the disclosed `local.create_command_id`; its retained ingress mapping preserves exact replay. The [coordinator CLI](../development/worker-coordinator-cli.md) uses these routes without opening another Agent or connecting directly to a relay.

When the coordinator service is absent, Status creates no worker identity, endpoint or history scan. It returns paired `jobs: null` and `unresolved_remote_tasks: null` for uninspected retained history, with known zero in-process preparations and operations; other coordinator queries require the retained service. A live settings disable retains that service for inspection, whose Status still scans and returns actual `Some` counts with `enabled: false`. Enabling or changing its relay requires Host restart; disabling fresh intake neither cancels remote effects nor converts unknown history to zero.

The dedicated executor instead serves `worker { query }` and `revoke_worker_peer`, together with its restricted existing identity/runtime/task/cleanup queries and exact cleanup attestation. Ordinary Host commands and coordinator operations are rejected there; an ordinary Host rejects executor-only routes. Both use the same authenticated LocalServer protocol and retained Agent lease. Their purpose identities, pins and native credentials remain separate from ordinary paired-device rights. Cleanup acknowledgment preserves Unknown outcomes and grants no model retry.

These source routes passed the six normal-package Rust 1.88 gates at `d273c52`. The actual Host consent, native-admission, credential-rejection, replay and joined-shutdown walkthrough passed; exact build/runtime provenance and separately completed executor/bridge qualifications are in [worker validation](../development/worker.md#combined-host-validation-checkpoint).
