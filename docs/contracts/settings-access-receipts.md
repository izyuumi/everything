# AccessStatus receipt storage

The held `Store::admit_settings_access` is the sole Access-specific receipt writer. It consumes no request owner and returns only `Duplicate` or `Fresh { reply }` metadata after an observed successful commit. It creates no Source, Original, parent, caller, effect, BUILD permission or private response. Accepted relay Delivery remains disabled until the actual owned receive and publication consumers exist. Compilation and SQLite/runtime behavior of this slice have not been verified.

The method borrows the genuine `OwnedVerifiedSettingsAccess`, its exact receipt authority and the original verified metadata. It checks the real receive-time Source and validates metadata before opening an Immediate transaction on that same Store connection. Existing receiver validation checks the complete pinned registration, revocation and local recipient. Exact sender/recipient/encrypted-envelope digest comparison for the message ID precedes pruning, query registration and all capacity checks. An exact duplicate receives no new query registration, reservation, owner or expiry; its read transaction still requires an observed successful commit. A changed encrypted identity remains a structured conflict.

Fresh admission uses the actual [Core receipt plan](settings-access-qualification.md), retaining the same capability, request and transaction. Only its opaque specification selects Default49152 with an actual grant reference or Denial4096 with `grant:null`; both preserve canonical complete-peer Host provenance and `parent_id:null`. The writer creates one reservation UUID, uses the existing shared queued-plus-reserved global/peer quota and the existing100000 replay-marker ceiling, and performs plain INSERTs for the exact schema17 reservation and processed marker. Marker payload, command ID and detail are NULL. It persists no plaintext, query body, private hash or model data, and writes no Original or command row.

Every text field in reservation/marker/duplicate readback is borrowed and bounded before comparison. Reservation readback covers all eight immutable columns; marker readback covers all ten columns and NULL/state semantics. After both inserts the writer repeats reservation and marker checks, validates the actual receiver again and invokes the same plan's final recheck immediately before its one COMMIT. The plan preserves the actual first-query and current replay Source clock bounds; the writer cannot renew them or promote a denial reservation.

All returned errors after transaction creation pass through explicit rollback. The primary actual qualification/storage/capacity cause is retained; rollback failure retains both that primary cause and the actual rollback storage error. Successful rollback preserves an expected capacity or narrow policy rejection classification. A rollback wrapper, bookkeeping/storage failure, unavailable observation or uncertain commit is neither capacity nor policy rejection and requires the actual owner to remain nonclean. No error text selects a disposition.

The pinned rusqlite0.37 consuming `Transaction::commit` cannot expose its Drop rollback failure. This writer therefore issues the same actual `execute_batch("COMMIT")` while retaining the original transaction. On failure it preserves a distinct Commit cause and explicitly attempts rollback once with DropBehavior::Ignore, preventing a hidden destructor retry. Even a successful rollback does not turn an uncertain COMMIT into NoEffects, Duplicate or Fresh. Successful COMMIT leaves the connection in autocommit and dropping its wrapper performs no further transaction SQL. These are source semantics, not observed engine/fault behavior.

The bounded `StoredSettingsAccessReply` contains only reservation/local/peer IDs, canonical public provenance, closed family and fixed creation/expiry metadata. It is data, not authority or proof of a joined worker. The request, actual Agent/StateLease/Main/endpoint/Host guard, returned metadata and structured error must remain registered through the original blocking job and true join. A dropped waiter must not refund a query or slot. Unknown commit/rollback outcomes must never cause automatic retry, new reservation, ACK or clean-drain claims.

Root owns narrow storage reexports and the real [receive/BUILD lifecycle](settings-command-receive.md). Access-specific joined events, counted permit-before-DATA construction, current projection, seal/transfer, queued/send ownership, cleanup and requesting-client adoption remain separate gates. Existing native, Bind, DirectUpdate, ordinary receipt and publication bodies are unchanged. Direct Rust1.88 formatting and static preservation provide no compilation, SQL, transported acceptance or security proof. Issues #116/#117 and deferred automated verification #32 remain open.
