# Settings operation service

The #109 service extends the [typed contract](settings.md) with one leased Host authority, a bounded journal in the existing Store, a revision-safe file writer and original-operation application work. The source implements descriptors, Host snapshots, typed batch updates, full-owner replacement receipts, protected native confirmation, explicit file reconciliation and redacted change hints. The existing Host now registers this service, its application worker and the [native](native-settings-routes.md) and [owner](settings-owner-routes.md) routes. Final combined source verification and disposable integrated observations remain coordinator gates. This document describes the implemented Rust boundary, not a completed #109 acceptance or security review.

## Trusted sources

SettingsService opens only with the same actual Agent StateLease as SettingsRepository and the configured Host endpoint. It shares actual Host mutation admission and binds one actual Arc<Composition> after comparing Store and retained StateLease identity. The same Arc may be rebound; another instance conflicts. This consistency check grants no authority. There is no back-reference cycle, and the whole service core retains its Agent last through actual blocking work.

LocalCall is the server-created, same-UID authenticated local request. A supplied principal/session UUID cannot create a caller. LocalOwner records the actual frame request ID and uses that command UUID only as a logical operation scope. It cannot impersonate NativeUi or approve a protected recipient. NativeUi requires a Host-minted private proof; a restricted SettingsAgent caller is an attenuation of the original live native session and one exact SettingsToolName. The two public Rust attenuation methods expose no owner/native constructor, serialization or arbitrary-ID authority. The immutable restricted model profile and executable seven-tool namespace remain #113 work. There is no remote caller constructor; #116 must supply authenticated envelopes and live explicit grants.

Native sessions use random 32-byte private capabilities, an in-memory domain-separated SHA-256 fingerprint, redacted Debug and shared zeroizing secret storage. There are at most sixteen native and sixteen restricted sessions, with original wall and monotonic lifetimes of at most five minutes. Public IDs, action references, inspections and receipts are metadata. Sensitive proof, credential and invitation values must not enter request files, durable rows, chat, relay or logs. Existing transport/serde/Swift/OS buffers do not provide universal zero-copy or secure erasure.

Closing a CLI connection is not UI-session close. Explicit close, expiry, target change or Host restart rejects new admission without renewing a lifetime. An already-admitted exact action may finalize or inspect through its original retained cleanup proof. Cleanup cannot read another action, approve another patch or retry a credential. Observed OS authorization is not a grant. This service currently rejects device-preference and observed-OS facade reads/patches without their genuine client-device adapter; it does not borrow the Host revision or substitute the Host ID for a phone/Mac identity.

## Registered local ingress

Verified LocalCall owner replacement invokes this same service without another outer mutation guard. Its durable SettingsReceipt may include full settings only for the exact original known-applied post-file; inspection and explicit original-ID reconciliation remain available through verified owner cleanup admission during drain. The [owner route contract](settings-owner-routes.md) defines frame/origin/revision/content checks and the retained legacy macOS decoder.

The closed [native route enum](native-settings-routes.md) maps Describe, Get, Update, ConfirmPatch, Changes and Reconcile to these actual methods, alongside existing native/device actions. Session proof and credential/invitation transfer use `owner --sensitive-stdin` with private pipe/FIFO descriptors and bounded zeroizing buffers. The ordinary request-file path rejects these frames. The native credential route supports configured replacement and narrow initial storage; it supplies no complete secure-entry/linking consumer, native settings screen, remote authority or dedicated seven-tool model runtime.

## Original operations and native actions

The retained target is a typed SettingsPatch, SettingsActionRequest, SettingsDeviceRequest or hash-only OwnerReplacementIdentity. Identity binds the real principal, source, native parent where applicable, exact scope/revision, canonical request digest and original times. Fresh confirmation metadata is rejected. Changing the target, source or binding under an original request ID conflicts. Exact replay precedes current-state/profile/capacity preparation and never creates a reference, extends expiry or starts application work.

| Phase | Meaning |
| --- | --- |
| AwaitingConfirmation | One original protected patch and reference await native confirmation. |
| AwaitingAction | One original native/device request and handle await admission. |
| InFlight | One exact native request is admitted; no revision is fabricated. |
| Applying | The immutable file intent is admitted, including expected/proposed revisions. |
| Finished | The original authoritative file/action result is retained; optional application has a distinct observation. |

A model/provider/endpoint change or System One recipient/model change requires confirmation of the retained original patch. Native confirmation does not resend changed JSON or add a reference to the original request. Raw local-owner protected changes return durable HostActionRequired; they cannot mint NativeUi. One native claim per effect is enforced in SQLite. An exact native invocation returns its existing inspection and grants no second dialog/effect; a changed native ID/session/reference conflicts.

Opaque non-Clone/non-Serde admission retains the original identity, Agent, cancellation and session. NativeHostEffectAdmission additionally owns the actual Host mutation guard. Potentially blocking revision inspection precedes final live-source, cancellation and original wall/monotonic checks. No deadline is recaptured. Closed native observations accept only dismissal, known-section navigation or actual notification authorization. A caller-supplied result, receipt, revision or generic success flag cannot complete an effect.

The real [device facade](device-settings.md#shared-settings-facade) creates/cancels exact pending pairing IDs and invokes existing exact-pin revocation cleanup. The [native credential adapter](native-credential-actions.md) invokes the actual vault for an already configured exact ModelCredentialReference/SystemOne binding, or for a genuine original NativeUi initial-storage action at the currently selected exact endpoint with no existing binding and an unused non-nil reference. Initial storage leaves settings unchanged; linking metadata is a separate owner CAS based on the original revision. The #110/#114 secure-entry consumer remains unimplemented. Neither adapter changes settings or claims rollback/remote stop.

## Descriptors and snapshots

`describe` requires the exact list tool and constructs the registry from the actual cached EmbeddingProfile. No active/known profile means dimension choices are absent. It does not load artifacts, probe credentials, discover providers or issue network requests. `get` requires the get tool and validates the actual private settings file against the repository cache. Its Host snapshot reports desired settings, actual semantic admission/backend metadata and real selector configuration. Model selection configures subsequent runs; captured active native inputs remain unchanged.

Disabled embedding preference preserves operator artifact paths/configuration. Dimension overrides distinguish Inherit, BackendDefault and Selected; new choices require the actual known profile. The backend default comes from the actual shipped backend, not a Swift list or pretend embedder. Missing metadata stays unavailable. A cached profile is metadata and does not prove a loaded/healthy helper. Failed, unavailable, stopped or superseded backend application is unavailable rather than perpetually pending or effective merely because values coincide.

## One file writer and exact reconciliation

`update` validates the complete same-scope batch before preparation. `replace_as_owner` preserves full typed settings validation/CAS while retaining only a canonical request hash, changed keys, revisions and authenticated owner scope in the journal. Actual validation and private filesystem reads run in owned blocking workers. Model bootstrap uses the existing CLI instruction/output defaults, without discovery, connectivity or fallback selection.

Every production writer must join this same mutation/intents boundary. The raw SettingsRepository replacement API retains its separate trusted-Rust-library contract; it is not the production owner route. Another unresolved intent blocks every facade writer. Existing owner full replacement must not bypass this barrier.

Preparation validates actual private disk equal to cache, derives immutable canonical full pre/post SHA-256 fingerprints including revision, and reserves bounded completion capacity. Durable Applying precedes synchronous suspension of affected semantic/classifier admissions and any temporary-file effect. Suspension does not change active captured native inputs. The checked writer rechecks only live origin, cancellation and original wall/monotonic bounds before private temporary-file creation and after write+sync immediately before rename. Its current-settings mutex remains held, so this callback never reads settings/Store or acquires a claim-state lock. Revision CAS is already proven under that guard.

File and SQLite are separate stores. No atomic cross-store rollback is claimed. Exact observation of the original pre-file records NotApplied; exact post-file records the actual revision. A third state, unreadable file or uncertain journal result retains Unknown and the original operation with structured repair errors. An Applying hint has no actual revision; the proposed post revision is separately labeled inspection metadata. Cancel/close/expiry never discard Applying or an unresolved intent. They request cancellation; the writer/reconciler alone establishes the file outcome.

Known no-file-effect restores only the original optional admission through fresh generations, without reloading a failed helper or reviving old tickets/captures. During Host drain it keeps admissions closed. `reconcile_write` is an explicit owner/original-native cleanup observation, never a SettingsAgent capability or fresh write/retry. Known receipt replay can retry exact resource release without rewriting the receipt or rereading/reapplying the file. Poisoned locks may require restart.

OwnerSettingsWriteResult is metadata. It includes full settings only when current validated disk/cache still equals that original known-applied post fingerprint. Newer settings never masquerade as an old result. Otherwise the retained original receipt has no snapshot. Restart-required is asserted only for an actual known file effect. Retained non-embedding memory, MCP, Worker and relay changes require restart; optional semantic/classifier changes use their actual live application path.

## Original application work and startup

A file-resolved PendingApplication result is immutable. It may acquire one separate terminal observation: Applied, RestartRequired, a closed Unavailable reason or a closed Failed reason. Exact terminal replay is read-only; a different observation conflicts. The original file intent and first known resolution remain anchored to their first records. No per-chunk progress or arbitrary summaries are journaled.

`pending_application_work` is a bounded typed original-ID lookup for the existing owned Host work lifecycle. It includes stale historical pending IDs so they can settle without loading a backend. `advance_application` accepts no supplied settings, generation or success flag. It checks the original known receipt and exact current full post fingerprint under Host mutation. A stale file settles Failed, without applying it. Real selector generation and MemoryService apply/Notify APIs perform the captured original work; a retained older Memory application snapshot cannot substitute for the new generation. Failed/unavailable/stopped/superseded work is terminal and never a reload/retry instruction. Before Applied is recorded, actual source/post/generation must still match; a later file or generic backend-ready status is insufficient.

The Host owns these calls through its existing run_owned/JoinSet lifecycle, subscribing to settings changes before authoritative pending lookup. The core starts no second settings runtime or detached application registry. stop_intake closes authority and application admission synchronously. An already active bounded memory step retains its actual owner until completion; drain closes settings intake and Composition under Host mutation, then releases the guard. SettingsService close settles actual file/claim cleanup without waiting for this driver. Composition.stop_work then starts actual Memory/selector shutdown, which wakes admitted semantic-generation waits; the final existing JoinSet joins the driver afterward. This order lets actual shutdown wake application waits before joining them; cancellation never certifies helper cleanup. Public reads and exact client replay never invoke apply.

`startup_context` reads actual disk/cache and typed-validates all bounded write histories before any optional service load. It returns that snapshot, a policy and the exact-current original PendingApplication inspection, if any. An unresolved intent or exact-current unobserved pending application requires optional-off startup. Its pure embedding_preferences and selection_configuration methods preserve operator configuration while resolving overrides once. Actual Host startup consumes that snapshot for MCP bootstrap, worker configuration, memory, selection, relay and Composition. Embedding off resolves before optional runtime/model/vector access; selector construction/configuration performs no credential lookup or remote request. The same Composition is bound back into this service before owner ingress and Scheduler activation. The obsolete startup_policy wrapper is removed; startup consumers use this one context. Startup does not recreate native authority, invitations, confirmations or file effects. An original unobserved application remains pending/unknown until owned work establishes a compatible source; general backend readiness is not its receipt.

## Journal bounds and hints

Migration0013 adds only three tables in the existing Store after actual schema12: immutable settings_operations identities (18KiB), immutable exact settings_native_requests (1KiB), and append-only settings_operation_updates (2KiB). SQL checks JSON/identifier/time/byte shape and immutable triggers; typed reads revalidate canonical encoding, full target digest, source/reference identity, native linkage and anchored file/application history. Borrowed SQLite lengths are bounded before copying. Database rows do not mint live caller authority.

Limits are1024 combined retained original/native identities,64 pending operations,8192 updates,64 retained live write captures and eight invitation leases. Transactions reserve finite native/terminal/repair rows before admission, including one terminal application observation. Exact replay precedes capacity; there is no eviction or renewed identity. Every write-history candidate is fully typed-validated before resolved/unresolved classification, so malformed resolved-looking JSON cannot reopen writers.

Changes reads at most128 indexed historical rows, validates each against original identity/intent, and rechecks the live caller. Each hint is at most1KiB, a page32KiB. Original authorized callers may see their operation state; shared facts expose only applied keys/revision, without foreign IDs, values, recipients, paths, credentials, references or invitations. Filtered rows may advance a cursor; a visible byte-excluded row remains available next page. The watch sequence increases only after actual commit and Store lock release and is merely a wake hint. Restart may reset it; durable sequence cursors remain authoritative.

## Validation boundary

Earlier core-only Rust1.88 checks and independent source reviews are historical prerequisite evidence. Current source registers the actual startup context, driver and owner/native pipe routes; partial checks of earlier source are not final combined proof. Exact-source Rust gates and disposable CAS/replay/cancellation/expiry/restart/drain/failure verification remain mandatory before acceptance. The private pipe and compatibility macOS consumer also require their applicable supported-platform checks. The integrated configured Session-vault walkthrough is recorded separately in [Settings validation](../development/settings-validation.md); it does not verify initial enrollment or native OS storage. No successful model inference, native OS credential-store write, Apple runtime, universal secure erasure or security readiness is asserted. Deferred automated coverage remains [#32](https://github.com/izyuumi/everything/issues/32).

The public `SettingsOperationInspection::validate` is the shared data-only inspection validator. It checks the original bounded binding lifetime/digest, actual origin-to-session metadata links, update-time lower bound, exact-expiry references, finished-result identity/scope, Applying/write revision consistency, sorted unique bounded Host key names, resolution and terminal application coherence, and encoded size. A SettingsAgent inspection names both its restricted session and native parent; the binding client_session_id is that original native parent, as in actual authority admission. Completion may occur after original expiry, so historical validation uses no current clock. This method reads no Store/session/file and verifies no authentication, original target digest, journal anchoring or native claim; those remain the authoritative service/journal checks. Native/owner/client consumers can reuse this validator without converting a DTO into an admission proof.

A private `local_owner_cleanup_caller` is minted only from the verified existing LocalCall channel, owner UID, uncancelled frame and its exact request ID. Its same-Authority-Arc opaque LocalOwner source allows original-operation inspection and explicit file reconciliation after intake closes. Global owner/open/validate behavior is unchanged: fresh writes and require_tool still use normal live validation and reject closed authority. Owner and original NativeUi operation inspection are bounded cleanup reads rather than expiration mutation. Native cleanup retains the original session/principal binding after close or expiry; SettingsAgent reads alone retain live validation and expiration behavior, with a final live check after the journal read. Reconciliation still denies SettingsAgent and preserves exact original NativeUi cleanup semantics. It may observe the original pre/post file and repair its receipt/resources; it never rewrites the settings file, reapplies a backend, renews a grant or forwards remote owner authority. On close, known no-file-effect cleanup leaves optional admissions closed; an observed post-file PendingApplication remains original work for explicit owned restart recovery. The Host uses this cleanup caller only for the owner operation query and explicit reconciliation ingress; fresh ReplaceSettings keeps the strict live-owner path. Owner responses use the central inspection validator. Actual integrated drain verification remains pending.
