# This Mac settings consumer

`ThisMacSettingsStore` owns the existing local SQLite preference actor and an independent native notification-action service. `ThisMacSettingsView` is its conventional macOS Form. They require no Host connection, model, provider, relay, owner pipe or UserDefaults authority. This source is not yet registered in the Apple project or composed into the Settings scene.

Root supplies one app-private Application Support directory to `init(directory:)` and retains this observable MainActor store across Host disconnects and Settings presentations. `open()` coalesces one owned initialization and runs `DevicePreferenceStore.local(directory:)` on a detached worker, then adopts the genuine snapshot device ID. It never substitutes a Host/paired-device identity or maintains a second copy of preference values. Later reads and transactions use that same actor. Directory privacy, SQLite limits, identity validation and durable request receipts remain the [existing store's responsibility](local-device-preferences.md).

Every valid snapshot adoption establishes the actual device-bound foreground session if none exists, including recovery after an initial snapshot failure. Later reads reuse that same session and its existing foreground generation; they never reopen the database or renew original action admissions.

## Saved values, drafts and original writes

The authoritative observed snapshot is separate from the draft's original baseline. The visible active surface runs one cancellable two-second SQLite snapshot observer. Presentation, foreground return, explicit refresh/reload, write completion and original-request inspection also read the actual actor. This observer does not poll OS notification permission. A newer revision preserves modified drafts and reports conflict; nothing silently rebases or writes the draft. Reload is explicit, with a native discard confirmation in the view.

`save()` synchronously constructs and retains one exact typed `DevicePreferencePatch` and original baseline before launching its owned apply task. The task records only a genuine returned Applied/Conflict result and reads actual saved values afterward. An Applied receipt is distinguished from a failed readback or a later concurrent revision. Errors and absent original-ID inspection results retain the pending patch and prevent new writes/actions. Inspection calls `result(for:)`, never apply. It cannot infer NotApplied or rollback from matching values, an absent result, cancellation or a poisoned connection. There is no automatic reopen, resubmit, new mutation identity or durable client recovery queue; unresolved client identities remain in this app-owned store's memory until actual inspection resolves them or the process ends. Hard-crash/restart recovery of that client correlation is not implemented.

At most 64 combined patch/action records are retained without eviction. Capacity refuses new effects while preserving originals. Opening, explicit snapshot refresh, mutation, original inspection, notification observation and notification action each have one owned/coalesced slot; the visible observer has one separately owned task. Accepted writes are retained through surface close and application drain. The underlying SQLite request ledger keeps its separate existing limit.

## Real foreground admission and OS observation

Root must call `setSurfaceVisible` from actual Settings-window visibility and `setApplicationActive` from actual application lifecycle, for this store and the separate native Host lifecycle. SwiftUI appearance alone supplies neither authority. Eligibility requires both values plus the real `NSApplication.shared.isActive`. Hidden/inactive transitions synchronously invalidate the existing foreground generation and cancel unpresented action eligibility. They never renew an old action on return.

The notification button calls `requestNotificationAuthorization()` directly in its MainActor gesture handler. This method synchronously calls the existing `DeviceNotificationActions.prepare` with the actual preference actor, device/session, revision and original 60-second wall expiry before creating its owned Task. That Task consumes the opaque ticket through the same action service. Existing source performs the actual OS queries, revision rechecks, authorization request or supported guidance; the consumer implements no second permission protocol, notification delegate, arbitrary URL or settings-pane scheme.

OS observations are requested on presentation, foreground return, explicit status refresh and the existing action's real interaction. Completion/attention preferences remain distinct from observed authorization, alert/sound/Notification Center support and query time. Denial supplies the existing macOS System Settings guidance, without claiming another dialog or a grant. Actual typed action results are retained locally; no Host Completed receipt is fabricated. Started OS callbacks continue to their actual result after surface close/cancellation and are joined by drain. This source schedules no notifications or category-aware completion/attention delivery.

The OS observation's wall-clock date is display-only. One owned query identity controls publication on MainActor; a newer explicit read request, foreground presentation or completed action retires an older query's publication and coalesces one follow-up read after that callback joins. Actual action observations remain retained, and a fresh post-action read is requested. A slow pre-interaction query cannot overwrite that result, and a backward wall-clock adjustment cannot discard a fresh observation. This is local query ordering, not an invented OS snapshot revision or authority token.

Hiding or closing Settings first calls `setSurfaceVisible(false)` synchronously. `drainSurface()` then captures and joins the currently owned finite tasks and a cancelled observer without permanently closing the store or changing visibility again. A later presentation can reuse the same actor, installation identity and original records. A new visible observer is excluded from an older close drain. Root must own its close-drain task; a reopened window cannot renew an old notification admission or relabel its original result.

`invalidate()` synchronously and permanently closes fresh admission and stops the observer; `drain()` invalidates and joins the owned work, including accepted SQLite writes and the real notification callback. Root must retain and await this drain during actual app shutdown. Neither surface closure nor app drain stops the Rust Host.

## Integration and validation

Root owns the actual private directory, app/window hooks, shared-store lifetime, Settings scene inclusion and Xcode target membership. These three source files alone do not establish functioning controls in the application. The [native action foundation](../architecture/native-settings-actions.md), [typed scopes](settings.md) and #110/#114/#118 remain authoritative integration boundaries.

Current Apple documentation confirms contextual first authorization and separate subsequent notification-settings observation: [request authorization](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/requestauthorization(options:completionhandler:)) and [read notification settings](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/getnotificationsettings(completionhandler:)). The source reuses the existing implementations of both. Linux grammar/source checks cannot verify AppKit, SwiftUI, UserNotifications, SQLite concurrency or a real Settings window. Supported macOS SDK build/analyze and disposable UI/storage/foreground/permission observations remain required. No stubs, new automated tests, fixtures or source comments are introduced; deferred coverage remains [#32](https://github.com/izyuumi/everything/issues/32).
