# Native root remote reservations

The Scheduler supports a trusted owner-only root reservation for an external worker. This is the native admission boundary for issue #29. The actual [Host approval/Gate](host-worker-admission.md), [Worker bridge](worker-bridge.md) and [verified result transaction](remote-result-admission.md) compose this lane without another local loop. The actual production Host credential-rejection/recovery walkthrough passed within the qualified scope recorded below.

`RemoteTaskSubmission` combines the original `TaskSubmission`, `RemoteTaskBinding` and `RemoteOwnerApproval`. The binding contains the complete manifest SHA256, original delegation/attempt UUIDs, coordinator identity, exact executor public keys and relay origin, explicit worker-side native IDs and creation/deadline timestamps. The original local task/conversation/command IDs remain those supplied in TaskSubmission. A binding is an immutable mapping, not proof that an arbitrary existing local or worker task belongs to this delegation.

`Scheduler::admit_remote(RemoteTaskAdmission)` requires the actual opaque capability minted from the staged worker approval, not a deserialized `RemoteTaskSubmission`. It retains the leased Agent, exact submission and original instruction/configuration, endpoint/Host guards and original wall/monotonic expiry. Admission requires a fresh bounded owner approval, an accepted matching local user command, an unstarted conversation with no native execution, a captured workspace policy and available primary capacity. It validates the registered narrowed file/discovery tool names, rejects FullHost and unsupported capabilities, requires an absolute deadline and cumulative output allowance, and stores a typed version-one remote definition plus its checkpoint in the existing task row. Immediate-transaction acquisition and precommit recheck the original approval. Definitions/checkpoints use existing task rows without a separate reservation table; migration12 adds the [indexed binding locator](remote-binding-lookup.md), and the worker ledger uses its separate ordered migrations. The native record remains a root task; active-parent delegation is unavailable.

Admission occurs through the existing Actor. The same Actor counts active local primary workers plus all unresolved remote reservations against max_primary_tasks. Remote admission returns Capacity while those slots are occupied; it does not create a remote queue. Local queued tasks remain queued while a remote reservation owns their required primary capacity. Existing retained/pending task limits include remote rows. Stored task input/checkpoint byte bounds are checked before their JSON is loaded.

Known precommit Capacity, Invalid, Conflict and OwnerDecision errors retain their structured meaning and leave the Actor available. Actual uncertain persistence failures stop further admission. Reopening a Scheduler with existing remote reservations requires the actual leased Agent too; an unleased Agent::from_store cannot recover or issue permits for them.

The full original model-attempt, tool-call, charged-token and cumulative output allowances are charged once in `RemoteBudgetCharge`. Exact original submission replay returns the same reservation without a new charge. Changed policy, binding, approval or local identity conflicts. The native loop never executes this task, so the reservation is not an additional uncounted native spend. These are request-admission allowances, not hard financial or operating-system resource guarantees. Worker-reported usage is not a refund authority.

The original owner approval command, local root command/conversation and delegation/attempt/worker-side identities belong to one immutable remote definition. Admission checks bounded validated retained remote definitions before reserving capacity, including records outside the current in-memory active set. A different root task cannot reuse an earlier approval command or adopt its worker identity mapping. Exact replay of the current task is checked first and remains idempotent.

`Scheduler::remote_status(task)` returns the current typed RemoteTaskSnapshot, including its exact immutable policy/configuration, binding, original approval, charge, phase and admission/last-dispatch timestamps. This query emits no Scheduler mutation notification. The ordinary task snapshot remains available too.

`Scheduler::remote_dispatch_permit(task, binding)` requires an activated live Scheduler, the exact original binding and live reservation, no cancellation, current captured workspace authority, no local native execution, no quarantined Broker, no observed clock rollback, and an unexpired deadline. The Actor reads the clock again after asynchronous native ownership checks. The short owner-approval lifetime applies at initial admission; its immutable approved job can be replayed through that job's original deadline. A new attempt or changed manifest requires new owner admission.

The returned RemoteDispatchPermit is opaque and has no Clone or serialization implementation. It retains the Scheduler admission mutex, the actual native conversation admission/write guard, and the leased Agent through the caller's real enqueue/send. Its snapshot is read-only. Host code must compare the complete actual worker manifest fingerprint and current purpose-scoped peer trust, retain its own current-authority guard where needed, and implement the existing WorkerOutboundGate with this permit. A database reservation or a caller Boolean alone is not dispatch authority.

The Scheduler handle acquires its owned remote admission mutex before enqueueing remote admission/permit, cancellation or orderly-shutdown controls. The Actor never awaits that mutex. A cancellation request waits outside the Actor while an already admitted send owns a permit, keeping status responsive. Cancel controls retain their guards through the actual commit even if the requesting future is dropped. The Host must use consistent endpoint-authority -> Host-mutation -> Scheduler-admission ordering and release Host mutation before initiating endpoint operations.

Remote cancellation persists CancellationRequested, keeps WaitingForChildren with an explicit Remote waiting reason, retains the original full charge and primary slot, and refuses new dispatch permits. It does not report confirmed remote stop. Native wake, steering and resume cannot start or change the approved remote task. Recovery validates its typed definition/checkpoint, restores its unresolved slot and never enters native acceptance repair, provider construction or local dispatch.

`ShutdownReport::unresolved_remote_tasks` reports these durable unresolved reservations separately from active_tasks, which proves owned local workers drained. Shutdown does not wait indefinitely for an unreachable remote machine or report it stopped. A dropped Scheduler's already issued permit continues retaining the actual StateLease until the admitted caller releases it. A subsequent host can reopen after actual ownership drains and sees the same original reservation. Only the separately guarded `admit_remote_result` transaction can settle a known authenticated terminal outcome. Unknown retains its slot and charge. There is no automatic retry, refund or capacity release based on shutdown, expiry, cancellation or ACK.

## Owner release

`Scheduler::release_remote(task, binding, RemoteRelease)` is the only way to free an unresolved reservation without a worker result. The owner names the exact task and full binding, the phase they expect (`CancellationRequested` or `OutcomeUnknown`), a bounded operator (1 to 128 bytes) and a reason (1 to 1024 bytes); neither may contain control characters. The request id is the owner request ID. The call runs on the Actor under the remote admission mutex. It refuses a different binding, and it refuses a current phase other than the expected one with `OwnerDecision`. Otherwise it commits phase `Released` and the `RemoteRelease` record, including `released_at`, into the task checkpoint. The task becomes Failed with the non-retryable code `remote_released_by_owner` and the slot is released.

Replaying the same request ID with identical fields returns the stored release unchanged. A different request after a release is a conflict. The release keeps the original charge and any existing Unknown report; it adds no result, report or conversation event. Validation requires the record exactly when the phase is `Released`, and requires an Unknown report exactly when the expected phase was `OutcomeUnknown`. `RemoteResultCommit` refuses a released task, so a late worker result cannot be admitted. Restart recovery treats the released task as terminal and does not reserve it again.

The profile permits only explicitly selected native workspace file tools and offline discovery. It cannot run arbitrary code, shell, MCP, network tools or nested delegation, and does not enforce hard CPU/RAM/PID/disk quotas. The trusted worker runtime owns native provider/relay access and its own credentials. OS sandboxing, malicious worker attestation and successful model inference are not implied.

Formatting, Rust 1.88 default/all-feature compilation, strict Clippy and disposable manual observations are recorded with the implementation handoff. The bridge has qualified native reservation/result evidence, and the actual combined consumer `d273c52` passed the six normal-package Rust 1.88 gates. The actual Host credential-rejection/recovery walkthrough passed; see [worker validation](../development/worker.md#combined-host-validation-checkpoint) for its limits. Automated coverage remains deferred in [#32](https://github.com/izyuumi/everything/issues/32).

## Current-main accounting preservation

Remote policy captures the independent `max_reserved_output_tokens` cap alongside request, tool and charged-token limits. `RemoteBudgetCharge` retains those original full allowances once; later reports, cancellation, revocation and restart never refund or replace them. The external root lane does not run the local native provider and does not manufacture private local `NoAttempt` terminal evidence. Its optional Scheduler evidence remains absent, preserving the distinction between unavailable local observations and an inspected zero. Remote settlement continues to use the actual lifecycle/evidence-aware checkpoint encoder and its existing byte reserves.

The current-main source union preserves the actual native output counter, terminal-evidence capture and scheduled-execution consumer, together with owned startup, validated SQLite handles, Broker recovery and local subagent/steering semantics. Remote admission is separate from the proposed restricted Settings profile; this change registers no settings-agent tools or generic owner pass-through. Source/format and preservation inspection do not establish current runtime behavior. Fresh exact-head CI and the separately qualified disposable coordinator walkthrough remain pending.
