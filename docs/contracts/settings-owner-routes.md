# Revisioned owner Settings receipts

Actual verified local owner ingress routes ReplaceSettings through the same SettingsService as native patches and restricted callers. The service creates its owner caller from the real LocalCall; the general internal owner-operation dispatcher cannot substitute for that ingress. The service owns mutation locking, full validation, exact request identity, file intent, CAS, protected-change rejection and durable original outcome. The route does not hold another mutation guard around it.

Production replies use SettingsReceipt with the original validated inspection, an optional current settings snapshot and the original restart-required flag. A snapshot appears only while the validated current file matches that original known-applied post-file. A later file revision cannot be substituted into an old receipt. Transport validation binds the receipt to the original owner request ID/revision/origin and compares any returned full snapshot with that request plus its one revision increment. A pending application or failed backend does not erase a known file save.

Raw full owner replacement cannot approve protected provider/recipient changes. It returns the durable HostActionRequired outcome; exact native confirmation uses the separate protected-patch path. Replaying a receipt performs no second write or application. The retained legacy Settings reply decoder supports this project's older Host response, while new production routes use the durable receipt.

The existing macOS general settings form accepts both reply shapes. It adopts only a returned validated saved revision, distinguishes saved/pending/restart/failed/unavailable states and retains the exact request for Applying or Unknown. Rejection is not displayed as Saved. The final valid positive signed-64-bit revision remains readable; another edit at that limit is refused before submission. This compatibility consumer is separate from the complete native settings store/screens and does not establish Apple UI runtime behavior.

An explicit owner ReconcileSettings operation references the original operation ID. It invokes actual pre/post-file observation and returns SettingsReconciled with that original validated inspection. The fresh transport request does not create another write identity, rewrite a file or directly launch a helper. OwnerQuery SettingsOperation remains observational; reads never reconcile or apply. A known post-file can become original pending work for the existing Host driver. If a restarted Host proves no file effect but has no prior live backend ticket to restore, optional admission remains visibly unavailable until an explicit restart adopts the unchanged saved configuration.

Configured worker metadata is notified only when an owner receipt includes the exact known-applied current snapshot; existing coordinator settings-change semantics remain unchanged. No second configuration store, secret-bearing file request, permission upgrade or automatic rollback is added. Actual route/runtime and supported Apple SDK validation are separate gates; automated verification remains [#32](https://github.com/izyuumi/everything/issues/32).
