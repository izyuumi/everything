# Scoped Settings grant storage

This source implements typed grant records, atomic storage and authenticated local-owner CLI/IPC consumers. Grant storage itself resolves no credentials, starts no model, cancels no session and changes no device trust. Existing paired devices receive no Settings authority. The [remote Settings transport](settings-access-transport.md) is the remote consumer: it rereads the current head under the Host mutation guard for every request, so an owner reduction or revocation applies to the next remote read or write, including already admitted requests. Deferred automated validation remains [#32](https://github.com/izyuumi/everything/issues/32).

## Domain and provenance

`SettingsGrantOwner` is supplied separately from the serialized change. It records the actual Host device ID and actual owner principal; the current Authority uses that Host UUID as its owner principal. Storage validates both against the existing complete Host endpoint configuration and Host role. This value is an internal storage invariant, not an authentication capability. The local owner ingress authenticates the real local caller, derives this context, captures real wall time for fresh admission and retains the actual Host mutation guard in its real blocking worker. Future remote activation must add actual generation retirement and cancellation bookkeeping under that same guard. No request-body principal, UUID or grant digest authorizes an operation.

`SettingsGrantChange` is a closed version-1 object with original request ID, existing complete peer public keys, optional expected grant ID/revision, explicit rotation flag and target. Target contains a nonzero grant ID, original issuance/expiry and Active or Revoked state. Creation expects absence and does not rotate. An existing head requires its exact grant ID/revision; changing the grant ID requires `rotate=true`. Revision increases across revocation and rotation and never resets. A historical grant ID cannot be reused for another head or restored after rotation. Lifetime is positive, at most seven days and within the existing signed timestamp domain. Fresh admission requires the supplied actual observation to be within that original lifetime.

Active state allows sorted unique readable keys from models.selection, tools.selection, memory.embeddings.enabled, memory.embeddings.dimensions and memory.embeddings.model. Sorting uses the existing `SettingKey` order. Writable keys are a subset of those readable keys and contain only memory.embeddings.enabled or memory.embeddings.dimensions. No value or partial patch is written by grant storage. Consent is None or ConfiguredProvider with an exact public provider/model/recipient tuple. Native model validation is reused; recipient is that provider's actual official endpoint or a canonical explicitly loopback endpoint. No credential reference, secret hash or credential lookup is stored. The complete change retains configured_settings_revision as a positive signed-range value exactly when ConfiguredProvider consent is present, and null otherwise. Fresh configured consent compares the tuple and that original settings revision to the same ServiceCore's actual observed configuration under the Host guard; domain validation alone cannot prove that comparison.

Fresh active grants require an unchanged complete nonrevoked peer pin and nonrevoked Host endpoint. A Revoked target for an existing head can reduce trust after the exact same peer pin or Host endpoint has been revoked. Missing or changed full keys fail closed. Current-head inspection explicitly reports `peer_revoked` and `host_revoked` alongside the stored target; an Active stored target is not proof of effective current authority. Expiry, later grant generation, provider binding and actual authenticated parent admission remain separate future checks.

## Atomic persistence and replay

Migration15 creates only settings_grant_versions and settings_grant_heads, plus their indexes and triggers. It does not rewrite existing Settings identities, reservations, fences, cleanup, ordinary state or transport tables. Versions retain the complete canonical typed record, including the original expected reference and rotation flag, once. Its single receipt column is the immutable logical owner-CAS receipt. No second request copy is stored. The head refers to an exact immutable version. Versions and receipts cannot update/delete; head identity cannot change/delete and its revision/reserve can advance only to an exact next version.

`Store::set_settings_grant(owner, change, now)` uses one existing connection and one immediate transaction. An exact original replay compares the complete retained canonical change plus its domain-separated public SHA-256 and original Host/owner context, then returns the same historical receipt with `replayed=true`. It does not apply a second change, select the current head, renew expiry, perform fresh pin admission or spend new history capacity. Changed reuse conflicts. A fresh original checks the exact current head, full pin, Host role, lifetime, retired grant identity, checked next revision and all logical capacity before inserting.

The version row contains both the bounded immutable record and bounded receipt. Its BEFORE INSERT trigger checks the CAS and projected capacity; its AFTER INSERT trigger installs the exact head in that same SQL statement. A failing install rolls back the original insert. Thus version, receipt and reserve transfer cannot be committed separately. Direct identity rewrites, head-only reserve release and original-request replacement are rejected. SQL constraints complement the closed Rust decoder, canonical re-encoding, public-key validation and recipient/model validation; SQL is not a second cryptographic or URL parser.

The receipt contains version, Host, peer, original owner request, grant ID/revision, request SHA-256 and actual committed observation. This digest identifies public canonical grant data and is not authority. Historical receipt and exact revision queries retain their original state even after a newer head, expiry or sticky peer revocation. The four internal Store entry points are set_settings_grant, settings_grant_head, settings_grant_version and settings_grant_receipt; genuine owner routes consume them for set/revoke, show current, show revision and inspect original receipt respectively. No paginated inventory or unbounded history API is added.

The crate-private `settings_grant_head_on(&Connection, SettingsGrantOwner, DeviceId)` factors the same current-head read for callers that already hold the actual Main transaction. It validates the owner and complete Host configuration, reads the exact head and checks the complete stored peer pin, returning the same explicit Host/peer revocation flags. It obtains no connection, begins or commits no transaction and grants no authority. The existing Store wrapper still validates the owner before acquiring its connection, owns its deferred transaction and commits only after this helper succeeds. A future paired producer must call the borrowed-connection helper inside its existing immediate transaction rather than recursively acquiring the Store mutex; live grant/epoch/lifetime admission remains that authenticated caller's responsibility. This source extraction has formatting/preservation checks only, with compiler and behavior verification pending.

## Authenticated owner routes

Use the existing `everything owner --request-file PATH` interface. Its Query envelope accepts `settings_grant_current { device_id }`, `settings_grant_version { device_id, revision }` or `settings_grant_receipt { request_id }`. Its Operation envelope accepts `set_settings_grant { change }` with the complete closed change. The outer Operation request_id is mandatory for Set and must equal change.request_id. A revoke uses that same operation with the closed Revoked target and null configured_settings_revision. Preserve the exact original file and ID for explicit replay; the CLI never generates a replacement mutation ID for these requests.

The existing authenticated Unix LocalCall and same SettingsService Authority validate peer UID and derive the real Host/owner outside the body. Dedicated dispatch handles these cases before generic owner routes; internal generic query/operate rejects them without that LocalCall. There is no OwnerOperation forwarding through paired transport or native-session proof reuse. Eight public data DTOs support the actual public IPC enums; trusted context, caller, commit and Store APIs remain internal.

Each handler acquires the existing owned Host mutation guard and moves it, the actual caller and immutable input into the actual blocking closure. The retained Host owns the same Agent, Store and StateLease until SQL and file observation return. A dropped request does not release that worker's guard or erase a committed receipt. Read/replay/trust reduction use actual local-owner cleanup authentication during drain. Fresh Active admission checks that the Host is accepting while holding the same guard that Host shutdown acquires before closing authority intake.

Before extra fresh checks, Set looks up the original receipt and delegates exact replay to Store with its retained historical committed observation. This path does not need a fresh wall clock, current configured tuple, active old grant or new capacity. Changed reuse conflicts. Fresh configured consent calls the same ServiceCore's synchronous owner metadata read inside the blocking worker, verifies its observed file/cache fingerprint, and compares original settings revision, provider, model and exact disclosure recipient. It reads no credential and creates no provider. None/Revoked targets perform no model-configuration lookup. Cancellation before fresh Store admission rejects; a disconnect or cancellation after admission can leave a durable outcome that must be inspected under its original ID.

The complete grant request and response wire frames are at most 32768 bytes, including the existing four-byte length prefix. Both actual received JSON byte counts and complete escaped serialized wrappers are bounded to 32764. Other local requests keep their existing 2MiB JSON limit. The reader still initially uses the existing global framing ceiling before typed classification; this is not a claim of a 32KiB parser or heap ceiling. Result validation correlates exact query targets or the full original canonical Set digest and receipt.

These direct Query/OwnerOperation routes do not enter HostInbox or duplicate the grant request in host_commands. The existing 100000-ID/1024-pending/128MiB generic command journal cannot consume reserved grant-history revocation capacity. Existing 32 connections/handlers/queued calls, timeouts, OS availability, pin integrity and actual disk/SQLite failures remain independent limits; this does not promise unconditional revocation delivery or physical storage capacity. An absent historical result means NotRecorded, not permission to infer no effect or mint a new original.

## Finite history and future revocation

There are at most4096 heads. Each full canonical version record is at most8192 encoded bytes, including its complete original change and all retained version context. Each receipt is at most512 bytes. Actual versions plus one reserved future version per Active head must fit8192; actual receipt count plus the same future receipt reserve must also fit8192. Actual version bytes plus2048 reserved future bytes per Active head must fit33554432. Actual receipt bytes plus512 future bytes per Active head must fit4194304. These are encoded metadata budgets, not SQLite file, WAL, heap or RSS bounds.

Activation reserves a future Revoked version and receipt before it becomes a head. Active-to-active replacement spends one actual version and transfers exactly one future reserve in the same statement. Active-to-revoked insertion consumes its old reserve, creates no new reserve and independently enforces its actual whole version at most2048 bytes. The closed revoked shape has no arbitrary strings: existing fixed public keys, UUIDs, positive signed-range integer fields, fixed tags and expected/rotation fields give a worst-case716-byte complete version and371-byte receipt. Base64 key text is fixed44 bytes and UUID text36; keys/numbers/tags require no variable JSON escaping. The enforced2048/512 allowances exceed those maxima. Therefore history exhaustion cannot consume already reserved trust-reduction capacity. A revoked-to-revoked administrative update has no reserve and can fail at capacity without increasing authority.

No history or original request is evicted, pruned, reset or silently reused. Capacity exhaustion refuses fresh activation/renewal. A successful grant CAS is a durable configuration fact, not proof that a worker stopped or that already disclosed relay ciphertext can be recalled. Actual generation retirement and cancellation under the same Host guard are required from the later consumer; no placeholder hook claims those effects now.

## Validation boundaries

The source has genuine local-owner consumers; no fake call or lint suppression is used. Source formatting and preservation checks do not prove compilation or behavior. Cargo, bundled SQLite migration execution, current CI, concurrent behavior, actual owner walkthroughs, crypto transport and remote clients require separate validation. No database was opened during this implementation and no new automated tests, source comments, fixtures or dependencies were added. Root integration and independent source review precede publication and actual CI. Remote activation still requires real grant-generation cancellation and private ingress; a persisted Active target alone grants no remote caller access.
