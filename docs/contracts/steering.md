# Durable native task inputs

Agent::accept_task_input is a trusted host delivery primitive. It accepts TaskInputCommand containing the exact conversation, task, active user command, unique delivery command, authoritative host acceptance time, and typed input. The scheduler must verify current task ownership, cancellation, descendant relationships and immutable child terminal records before constructing these commands. A remote caller cannot supply a successful child result or an outcome_unknown decision directly.

TaskInput is Steering, WaitForChildren, or ChildFinished. Steering instructions require nonempty UTF-8 of at most 32768 bytes without NUL. A wait contains 1 to 32 distinct child task IDs. ChildFinished references the exact wait command, a terminal child status, a bounded 8192-byte output preview, and an explicit unknown-outcome flag. That flag preserves uncertainty rather than converting a failed child into an ordinary successful completion.

Acceptance appends SteeringReceived, TaskWaitRequested or SubagentFinished and the private input queue in one sequence/revision-CAS transaction. Event causation is the delivery command; the payload command_id is the original active command. TaskInputReceipt returns the original event sequence. Exact replay returns that same sequence even after consumption or task completion; a changed target, payload or acceptance time conflicts. A fresh delivery to a completed command or terminal task is rejected.

The private queue lives in the existing conversation checkpoint, outside the immutable native definition. It holds at most 64 deliveries and 512 KiB in aggregate. It validates ordering, journal identity, target, payload and cursor bounds. Consumed identities remain in the immutable public command journal; the checkpoint stores a monotonic consumed event cursor rather than an unbounded list of IDs. The existing public 256-KiB and private 8-MiB limits also apply.

Only the native kernel consumes inputs. It appends steering and known child-result User messages with the delivery causation and advances the consumed cursor atomically. Child text is explicitly structured as untrusted output; it does not replace fixed constraints, task objective, authority, model configuration, memory or tool setup. Original command identity, limits, counters, deadline, continuation and native tool-call mappings remain intact. Inputs cannot split a tool-call/result round. WaitingForEvents yields only after all ordered known results have committed. A child with an unknown outcome pauses at ChildOutcomeUnknown for owner reconciliation and never authorizes another provider attempt automatically. Steering accepted while an explicit child wait is still open is committed as a User message at that safe boundary, but the kernel stays at WaitingForEvents; the model sees it with the child results once the wait is fulfilled. Steering does not cancel or shorten a wait. Cancelling the waiting task, or the remaining children, is the available way to end it early.

One short per-conversation write gate serializes input acceptance and native commits across Agent clones, independently from the full-turn execution gate. A cached kernel snapshot may merge appended, validated input deliveries and the trusted task or permission metadata described in [the publication contract](control-events.md). Each intervening single-event journal must prove its exact envelope and reconstructed private-checkpoint digest, with at most 256 intervening events. Raw messages, native phase, continuation and every other non-input checkpoint field must still match; any other concurrent mutation fails. If input arrives during context preparation, the kernel rebuilds before charging or sending a new model request. If acceptance wins the final-response commit race, the assistant response commits while retaining the active turn and counters for the queued inputs. If finalization wins, subsequent fresh delivery is rejected. A paid or uncertain request is never repeated to resolve a checkpoint conflict.

Input acceptance, native control refresh, native event commits, and expired-round journal inspection explicitly retain the complete Agent inside their actual blocking SQL workers. Dropping an awaiting future therefore cannot release an Agent-owned state lock before the worker returns or unwinds. A Store-only capture does not provide that lifetime guarantee. An Agent created with `from_store` still requires its caller to retain the external state lock. These bindings do not change write gates, durable ordering, uncertainty, or retry permission.

A child input may be accepted after safe consumption computed WaitingForEvents but before that pause commits. The accepted delivery remains in the durable queue. The scheduler must recheck pending input when settling that exact safe wait, or retain an active-worker wake hint, and requeue it without requiring another external event. Subscribe-before-query notifications and startup repair complement this durable check. Provider uncertainty and ChildOutcomeUnknown must never use that automatic path.

Steering acceptance does not grant retry permission. ProviderInFlight, interrupted execution, unknown effects, reconciliation and exhausted budgets retain their original owner-action requirements. Cancellation continues to signal native provider and broker futures and preserves queued input for inspection; it does not manufacture a completed result or erase an uncertain turn. Legacy text-only execution cannot consume task inputs and rejects a queued input before inference.

The Agent primitive is implemented independently of Scheduler and HostInbox. The [Scheduler contract](scheduler.md) documents the implemented wait-set ownership, child terminal delivery repair and approval wake handoff. Authenticated command admission and production background-host composition remain separate work in #18/#68. Automated acceptance coverage is deferred to #32. Successful live model continuation remains unverified without authorized credentials.

## Agent validation

Rust 1.88 formatting, all-target/all-feature compilation and strict Clippy passed. A disposable release executable used the actual Agent, Store, Authorizer, broker and native OpenAI adapter against a held loopback HTTP 503 response. It observed mid-request input acceptance, concurrent exact duplicate acceptance, changed-command conflicts, self-wait rejection, ordinary uncertain-resume stops, and consumption after an explicit owner retry without a new model attempt. Known child input fulfilled its exact wait; unknown child input produced the typed owner stop. Definition, attempt count, charged tokens and deadline remained unchanged. A rejected SQLite private update rolled back both event and queue, and reopen retained consumption.

A separately labeled seeded final-phase inspection observed retained active-command state when steering preceded finalization, unchanged generic opaque continuation/binding data, the 64-input bound, replay at capacity, and rejection of a non-control concurrent checkpoint mutation before inference. These seeded records do not verify a successful model response, an authentic reasoning signature or live provider continuation. No automated tests or repository fixtures were added.

## 2026-10-17 loopback Host observations

A release Host from this branch ran on disposable macOS state with a session credential bound to a scratch loopback server that implements the real Responses SSE wire protocol; no remote provider or real credential was used. Owner `steer_task` was accepted while the first model request was held; that response's `read_file` round completed, and the next request carried the full tool round followed by the steering User message before the task completed. Steering accepted during a held final text response kept the turn open; the next request carried the first answer and then the steering message, and the task completed. A spawned child's completion produced the parent's next request with the `subagent_result` input within about two milliseconds, and the parent completed. Cancelling a parent while its child request was held closed the child's HTTP connection within five milliseconds; the child settled Failed with its uncertain provider attempt and the parent Cancelled. An unanswered FullHost shell approval reached its real 30-minute expiry: the continuation request followed 39 ms after `expires_at`, carried the `approval or scoped grant expired` denial, and the task completed with no owner action. These observations do not establish real model behavior or live provider continuation.
