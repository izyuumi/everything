# Durable task preparation

`Agent::capture_tools_setup(conversation_id, command_id, setup, cancellation)` validates the actual registry, inherited authority, selected definitions, context budget and memory through the same native preparation path as `run_tools`. It captures the definition in the existing private native checkpoint without constructing a provider, executing a tool or consuming a model allowance. The returned `NativeRunInfo` describes the saved native boundary. The task must already be running in its conversation. Exact setup reuse preserves the frozen definition; changed inputs conflict. Relative native duration starts at capture, so provider construction consumes that duration. An absolute deadline remains unchanged.

Capture uses the existing execution admission and short write gate. Concurrent accepted steering or child input merges through the established native control rules; the preparation path does not replace scheduler queues. Cancellation before admission prevents work. Already admitted blocking preparation or commit retains Agent ownership and can finish durably before returning cancellation. Callers inspect or resume the saved boundary rather than infer rollback.

The extracted blocking preparation worker explicitly moves the complete Agent into a local guard before reading its Store. Caller drop cannot reduce that ownership to a Store clone while preparation continues. This focused extraction preserves the current whole-Agent SQL guards, retained tool owners, cumulative output accounting, observed-wall and fixed monotonic deadlines, native control/CAS rules, and scheduler uncertainty checks. It has source and Rust 1.88 formatting inspection only; fresh focused CI, compilation/static gates and capture/retirement/caller-drop runtime verification remain pending. The earlier walkthrough below predates this correction and does not verify this prerequisite union.

`Scheduler::start_with_preparation(services, limits, preparation)` adds one optional `TaskPreparation` implementation without changing `SchedulerServices` or ordinary `Scheduler::start`. A fresh command passes its actual task/conversation/command identity, accepted objective, captured execution policy, effective authority and ordinary locally selected definitions. The adapter returns bounded actual memory excerpts, quoted context blocks (the Host's project `AGENTS.md` and skills catalog, [unit 7](../architecture/agents-and-skills.md#unit-7-as-built)) and selected definitions. The native preparation path independently validates these results and persists them before provider construction. Every task using that scheduler, including children and scheduled roots, follows this same path. An active native command resumes its saved memory, quoted context and definitions without invoking preparation again. A new FIFO command prepares independently.

The hook is a trusted host composition boundary, not a model tool or permission grant. It must preserve cancellation and retain any admitted blocking/native work until quiescent. The default scheduler still uses genuine offline selection with no memory service or classifier network request. The headless host must explicitly compose its actual memory and approved selector adapter before those features become application behavior.

`Scheduler::retire_provider_unavailable(task, expected_command, request_id)` is a trusted scheduled-execution prerequisite. It terminally fails only an inactive root whose saved typed waiting reason is `ProviderUnavailable`, with no cancellation, queued messages, resume authorization or child wait. It obtains native execution and short write ownership, checks the exact pending command and absence of pending, waiting or previously consumed task inputs, then permits only a legacy absent native setup or a ready setup with no round, model/tool attempts, reserved output, charged usage or reported usage. The transactional checkpoint read checks its SQLite type and byte limit before allocating a Rust string. A transaction checks that the task checkpoint is unchanged and that no broker operation exists for the task before atomically recording its immutable retirement audit and terminal failure. Broker quarantine rejects fresh retirement.

The audit binds the original task/command and retirement request identity. Exact replay returns the saved terminal snapshot before current execution-state checks; changed reuse conflicts. Retirement changes no Agent pending turn or history and performs no retry or budget refund. It does not prove that any other failed or uncertain task is safe to retry. Scheduled execution owns its durable retry intent, cumulative budget and original deadline separately.
