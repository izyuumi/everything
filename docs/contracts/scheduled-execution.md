# Scheduled execution policies

Issue #52 extends the existing ScheduleEngine and Store with serial attempts, cumulative budgets, explicit uncertainty acknowledgement and terminal notification delivery. It uses the one native Scheduler and global Tool Broker. Schema 9 follows actual schema 8 and preserves every existing first-attempt identity and serialized policy. The execution source and [headless owner controls](scheduling-controls.md) are integrated through [#103](https://github.com/izyuumi/everything/pull/103) and [#105](https://github.com/izyuumi/everything/pull/105) after exact-source Rust CI. Historical disposable walkthroughs retain their source qualification. Successful loopback inference is recorded in the [2026-10-17 walkthrough](#2026-10-17-successful-inference-walkthrough).

## Attempts and retry

The immutable occurrence owns at most its captured 1–8 attempts. Attempt 1 retains the original reserved TaskId. Each later attempt reserves fresh isolated conversation, creation/input commands and native task before Agent admission, with the original occurrence deadline. Definition generation, endpoint, instructions and authority never follow mutable host defaults. The original captured allowlist is reused and all actual SCHEDULER_TOOL_NAMES remain excluded. A new never-paid attempt may capture fresh local preparation; active resumes reuse their exact native Definition. An approved classifier result is not copied or automatically approved for a different task.

A durable admission marker distinguishes an unadmitted reservation from a previously admitted missing native task. Schema-8 running occurrences seed that marker. Missing admitted tasks become Unknown; replacement work is forbidden. Exact native enqueue reuses identities and policy. Attempt results are immutable, including settlement time, charged usage, typed disposition, bounded diagnostic, outcome digest and optional next-retry instant. Terminal settlement updates the final run outcome and notification readiness in the same transaction. Run history and its original immutable snapshot remain authoritative.

Automatic retries are restricted to the actual trusted Scheduler retirement proof for ProviderUnavailable. The engine reserves the retirement request identity first. The actor proves an unused factory boundary, atomically retires the exact native task and records its audit; its exact request replay repairs a crash before ledger settlement. A generic Failed status, diagnostic text, native request, interrupted tool, provider uncertainty, child uncertainty or broker reconciliation never authorizes retry. Before recording any completed, failed or cancelled native result, the engine independently checks the validated saved native phase, typed waiting state and any immutable Running/Unknown tool journal for that exact task. Any uncertainty yields Unknown regardless of terminal status. Cleanup acknowledgement or zero unresolved cleanup count does not change this classification. A cancellation is not converted into a factory failure. The existing native paid-retry owner API is not used.

Each proven factory failure consumes an execution-attempt ordinal and zero paid/native model, output or tool allowance. Queue-capacity replay consumes no additional ordinal. Checked exponential backoff uses the captured initial/capped values and is persisted with settlement. No next attempt is reserved until its predecessor is settled, eligible, before the original deadline and within all ceilings. The final permitted failure settles the occurrence; no occurrence UUID or generation is invented for retry.

## Limits, deadline and cancellation outcomes

The scheduled budget is captured and cannot be raised for an existing occurrence. When the native task pauses with the typed `limit` waiting reason, the engine requests native cancellation at once instead of holding the overlap slot until the deadline. A cancelled task whose original native turn paused at its model-attempt, tool-call or token limit records `Failed` with code `run_budget_exhausted`. A cancelled task whose native turn paused at its duration limit, or whose terminal update is at or after the occurrence deadline, records `Cancelled` with reason `scheduled execution deadline expired`. Other cancellations, including owner cancellation of a queued or running task, keep `native scheduled task cancelled`. Uncertainty still takes precedence: an uncertain task ending at or after the deadline records `Unknown` with a deadline-specific reason. These labels change only new terminal records; none of them authorizes retry, refund or overlap release beyond the existing rules.

## Terminal evidence consumption

The Engine reads the original TaskSnapshot and optional private terminal evidence from one validated Scheduler row through its retained blocking-work boundary. It rechecks task/conversation/input identity and binds durable evidence to the original occurrence configuration and execution policy. Observed counters, optional output reservation, native deadline and uncertain phase come from that immutable task evidence; later reuse of the execution conversation cannot replace them. An inspected NoAttempt records zero accounting only and does not erase independent journal or typed waiting uncertainty.

Legacy accounting requires a summary matching the exact original task, command, configuration, workspace, mode, complete allowlist, deadline and validated counters. A later command's summary is ignored for both accounting and outcome classification, even if that later command is in-flight or uncertain. Missing, unreadable or nonmatching original accounting consumes all of the captured attempt's model/tool/output allowance with known=false. The original native phase is inspected independently after exact task, command and configuration matching; an accounting validation failure cannot erase that phase's uncertainty. Read/validation errors remain visible in Engine diagnostics. An observed legacy output reservation of None similarly consumes the full captured output ceiling while retaining observed request/tool counters and known=false. Missing accounting alone never changes a known terminal effect outcome to Unknown, grants a refund, replacement work or a retry.

Original typed waiting reasons and exact immutable Running/Unknown tool journals remain independent uncertainty sources, as does a validated original native phase. Separately, the existing exact retire_provider_unavailable task/command/request/audit replay proves an unused factory boundary under its strict native guard and no-operation transaction. That genuine zero-effect authority is preserved for historical retirement audits without the newer evidence field; it is not a general missing-evidence fallback. Deadlines, attempt ordinals and cumulative ceilings still apply.

## Budgets and time

Native requests reserve their full configured output maximum before ProviderInFlight. New scheduled policies set max_reserved_output_tokens to the remaining captured output ceiling and keep the captured model-request ceiling; a request that cannot fit stops without shrinking its output maximum. Reservations survive failures, uncertainty and restart. Completed-attempt accounting is summed before a successor is reserved. Output reservations are distinct from reported output. Model requests, tools and reserved output cannot exceed the original occurrence capture across attempts.

Historical schema-8 policies with no exact output ceiling retain their original conservative request bound and are never rewritten. Missing historical output accounting conservatively consumes that attempt's unprovable allowance. cumulative_usage includes conservative allowance for unsettled or unaccounted attempts and sets known=false; it does not claim those allowances are observed paid usage. Settled validated native counters replace that accounting uncertainty only with actual evidence. known=true describes recorded accounting, never certainty about external effects or permission to retry or release overlap. Factory proof is the only automatic zero-effect retry boundary.

The absolute deadline is original actual claim time plus captured timeout. Queue, provider construction, approval, offline and backoff waiting all spend that time. New attempts never reset it. Recording timestamps may clamp for ordering, but admission and retry eligibility use actual realtime. Native fixed monotonic caps and persisted maximum observed wall samples remain in force. Detection is relative to recorded samples; unseen clock movement during downtime is not established. Retained optional result publication may wait beyond execution completion without starting work.

## Unknown acknowledgement

terminal_outcome_digest returns a canonical SHA-256 digest over the ASCII bytes everything.scheduling.outcome.v1 followed by one NUL byte, the occurrence's 16 UUID bytes in network order and its bounded UTF-8 typed RunOutcome JSON. The JSON has no whitespace; the kind field comes first, followed by that variant's fields in the Rust contract declaration order, using serde_json string and integer encoding. The returned digest is 64 lowercase hexadecimal characters. Changing that encoding requires a new digest domain version. acknowledge_unknown_as_owner accepts the exact occurrence, stable command, digest, note and acceptance time. It derives the process's real effective UID for the operator audit. Only an authenticated trusted owner route may expose this API; model tools and paired execution controls must not expose it.

Exact replay compares the complete acknowledgement before live-state checks. Changed reuse conflicts. A new acknowledgement requires that exact terminal Unknown and digest. It appends an immutable bounded record; it never rewrites the outcome, clears native uncertainty, grants a retry, resurrects a task or proves an external effect stopped. Overlap queries exclude only explicitly acknowledged Unknown outcomes. Global broker quarantine and native owner-action requirements remain independent. The running host exposes this through the authenticated [owner CLI](../development/scheduling-cli.md#acknowledge-an-unknown-outcome); native scheduling tools and paired commands cannot acknowledge it.

## Delivery

Captured conversation delivery reserves immutable destination, command and event IDs in the claim transaction before effects. Legacy unfinished rows reserve before further admission. Terminal outcomes and ready notification bodies commit together; legacy terminal rows can be backfilled without changing their outcomes. The full bounded notification is checked against the immutable run capture before publication. Task references describe only the latest reserved attempt when its matching native task exists; a missing or never-admitted latest task yields paired None references, never an older attempt.

The engine polls at most once per second, uses bounded pages and a rotating cursor, and invokes the actual Agent publish_scheduled_result primitive. Busy destinations retain their intent. Missing destinations expose a delivery error with no alternate destination. Legacy backfill prepares existing reservations before admitting missing intents. Each bounded preparation transaction commits successful rows even when other rows cannot acquire one of the 2048 pending slots; DeliveryPreparation reports the prepared count and capacity_deferred separately. Only that exact new-intent slot exhaustion is deferred. Invalid counters, notification byte limits and every other failure roll back the transaction. A failed or partially deferred legacy backfill does not prevent existing ready deliveries from draining and freeing slots. EngineStatus.delivery_preparation_error retains the bounded capacity diagnostic while any selected intent is deferred, including a page with successful progress, and clears after progress without deferral; delivery_error separately reports publication and receipt errors. Cancellation still stops admission. Publication creates no model message, pending turn or task. After append, acknowledgement checks the complete durable Agent command journal and original event sequence before releasing the pending reservation. A crash between append and acknowledgement replays the same full request. Delivered payload storage is released; immutable IDs, digest and sequence receipts remain.

A historical disposable quota walkthrough allocated all 2048 pending slots through actual repository claims and terminal outcomes, then added one qualified legacy terminal row without an intent. Backfill Capacity stayed visible while existing ready deliveries drained and acknowledged; freed capacity admitted the legacy notification and only that actual progress cleared its preparation diagnostic. Full clean host reopening with the retained backlog also passed. This establishes the exercised delivery quota, not exhaustive retention limits.

The later partial-page progress and existing-reservation ordering correction has source review and formatting validation only. The earlier walkthrough used one legacy row and does not verify multirow partial-capacity behavior. Fresh combined compilation, CI and a disposable partial-capacity walkthrough remain required.

At most 100000 attempt rows and 64 MiB of serialized execution policies are retained. Each open attempt reserves bounded result metadata; results store at most 1024 diagnostic bytes. At most 2048 pending delivery slots reserve notification bodies of at most 32768 bytes each. Acknowledgement metadata is capped at 16 MiB. Existing job/run/history/native limits also apply. Capacity failures roll back admission and remain visible; no automatic history pruning or backup subsystem exists.

## 2026-10-17 successful-inference walkthrough

A debug build of this branch ran one `serve` Host on fresh disposable state with a session credential bound to a loopback fake server implementing the OpenAI Responses streaming wire protocol. All jobs used read-only authority unless stated. Observations:

- Isolated success: a manual run created its own execution conversation, made one model request and recorded `Succeeded` with the model text, known usage of 1 request/256 reserved output tokens, about 0.1 s after claim.
- Conversation delivery: a job targeting an existing conversation appended exactly one `scheduled_run_finished` event carrying the execution conversation, task, digest and summary, with no model message.
- Overlap: while a first run held its model response for 12 s, a second manual claim was recorded `Skipped/overlap`; a claim after the first finished was admitted and succeeded.
- Timeout: a run with an 8 s timeout whose model response never arrived was cancelled 38 ms after its deadline; the provider saw the connection close. The recorded outcome is `Unknown`, because the request was in flight. A `full_host` run whose `shell` call awaited approval stopped at its 10 s deadline as `Cancelled`. A later owner approval of that stale operation executed nothing.
- Cancellation: owner cancellation of a running task holding a model request recorded `Unknown` within 25 ms. Cancelling a task still queued behind another primary task recorded `Cancelled` with zero usage.
- Retry: provider-factory failures with `max_attempts=3`, 1000 ms initial and 1500 ms maximum backoff produced three attempts with fresh task/conversation identities, persisted retries 1000 ms and 1500 ms later, the original deadline, and terminal `Failed` with no fourth attempt.
- Permissions: a job allowing only `read_file` advertised only `read_file`; a model `shell` call returned `tool_not_advertised` and created no file. An allowed `read_file` call succeeded. Creating a read-only job that allows `shell` was refused as exceeding captured authority.
- Budget: a 1-request job whose model asked for a tool previously stayed `running` until its 15 s timeout and then recorded a generic cancellation. With this change it settled in 142 ms as `Failed/run_budget_exhausted`.
- Missed runs: two enabled 20 s interval jobs ran on time (1–94 ms late). The Host then stopped with SIGINT (exit 0) and restarted 50 s later. The `skip` job recorded one `skipped_missed_range` through the latest missed instant and did not dispatch. The `latest` job collapsed the older instant and dispatched the latest missed occurrence 12.5 s late. Both resumed normal timing, and earlier history was unchanged after restart. The catch-up attempt failed at provider construction because the session credential was restored only after restart.
- Interrupted run: SIGINT during a held model request left the reopened native task waiting on `provider_uncertain`. The occurrence kept its overlap slot and became `Unknown` 652 ms after its original deadline.

Native primary execution is serial by default, so a queued scheduled task spends its own deadline while it waits. Wake-up for retry instants and deadlines still uses the one-second audit, with native scheduler change notifications in addition. This walkthrough does not cover arbitrary process crashes, OS clock changes, the Anthropic adapter, Apple delivery or production security.
