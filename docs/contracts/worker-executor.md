# Headless worker executor

Issue [#29](https://github.com/izyuumi/everything/issues/29) implements the optional worker. Automated verification is deferred to [#32](https://github.com/izyuumi/everything/issues/32). The command leaf, top-level CLI and existing owner IPC compose the executor. Coordinator controls use the authoritative Host and have a separate composition contract.

## Explicit executor configuration

`worker::commands::WorkerArguments` parses the executor commands. `commands::run(arguments, state_directory, cancellation).await` returns bounded JSON command output after the requested operation completes. The application must pass an explicitly selected dedicated worker directory and await this future through ordinary token cancellation. An ordinary Host directory is rejected, and an active owner of either role holds the same exclusive lease.

`serve --config PATH` reads a nonsecret `WorkerExecutorConfig` before opening relay connections. Its exact fields are `schema_version: 1`, `relay: RelayOrigin`, `model: WorkerModelBinding` and `coordinators: Vec<WorkerCoordinatorPin>`. Each coordinator binds complete `DevicePublicKeys` plus its exact `expected_fingerprint`. At most sixteen distinct IDs/signing keys/encryption keys are accepted. Empty coordinator configuration grants no remote task authority. The model configuration and credential reference are immutable for that dedicated worker state.

The source file must be an owner-controlled single-link ordinary file without group/other write permission, at most 64 KiB, selected through a bounded UTF-8 path. Reading runs outside Tokio workers and uses NOFOLLOW, NONBLOCK and a final descriptor metadata check. Unknown fields, malformed encoding, unsupported versions, invalid profiles, duplicate peers and fingerprint mismatches fail without echoing file contents. Parent-directory symlinks are not claimed as a hard isolation boundary for this owner-selected metadata file. No file field accepts a model secret.

Purpose identity and endpoint/profile binding happen locally before the explicit relay future starts. Every retained active coordinator must appear in the configuration, with the same exact keys. A known revoked entry can remain in the file as historical metadata without restoring trust. New confirmed pins are individually durable; a later local startup failure may leave those explicitly authorized pins retained, and an identical retry reuses them. No implicit pin deletion, credential fallback or profile rebinding occurs.

## Commands and native credentials

The leaf provides `serve --config PATH`, `identity`, `status`, `inspect --task TASK_ID`, `inspect --delegation UUID`, `inspect --cleanup`, `revoke --peer DEVICE_ID --request-id COMMAND_ID`, and `acknowledge-cleanup` with the original operation ID, original result digest, operator, note and stable request ID. Use `vorra --state-dir DEDICATED_PATH worker ...`, or explicitly select `VORRA_STATE_DIR`. Worker commands reject an omitted state selection before opening the ordinary Host default directory.

Online inspection and revocation use the existing `HostClient` and owner-only `LocalServer`. Identity output contains only the worker-purpose public keys and fingerprint. Offline identity creation acquires the actual dedicated Agent lease, never a replacement lock. Worker status includes the real phase, explicit relay state, immutable model reference, bounded public pins and job count. A delegation summary contains identities and semantic status, not copied file contents or a complete private manifest. Its native task ID requires the actual immutable worker-native admission and a validated owned Scheduler snapshot; a manifest alone cannot establish task admission.

`credential store --config PATH --source-environment-variable NAME` and `credential delete --config PATH` are explicit offline operations. They acquire the same exclusive state lease, validate/bind the worker's profile, and derive only `WorkerModelBinding::credential_key(actual_worker_device_id)` under `to.yumi.vorra.worker.models`. Running executor state cannot be opened by these offline commands. Stop the process before changing its native credential.

Store reads only the explicitly named ASCII environment identifier. The selected value moves through zeroizing bytes into `CredentialSecret`, must be nonempty printable UTF-8 within 8192 bytes, and is never accepted as a raw argument, serialized setting or file field. There is no ordinary Host vault, default provider environment, instance metadata or cloud-SDK fallback. Unavailable or unsupported native credential backends return their actual error. A native write/delete admitted before cancellation may complete; its owned operation retains the endpoint and leased Agent through the real native-store await, even if its caller drops. Inspect the native store before an explicit retry after a lost response.

## Process ownership and owner recovery

The serve waiter requests stop on cancellation or drop. The complete service loop lives in an owned Tokio task, so aborting that waiter does not abort its LocalServer, relay task, native runtime or recovery loop while the Tokio runtime remains alive. It composes the existing `WorkerRuntime::start` and exactly one executor `run_relay(None, ...)`; no coordinator gate or second native kernel is introduced.

The existing local socket reuses the exact Agent-owned lease. Its same-user authentication, frame/time/channel bounds and request validation remain authoritative. The executor serves existing Identity, Runtime, Transport, Task and ToolRecovery queries plus the bounded Worker query extension. Its only effectful owner operations are purpose-specific RevokeWorkerPeer and exact AcknowledgeCleanup. Ordinary Host commands, synchronization, pairing, scheduling, provider retries and permission changes are rejected.

Cancellation or a service failure starts native drain and cancels relay I/O. The owner endpoint remains available through NeedsOwner and cleanup pending. If its listener fails, the owned service attempts to rebind that same existing protocol with the same lease while retaining native ownership. A native supervisor join failure remains an owner-visible unresolved condition requiring inspection; it cannot become a successful later shutdown. Cancellation acknowledgment never proves effects stopped.

After actual native stop and supervisor join, the service cancels local accepts and awaits every owned local/relay task. It returns successful JSON only after those joins. No timeout is treated as joined, and no ordinary Ctrl-C path exits Tokio with pending cleanup. A caller that destroys the entire Tokio runtime or terminates the process can still interrupt execution; restart relies on the existing uncertainty journals and never authorizes an automatic paid retry.

## Retained execution and shutdown

`WorkerRuntime` retains its actual native supervisor task. `request_shutdown()` synchronously requests cancellation. `join(&mut self)` requests shutdown and awaits that original supervisor; canceling or timing out the borrowing future leaves the join handle retained in the runtime. A completed join error is sticky and cannot become a successful later join. Success requires both the actual joined supervisor and its `Stopped` phase.

The existing `shutdown(&mut self)` still waits at most twenty-five seconds and returns `ShutdownPending` while execution or cleanup remains owned. Successful shutdown now includes the actual supervisor join. Dropping a handle requests cancellation and does not assert completion. A process embedding this runtime must retain its runtime, leased Agent and authenticated owner recovery endpoint until native shutdown and actual owned task joins complete. A cleanup acknowledgment records the existing broker's exact operator attestation; it neither changes an immutable Unknown outcome nor authorizes a model retry.

Executor broker startup uses the native `start_with_owner` API with the actual leased Agent clone, including its blocking recovery work before the runtime supervisor exists. Integration must preserve the native prerequisite's retained-owner propagation through broker supervision and complete ToolExecutionContext ownership in filesystem blocking workers. This startup adaptation depends on that reviewed prerequisite and has source review only here; fresh combined compilation, CI and lifecycle observations remain required.

## Dedicated executor state

Synchronous `WorkerEndpoint::validate_executor_agent(&Agent)` requires an actually leased Agent and performs a read-only dedicated-state check. Call it outside Tokio workers while retaining that Agent. Executor endpoint opening performs the same check before immutable endpoint binding; coordinator endpoints may share their authoritative Host state.

The executor rejects ordinary host or replica transport identities, ordinary device trust, host command inbox records, scheduled jobs/runs, remote host commands and replica events. Every retained conversation must be bound to an original worker-native admission and manifest conversation identity. Tasks and tool journal rows must belong to that same exact admission; global or unrelated permissions are rejected. This protects configuration separation, not arbitrary-code isolation. An active host additionally holds the same singleton state lease and therefore cannot be opened by another executor process.

Runtime startup repeats dedicated-state validation and the existing full native ownership checks before binding its immutable worker model profile or starting native execution. The command composition must perform validation before adding new peer trust or opening a relay connection. Foreign state is never deleted or adopted.

Worker file helpers inspect `vorra.sqlite3` with a descriptor-relative, no-follow metadata query instead of opening and closing another descriptor for the live database inode. The database must remain a regular, singly linked, owner-owned file with mode 0600. This preserves the existing inode-based state exclusions without releasing SQLite's process record locks through an unrelated descriptor close. The metadata is a snapshot under the trusted private state-directory boundary; it does not pin a replacement inode or make SQLite adopt the validated descriptor. This correction has source review only; fresh combined CI and live-WAL/file-helper observations remain required.

## Purpose peer inspection

`WorkerEndpoint::peers().await` returns at most sixteen validated `WorkerPeerState` records containing complete public keys, original pin time and optional revocation time. It checks encoded size before decoding each record and verifies that the stored device ID matches its public keys. This is read-only inspection; it grants no trust or ordinary Host/Replica rights.

Explicit startup configuration must account for every retained unrevoked pin. An omitted active peer fails startup rather than silently retaining an undeclared coordinator. A configured exact historical revoked key may remain visible as revoked metadata and must never be passed to `pin_peer` to restore rights. New pins require exact full-key fingerprint confirmation. Revocation remains sticky and records cancellation intent, not proof that remote or native effects stopped.

## Current-main ownership integration

The current-main extraction retains the complete Agent as the first local of the Worker registry-construction blocking worker and as the last field of its successful returned tuple. The named returned owner remains live through `ToolBroker::start_with_owner`, which receives the actual endpoint Agent. This covers queued work, setup errors, unwinding and abandoned successful outputs without another broker or a caller-owned cleanup wrapper. The existing descriptor-relative administrative-file checks use no-follow metadata for the SQLite identity and do not open or close another descriptor for its inode.

This integration has source, Rust 1.88 formatting and structural preservation checks only. Earlier executor and coordinator walkthroughs retain their original source and artifact identities; they do not verify this current-main union or its caller-drop behavior. Fresh exact-head CI and disposable runtime checks remain pending. Successful inference, native credential persistence and security acceptance are not implied; automated coverage remains deferred to [#32](https://github.com/izyuumi/everything/issues/32).

Current executor recovery and reconciliation distinguish a missing or revoked purpose peer (`UntrustedPeer`) from storage, decoding and key-validation failures. Only that exact trust error is classified as revocation; other errors propagate through the owned runtime cleanup and remain visible as failure. Startup retains the earlier unsafe-dispatch short circuit before peer lookup. This correction has source review; no new runtime fault-injection observation is claimed.
