# Scheduler contract

`Scheduler` is the host's single durable native task queue. Construct one `SchedulerServices` from the host's shared Agent, ToolRegistry, global ToolBroker, TaskProviderFactory, and optional local discovery services. `Scheduler::start(services,limits)` validates and recovers scheduler-owned rows without inference. Register native task tools before constructing the final registry and Authorizer, bind them to the returned Scheduler, retain the binding guard, and call `activate()` when host composition is ready. Never start a second scheduler or broker over the same host Store.

## Admission and identity

`ExecutionPolicy` contains an absolute workspace, execution mode, tools switch, optional allowlist, ContextBudget, and LoopLimits. `capture(registry)` canonicalizes an existing workspace and freezes the actual registered names into an explicit allowlist. Disabled tools capture an empty allowlist and zero tool calls. Capture and persist effective owner policy once at command acceptance; replay must reuse it even when host defaults change. Credentials never belong in this snapshot.

`TaskSubmission` supplies task, conversation, and accepted user-command UUIDs, original host acceptance time, and captured execution policy. The host first uses Agent's idempotent create/accept APIs. `enqueue(submission)` verifies the durable user instruction, captures that conversation's exact configuration, and atomically reserves a Queued TaskRow. Exact existing definitions return the current snapshot before capacity checks; changed identity or policy conflicts. Different tasks cannot own the same accepted command or simultaneously occupy one conversation. Pre-existing foreground TaskRows return NotOwned; they are not silently rewritten or adopted. An owner must stop the host and explicitly resume/settle the prior foreground task with the existing CLI before continuing, or address that reported legacy-state boundary. Original acceptance time is independent of the user-message timestamp.

Queue admission is not completed inference. `status(task_id)` also reads terminal rows. `active_in_conversation(conversation_id)` returns the one nonterminal task or None; foreign foreground ownership returns NotOwned and inconsistent multiple owners fail closed. The host must query under its mutation gate before accepting a different user command, deferring inbox application until the previous task settles even when Agent.pending has already cleared. Same-command replay remains allowed. TaskSnapshot includes immutable TaskRecord identity, current status, active command, pending-message count, cancellation flag, waiting reason, and bounded last output/diagnostic. Root submissions accept caller-reserved UUIDs; scheduled or remote adapters must reserve their own immutable intent before calling Agent or enqueue and replay those same identities after uncertainty.

`scheduler::task_snapshot(&Store, task_id)` reads the same validated durable snapshot without a live scheduler actor, including after shutdown. It performs synchronous SQLite work; asynchronous hosts must call it on a bounded blocking worker while retaining their state lease. It does not admit, wake, mutate or execute a task.

`scheduler::task_publication_records(&Store, task_id)` returns the immutable initial TaskRecord and current checkpoint TaskRecord from one validated repository read. Publication uses this source without changing task state. This synchronous read has the same bounded blocking-worker and state-lease requirements.

## Execution and wakeup

At most four configured primary tasks and three configured subagents run; defaults are one primary and three subagents. All nested descendants share the same global subagent allowance. Each activation uses the actual Agent::run_tools kernel and its per-conversation admission, with the same shared broker. A worker marks no TaskRows itself. The serialized control actor persists Running before dispatch and drains the full stream before recording an outcome. Only matching durable final native state completes a task. A successful shutdown report is retained in the handle before the actor exits, so retries after a timeout or a dropped caller still return the actual completed drain proof; generic actor closure never implies success.

`TaskProviderFactory::create(&ConversationConfig,CancellationToken)` must construct the native provider for that exact immutable provider/model/endpoint and approved credential binding. It must not perform inference or detach work. Construction is cancelled and bounded to 30 seconds. No credentials are serialized. Ordinary startup prepares fresh contexts from the accepted instruction and that isolated conversation's history. `start_with_preparation` optionally supplies the trusted [task preparation boundary](task-preparation.md), whose returned memory and selected definitions are independently validated and captured before provider construction. Active resumption reconstructs that exact saved native setup and discovery binding without invoking preparation again. No memory or remote-selector application adapter is supplied by this generic interface.

`subscribe()` returns a coalescing process-local watch revision. Subscribe before reading durable events or snapshots, then requery on changes. Native stream progress and applied mutations notify it; status reads do not. Notifications are hints, never authoritative events or durable cursors. After reconnect or restart, query actual Store/Agent state. No independent polling or model execution loop is required in the host.

`wake(task_id)` permits safe approval continuation and exact in-flight broker polling. A wake accepted while the worker is active is retained until its result settles, then used only if the actual saved phase remains approval or broker InFlight. Startup performs one exact broker status/authorization recheck for each such task; an unchanged pending approval yields again. Duplicate repairs do not repeat this startup check. No new paid model request occurs until the actual ordered tool round completes. It does not authorize another uncertain provider request, widen budgets, replace saved setup, or retry unknown effects. Reconciliation, invalid state, interrupted tool execution, and exhausted limits require explicit owner handling. Invalid workspace ownership is isolated as Waiting Interrupted for that task; unrelated tasks can recover.

`resume_provider_once(task_id,expected_attempt,request_id)` is a trusted owner API and never a model tool. It verifies the exact saved ProviderInFlight attempt, durably appends an immutable audit, and issues one ephemeral dispatch permit. Exact request replay returns its receipt without granting another attempt. Permits disappear on dispatch, provider construction failure, cancellation, or host restart. Recovery never reconstructs them. A new owner decision with a new request UUID is required if a crash consumed an accepted permit before dispatch. Retry never permits unknown tool effects to execute again.

`resume_interrupted_once(task_id,expected_command,expected_revision,expected_status,request_id)` is a separate trusted owner action for exactly Paused(Cancellation) or Paused(InterruptedTool). It binds the command and conversation checkpoint revision as well as phase, refuses Running broker operations, and uses the same durable audit/ephemeral permit discipline. The native phase is rechecked at dispatch, preparation, and after provider construction. A new revision or phase requires a fresh owner decision. Unknown, broker InFlight, and Reconciliation are excluded from this path. Plain wake and restart never grant it.

## Task controls and isolation

SchedulerTools registers `spawn_agent`, `send_agent`, `agent_status`, `cancel_agent`, and `wait_agents`, then returns their trusted RuntimeTask scope rules. Descriptors have no filesystem, shell, network, or MCP capability. Mutators truthfully declare read_only=false; all controls are concurrent broker tools whose state changes serialize through one actor. RuntimeTask permission remains subject to the caller's frozen allowlist. It conveys no additional external privilege.

Every tool verifies its host-issued caller task and workspace against an existing Running scheduler task. Spawn/send operation UUIDs must identify that caller's actual Running broker journal entry. Model arguments cannot supply a caller identity or broader authority. Targets must be descendants; status may inspect self. Send/cancel cannot reach an ancestor, sibling, unrelated task, or primary root. Each action returns bounded acceptance/state and never waits for child completion while holding broker admission. Known rejected controls return completed semantic errors. Once a workspace/domain/checkpoint mutation has begun, ambiguous failure or loss of an admitted actor reply returns EffectsUnknown with unconfirmed cleanup, forcing broker quarantine and parent reconciliation. A proven durable snapshot returns an applied receipt, including a minimal receipt if a preview cannot fit; partial admission never becomes an ordinary failed spawn that invites a new operation ID.

Spawn derives stable child task, conversation, creation-command, and instruction-command UUIDs from its immutable broker operation using namespaced SHA-256 identity derivation. Child mode defaults to the parent and may only narrow. Configuration, explicit tool allowlist, and per-command context/loop budgets inherit unchanged. A child authority is derived through `child_in_workspace`, never reconstructed as a wider root authority. Child roots are distinct private physical descendants, with no inherited parent files, cloned repository, or implicit parent conversation/memory. Only the supplied instruction and later messages enter their conversation.

Native controls may create private `.everything-agents/<task-uuid>` application workspace directories even for ReadOnly tasks. ReadOnly child filesystem tools still cannot mutate user files. Components are opened relative to directory capabilities with NOFOLLOW; directories require current-owner mode0700 and markers require single-link owner mode0600. Authority checks validate the marker and strict physical descendant on every activation. Native filesystem operations reject reserved `.everything-agents` and `.everything-workspace.json` components relative to the current workspace, and search skips them, so supported model file tools cannot overwrite control metadata. Normal files within a child root remain available. Application checks do not sandbox arbitrary trusted FullHost shell or a hostile local owner changing mount/inode state.

Send persists a bounded FIFO of follow-up commands. It does not interrupt an active provider request or bypass an approval/uncertain boundary. After a durable final response, the next command is idempotently accepted into that child's same isolated conversation. Recovery repairs the acceptance/checkpoint handoff using exact pending command and previous completed-run identities. Each follow-up uses inherited per-command budgets. Terminal tasks reject new messages. Spawn does not imply that the parent waits for descendants before completing.

## Steering and explicit child waits

`steer(task_id,delivery_id,accepted_at,instruction)` is a trusted authenticated-host API returning Agent's durable TaskInputReceipt. The host must verify its command conversation against the task's immutable conversation and reuse its original inbox delivery UUID and acceptance time. A fresh delivery binds the current active task command under the serialized actor. Exact replay first recovers that binding from the original SteeringReceived event, even after the command advances or the task terminates; Agent verifies the full payload, target and acceptance time. Changed content conflicts. New input to cancelled or terminal work is rejected. Acceptance grants no authority, budget extension or uncertain-provider retry. Storage/worker ambiguity after input admission is reported as MutationUncertain for idempotent inbox replay.

`wait_agents` takes `task_ids`, a distinct array of 1 to 32 strict descendants. It validates the caller's current Running task/workspace and its actual Running broker operation. The tool persists a typed wait intent before delivering Agent's WaitForChildren input, then returns bounded acceptance immediately. Its broker permit is released before the native kernel yields at a safe known-result boundary. Spawn alone remains nonjoining. An unresolved wait cannot be replaced, and a later wait requires the previous wait and queued inputs to have been consumed.

The checkpoint's optional child_wait field is omitted when absent, preserving prior scheduler-row serialization. It binds the exact parent command, namespaced wait UUID, original operation time and child IDs. For each terminal child, the actor records a stable delivery UUID, terminal command/status/time, bounded output and derived uncertainty before accepting ChildFinished. The delivery comes from actual terminal TaskRows, native phase and tool journal state; callers cannot assert success or cleanup. ProviderUncertain, Reconciliation, InFlight, propagated child uncertainty or Running/Unknown tool journals produce an unknown child result. The parent stops at typed ChildOutcomeUnknown for owner inspection; plain wake, steering, cancellation and provider retry cannot turn it into a normal retryable failure.

Child completion/cancellation and startup repair the wait-intent, terminal-save and Agent-delivery gaps using the same identities and captured times. Completed parents never reopen. A process-local wake is only a hint: after every waiting worker finishes, the actor rereads actual durable pending input and requeues only Ready or WaitingForEvents work. A delivery received while the parent was active therefore remains actionable after queue admission was skipped. Unknown, approval, interrupted and exhausted-budget boundaries keep their existing requirements. Known inbox-capacity rejection defers child delivery while retaining its exact saved identity; safe existing inputs may drain before the next repair. It does not stop the actor or claim delivery. A first wait that cannot fit is retired before a semantic capacity failure. ProviderUnavailable and host-stopped tasks do not self-requeue on duplicate repairs; after credentials change, an explicit owner wake or restart grants another construction attempt. Deferred delivery emits a bounded diagnostic trace. Every nonterminal checkpoint also reserves variable lifecycle growth: 81920 bytes minus the current serialized output, diagnostic, waiting reason, TaskRecord.failure, TaskRecord.status and TaskRecord.updated_at sizes, saturated at zero. An 8192-byte output can expand to49154 JSON bytes; the 2048-byte diagnostic and its failure-message copy each expand to approximately12300, leaving several KiB for bounded phase/identity metadata. Terminal checkpoints need no future lifecycle reserve. The reserve shrinks as those fields grow, including status-name and timestamp digit growth at an exactly full admission boundary, preserving room for final output and failure state without placeholder records. Every checkpoint insertion/save reserves 1024 serialized bytes for each undelivered child while the parent remains uncancelled. Empty typed delivery metadata is checked against that bound before capture. New waits and queued messages must leave this reserve intact. Terminal capture halves its UTF-8 preview, possibly to empty, until it and all remaining metadata reservations fit. The complete output remains in the child conversation/task history. The first captured prefix is immutable: replay verifies terminal identity, time, status and uncertainty, and requires the saved output to remain a prefix of the actual bounded child output before delivering exactly the saved payload. Once every child is captured, the actual input state has no wait or pending input, and original wait/child receipts all fall at or below the consumed cursor, the actor retires the completed private wait before saving new lifecycle metadata. Original events and command receipts remain authoritative and unchanged. A legacy checkpoint which cannot fit even empty metadata is deferred only on the known pre-SQL checkpoint-byte capacity error; its unsaved snapshot is restored, no Agent result is delivered, and admission emits an owner-action diagnostic instead of preventing unrelated startup. Explicit cancellation preserves native inputs/journals and retires future delivery eligibility, so it needs no additional delivery reserve. There is no polling loop or second agent kernel. `SCHEDULER_TOOL_NAMES` exports the five actual registered control names so restricted execution profiles can exclude the entire control surface without duplicating a stale list.

## Cancellation, shutdown, and recovery

`cancel(task_id)` durably marks the parent first, then marks/cancels bounded descendants. Admission checks the entire ancestor chain, including after restart; an interrupted cascade cannot restart a child of a cancelled parent. Active tokens cancel providers and broker futures, while workers keep draining. A terminal task cancellation is an idempotent no-op; surviving descendants of an already completed parent must be cancelled by their own IDs. Recovery and dispatch settle a matching durable final response through the same completion path before cancellation, requiring exact configuration/task/command, no unrelated pending command, and a final assistant message without calls. Known completed native output wins a racing cancellation only when no queued follow-up is abandoned; otherwise the task records Cancelled while retaining final output and the unexecuted queue. Uncertain provider/tool boundaries remain explicit and cannot become ordinary successful results or automatic retries. Cancellation also checks immutable Unknown tool journal entries, including older stopped native phases after cleanup attestation and restart. Cleanup review cannot convert their effects into a known cancellation. Cancellation settles an inactive uncertain task as nonretryable Failed with its waiting reason and immutable native journal retained only after no Running tool journal entry and no broker quarantine remain. Known interrupted results can settle Cancelled. Active cleanup stays Waiting until owner reconciliation; cancellation does not assert that prior effects were reversed. Terminal cancellation does not erase an uncertain native pending turn or manufacture missing results. Such a conversation remains stopped; starting a new conversation is the available continuation boundary until a separate explicit abandonment/branch contract exists.

`shutdown()` requests the actor to stop admission, cancel active tokens, and retain workers, broker, and services until streams drain. One monotonic deadline covers both bounded control-queue admission and the reply. If the deadline expires before enqueue, the stop request has not been admitted and the caller must retry; after enqueue, ShutdownPending preserves the admitted request and the actor's cleanup ownership. Neither timeout aborts ownership. The host must retain its state lease and global services, inspect broker recovery, and retry shutdown. ShutdownReport has zero active tasks only after all scheduler workers have stopped; broker_quarantined independently reports unresolved cleanup. Dropping the final scheduler handle closes control admission and starts the same drain. Runtime/task abort is not a safe host shutdown method.

Startup examines bounded nonterminal scheduler rows and exact native checkpoints. Unstarted or completed-but-unsettled work can repair through the same task/command identities. ProviderInFlight stays stopped pending explicit owner action. Approval and exact broker in-flight operations retain identity; Unknown effects remain nonretryable. The host must start broker recovery before scheduler activation. Persisted broker quarantine prevents every new native task dispatch until explicit host cleanup reconciliation.

## Bounds and deferred validation

The control channel holds 64 requests. Durable pending tasks are configurable 1..256 (default 128), retained scheduler tasks at most 4096, ancestry at most 16, direct private child workspaces at most 64 per workspace, queued follow-ups at most 32 per task, and provider retry audits at most 32. Task input/checkpoint serialization is capped at 786432 bytes each. Task tools accept instructions at most 32768 bytes and return at most 65536 serialized bytes, with output/diagnostic previews of8192/1024 bytes. Native event, model, context, filesystem and broker bounds remain independently enforced.

Workspaces and conversation history are retained after completion/cancellation. No automatic deletion or backup subsystem is implemented. A crash before a new directory's ownership marker becomes durable leaves an unclaimed directory which is rejected, requiring explicit owner inspection/cleanup. Foreign or partially written markers are never silently adopted. Capacity includes retained task state and private directory entries; owners must intentionally retire data rather than bypass limits with new identities.

Automated testing is deferred to [#32](https://github.com/izyuumi/everything/issues/32). Live inference and tool-choice quality require authorized native provider credentials; static checks and failure-only local protocol observations do not verify successful inference.
