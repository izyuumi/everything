# Context contract

`src/context.rs` constructs provider-neutral `model::ModelRequest` values without reading or writing storage. `ContextBuilder::new(ContextBudget)` validates the explicit budget; `build(ContextInput)` returns `BuiltContext` or a typed `ContextError`. The caller supplies reconstructed history, current task state, ranked memory, and tools selected by the discovery layer. The builder does not infer execution permissions, select tools, retrieve memory, or call a model.

## Input and immutable content

`ContextInput` contains the model identifier, immutable `instructions`, `TaskContext`, history, memory, selected tool definitions, tool choice, temperature, optional persisted summary, and optional continuation binding. `TaskContext` contains `objective`, ordered `constraints`, and `state`. Callers must supply every active task constraint explicitly; the builder cannot infer constraints hidden in old conversation text.

Instructions remain exact in `ModelRequest.instructions`. The complete task object is serialized into the first user message. All selected tools and their schemas remain exact. These fixed components receive budget before any history or memory. They are never silently shortened or removed; inability to fit returns `FixedContextTooLarge` or an input/model-validation error. Empty instructions and an empty objective are rejected. Task JSON is limited to 1 MiB and 1024 constraints.

`HistoryEntry` combines a protocol `EventId`, `EventSequence`, and model `Message`. Events must have unique IDs and strictly increasing sequences. Sequence gaps are valid because unrelated durable events may occur between messages. System messages are rejected with `InvalidHistory`; callers place immutable system content in `instructions`. Messages retain their original roles and content. Raw events remain owned by storage.

Tool-call identifiers must be unique across the supplied history. Every result must match exactly one pending call. An assistant message containing calls and its immediately following tool-result messages form one indivisible group. The whole group must complete before another conversation message. Orphan results, duplicated results, and unfinished calls are errors. Other user and assistant messages each form a group. Trimming removes only an oldest prefix ending at a complete group boundary and always leaves the newest group. If that group and the required digest cannot fit, `LatestHistoryTooLarge` is returned.

## Budget and selection

`ContextBudget` requires `max_context_tokens`, positive `reserved_output_tokens`, `safety_margin_tokens`, `max_request_bytes`, and `max_compaction_bytes`. The input estimate is serialized request bytes plus 16 per message, 32 per tool, and 64 for envelope overhead. One JSON UTF-8 byte is charged as one estimated token, including escaping and schemas. This is intentionally conservative for typical text; it is not a provider tokenizer or a proof of every native encoding's token count. The runtime must use the selected model's actual limits, retain a suitable safety margin, and handle provider-side limit errors.

The estimate plus output reserve and safety margin must fit the context limit. Output reserve is copied to `ModelRequest.max_output_tokens`. The complete serialized request also fits the explicit byte limit, which cannot exceed the model contract's 32 MiB maximum. Other model limits, including 4096 messages, remain enforced. The builder accepts at most 65536 raw history entries and 64 MiB of serialized input components. Compaction text is configured between 256 bytes and 64 KiB.

Selection keeps fixed content first, then the longest fitting recent history suffix with its digest, then memory in caller-provided priority order. Oversized memory entries may be skipped while later smaller entries are retained. `BuiltContext.citations` and `omitted_memory` report every supplied memory chunk's outcome. Memory contains at most 1000 excerpts, each with title, heading, and text fields bounded to 64 KiB. Chunk IDs must be unique and bounded; provenance requires a relative Markdown path and a valid one-based inclusive line range. `MemoryExcerpt::from(SearchHit)` preserves wiki retrieval provenance.

Wiki excerpts are JSON-quoted user messages explicitly labeled as source data. Digests are also user messages, labeled as quoted history with omitted details. Neither is promoted to system instructions. These labels preserve the trust distinction but do not establish a prompt-injection security boundary.

## Compaction and durability

When trimming is necessary, the builder produces a `CompactionRecord`. It records the first and last source event IDs and sequences, source message count, SHA-256 digest, method, summary, and `lossy = true`. `DeterministicExtractive` writes an explicit loss notice, source sequence range and hash, and bounded snippets from the first twelve covered messages. It copies at most 160 characters from each text block and identifies tool calls/results without copying their argument or output bodies. It does not claim to preserve every fact or decision and does not perform semantic LLM summarization.

`CompactionRecord::from_model_summary(history_prefix, provider, model, summary)` attaches a real externally generated summary to validated complete source history. This method validates and records the supplied text; it does not invoke the named provider or attest to summary accuracy. The caller performs model inference separately. The source prefix must be followed by at least one newer complete group when supplied to a build.

An input summary is accepted only when its source metadata and digest match an exact complete prefix of the supplied raw history. Stale or incompatible source records are rejected. A fitting existing summary is preserved. If more history must be removed, a new deterministic record covers the enlarged prefix and its method makes that change explicit. Summary content cannot exceed the configured compaction limit.

The source digest is SHA-256 over the bytes `everything-context-history-v1` followed by NUL, followed by each `HistoryEntry`'s compact Serde JSON and a newline in sequence order. It is a content identity, not an authentication mechanism. Callers persist the returned compaction record separately from raw events and can retain its range and hash for provenance. This module never rewrites, deletes, or mutates raw events, tasks, checkpoints, or previously stored summaries.

## Continuation

`BuiltContext::bind_continuation(ProviderContinuation)` creates a binding for the returned request's raw-history prefix, fixed context, and optional compaction record. Persist that binding with a continuation returned by the provider and retain the compaction record used by that request. On the next build, an unchanged prefix with append-only complete history may reuse it. An unchanged existing compaction record can also continue a native round; a new cutoff or changed summary invalidates its compaction hash. Reordering, editing, dropping, or replacing source entries invalidates the prefix hash. Instructions, task state/constraints, model, or selected memory changes invalidate the fixed-context hash. Tool definitions, tool choice, temperature, and output reserve are not history anchors and can change without invalidating it; native adapters still validate their capabilities and request options. This permits a tool-discovery result to expand available tools during the same native round.

At a completed assistant/user boundary, the builder explicitly clears continuation for a changed compaction record, history changes, fixed-context changes, or insufficient remaining budget. A binding cannot end inside a call/result group. `ContinuationDisposition` reports absence, retention, or the clearing reason. If the current history ends in tool results, any attempted clearing instead returns `ContinuationRequiredForToolRound` with the reason. A native reasoning/thinking round may require that opaque state; a complete-looking neutral tool transcript alone does not establish resumability. The host must complete such a round using its stable prior instructions/task state/memory/summary before applying context-changing steering, memory refresh, or compaction. On restart, persist and reconstruct that stable context and its continuation binding, or report that the round cannot resume. Do not drop the error or retry the tool side effect. The builder cannot detect missing continuation that a caller has already discarded; the host must persist every provider-required continuation. Native adapters still own interpretation of continuation and prevention of duplicate history replay; the builder does not inspect provider state.

`ContextUsage` returns the final estimate, output reserve, safety margin, exact serialized request bytes, retained history count, and compacted history count. The request is validated again after construction.

## Validation boundary

Formatting, compilation, strict Clippy, release compilation, and a disposable pure-builder walkthrough validated this implementation stage. The walkthrough compacted 32 of 40 UTF-8 messages while retaining the raw inputs, preserved task constraints, fitted the 12000-token estimated budget, retained one cited excerpt while reporting an oversized omission, accepted unchanged summary provenance and rejected edited provenance, rejected an orphan result, and rejected an undersized fixed budget. It also retained continuation through tool-discovery expansion and an unchanged saved compaction record, and returned an explicit error for changed task state during a tool-result round. Automated budget, source-integrity, grouping, Unicode, compaction, and continuation assertions are deferred to [#32](https://github.com/izyuumi/everything/issues/32). Provider token counts, semantic summary quality, persistence integration, and live model behavior are not verified by this module.
