# Threat model and limitations

Everything's local host owns task execution and durable state. A relay may be curious, compromised, or actively malicious. Its database, network handlers, and operators must never need message plaintext, device encryption secrets, pairing secrets, provider credentials, shell capabilities, or wiki data. A network attacker can observe, delay, duplicate, drop, or reorder traffic. A paired device is trusted only for its assigned application permissions, and the host must validate each decrypted command independently.

`src/crypto.rs` provides Ed25519 sender authentication, X25519 agreement, HKDF-SHA-256 key derivation, ChaCha20-Poly1305 payload confidentiality/integrity, timestamp bounds, a mandatory replay/inbox persistence boundary, and possession-authenticated mutual key pairing. These use maintained cryptographic libraries rather than custom primitives. Signatures and AEAD bind the routing header to the ciphertext. Modified headers, modified ciphertext, mismatched receivers, expired envelopes, unsupported versions, and unknown or revoked senders must be rejected before dispatch.

A relay still sees device and envelope IDs, sender/recipient relationships, public keys, timestamps, message sizes, queue state, acknowledgments, IP addresses, and connection timing. Message padding, traffic analysis resistance, sender anonymity, and metadata confidentiality are not implemented. TLS is required for routing privacy and relay endpoint authentication, but the relay remains able to deny service. E2EE does not establish delivery availability.

Version 1 uses static device X25519 identity keys. Fresh salts and nonces separate message keys but do not provide forward secrecy or post-compromise security. Compromise of either participant's identity encryption key can expose recorded traffic to or from that identity when counterpart public keys are known. There is no double ratchet, prekey protocol, group key schedule, or automatic cryptographic recovery. Device revocation rejects future traffic at honest endpoints and the relay; it cannot erase messages or keys already held by a revoked device. Re-pairing with new keys is necessary after key compromise.

The invitation's out-of-band channel is a trust root. A substituted QR or unverified fingerprint can pair an attacker. Anyone who obtains an unexpired invitation secret can request pairing; short lifetime and single-use local pending state limit exposure. Identity secrets need OS protected storage, and pairing invitations must not be logged or routed as ordinary messages. Public-key fingerprints do not independently prove a person's identity.

Local endpoint compromise, malicious privileged code, an unlocked compromised device, extracted OS credentials, plaintext memory inspection, or a user explicitly approving a malicious peer remain outside this transport's protection. Zeroizing buffers reduce residual key and plaintext exposure but cannot guarantee erasure of all operating-system or allocator copies. Encrypted transport does not make arbitrary shell execution safe or constrain native tools. Tool Broker permissions, explicit shell trust decisions, sandboxing where available, and host authorization remain separate boundaries.

Replay protection depends on a durable atomic receiver adapter. It must commit the replay marker and authenticated inbox together, recover pending deliveries after crashes, and keep unexpired markers across restarts. Queue bounds, transport frame limits before deserialization, per-device authentication/rate limits, sender registry ownership, revocation distribution, sync cursor validation, command-ID idempotency, and denial-of-service resistance are integration requirements rather than properties of the cryptographic primitives.

No security audit, formal analysis, deterministic interoperability vectors, or Apple runtime verification has been completed. Automated verification is tracked in #32. Completion of this development stage does not establish production readiness.
