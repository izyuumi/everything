# Cryptographic foundation validation

For issue #7, the crypto worktree passed `cargo fmt --all --check`, `cargo check --workspace --all-targets --locked`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, and `cargo build --workspace --release --locked` on Linux with Rust 1.99.0. The crate declares Rust 1.85; an actual Rust 1.85 compiler was not available for this validation.

A disposable local executable generated two fresh identities and exercised invitation JSON transfer, request/acceptance pairing, exact mutual key pinning, signed envelope JSON serialization, receiver decryption, and inbox delivery. Manually inspected output confirmed the original payload matched, the serialized relay envelope did not contain the plaintext string, and the sender signature verified without decryption. A repeated envelope returned the replay error, modified ciphertext returned the signature error, and an expired envelope returned the expiry error. Exporting and importing zeroizing key material preserved public keys, and a signed challenge verified. No credentials, real conversations, production services, or user data were used.

The disposable inbox was in memory for this manual exercise; this does not verify crash recovery or durable SQLite inbox/replay integration. Native Apple builds, CryptoKit interoperability, deterministic vectors, exhaustive negative cases, persistent replay across restarts, relay reconnect behavior, and security review remain unverified. New automated tests and vectors were intentionally not created; consolidated issue #32 tracks the deferred work.
